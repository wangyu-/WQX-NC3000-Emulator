# LAVA X 播放器 → 主控 ROM → SPCE061A：完整语音播放协议

> **现状（2026-09-27）**：本文的协议分析（§1–§4、§15/§16 **S200 通路已定版**）仍然有效；
> 中间的 §9–§14 是"一路把爆音啃掉"的过程记录。整条链路在模拟器里已经跑通：
> LAVA 播放器 → 主控 bank 9 引擎 → UART → 061（见 `NC3000模拟器_改造计划.md` 第 5/10 节）。
> 总览见 `docs/README.md`。

`info/NC3k_LAVAX/`、`info/音文16.txt`、`info/音文同步.lav` 这三份材料把
**"教材播放器怎么让 061 放 S200/A1600"** 这条链路彻底打通了。结论如下。

## 1. `音文同步.lav` 与 `音文16.txt` 是同源程序

`音文同步.lav` 的文件头 `4C 41 56 12`（"LAV" + 类型 $12），数据段里偏移
`0x15` 起的 12 字节正好等于 `音文16.txt` 里的
`char char_tbl[]={12,5,8,11,3,15,10,21,9,19,1,13}`：

```
lav:  ... 00 40 0c 00 0c 05 08 0b 03 0f 0a 15 09 13 01 0d 41 0c 40 ...
                         ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ char_tbl
```

所以虽然拿不到源码，`.lav` 用的就是 `音文16.txt` 那套 API。

## 2. 播放器告诉虚拟机：这是哪种编码

`音文16.txt` 的 `play_voice()`：

```c
if (mhead[0]==0x10) {                       // S200
    ps=pause_x*250/100;  pe=total_len;
    ps=ps-ps%5 +6;       pe=pe-pe%5 +6;     // 5 字节一帧，数据从 +6 开始
} else {                                    // A1600
    ps=pause_x*20;       pe=total_len;
    ps=ps-ps%32+2;       pe=pe-pe%32+2;     // 32 字节一帧，数据从 +2 开始
}
System.SndPlayFile(fv, pe-ps+2, 0x20000+mhead[5]+(mhead[6]<<8));  // S200
System.SndPlayFile(fv, pe-ps+2, 0x10000+mhead[1]+(mhead[2]<<8));  // A1600
```

- `mhead[0]`：`0x40` = A1600，其它一律当 `0x10` = S200；
- `mhead[1..2]`：`.vnt` 的头 2 字节（A1600 是 `07 80`）；
- `mhead[1..6]`：`.vnt` 的头 6 字节（S200 是 `u32 长度 + u16 配置`）；
- 第三个参数 = **`0x10000 | 格式字`**（A1600）或 **`0x20000 | 配置字`**（S200）。

**这一条独立证实了前面的结论**：S200 是 5 字节/帧。5 字节 / 20 ms = **2000 bps**；
A1600 32 字节 / 16 ms = 16000 bps，比值正好 8，与 568 组文件实测的
`0.124996 ± 0.000007` 完全吻合。

## 3. 虚拟机把参数交给主控 ROM

`备份/GVmaker.obj` 是**带声音的新版虚拟机**（`LVM.obj` / 主目录的
`System_Code.asm` 里 `Snd*` 是空壳，所以那两份是无声版本）。它的系统函数实现：

| 地址 | 内容 | 对应 |
|---|---|---|
| `$BCEB` | `sta $03e9` + **`INT $0951`** | SetVolume |
| `$BCF2` | **`INT $094D`** | PlaySleep（停止） |
| `$BCF7` | 从参数块拷 7 字节到 `$2000` + **`INT $094E`** | PlayInit/SndOpen |
| `$BD53` | 填 `$14D3..$14D8` 后 **`INT $0950`** | **PlayFile** |
| `$BD5F` | **`INT $094F`** | PlayStop |

`NC3000_trap.txt` 给出这些中断的落点：

```
094D B26C   //PlaySleep
094E B551   //PlayInit
094F B220   //PlayStop
0950 B375   //PlayFile
0951 B595   //SetVolume ($03e9)
```

高字节 `0x09` = **bank 9**，地址是 bank 9 窗口（`$4000-$BFFF`）内的 CPU 地址。
对应文件偏移 = `9*0x8000 + (addr - 0x4000)`。

## 4. Bank 9 里真正的 6502 播放引擎（已完整反汇编）

文件偏移 `0x4F1FE - 0x4F73B`（CPU `$B1FE-$B73B`）就是整个 061 驱动。

### 4.1 BIOS 跳转表（bank 0，`$E080` 起）

| 入口 | 跳到 | 作用 |
|---|---|---|
| `$E093` | `$FABE` | 等 061 就绪（IO `0x0E` bit4） |
| `$E096` | `$F9CE` | 复位/清链路 |
| `$E099` | `$FAEE` | **音量 `0x44 <v>`** |
| `$E09C` | `$FA71` | **睡眠 `0xAA 0x01`** |
| `$E0A2` | `$FA98` | **结束应答 `0xAA 0x03`** |
| `$E0A5` | `$FA44` | **停止 `0xAA 0x00`** |
| `$E0A8` | `$FAE3` | **选解码器 `0x99 <A>`** |
| `$E0AB` | `$F9E9` | **链路握手 `0xBB 0x0A`** |
| `$E0AE` | `$FA83` | 结束 `0xAA 0x02` |
| `$E0B4` | `$FB1C` | 发一个字节 |
| `$E0B7` | `$FB49` | 收一个字节 |
| `$E0BA` | `$FB73` | 延时/喂节拍 |
| `$E0C9` | `$FB01` | 语速 `0x55 <n>` |

### 4.2 选解码器 `$B520`

```asm
        JSR $B676        ; 等就绪
        LDA $2000
        CMP #$40
        BEQ +            ; $2000 == 0x40 → A1600
        LDA #$10
        STA $2000        ; 否则一律当 S200
+       JSR $E0A8        ; 0x99 <A>   → 0x99 0x40 / 0x99 0x10
```

> `$2000` 就是播放器里的 `mhead[0]`：**0x40 = A1600，0x10 = S200**。
> 这正是之前 `0x99 0x10` 一直没把 S200 跑起来的原因之一——还缺第 4.3 步的头。

### 4.3 单独发流头 `$B53C`

```asm
        LDA #$06 / #$02      ; S200=6, A1600=2
        STA $201B
        LDA #$22 ; JSR $E0B4 ; 0x22
        LDA $201B; JSR $E0B4 ; 长度 6 / 2
        ; 再依次把 $2001.. 的 6 / 2 字节发出去
```

即 **`0x22 <n> <n 字节>`**：

| 编码 | 发出的头 |
|---|---|
| A1600 | `0x22 02 07 80`（格式字） |
| **S200** | **`0x22 06 <u32 长度> <u16 配置>`** |

### 4.4 送音频数据 `$B5B3`

```asm
        LDA $2000
        CMP #$40
        BEQ A1600_path
        ; ---- S200 ----
        LDA #$33 ; JSR $E0B4          ; 0x33
        ; 送 15 字节字节流，指针 $FB/$FC 前进 15
A1600_path:
        ; 每次 JSR $B676（等就绪）后发 0x22 04 + 4 字节，重复 8 次 = 32 字节
```

| 编码 | 数据帧 |
|---|---|
| **S200** | **`0x33` + 15 字节**（连续字节流） |
| A1600 | `0x22 04 <4B>` ×8 = 32 字节 |

### 4.5 结束 `$B67C`

发 `0xAA 0x03`，然后等 061 回 `0xAA 0x00`（对应 `[0x0000]` 的 bit10）。

### 4.6 PlayFile `$B375` 的其它要点

- 参数：`$14D3/$14D4/$14D5` = 起始 24 位偏移，`$14D6/$14D7/$14D8` = 结束偏移
  （所以 `SndPlayFile` 的第二个参数是"播放窗口长度"，不是文件长度全部）；
- 先用 `INT $0519`（doSeek）定位；
- 算 `$201C-$201E` = 长度，非 A1600 时把它搬到 `$2001-$2003` 并 **+2**、`$2004=0`
  —— 于是 S200 的 6 字节头 = `[长度+2][0][配置]`，与 `.vnt` 的 `[u32][u16]` 一致。

## 5. 实测：S200 现在真的跑起来了

按上面协议改 `spce061a/host/s200_probe.c`（新增 `mode 2`）：

```
0x99 0x10 → 0x22 06 <2b 5e 01 00 08 00> → 0x33+15B 循环
```

结果（`build/s200_full.wav`）：

```
after 0x99    04CE=0002 0504=0000 0000=0010
sent 0x22 6 header: 2b 5e 01 00 08 00
after stream  04CE=0002 04D2=0007 04E3=BE00 0504=0001 0000=3090 0714=8020
fed 15756/89647 bytes in 1050 blocks
decoded 1950945 samples @31958 Hz (61.05 s)
```

- `04D2=0007`：S200 配置号解析正确（参数 `0x0008` − 1）；
- `0504=0001`：S200 内核（`0xC8C6 → 0x826F`）真的被执行了；
- `0000=3090`：音频门与握手位，和 A1600 正常播放时**完全一样**；
- 15756 字节 @2000 bps = **63.0 s**，解出 1950945 采样 @31958 Hz = **61.05 s**，
  时长对得上 —— 采样率就是 31958 Hz。

## 6. 还差什么

输出**前 ~19 秒**的统计特征像语音（ZCR 0.05–0.09、频谱起伏正常），但之后
退化成两值方波（`uniq400=2`、ZCR≈0.003、幅度打满），而且和同内容的 A1600
解码做互相关几乎为 0。所以**协议已经对了，剩下的是模拟器的时序保真问题**：

- 我在 `nc3000_dsp.c` 里用"每 1538 条指令触发一次 TimerA FIQ"来模拟音频时钟，
  这个节拍和数据消耗量是解耦的；S200 解码器一旦供不上，DAC 就会重复上一采样，
  于是出现方波/饱和；
- 真机上 TimerA 的节拍由 `$C438`–`$C4E0` 的音频 FIQ 严格控制，且它按
  `[0x04C1]/[0x04CD]` 的输出缓冲水位来判断要不要取新样本。

下一步应该把 `audio_pace` 改成**按解码器输出水位驱动**（而不是按指令数），
或者干脆绕过 FIQ，直接读 S200 内核合成后的缓冲。

## 7. 顺手记下的几个结论

1. `info/NC3k_LAVAX/LVM.obj` 和主目录的 `System_Code.asm` 是**无声版本**
   （`SndOpen/SndClose/SndIfEnd/SndPlayFile/SndStop/SndPause/SndResume/SndGetPlay`
   全是单字节 `60`/几字节空壳），只有 `SndSetVolume/SndGetVolume` 是真的。
2. `备份/GVmaker.obj`（= `GVmaker.dat`，15721 字节）才是**能用声音的虚拟机**，
   它通过 `INT $094D/$094E/$094F/$0950/$0951` 调用主控 ROM 的播放引擎。
3. 主控固件里 `0x99` 只出现在 `$FAE3`（通用入口）、`$FE2A`（`0x99 0x00` = MS01）
   以及 bank 9 的 `$B520`；`$B520` 是教材/LAVA 播放器用的那条。
4. 高品质 `.vnt` = `07 80` + A1600 流（32 字节/帧，数据从 +2 开始）；
   一般品质 `.vnt` = `u32 长度` + `08 00` + S200 流（5 字节/帧，数据从 +6 开始）。

## 9. 后续进展：一般品质出声了，剩下的是爆音

按第 4 节的协议改好 `host/s200_probe.c` 的 `mode 2` 之后，一般品质**已经能放出正确的声音**：

```
0x99 0x10 → 0x22 06 <2b 5e 01 00 08 00> → 0x33+15B
after stream  04CE=0002  04D2=0007  0504=0001  0000=3090
fed 89647/89647 (整文件) → 2851054 个解码样本
```

**采样率**：整文件 89647 字节 × 1/2000 bps = 358.6 s，解出 2851054 个样本
⇒ **8000 Hz**（5 字节/帧 = 20 ms = 2000 bps ✓）。FIQ 每个节拍把 1 个样本推进
8 项环 `0x0765+`，DAC 以 4 倍过采样输出（31958 Hz），所以
`s200_long.wav` 是 4 倍过采样版、`s200_long_tap.wav` 是 8000 Hz 原始样本。

**内容验证**：把同内容的 A1600（高品质）解到 43 秒做包络对比，
静音/语音分段逐秒吻合（t=1 静音、t=2 语音、t=3–4 静音、t=5 语音 ……），
而且高品质版从 t≈18 s 起真的是纯静音（125/125 帧都是静音码），
所以"后半段没声"不是解码问题。

### 9.1 杂音 = DAC 被推满量程的突发

- 一般品质解码里有 **11351 个 `|Δ|>15000` 的跳变**，而高品质只有 1 个；
- 这些地方 DAC 写的是 `0x0000/0xFFFF/0x0020/0x7FE0`，即**满量程**；
- 用 `unsp_write` 钩子记录写出满量程时的 PC，全部指向 **`$C757`**（TimerA 音频 FIQ 的 DAC 输出），
  此时 `[0x0000] = 0x1290`（bit12 + bit9 等）。

### 9.2 已经排除的原因（都是实测）

输出与下列因素**逐位无关**（多次对照，样本数和爆音数完全相同）：

| 变量 | 取值 | 结果 |
|---|---|---|
| 每块后的等待 | 0 / 4000 条指令 | 相同 |
| 解析器状态门控 | 开 / 关 | 相同 |
| 第 40 块发 END | 发 / 不发 | 相同 |
| `fire_every` | 1100 / 1300 / 1538 / 1800 / 2200 / 3000 | 相同 |
| 数据命令 | `0x33`+15 / `0x22`+15/16/20/32 | 15 最好，其余更差 |
| 数据起点 | 偏移 5 / 6 / 7 | **6 最好**（与 ROM 的 `+6` 一致） |
| `uart_rx_drops` | — | 0（没丢字节） |

关键：**节拍参数完全不起作用**，因为音频时钟其实是**模拟器里的 TimerA 硬件定时器**
（`spce_tick` 溢出时置 `INT_FIQ_TMA`），`nc3000_dsp.c` 里的 `audio_pace` 只是补充。
所以这是**确定性**的固件行为，不是主机喂数据造成的饥饿。

### 9.3 最可能的原因

`$C7D8` 处 FIQ 按 `[0x0000]` 分叉：

| 位 | 分支 | 行为 |
|---|---|---|
| bit13 | `$C786` | 从播放缓冲 `0x019F` 取样本，写 8 项环（`[0x0785] & 7`） |
| **bit12** | `$C7E3` | **读 `P_ADC (0x7014)`，写 32 项环（`[0x0785] & 0x1F`）** |

两条路径共用同一个 `[0x0785]` 索引但环长度不同（8 vs 32），
bit12 一旦置位就会用 ADC 值污染 DAC 环形缓冲，正是满量程突发的来源。
固件在开音频时会 `[0x0000] |= 0x3300`（bits 8/9/12/13），说明它本来就允许这两位；
真机上 bit12 什么时候清掉、由谁清掉，还需要再查（`$C578`/`$C584` 是专门的清/置位例程，
但它们的调用者还没定位到 —— 那两处的引用落在 `0xDC00` 附近，超出当前模拟器映像范围）。

### 9.4 临时可听版本

爆音样本是 `|x| ≥ 30000`（正常语音 RMS 约 2000），可以用阈值 + 线性插值修掉：

```powershell

node tools\wav_declick.js spce061a\build\s200_long_tap.wav out\fixed_full.wav 8000
```

产出：

- `out/场景一_一般品质_S200_全程8kHz_去爆音.wav`（8000 Hz，整文件 356 s，修掉 5.73%）

## 10. 复现：不是协议、不是数据、不是时序 —— 是模拟器里 S200 内核的运算

### 10.1 官方 S200 样本一样坏

拿 Sunplus 自带的 `spce061a\ref\gpce063_samples\S200_f2_3360.bin`（原 `gpce063/demoCode/S200/voice/f2_3360.bin`，cfg `0x000B`）
按同一协议跑：

```
0x99 0x10 → 0x22 06 <5f 0f 00 00 0b 00> → 0x33+15B
04D2=000A 0504=0001 0000=3090     ← 一切正常
299602 样本，其中 26426 个满量程（8.82%）
```

**所以这跟 `.vnt` 数据无关，是模拟器 S200 解码通路本身的问题。**

### 10.2 输出对一切时序旋钮完全不变

对同一个输入，下面每种改动都得到**逐位相同**的结果（样本数、饱和数都不变）：

| 旋钮 | 取值 | 结果 |
|---|---|---|
| `fire_every`（软件补发 FIQ 的间隔） | 1100 / 1300 / 1538 / 1800 / 2200 / 3000 | 相同 |
| `tick_div`（外设时钟分频，新增） | 1 / 2 / 4 | 相同 |
| 每块后等待 | 0 / 4000 条指令 | 相同 |
| 发不发 END | 发 / 不发 | 相同 |
| `no_hold`（不因缓冲空而暂停 FIQ） | 0 / 1 | 相同 |
| 数据命令 | `0x33`+15 / `0x22`+15 | 相同 |

样本数恒为 **128 个/输入字节**（= 640/5 字节帧 @31958 Hz，8 kHz 内容 4 倍过采样），
说明解码器和 DAC 是**数据驱动**的，因此这是**纯算术**问题（给定数据 → 固定输出）。

### 10.3 已排除

| 怀疑点 | 结论 |
|---|---|
| 音频缓冲指针 | 正常：`r2` 落在 `0x019F..0x02DF` 内，`[0x04C1]` 递增 |
| DAC 环索引 | 正常：`[0x0785]` 按 `&7` 循环 |
| `[0x0000]` bit12 | 开机即置（`0xC4E9 \|= 0x3300`），并非误置；爆音时看到的 `0x1290` 只是"收到过 END"（bit7） |
| 发 END 引起 | 反了：不发 END 时饱和更多（6.23% vs 4.87%） |
| `fir_mov` | S200 内核窗口内 **0 条**指令处于 `fir_mov=1` |
| MULS 符号模式 | S200 内核 10 条 MULS **全部**是 `ss`，与模拟器一致 |
| 系统变量 `[0x0000..5]` | 爆音时正是 `3010 8000 000C 0002 0002 0002`，正常 |
| `uart_rx_drops` | 0 |

### 10.4 剩下最可疑的一处：`MULS` 的 `n`

对两个内核的乘法指令做差集统计：

| 内核 | 用到的乘法 |
|---|---|
| A1600（已用参考 WAV 逐样本验证） | `MULS ss n=2`、`MUL ss`、`MUL us` |
| **S200** | `MULS ss n=1/2/4/10/11/15`、`MUL ss`、`MUL us` |

`emu/unsp.c` 的 `do_muls()` 除了内积与指针推进，还按 `fir_mov` 做内存搬移：

```c
for (i = 0; i < n; i++) total += (int16_t)read16(a+i) * (int16_t)read16(b+i);
r4 = total >> 16; r3 = total;
r[rd] = a + n;  r[rs] = b + n;
if (fir_mov) shift memory a[i] = a[i+1];
```

它只在 **n=2** 上被 A1600 参考对拍验证过；n=1/4/10/11/15 的
“指针推进量 / 结果移位 / 内存搬移”语义都没有第二份证据。
下一步就是拿 SPCE061A 手册把 `MR = [Rd]*[Rs], ss, n` 对 n=1..16 逐条定义清楚，
写一个单元测试对拍，再回来跑 S200。

### 10.5 这一轮新增的调试手段（可复用）

- `emu/unsp.h` 的 `wr_trace`（每次数据写入回调）——用来抓 DAC 环写入、`[0x0000]` 写入；
- `emu/unsp.h` 原有的 `trace`（每条指令后回调）——用来做内核指令直方图；

## 11. 对着 MAME 的 unSP 内核源码逐行核对乘法指令

工作区里其实已经有权威资料（前一轮对话留下的）：

- `spce061a\ref\mame_unsp\` = **MAME 的 unSP CPU 内核源码**（2026-09-28 从早期工作区
  `…\ce\work\unsp\` 搬进仓库）
  （`unsp_fxxx.cpp` 里有 `execute_muls_ss()` 等）；
- `...\work\ref\凌阳16位单片机应用基础\编程速查\附2《unSP指令速查表》`（含 txt 提取版）。

速查表确认语法：

```
MR = Rd * Rs {, ss}            单字  12 周期
MR = [Rd] * [Rs] {, ss} {, n}  单字  10n+8 周期
```

### 11.1 逐条对比结果

| 项 | MAME | 我们 | 结论 |
|---|---|---|---|
| `MUL us` | `lres = Rd*Rs; if(Rs&0x8000) lres -= Rd<<16` | 同 | ✅ |
| `MUL ss` | 两处 `<<16` 修正 | 同 | ✅ |
| MULS 的 `n` | `((op>>3)&7) + 8*bit6`，0→16 | `(op>>3)&0xF`，0→16 | ✅ 等价 |
| MULS 的有符号乘积 | `tres` 两处修正后累加 | `(int16)*(int16)` | ✅ 等价 |
| MULS 结束后 | **`m_sb = 0;`**（清 4 位移位缓冲） | 没有 | ❌→ 已补 |
| `fir_mov` 时的内存搬移 | `mem[i] = mem[i-1]`（向**上**搬） | `mem[i] = mem[i+1]`（向**下**搬） | ❌→ 已修 |

两处都改了（`emu/unsp.c`）。**对 S200 的爆音没有影响**（`fir_mov` 在 S200 解码全程为 0，
`sb` 也没有被后续指令读到），所以乘法语义不是元凶。

### 11.2 回归验证

→ 22 passed, 0 failed；73042 样本

## 15. S200 解码器的完整数据通路（这一轮摸清了，之前取错了输出点）

### 15.1 输出点不是 `0x0541`，而是转移之后的 `[0x04C2]`

固件里的 S200 内核（`0x82C6` 进入）**不是直接把 PCM 交给播放 FIQ** 的。
完整链路是：

```
0x82C6  读帧参数（位流）→ 查码本 → 插值系数 → 激励合成
0x8704  激励 + 2 极点谐振器，逐样本写 0x0541+idx（idx = 0..159）
0x83A8  4 个子帧（step = [0x04D5] = 40）逐个做 11 抽头 IIR，原地滤 0x0537+…
0x8496  ★转移+标度★：把 0x0537 起 160 个字 ×2 并饱和后写进 [0x04C2]
0xC742  播放 FIQ：[0x04C1] → 8 抽头相位插值（表 0xC70A）→ P_DAC2(0x7016)
```

`0x8496` 那段长这样（反汇编在 `out\s200_kernel_disasm.txt`）：

```
8496: r1 = 0x0537            ; 源
8498: r2 = [0x04C2]          ; ← 真正的输出指针（变量！不是常量）
849a: r3 = r2 + [0x04D4]     ; + 帧长 160
849c: r4 = [r1++]
      if (r4 >= 0) { if (r4 >= 0x3FF0) r4 = 0x7FDF; else r4 <<= 1; }
      else         { if (r4 >= 0xC000) r4 <<= 1;   else r4 = 0x8000; }
84ae: [r2++] = r4            ; 写进 [0x04C2]+
```

即：**×2 标度 + `+0x7FDF / -0x8000` 饱和**。`[0x04C2]` 在
`0x019F` 与 `0x019F+160` 两个半缓冲间交替（`0xC66D` 处按 `[0x0000]` bit9
切换并翻转该位），`[0x04C1]` 是 FIQ 的读指针，两者构成乒乓。

**所以之前所有"听感/相关性"对比都取错了点**：读 `0x0541`（激励缓冲）拿到的
是**转移之前**的信号。用正确的点重测（`spce061a\host\s200_map.c`）：

```
ref samples: 80000 ; emu 80000
  023F (真正的 PCM) : best corr 0.1541 at lag 31
  0537 (内核原始)   : best corr 0.1541 at lag 31     ← 两者等价，说明转移段是对的
```

（上一轮用 `0x0541` 测出的是 −0.06；换成正确点后是 0.154，但**离 1.0 还很远**，
所以噪声确实出在解码本身。）

### 15.2 帧格式（已用官方汇编器 / 配置表钉死）

`[0x04D2] = 配置字 − 1`（容器第 3 个字，本例 `0x0008` → 索引 7），据此
（1）从 `0x994D` 取 16 字记录 → 拷到 `0x04D3`；
（2）在 `0x8357` 处再从 `0x9E98[idx] → 0x9D63 + 5*[0x0002]` 取 5 字子记录 → 覆盖
`0x04D4..0x04D8`。

| 参数 | 本例（idx 7 / `[0x0002]=0x0C`） | 含义 |
|---|---|---|
| `[0x04D4]` | `0x00A0` = 160 | 帧内样本数（8 kHz × 20 ms）|
| `[0x04D5]` | `0x0028` = 40 | 子帧步长（160/4）|
| `[0x04D6]` | `0x00CC` | 谐振器系数增量 |
| `[0x04D7]` | `0x014B` | — |
| `[0x04D8]` | `0x7EB4` | — |
| `[0x04DA..0x04DF]` | 7,8,8,8,6,3 | **逐帧比特宽度，合计 40 bit = 5 byte ✓** |
| `[0x04E0..0x04E2]` | `0x8DA8,0x90A8,0x93A8` | 三个码本基址（256×3 / 256×3 / 256×4）|

位读取器在 `0x8659`，**字内 LSB 优先**、跨字自动续接；初始状态
`[0x04E3]`=流第 1 个字（= 容器头 6 字节之后的前 2 字节）、`[0x04E4]`=0、
`[0x04C0]`=后继指针。

`0x9E98` 表（每个速率一组）× `[0x0002]`（系统音质档，0~23）给出上面 5 字子记录，
所以 `[0x04D4]` 会在 320/300/284/…/160/…/84 之间变；**音质档设错，帧长就错**。

### 15.3 指令语义：用官方汇编器把编码钉死了

`out\asmtests\enc.asm` + `xasm16 -t5`（ISA 1.3）生成的对照，全部与
MAME/手册一致（详见 `out\asmtests\enc.lst`）：

| 写法 | 编码 | 结论 |
|---|---|---|
| `MR = R1 * R2, ss` / `,us` | `F30A` / `F20A` | 有/无符号之分在 bit8 |
| `MR=[R1]*[R2],ss,1` | `F38A` | **n=1 → 字段 1**（"缺省值 1" ✓）|
| `,ss,2/3/4/7` | `F392/F39A/F3A2/F3BA` | 字段 = n |
| `,ss,8/9/15` | `F3C2/F3CA/F3FA` | 高组：字段+8 |
| `,ss,16` | `F382` | **字段 0 + 低组 = 16**（MAME 的 `field?field:16` ✓）|
| `R1=R1 LSL/LSR/ROL/ROR/ASR n` | `9341/9361/9381/93A1/9321` | 移位族与 SB 语义与手册位图一致 |
| `R2 += R1 ASR 1{,Carry}` | `0521` / `1521` | `,Carry` = 置 bit12（ADC） |
| `INT OFF` / `NOP` / `FIR_MOV ON` / `IRQ ON` / `FIQ ON` | `F140/F165/F144/F149/F14E` | 与模拟器分派一致 |

注意：`FIR_MOV ON`（`0xF144`）**在整个固件里一次都没用**（只有 `0xC41F` 的
`FIR_MOV OFF`），所以 MULS 的自动移位窗口对 S200 路径不生效。
`INT OFF`（`0xF140`）也只出现在 `0x8E29`——那是**码本数据**，不是代码。

### 15.4 缩小后的嫌疑范围

同固件里的 A1600 解码器是**逐样本对拍验证过（相关系数 1.000000）**的，所以
"S200 用到、A1600 没用到"的指令才是没被验证过的。按 0x8256–0x8A20 与
0xB5D0–0xC0C4 两个区间的操作码求差，S200 独有 195 条，其中真正有语义意义的
（而非单纯寻址组合差异）目前只剩：

* `MULS` 的 `n = 1 / 4 / 10 / 11` 等非 2 项形式（`F589,F5A1,F5D1,F5D9`…）；
* `pc += r2 lsl N` 计算跳转（`0F52`，位读取器的移位分派表）；
* `role`/`asr` 串起来的 32 位定点移位惯用法（`r3=lsl4` → `r4=rol2` → `r4=asr1`）；
* `[BP+IM6]`、`[A6]` 直址与自增/自减的混合组合。

这三类都已经对着手册、MAME 和官方汇编器核对过**编码**，但**尚未做逐指令的
执行级对拍**——下一步就在这个集合里做。

运行 `build\s200_mapb.exe ..\out\s200test.bin 0 12`：

| 帧 | 手算（LSB 优先，8/8/8 位）| 模拟器 |
|---|---|---|
| 0 | `00DE 0074 0031` | `00DE 0074 0031` |
| 1 | `00A6 00BB 00ED` | `00A6 00BB 00ED` |
| 2 | `00D2 00BB ...`   | `00D2 00BB 00B2` |

手算依据：流载荷从第 6 字节开始，`de 74 | 31 42 | 00 a6 | bb ed | c3 1e | d2 bb …`
（`s200test.bin` 第 10/11 字节是 `00 a6`，即字 `0xA600`），
`0x8659` 按字内 LSB 优先取 8/8/8/7/6/3 = 40 bit。
`[0x04C0]` 每帧前进 2~3 个字（40 bit = 2.5 字）也与预期一致。

同时把两个"可变移位"例程单独拉出来做单元测试（`spce061a\host\s200_shift.c`）：
`0x8905`（`r1 = r1 << r2`）、`0x8994`（`r1 = r1 >> r2`，带符号饱和），
它们靠 `pc += r2 lsl 3` 跳进 8 字一格的移位块。
`build\s200_shift.exe` → **all shift checks passed**（n=0..18 共 40 项，
含手册里的 `0xF00F LSL 3 = 0x8078` 例子）。

⇒ **位流解析、跳表分派、移位语义都不是问题。** 剩下的只能是合成级：

1. `0x8704` / `0x8729`：用 `[0x04F4]/[0x04E6]/[0x04F2]` 算谐振器系数，
   然后 **160 次循环** 生成激励并写 `0x0541+idx`
   （噪声 LCG `[0x04FF] = 0x7C4D*[0x04FF] + 0x3619` → 4 抽头 FIR `0x9960`；
   过零时注入 13 样本脉冲串，脉冲形状由 `0x04F4/0x04E7` 索引 `0x9964` 附近的表）；
2. `0x83B1`：10 个 LPC 系数在上一帧/本帧之间插值到 `0x06D4..0x06DD`；
3. `0x87F6`：11 抽头 IIR **原地**滤波（`MR=[r2]*[r1],ss,10` + `,ss,1`，
   再用 `lsl 4`/`rol 4` 的 32 位右移 + `cmp r3,0 / r4+=1` 的取整修正）。

这三段用的都是"合法但 A1600 没验证过"的组合（`MULS n=10/1`、32 位移位惯用法）。
下一步的确定做法：**把这三段按反汇编逐条用 Python 独立实现，喂同一帧参数，
和模拟器里 `0x06D4..0x06DD / 0x051C.. / 0x0541..` 的中间状态逐步对拍**，
第一个不一致的变量就是 bug 所在。

### 15.7 官方参照是有效的；真正塌掉的是"激励"，不是滤波器

**先纠正一个测量错误**：之前用 PowerShell 读 `.pcm` 时 `[byte] -shl 8` 溢出，
把 `ff ff`（16 位 −1）读成了 `255`，于是误以为"参考信号只有 ±255"。重算后：

| | RMS |
|---|---|
| 官方参照 `s200test_ref.pcm`（10 s 语音）| **1235.6** |
| 模拟器 `s200_emu_021F.pcm` | **71.4** |

模拟器小了 **17.3 倍**，而且归一化后相关系数仍只有 0.154（尺度不是原因）。
为确认参照本身没坏，用 1 kHz 正弦做了一次最小实验：
`S200.exe sine1k.wav sine1k.bin sine1k.pcm -r 2000 -0` → `.pcm` 8000 样本、
min −20516 / max 20449 / **RMS 6888**，是正常波形。⇒ 参照可信。

**再定位到"激励塌了"**。用 `s200_map.c` 的 PC 触发探针在 `PC=0x839B`
（`call 0x8704` 合成循环刚返回）抓 `0x0541..`：

| 帧 | 激励 rms | 范围 | 滤波后 |
|---|---|---|---|
| 0、1（编码器静音帧）| 0.0 | 0 | 0 |
| 18–21（真实语音）| **0.7** | −1..0 | 0.7 |

同一时刻的参数块却是**正常的**：

```
04E5..04F1 = 03B8 0006 0000 05D2 0B90 1168 1754 1D2B 22F7 2926 2EB9 34D6 39D0
             ↑增益/音高=952  ↑两个脉冲索引=6,0   ↑10 个 LPC 系数，平滑非零
06D4..06DD = 000E 000E 0005 0005 FF34 80CB 0B1C 00B1 00A0 444D
```

也就是说：**位流 → 参数 → 码本 → 系数这一整条链都是对的，但激励只有 ±1。**

把激励公式按反汇编展开（`0x8765..0x8772`）：

```
MR = [0x06D4]*[0x06D8], ss, 2   ; 2 抽头：state·(cos,sin)
r3 = [0x06DD]                    ; 4 抽头噪声
MR = r4*r3, ss                   ; 高字 × 噪声
r4 = r4 asr 1                    ; 再右移一位（总计 >>17）
[0x0541+idx] = r4
```

`state = (参数 × 增益表[0x9958+[0x04F4]]) >> 13 = (6 × 0x4E20) >> 13 = 14`，
所以 2 抽头只有 ±7，`(7 × 噪声) >> 17` 必然落到 0/±1。
**脉冲支路确实在工作**（实测一帧末尾 `[0x0500]=0007`、`[0x0501]=[0x0502]=0x9B0A`，
即正在播放形状号 `(0x9B0A-0x9964)/13 = 38` 的 13 样本脉冲），所以不是"没触发"。

问题在**标度**：两条支路的幅度都先被 `× 小参数 >> 16` 压掉一次——

```
噪声支路：2 抽头高字 = ([0x06D4]/[0x06D5] = 14) · (cos,sin) >> 16 ≈ ±7
          sample = ±7 × 噪声(±32k) >> 17   →  0/±1
脉冲支路：h = ([0x06D6]/[0x06D7] = 5) · (cos,sin) >> 16 ≈ ±2
          contribution = 脉冲样本(±15k) × ±2 >> 13 ≈ ±7
```

而 `[0x06D4] = ([0x04F3]=[0x04E6]=6) × 增益表[0x9958+[0x04F4]=0x4E20] >> 13 = 14`，
`[0x06D6] = (6 × 表[0x9B5F+60]) >> 13 = 5`。**要让它达到语音量级，这个"6"
必须在 0x1999~0x2000 量级**——而配置记录里正好有 `rec[6] = 0x2000`
（本例记录 `0001 00a0 0028 00cc 014b 7eb4 2000 0007 …` 的第 7 项），
它是 `0x2000/0x2AAA/0x1999` 这种典型 Q-标度常量。

⇒ **结论：解码链本身没问题，是"激励标度"用错了量。** 下一步只需盯一件事：
在 `0x8704`（`[0x06D4]/[0x06D5]` 的赋值）与 `0x871C–0x8728`（`[0x06D6]/[0x06D7]`）
这两处，确认乘数应当取 `[0x04F3]/[0x04F4]`（来自 6 bit 表 / 3 bit 字段，实测只有
6 和 0）还是取配置记录里的 `rec[6]=0x2000` 之类。范围只有十来条指令。

### 15.8 量纲核对：缺的正好是 `0x2000`；而且第一组滤波系数没人直接写

按反汇编把激励的 Q 标度算一遍（设噪声 `[0x06DD]` 满幅 ±32000）：

```
sample     = (2 抽头高字) × [0x06DD] >> 17
2 抽头高字 = ([0x06D4]/[0x06D5]) · (cos,sin) >> 16
```

| | 2 抽头高字 | sample | 结果 |
|---|---|---|---|
| 实测 `[0x06D4]=14` | ±7 | ±1 | 现在（等于静音）|
| 需要 RMS≈1236（官方参照量级）| ±4000 | ±1000 | 需要 `[0x06D4] ≈ 0x2000` |

`[0x06D4] = ([0x04F3] × 增益表[0x9958+[0x04F4]]) >> 13`，增益表首项 `0x4E20`。
**要得到 `0x2000`，乘数就得是 `0x2000`** —— 正是配置记录第 7 项
`rec[6] = 0x2000`（也就是固件里的 `[0x04D9]`）。而代码实际用的是
`[0x04F3] = [0x04E6] = 6`。脉冲支路同理：`h = ([0x06D6]=5)·(cos,sin)>>16 ≈ ±2`，
贡献 `= 脉冲样本(±15k) × ±2 >> 13 ≈ ±7`，被同一个"小乘数"卡住。

**另一条独立线索**：`0x87F6` 第一次调用（`0x83E4`）的系数指针是 **`0x06DF`**，
而内核里 `0x06DF..0x06E9` **只有被引用、没有任何一条指令直接写**。它们只能由
`0x84C3 / 0x8518 / 0x85C1 / 0x85E2 / 0x8603 / 0x8638` 这一组辅助例程
（入口参数放 `[0x04CF]`/`[0x04D0]`，实参出现过 ROM 表地址 `0xA666`、`0xC000`
以及 `0x06D4`/`0x06E4`/`0x06E9`）算出的**滤波系数合成**结果 —— 正是 A1600
内核从不使用、因而从未被验证过的部分，也与"滤波后幅度不变"的实测吻合。

⇒ 下一步：把 `0x85C1 / 0x85E2 / 0x8603 / 0x8638`（各约 30–40 条）读透，
手算一遍 `[0x06DF..0x06E9]`，与模拟器同一时刻的值对拍。

## 16. 结论：S200 通路已打通（2026-09 定版）

**S200 解码器没有 bug。** 用"直驱通路"（逐帧直接调 `0x82C6`，自己按固件时序喂
流）与官方 `S200.exe` 的参照逐项对拍：

| 指标 | 结果 |
|---|---|
| 500 帧逐帧能量包络相关系数 | **0.9911** |
| 响帧波形相关系数（lag = −9 样本）| **0.95 ~ 0.98** |
| 电平 | 约为 PC 参考工具的 0.63 倍（设备 DAC 通路后续还有 ×8 与音量控制，听感正常）|
| 固定延时 | −9 ~ −10 样本（转移段从 `0x0537` = `0x0541 − 10` 起读所致，恒定无害）|

实测输出：`中级读物-2.vnt`（一般品质，59.5 s）→ RMS 792 / 峰值 10520，听感正常；
静音帧输出 RMS 1~2（与官方的数字静音一致）。

### 16.1 一条命令提取（推荐用法）

```powershell
.\tools\vnt2wav.ps1 <某个一般品质.vnt> [输出.wav]
```

内部就是：算帧数 `(文件长度−6)/5` → 跑 `spce061a\build\s200_mapr.exe` →
给 476k 样本补 8 kHz/mono/16-bit WAV 头。

### 16.2 排查过程中踩过的四个坑（都有实测教训）

1. **不要用单一全局 lag 比对整段长音频。** 素材里常有大片数字静音
   （本例第 5–49 帧官方 RMS = 1），全段相关系数会被静音段主导，
   把本来 0.95 的匹配显示成 0.154。正确做法：**逐帧包络** + 每帧单独找 lag。
2. **小心输出文件被覆盖。** 一系列扫描参数（如强制增益）会反复覆盖
   `out\s200_emu_021F.pcm`，之后又跑短帧数会把文件截短，
   于是"静音段有 190 底噪"这种结论其实是污染数据。跑正式结果前先删旧文件。
3. **PowerShell 读 16-bit PCM 要显式 `[int]` 转换**：`[byte] -shl 8` 会溢出，
   把 `ff ff`（−1）读成 255，直接误导了整整一轮分析。
4. **不要用 ROM 协议探针（`s200_probe`）做提取。** 它走 `0x22/0x33` 打包通路，
   喂流对齐有误，解码器读到垃圾 → 输出冲顶 → 转移段钳位
   （`0x84A4` 的 `0x7FDF` / `0x84AC` 的 `0x8000`）→ DAC 限幅器削顶，
   3 秒静音能产生 **2032 次满量程写**。真正可信的是直驱通路。

### 16.3 ROM 协议通路也修好了（两个 bug）

1. **流头必须一次发 8 字节。** 内核的 `0x8254` 读 **4 个字**：`u32 长度`、
   `u16 配置`，**然后是第一个数据字**。原来探针把 6 字节头和后续数据分两次发，
   解析时第 4 个字为 0 → 位读取器起始字错 → 整条位流错位。
   改成一次发 8 字节后，RAM 实测为 `02F1 0000 0008 74DE`，与期望完全一致。
2. **S200 不能给音频 FIQ 上 hold。** `nc3000_dsp.c` 的 `audio_pace()` 里有段
   "到半缓冲末尾就 hold FIQ"的逻辑，是当年为 A1600 调的；而 S200 的补数据
   本身就由同一个 FIQ 驱动，hold 会把服务饿死、导致播放缓冲被边写边读（撕读）。

   实测（20 帧纯静音）：

   | 设置 | railing DAC 写 |
   |---|---|
   | `no_hold = 0`（原默认）| **494** |
   | `no_hold = 1` | **1** |

   现在 `s200_probe` 对 S200（`codec != 0x40`）默认 `no_hold = 1`。
   修好后 ROM 通路的解码输出与直驱通路**逐项一致**（激励缓冲前后半都是 ±1，
   `[0x0503]/[0x0504]/[0x0507]/[0x04F4]/[0x06DA]/[0x06DB]/[0x06DC]` 全对）。

### 16.4 仍然存在的（by design，不是 bug）

* 满音量下响段会被 **DAC 限幅器削顶**：`0xC769` 那段在插值结果 ≥ `0x0FFC`
  时钳到 `0x7FDF`、≤ `-0x1000` 时钳到 `0x8000`，再 `<<3 +0x20` 输出。
  实测 4 秒真实语音有 1965 次限幅写 —— 音量 `[0x0001] = 0x8000`（=1.0）时
  这是设计行为；把音量档调低即可避开（字典的音量设置本来就是用户可调的）。
* 0.63 倍电平差的来源（`0x8496` 的 ×2、`0x8771` 的 `asr 1`、增益表 `0x9958` 的 Q 标度）
  尚未逐项拆开，但不影响听感与提取。
* A1600（高品质）素材的整理——那份解码器早已逐样本验证（相关系数 1.000000）。
