## 2. 本轮做完的事（每条都写了证据在哪）

### 2.1 32 位 / WinXP 版 exe ✅

* 原 exe 是 **x86-64 + UCRT**（导入 `api-ms-win-crt-*`）⇒ XP 必然跑不了，不是加开关能解决的。
* 新增 `build.ps1 -XP`，用另一套工具链：`toolchain\mingw32`（i686 + **msvcrt**）+ `toolchain\sdl2_xp`（**SDL2 2.0.22**，
  2.24 起官方放弃 XP），宏 `-D_WIN32_WINNT=0x0501`，输出 `nc3000_xp.exe`。
* 验证：`objdump -f` = `pei-i386`；导入表只有 XP 那几支（**没有** `api-ms-win-crt-*`）；
  **32 位与 64 位无头版跑同一串按键，液晶逐帧逐字节相同**。
* 细节见改造计划 **第 20 节**。

### 2.2 游戏 BGM（拼图 / 黑白棋）没有声音 ✅

* 真正的根因**不是**"缺 4 通道 PCM 实现"，而是 **061 在没有音频流时被模拟器限速**：
  `nc3_dsp_run()` 里 `gate==0` 时每片最多给 061 3000 条指令，而游戏开局的音乐握手
  恰恰发生在 `gate==0` ⇒ 061 应答慢十倍 ⇒ 主控等不到就重发/超时 ⇒ BGM 起不来。
* 修法：加"活跃窗口"（`N3_LINK_ACTIVE_MS 150`）——真的跟 061 通信过之后 150 ms 内不限速。
* **用户已确认：游戏音乐现在都正常了。**
* 顺带结论（**2026-09-28 更正**）：`INT $0505` **不是**音乐专用 —— 只停在游戏菜单、一次游戏
  都没进也有 400 次（≈16 次/秒），是周期性节拍；判断放没放音乐要看 `[061] sent=... / dac fired=...`。
  当天复测：华容道 505 字节 / dac 147 万点、黑白棋 607 字节 / 101 万点、拼图 520 字节 / 126 万点，
  都是 63833 Hz；不进局则 `dac fired=0`。
* 细节见改造计划 **第 21 节（已作废，更正见第 24 节）**。

### 2.3 系统自测第 9 项 `SPCE061检测`（两个根因 + 一个真相）✅ 2026-09-28 已解决

> **结论更新（2026-09-28）**：本节当初判的"剩下的 ERR 在固件里"**不成立** —— 真因是
> `IO 0x0E` bit3 = 061 复位线没建模。现在自检第 9 项在模拟器里**通过**，
> 详见改造计划 **第 25 节**；下面保留的是当时的排查记录（根因一/根因二仍然有效）。

进自测菜单：**先关机，然后按住 W+V 再按 ON/OFF**（三键在按 ON/OFF 那一刻必须都按住；
GUI 里对应"按住 W、V 再按 F12"；headless 用 `--hold 600`，短了 W 会先松开就只正常开机）。
菜单里**直接按数字键**运行对应项（按 `9`）。

* **根因一**：NAND 里的 `升级061.bin` 是"待烧写映像"，校验和标头前一对是 `0000`；
  284F 固件会**自己算** 32 位字和再比对 ⇒ 恒报 `BB FC`。
  当时的修法是"按固件自己的算法重算并写回两对标头"；**后来用户要求把它默认关掉**
  （那等于替真芯片补个漂亮答案）⇒ 现在默认**一个字节都不改**，只打印一行提示，
  要显式 `set NC3_DSP_FIX_HEADER=1` 才补写（配 `NC3_DSP_NAND=1` 研究 284F 时用）。
* **根因二**：主控等回包只等 ~14 ms，而我们的 061 被上面的限速拖成 ~37 ms ⇒ 主控重发
  `BB 0B`，队列里堆出几份回包 ⇒ 后面每条命令都读到陈旧字节 ⇒ ERR。
  修法同 2.2（活跃窗口），实测 `sent=668/recvd=576`（一堆重试）降到 `sent=24/recvd=28`。
* **真相**：用户读出真机这一项是 `Check_Sum: f7 10 3b 30` / `Version: 3d 28`
  ⇒ 真机那颗 061 跑的是**出厂 283D**（= `spce061a/rom/061.dat`），而模拟器一直默认加载
  NAND 里那份 **284F 升级包**。已把默认固件改成 **061.dat**（`g_use_nand = 0`），
  现在模拟器自检读数与真机**一字不差**（截图 `out/selftest/r283__32750.bmp`）。
  想研究 284F 用环境变量 `NC3_DSP_NAND=1`。
* **为什么最后还是 ERR**：283D 固件里 `CC 0F`（SRAM 测试）恒定回 `r1 = 0x0FCC`（即 `CC 0F`），
  而主控 BIOS 在 `$7398` 要的是 `CC FF` ⇒ 必然走 ERR。旁证：同类子命令全是 `0xF0|参数`
  （`CC 05`→`CC F5`、`CC 06`→`CC F6`、`CC 01`→`CC F1`），只有 `CC 0F` 的高字节是 `0x0F`；
  而且仓库里**两份互不相干的同版本内核**（`rom/061.dat` 和 `emu/a1600_image.c`）那一处**都是 `0x0FCC`**。
* 用户判断（和代码一致）：**能显示 Check_Sum/Version 就说明 SRAM 测试过了、真机是 OK**，
  所以真芯片那一处应是 `0xFFCC`。**但用户要求先挂起，且明确"不要改映像骗自己"** ——
  这条纪律写在改造计划 **§22.9**，动手前务必读一遍。

### 2.4 播放和弦音乐时"中间有一小段突然变快" ✅

用户问"会不会是缓冲区的问题"——**正是**。把 GUI 的音频队列曲线录下来后现场很清楚：

```
blk=1426  q=15501  push+49249    ← 产率突然 1.33 倍（模拟器在追进度）
blk=1451  q=24000  ovr+4152      ← 顶到 24000 上限，开始丢样本
…（共丢 ≈19000 样 ≈ 0.3 s 音乐）
```

* 根因：061 的采样跟**模拟时间**产、声卡跟**墙上时间**放，队列是缓冲；模拟器追进度时会
  短时间全速跑（主循环那套 ±300 ms 漂移逻辑）⇒ 队列冲顶 ⇒ `drain_dsp061_audio()` 丢新样本
  ⇒ 听起来就是"音乐往前跳一下"。
* 修法：**主循环加音频背压**（积压 >47 ms 就 `SDL_Delay` 等声卡，回到 ~24 ms 再跑，阈值按
  当前采样率折算）+ `dsp061_max_queue` 24000 → **32000** 当保险。
* 实测：丢样 **19000 → 0**，队列峰值 **24000 → 9333**，稳态 ~3000 样（≈45 ms）。
* 细节见改造计划 **第 23 节**。

### 2.6 本轮新增的调试手段（下一轮直接用）

| 手段 | 用途 |
|---|---|
| `--cmd-at <ms> "call1 <idx> <bank>"` | 和 `call` 一样触发 INT，但**只触发一次**并把返回进位写到 `$03F0`（1=成功）。查"某个自检项到底过没过"必备——`call` 那个桩会不停重发，最终画面只闪现几毫秒 |
| `spce061a/host/dsp_selftest.c` | 独立探针：不经过 6502，直接把命令喂给 061 固件（mode0 直接查 / mode1 完整自测顺序 / mode3 休眠唤醒 / mode4 空闲+RAM diff）。编译命令见文件头注释 |
| `spce061a/host/wd_probe.c`（2026-09-28 新增） | 比上面更进一步：**看 061 内部**——每条命令的回包、喂狗次数（`$7012` 写）、PC 页热点、首个 PC 序列，还能停在 `P_SystemClock` 进 sleep 的那一拍。§25 就是靠它把"`CC 0F` 两条分支"钉死的 |
| `--io-watch <addr>` / `--io-after <ms>` | 记录主控往某个 IO 口的写（带 PC 和值）。**查硬件控制线必备**：`--io-watch 0x0e` 一眼看出 BIOS 在自测项开跑脉冲 061 复位线（§25）|
| `NC3_SND_DEBUG=1` + `--no-console` | 把音频队列曲线打到 stdout（`q / qmax / push / cons / starv / ovr`）。**GUI 默认会抢控制台**，抓日志必须加 `--no-console` 再重定向 |
| `NC3_DSP_NAND=1` | 061 固件切到 NAND 那份 284F（默认 061.dat 283D） |
| `NC3_DSP_FIX_HEADER=1` | 允许在内存副本里补写 061 映像的校验和标头（**默认关**，见 §2.3 与 §3：禁止改映像糊过去）|
| `NC3_BEEP_TRACE=1` / `NC3_NO_BEEPER=1` | 打印蜂鸣器翻转周期 / 关掉蜂鸣器（分离噪音来源）|
| `--dump-061 <file>` | 抓 061 的**原始 DAC 流**（分析音质用这个；`--dump-audio` 是离线混音泵，长曲子会丢样）|
| 给 GUI 送按键 | `PostMessage(WM_KEYDOWN/UP)`；**方向键等扩展键必须把 lParam 的 bit24 置上**，否则 SDL 认不出来（表现：F11/回车有效、方向键没反应）|

## 4. 踩过的坑（务必避免重复）

1. **批处理里 `)` 会提前结束 `if (...)` 块**：提示文字里写 `(in the source tree)` 会让后面的
   `pause` 无条件执行，表现成"文件明明在，却停在一句 `Press any key`"。别再在 if 块的
   `echo` 里放括号（或转义成 `^(` `^)`）。
2. **GUI 抓不到日志**：`main.cpp` 默认 `AllocConsole()` 会把 stdout 抢到控制台窗口，
   要重定向必须加 `--no-console`。
3. **搬 exe 忘了带 `resource\`**：窗口能开，但液晶皮肤是空的/花屏。查找顺序是
   "当前目录 `resource\` → exe 同目录 `resource\`"（`main.cpp` 的 `resolve_resource_path`）。
4. **`--dump-audio` ≠ 真实音质**：它是离线混音泵，长曲子会丢样（实测 `overruns=35711`）。
5. **改固件/映像前先看 §22.9**：用户明确反对"为了让自检显示 OK 而改映像"。
6. **主频别再按 10.24 MHz 算**：真值是 **14.7456 MHz**（`CYCLES_MS = 14745`），
   061 是 49.152 MHz，两者比例正好 **10/3**。所有"时间/音高不对"的问题先回来核这个。

## 5. 关键结论速查（直接抄）

| 项 | 结论 |
|---|---|
| 主控主频 | **14.7456 MHz**；`CYCLES_MS = 14745`；061 = **49.152 MHz**，`N3_INSN_PER_SEC = 49152000`，主控给 061 的预算是 `×10/3` |
| 真机 061 固件 | **`061.dat`（283D）**；`升级061.bin`(284F) 只是随机器带的升级包 |
| 061 协议 | `BB 0A`→`BB FA`（链路）｜`CC 0F`→`CC FF`（SRAM 测试，固件实际回 `CC 0F`，见 §2.3）｜`CC 01`→`CC F1`｜`BB 0B`→`BB FB`+4 字节（Check_Sum）｜`BB 00`→版本字 |
| 采样率 | 音乐 63833 Hz、单词发音 36790 Hz、空闲 7997 Hz（由 061 的 TimerA 决定，重采样比要跟着它走）|
| 音频队列 | 上限 32000 样；背压阈值 47 ms / 24 ms（`main.cpp`）；正常稳态 ~3000 样（≈45 ms）|
| 自测菜单 | 关机后按住 **W+V** 再按 ON/OFF；菜单里按数字键运行（`9` = SPCE061 检测）|
| 开机流程 | 系统空间整理 → 闪存清除提示（按 **N**）→ 名片整理 → 授权⇄LOGO → 按**输入**进 2×6 菜单 / 按热键直进功能 |
| 菜单热键 | 12 项 2×6；顶排 6 个实体键，按一次主功能、再按一次副功能（英汉↔汉英、AHD↔词库、剑桥↔学习、PDA↔游戏、计算↔换算、时间↔系统）|
