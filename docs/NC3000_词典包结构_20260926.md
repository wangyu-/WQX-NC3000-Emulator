## 0. 一句话

词典包的**静态布局**现在读通了：`[4 字节地址表 66,580 条][正文][…词条压缩数据…]`，
地址的编码就是 ROM `$718C` 那套 `(页 = N>>14, 页内偏移 = N&0x3FFF)`（16 KB 页、
64 KB 只用前 16 KB）。剩下的硬骨头只有一个：**"词条序号 ↔ 词头拼写"**，
而它现在有三条**具体的**线索（§6），不再是黑盒。

## 1. 厂方文档（本轮最大收获）

`src_nc2000/nc2000f/dict_packet/h/` 里躺着三份说明书（GBK 文本）+ 一份头文件：

| 文件 | 内容 |
|---|---|
| `data_stru.txt` | **压缩数据空间摆放**：索引表 / 高频词库 / 单词压缩数据 / 例句 / 文法，逐字段列出 |
| `doc_format.txt` | **第四章 = 字典数据压缩方案**（编码表、单元定义、高频词筛选、索引表生成），第八章 = 包结构 |
| `INDEX.H` | 各区起始地址（块号+块内偏移，16 KB 一块）与各区**字节数** |
| `dict.h` | 运行期程序的常量：**控制码语义**、缓冲区长度、变量 |

### 1.1 包结构（`doc_format.txt` 第八章，与实测逐条对上）

```
1. 各区起始地址列表        32 B    （8 个 4 字节地址；实测本轮文件里没有这一段）
2. 高频词索引表            74760*4+4 = 299,044 B   ← 一级 8 + 二级 1024 + 三级 8192
                                                      + 四级 65536，再 +1 个"虚拟结束项"
3. 高频词数据              441,500 B   （高频词 1,分隔符,高频词 2,分隔符,…）
4. 单词 ID 索引表          单词数/128*4 B
5. 单词前几个字母索引表     索引入口数*12 B   节点 = NEXT_CLASS_PTR(4)+WORD_DATA_PTR(4)+ID_NO(3)+RESERVE(1)
6. 单词解释压缩数据
7. 例句 ID 索引表 / 8. 例句压缩数据 / 9. 文法 ID 索引表 / 10. 文法压缩数据
```

**关键**：`高频词索引表`的每一项就是**该高频词在"高频词数据"里的起始地址**，
并且**末尾多写一个虚拟入口表示最后一个高频词的结束地址**
⇒ *解压时直接用相邻两个入口之差表示该高频词的长度*。

### 1.2 控制码语义（`dict.h`，直接回答了"正文里那些怪字节是什么"）

```c
STOP/ALL_OVER_SIGN   00h   所有解释结束
EXPLAIN_SIGN/LJ_ID   01h   解释结束 + 后跟 3 字节例句 ID
EXPLAIN_START_SIGN   02h   每条解释开始
WORD_BOTTON_SIGN     03h   单词结束 / 同一解释中例句分隔
SYLLABLE_SIGN        12h   主题词（词头）里的音节分隔符 ★
PHONE_SEPARATOR      '/'   词头与音标的分隔符 ★
ITEM_OVER_SIGN       '/'   主题词结束标识
STRING_END/LJ_END    00h
```

> 这两个『/』和『0x12』本轮都在**数据区里直接看到了**（见 §4.3、§5.2），
> 也就是说这些控制码不是"解码器的想象"，而是**原样存进压缩数据的单元**。

### 1.3 压缩方案（`doc_format.txt` 第四章）

* 编码：`0`+3bit(8) / `10`+10bit(1024) / `110`+13bit(8192) / `1110`+16bit(65536) /
  `1111000`+8bit（ASCII 原样）/ `11111`+16bit（汉字原样）——本仓库 `tools/dict_huff.js` 已实现。
* 单元定义：**连续字母 = 1 个单元、1 个汉字 = 1 个单元、其它单字符 = 1 个单元**。
* 高频词 = "所有单元组合"里按 `(词长-编码长)*(词频-1)` 省钱最多的那些，
  所以**高频词条目可以是一整段短语**（含空格、括号、控制码）。
* 生成索引时：`块号(2B)+块内偏移(2B)`，块 = 16 KB。

## 3. 4 字节地址表：定死的部分

`python tools/dict_pack.py index 9`：

* 条目数 **66,580** = **66,579 个词条 + 1 个虚拟结束项**（`0x41050 = 66580*4` ✓ 与
  `doc_format.txt` 说的"多写一个虚拟入口"完全一致）。
* 每条的 24 位值 `v`：`页 = v>>14`、`页内偏移 = v & 0x3FFF`
  （= ROM `$718C` 的换算方式，也就是"16 KB 一块、64 KB 只用前 16 KB"）。
  * inode 9：页 121..149（外加一个 `0x20` 的**虚拟项** `0x201B28`）；
  * inode 8：页 120..144（+ 虚拟项）。
* 相邻差（= 被索引对象的长度）**3..13 字节，均值 6.8**；小步合计
  **454,055 字节**（inode 9）/ **399,039 字节**（inode 8）——与"16 KB × 页数"同量级，
  也说明被索引的东西**确实是一条连续数据**。
* 落点（`targets 9 flat`）：`0x792A39..0x953FFF`——**正好在词条压缩数据区里面**。
  例如第 5 个落点 `0x792A66` 就是 `out/ahd_headwords_clean.txt` 里
  `0792A64 hydrogenase` 的词头首字节（`00 00 F0 68 F0 79…`）。

## 4. 正文区（`0x041050..`）＝ 高频词/单元数据

* 开头 20 字节就是已验证的 T1：`the 的 。 ， to of and that`（3+2+2+2+2+2+3+4），
  随后是 `which with people you someone The for [C] have person 我们 gradable from
  usually was are in particular is not disapproving esp. about infml …`
  —— 一条**按频率降序**的"单元/短语"列表，和 `doc_format.txt` 说的
  "高频词 = 单元组合、长度 3..13"一致。
* inode 9 的同一段是**另一份**列表（`. 的 the [Inf.]of / and especially [参见] /
  Population,[See] 一种 that or with NONE 或 The 一个 American adj for from in
  relating having to used 美国 which 城市 , 位于 …`），所以两份文件各自的这段
  **不是同一张码表**；而 T1 能同时解 inode 9 的流 ⇒ **共用的是 inode 8 那张表**（与 §15.1 一致）。

### 4.1 已排除：地址表的差值 ≠ 词条长度

如果落点就是"这一段的第 k 个单元开头"，那么"相邻落点差"必须等于单元长度，
于是**落点不可能落在一个 GBK 汉字内部**。实测（`targets`）：

| 映射 | 落点范围 | 落在汉字内部的落点 |
|---|---|---|
| `flat`（= `v` 本身，按 `$718C`） | `0x792A39..0x953FFF`（词条数据区） | 32.4% |
| `base99`（把页号当绝对块号） | `0x05AA39..0x0CBFFF`（正文区） | **14.7%** |
| `page`（旧的 `page*0x4000`） | 索引表自己 | — |

再进一步：把 inode 8/inode 9 的**每一页单独搜索最佳页起点**（0..8191 全部试过），
最好的组合仍然有 **4.7%（inode 9）/ 7.0%（inode 8）** 的落点切在汉字中间
（随机期望 ~8%）⇒ **"差值 = 单元长度"这条假设不成立**，正文区不是这张表的目标。

### 4.2 已排除：表里没有"词头位置"

把 27,235 条逐字母转义词头的 `00` 标记位置（±3 字节）拿去和表的 66,580 个值求交：
命中率 **0.4%**（随机期望约 14%）⇒ 这张表**不是**"词头地址表"，
而且它的落点**系统性地避开**词头位置。

### 4.3 已排除：正文区里没有任何"单字节分隔符"

`python tools/dict_pack.py escapes 9`：正文区（0x41050..0xBC000，503,728 B）
里**除 `0x2F('/')` 出现 73 次外，没有控制码**（inode 8 里则满是 0x00/0x01/0x03/0x04/0x12）。
所以"高频词 1,分隔符,高频词 2"里的分隔符**在文件里并不存在**——
只能靠上面那张**地址表**切；这也解释了为什么上一轮的贪心切分总是差点意思。

## 5. 两块从没被描述过的结构（新线索，务必接着啃）

### 5.1 `0x0BC000..0x0C0000`：16 KB 的"降序记号表"

`b4 4f fc a8 53 2c fc b4 4f 2c fc b3 4e 2c fc …`：
一串**值单调递减**的 2~4 字节小记号（后缀 `fc`/`f7`/`f6`…），
像"按大小降序排列的记号表"。位置正好卡在正文区末尾与节点表之间。

### 5.2 `0x0C0000..0x0E0000`：10,922 个 12 字节节点（**疑似字母索引**）

`python tools/dict_pack.py nodes 9 0xC0000 30` 的前几个节点：

```
 0  A=0001534a B=3c200398 C=5f0736 D=05   4a 53 01 00 98 03 20 3c 36 07 5f 05
 1  A=0001534a B=00000000 C=d10742 D=38
 2  A=00015789 B=00000000 C=fd0743 D=04
 3  A=000157a8 B=3d580398 C=d80743 D=05
 …
22  A=00015ac0 B=01000399 C=d9074b D=30
24  A=00015f6f B=02380399 C=c90756 D=2c
26  A=00016000 B=03700399 C=f90758 D=06
```

全部 10,922 个节点的统计（可复现：`nodes` 命令 + 下面这几条判据）：

| 字段（按 12 字节对齐） | 实测 | 解读 |
|---|---|---|
| 字节 0-2 | 单调性 60.4%，范围 **47 .. 95,702** | 上界 < 131,072 = 区块大小 ⇒ **很可能是"本区块内的偏移"**（自指的树结构） |
| 字节 4-5 | 只有 **920 / 921** 两个值 | 像"该前缀下的单词个数"（>100 就建下级索引，与 `doc_index` 的说法一致） |
| 字节 6-7 | `0x3C20 + 312k`（k=0,1,2,3…），**步长恒为 312 = 26 × 12**；换一个"个数"值时**重新从 0x0100/0x0238/0x0370… 起算** | 下级索引地址：**每级 26 个节点 × 12 字节 = 312** |
| 字节 8-9 | **100% 非递减**，范围 **926 .. 1,939** | 单调 ⇒ 是"ID_NO"；但**不是** 0-based 的词号（0..66,580 那个），
所以要么它指另一套编号（如另一部词典/词尾桶），要么字段还要再错开 1~2 字节 |
| 有下级索引的节点 | **281 个**（前几个节点下标：0, 3, 5, 7, 22, 24, 26, 35, 39, 43…） | 与"26+26×26 一级/二级"量级吻合 |

> 综合：这几乎肯定是**索引树（字母索引）**——字段里既有"本区块内偏移"（自指）、
> 又有"下级索引地址（步长 26×12）"、又有单调 ID。
> **它就是"拼写 → 词 ID"那条缺失的一环**，但字段顺序/对齐还差最后一层（§6 优先级 1）。

## 6. 下一步（按性价比排序）

1. **定死 §5.2 的节点表**（最高优先）。
   * 判据 A：节点数 10,922 应能被"一级 26 + 二级 26×26 + 三级…"解释；
     用第 2 字段的 281 个下级地址去**逐级走**，看能否走到"26 个节点一组"。
   * 判据 B：第 3 字段（ID_NO）应当**单调**且**首节点 ID = 0**（第一个字母 'a' 的第一个词）；
     如果不是 0，说明字段偏移差 1~2 字节，用"ID 必须从 0 开始"反推对齐。
   * 判据 C：走通后拿 `apple` 做端到端验收：字母索引 → 词 ID → `ahd_celp[词 ID]`
     → `celp_data+0x284000+5N` 记录链 → 帧 → 061 → WAV。
   * **本轮新想到的一条捷径**：ID 字段的范围是 **926..1,939**，
     完全落在 `word_ID`（inode 25）那 **7,413 条**之内 ⇒ 它有可能不是"词号"，
     而是"**有发音的词**的序号（= `word_ID` 的下标）"。若是这样，
     节点表 → `word_ID[序号]` 就直接给出 `ahd_celp` 下标，**一步到位**。
     验证办法：取一个 ID 已知的节点，用 `tools/ahd_celp_probe.py` 把
     `ahd_celp[word_ID[ID]-0x10000]` 的记录链放出来听，看是否与该前缀的单词吻合。
2. **`word_ID` 与 `ahd_celp` 的语义复核**（`docs/NC3000_单词发音数据.md` §8.3/§9.2 已给出模型）：
   `ahd_celp[词 ID]` = 累计记录序号（步长 = 音节数，47.5% 的项是 `FFFF`）。
   本轮复核时注意：**读 u16 要用 int32/int64 再移位**，
   `np.uint8 << 8` 会溢出成 0（本轮就踩过这个坑，差点把 47.5% 的 `FFFF` 读成 0%。
   上一轮 §14.3"7413/7413 命中"之所以成立，是因为非 `FFFF` 项占 52.5%，
   随机命中率就有 52.5%，所以那条证据**偏弱**，不能单独当结论）。
3. **正文区（§4）切分的正路**：既然没有分隔符、地址表又对不上，就只剩
   "用解码器当 oracle"：把 T1 锚死（已验证），用 §1.3 的码长（9/12/16/21 bit）
   反推 T2..T4，判据仍然是"解出来的释义是否通顺"。
   `tools/seg_freqtable.py` 的贪心只是起点，建议改成**带词频先验的 DP**，
   并用 §5.1/§5.2 两张表交叉验证。
4. 记一下本轮**踩过的坑**（避免重犯）：
   * `np.uint8 << 8` 溢出（见上）；
   * 4 字节地址表**不是**按 `page*0x4000 + off16`（那是把 16 位偏移当 14 位用）；
     正确编码是 `page = N>>14, off = N & 0x3FFF`，即 **`file_offset = N` 本身**；
   * 正文区在 inode 9 里几乎**没有控制码**（0x00/0x01/0x03/0x12 一个都没有），
     但 inode 8 里满都是 ⇒ 不要把"inode 8 的正文结构"直接套到 inode 9。
