## 1. 固件侧：按键是怎么被读到的

反汇编 `NC3KSYSNOR.nor` 得到主扫程序（bank0，CPU `$EAE0`–`$EC10`），主循环
`INT $C00A = sys_key_proc`（`info/NC3000_trap.txt` 里有名字）→ `$D71D` → `$D753` → 扫描。

扫描动作是"逐行驱动、读回感应线"：

```
每次先清 0x09(port1) 和 0x1E(port6)，再写一个行选值给 0x09，然后读回：
   行选 0x80 → 读 0x08(port0) bit6
   行选 0x40 → 读 0x1E(port6) bit1
   行选 0x10 → 读 0x1E(port6) bit1
   行选 0x08 → 读 0x08 bit7 与 0x1E bit1
   行选 0x04 → 读 0x1E bit1
   行选 0x02 → 读 0x08 bit7、bit5
   行选 0x01 → 读 0x08 bit6
```

把读到的东西拼进 `$D2`，再查表 `$EF73[X]` 得到键值，写进：

* `$C7` —— 键值，**bit7 = 1 表示"没有新键"**（有键时是 `键值 | 0x80`）
* `$040A` —— `Line_Key`，上一次按键
* `$0A2D/$0A2E/$0A2F` —— 三次采样的去抖历史（必须连续三次相同才算数）

**关键点：有 4 条行（0x40/0x10/0x04/0x08）的感应线在 port6 上，而不是 port0。**

## 2. 模拟器侧：现在是个明确标注的 hack

`NekoDriverIO.cpp`：

```cpp
//// hack, 主要是为了骗nc3000的按键运行起来
BYTE ReadPort6EX(BYTE read){
    UpdateKeypadRegisters();
    return ((r08_port0_ID & 0x0c) >> 2);   // ← port6 直接抄 port0 的 bit2/3
}
```

也就是说 port6 的感应线没有真正建模，只是抄了 port0 的两位。**这就是"有些键按了没反应 /
几个键出同一个键值"的根因。**

## 4. 已实施的修复（第二轮）：真正的 port6 列线模型

找到真正的键盘扫描程序在 **bank 0x10**（`$8CFF`–`$8D7x`），两张列线掩码表：

```
$94AE (port6, 4 项): 01 02 04 08          → port6 bit0~3 四条列线
$94B6 (port0, 8 项): 10 20 40 80 EF DF BF 7F
                                          → 前 4 项 = port0 bit4~7 单条拉高
                                            后 4 项 = 同样的线拉低（互补驱动）
行线：port1 的 8 位
```

扫描方式是"驱动一列、读回 port1，和刚写出去的值比较"——**说明 port0/port6 与 port1
在无键时是同一条线**（通了就是同一个电平），按键才会把电平拉走。

据此改了两处：

| 位置 | 改动 |
|---|---|
| `NekoDriverIO.cpp` 新增 `Write1EPort6()` | 写 port6 时把值传导到 port1 的低半字节（无键基线），并保存锁存值 |
| `NekoDriverIO.cpp` `UpdateKeypadRegisters()` | 新增 port6 列线的按键传导：按下 (行 y, 列 c=0..3) 且 port6 bit c 被驱动时，拉 port1 bit y |
| `ReadPort6EX()` | 不再抄 port0 的 bit2/3，改为返回真正的 port6 输入值 |
| `io_new.cpp` | `nc3000mode` 下把 IO `0x1E` 的**写**接到 `Write1EPort6()` |

### 修复后的实测（`--key-probe`，见 `out/nc3000/按键实测_64位置.txt`）

**之前按不出来 / 按错的字母现在全对了**：

（注意 `$C7` 的 bit7 是"有键"标志，键值要 `& 0x7F`。）

解出键值的位置从约 40/64 提升到 **62/64**。

### 还没收干净的

1. port6 那 4 列（x=0..3）目前**都解成 0x1B(ESC)**——说明按键被检出了，但行号对不上；
   这 4 列应该就是 NC3000 独有的那几个键（网络/计算/时间/英汉/剑桥…）。
2. port0 的"互补驱动"那一半（`EF DF BF 7F`）还没建模，导致第 5~7 行的 x=5 与 x=4
   仍然互相串（`(5,4)` 与 `(5,5)` 都是 'y'、`(6,6)` 给出 'j' 而不是 'm'）。
   真实机制是"列线被拉低时按键把行线也拉低"，需要给 `tmpdest1` 配一个"拉低掩码"。

## 5. 又试了一版"忠实 16 列模型"，被 ON 键卡住（已回退）

按第 4 节的表把模型做成"16 条列线 × 8 条行线、按键把列线电平短接到行线"，
并让 port0/port6 的被驱动电平传导到 port1 作为无键基线。结果：

* 键扫描本身说得通了，但**固件复位后不再进入主循环**（`INT` 历史为空、
  061 也没有任何流量、屏幕停在关屏态）；
* 回退到第 4 节那一版（旧的 port0 传导 + 新的 port6 传导）后，立刻恢复正常：
  `INT $C00A = sys_key_proc` 6.5 万次、按键能进词典。

**原因**：ON/OFF 键在忠实模型里落在"被驱动的那一行"上——扫描时把该列线驱动到 1，
按键把同一行也短接到 1，**读回来没有变化，扫描器看不见它**。
而固件复位的唤醒流程又必须看到 ON 键（这就是当初 (0,0) 能唤醒的原因：
那一版模型里它恰好可见）。真实的 ON 键应该是走独立的检测通路（真机上是
KBI 中断/独立引脚），不在这个 8×4 的扫描矩阵里。

> 结论：**忠实矩阵模型要落地，得先把"ON 键怎么被固件看到"单独搞清楚**，
> 否则它会连带把启动流程弄坏。这一条列进下面。

## 6. ON 键 / 唤醒线查清了（2026-09-26 第三轮，地址已复核）

在 **bank 3 `$44DA` / `$4538`** 找到开关键的检测程序（之前把反汇编的第二列
当成了地址，实际入口是这两个）：

```
$44DA  LDA #$24 / STA $3E / LDA #$00 / STA $3F   ; 扩展寄存器 0x24 = 0
$44E3  LDA #$22 / STA $3E / LDA #$00 / STA $3F   ; 扩展寄存器 0x22 = 0
$44EB  LDA $08 / AND #$01 / BEQ $4518            ; ★ port0 bit0 = "有键按下"
$44F1  LDA $08 / AND #$04 / BNE $4516            ; ★ port0 bit2 = 另一个判据
       ... 操作 $3A/$3C(bank3) ...
$4518  (唤醒/热键列组扫描)
$451C  LDA #$FF / STA $15 / STA $09              ; port1 全输出 = 0xFF
$4524  LDA #$20 / STA $3E / LDA #$0C / STA $3F   ; 扩展寄存器 0x20 = 0x0C
$4528  LDA #$0C / STA $1E                        ; port6 = 0x0C
$452C  JSR $E0CC
$452F  LDA $08 / AND #$01 / BNE $4556            ; ★ 再读 port0 bit0
$4535  JSR $463C                                 ; 否则走另一支
```

后面（`$4556` 起）依次用表 `$4628`（给 port1，从 Y=7 递减）和 `$4630`
（给 port6）驱动列组，每驱动一次就**读 port0 bit0**：

```
loop1: LDA $4628,Y / STA $09 / NOP / LDA $08 / AND #$01 / BEQ 命中
loop2: LDA $4630,Y / STA $1E / NOP / LDA $08 / AND #$01 / BEQ 命中
命中:  LDA $4632,Y → STA $03E3 (Curr_Function)，并维护 $03E1 (Wakeup_Flag)
```

全库检索确认：**port0 的 bit0 只有这一处会读**（`A5 08 29 01` 共 6 处，
全部落在 bank 3 `$41D2`–`$45AF` 这条开关键/唤醒链里），
而 port0 只在这几处被写：`$C3A4`(写 0)、`$E32E`(写 0x02)、`$4C1D`、
`$89C1/$89D9`(识别扫描的列线图案)。
也就是说 **bit0 是一条纯输入线，专门表示"有键按下"**。

**两个重要结论**：

1. **"有没有键按下"是 port0 bit0 这一条公共线**，不是从矩阵里读出来的。
   这正好解释了为什么老模型里按 (0,0) 能唤醒——`keypadmatrix[0][0]` 经老传导
   恰好拉的就是 port0 bit0。
2. **按键的"身份识别"在 bank 0x10 的另一个扫描程序**里（驱动 port0/port6 的
   一列、读 port1 的 4 行、和刚写出去的值比较），也就是第 1 节那张表。
   两套扫描分工：bank 3 判"有没有键"、bank 0x10 判"是哪个键"。

### 试过但被否掉的两个改法

| 改法 | 结果 |
|---|---|
| 在忠实 16 列模型里去掉老的 port0 传导（只留新的列线传导） | 开始不了机——唤醒要的 port0 bit0 没人为它拉高 |
| 保留老传导 + 加上 port0→port1 电平传导（识别扫描需要的基线） | 能开机，但键位识别反而变差（62/64 → 40/62），已回退 |
| 任意键按下就拉 port0 bit0 | 开机失败（bit0 在启动阶段还有别的用途） |

**当前采用**：老传导（负责 port0 bit0 公共线）+ port6 列线传导（负责识别），
即第 4 节那一版：能开机、62/64 位置能解出键值。

下一步若要把 ON 键做"真"：**port0 bit0 就是"有键按下"这条纯输入线**
（全库只有开关键链会读它）。之前"有键就拉 bit0"失败，原因不在 bit0 本身，
而在同一条链紧接着读的 **port0 bit2** 以及随后的 `$3A/$3C`(bank 3) 操作——
那条支路在模拟器里走出来的结果不对，才把启动带偏。所以下一刀应该切在
`$44F1` 的 bit2 判据和 `$3A/$3C` 那段（bank 3 的 GPC/P05 寄存器语义），
而不是继续动矩阵。

### 6.1 已落地：bit2 也补上了（2026-09-26 第四轮）

把开关键检测那段读全后，逻辑是：

```
$450B  LDA $08 / AND #$01 / BEQ $4538   ; bit0=0（没键）→ 去 $4538 扫列组
$4511  LDA $08 / AND #$04 / BNE $4516   ; bit2=1 → 直接 CLC/RTS 返回
$4517  ...                              ; bit0=1 且 bit2=0 → 走 $3A/$3C(bank3) 那条支路
```

所以 **bit0 = "有键按下"，bit2 = "按的是开关键"**。据此在
`UpdateKeypadRegisters()` 里、**和老传导同一处（只在 port1 被驱动的阶段）**
补上：按 (0,0) 时同时把 port0 的 bit2 拉高。

> 注意：**不能在别处无条件地拉这两条线**。试过"任意键就拉 bit0"，
> 结果连开机都过不去——因为识别扫描（bank 0x10，驱动 port0 读 port1）
> 期间那两条线也被拉高了，固件把"有键按下"的时序判断错了。

实测效果：**键位表零差异（62/64 不变）、开机正常（`sys_key_proc` 6.5 万次）**，
但固件现在会走对 ON 键那条返回分支，不再误入 `$3A/$3C` 支路。

> 仍未解决：**运行中按 F12 不会进入睡眠**——因为 F12 走的矩阵位置 (0,0)
> 并不是固件认得的那颗开关键（固件认的是能解出 0x18 的那个位置）。
> 要么把 F12 同时映射到那个位置，要么让 `warm_reset_if_clkoff()` 之外
> 再加一条"主动请求睡眠"的通路。

## 8. ★ 重要更正（2026-09-26 晚）：`$C7` 的 bit7 语义搞反了

上一版写的"`$C7` 的 bit7 = 1 表示**没有**新键"是**错的**。反汇编 bank 0 的扫描
收尾代码（file `$EE1F`–`$EF31`）后，真实语义是：

```
$EF09  LDA $EF32,X          ; 查键值表
$EF0C  BMI $EF2C            ; 表项 >=$80 → 无键（清 $0401 返回）
$EF0E  ORA #$80
$EF10  STA $C7              ; ★ $C7 = 键值 | $80  → bit7 = 1 表示"来了一个新键"
$EF19  BIT $03ED
$EF1C  BPL $EF2C            ; $03ED bit7 未置 → 新键保留
$EF26  LDA $C7 / AND #$7F / STA $C7   ; 否则把 bit7 清掉 → 只表示"键还按着"
```

而且前两个文档里说 `$C7` 的 bit7 语义相反，所以之前的推断都按反的走。

| 变量 | 含义 |
|---|---|
| `$C7` bit7=1 | **有新键**（扫描刚解出一个键） |
| `$C7` bit7=0 | 只有"键还按着"或"没键" |
| `$03ED` bit7 | 与"读键/重复"有关，扫描用它决定要不要清 `$C7` 的 bit7 |
| `INT $C006` | = `repeat_key`（读键，读走之后 bit7 被清） |

### 8.1 由此定位到的两个"卡住点"

**A. 开机动画 = 一个 1 秒超时的轮询**

动画里等按键的例程在 bank 3 `$8C0E`（被拷到 RAM `$4C0E` 执行）：

```
$8C10  LDA #$20 / STA $15      ; port1 方向 = 0x20
$8C21  LDA #$20 / STA $09      ; port1 输出 = 0x20
$8C2C  DEY / BNE / DEX / BNE   ; 内层延时
$8C32  INC $80 / LDA $80 / CMP #$FF / BEQ 超时返回
$8C3C  LDA $08 / AND #$50 / BEQ $8C29   ; ★ 读 port0 的 bit4 / bit6
...
$8C60  LDA #$00 / STA $09 / STA $15 / RTS   ; 超时
```

两个包装函数直接给出语义：

```
$8C02  JSR $4C0E / AND #$10 / RTS     ; 等"bit4 那一组"键
$8C08  JSR $4C0E / AND #$40 / RTS     ; 等"bit6 那一组"键
```

所以 **动画是靠"每秒一次的超时"翻页**的（`$03FE` 存的是 RTC 秒 —— 见
`$430C` 那段：`LDA #$00 / STA $3E / LDA $3F / AND #$3F / ASL A / STA $03F9`），
按键只是让轮询提前返回。

**B. 按过键之后，固件在等"输入"键**

在 bank 3 `$B97F`（拷到 RAM `$797F` 执行）：

```
$B97F  LDX $03FE
$B982  JSR $05E7        ; 等键事件（子程序在 bank 0 $E4BD，拷贝到 RAM $05E7）
$B985  LDA $C7
$B987  BMI $B9B4        ; ★ $C7 bit7=1（有新键）→ 去读键
$B989  DEC $82 / BPL $B97C
...
$B9B4  INT $C006        ; repeat_key：读走这个键
$B9B7  CMP #$0D         ; 是不是"输入"？
$B9B9  BNE $B9C0        ; 不是 → JMP $7969
$B9BB  LDA #$FF / STA $CE / RTS   ; ★ 是"输入" → $CE=$FF（确认标志）
```

**当前模拟器卡在这里**：按 (5,3) 输入键时，固件把 `$C7` 写成 `0x79` 之类的
**bit7=0**（"键按着"）而不是 bit7=1（"新键"），所以这两处轮询都永远退不出来
（实测 `$CE` 一直是 00）。也就是说按键的"**新键边沿**"没有被固件认到 ——

## 9. ★ 2026-09-27：port0 的 bit4 / bit6 是 **Y 键线和 N 键线**（实测证明）

为了验证"动画那条线是不是'任意键'"的猜想，我做了一次反证实验：在
`UpdateKeypadRegisters()` 里加了一段"port1 驱动 0x20 时，任意键都拉
port0 bit4/bit6"，然后开机按 N（矩阵 (5,6)）。

结果固件**走进了"清除"分支**：

```
闪存中有数据 清除吗？ Y清除，N保留
   ↓（本该按 N 走"保留"）
数据将全部清除   是否取消操作   Y取消，N继续
数据删除后将无法恢复，确认吗   Y确认，N返回
```

说明这两条线是**两个具体按键的专用线**，不是"任意键"：

| 线 | 对应的键（矩阵） | 说明 |
|---|---|---|
| port0 **bit4** | (5,4) = Y | `$8C02  JSR $4C0E / AND #$10 / RTS` = "等 Y" |
| port0 **bit6** | (5,6) = N | `$8C08  JSR $4C0E / AND #$40 / RTS` = "等 N" |

（所以"闪存中有数据，清除吗"这种 Y/N 对话框，走的正是这两条线。）
**这个实验改动已经回退**，回退后启动流程恢复正常。

## 10. ★ 键位识别扫描有个总开关：`$03F1` bit6

bank 0 的扫描入口前有这么一句：

```
$EAD8  BIT $03F1
$EADB  BVS $EAE0        ; ★ $03F1 bit6 = 1 才做"是哪个键"的识别扫描
$EADD  JMP $EC23        ; 否则直接跳过
```

而全库检索 `$03F1` 的写入点（`8d f1 03` 共 7 处：bank 2 `$52B4`、
bank 3 `$8469`/`$9988`、bank 0x0D `$4440`/`$4449`、bank 0x10 `$4BE2`/`$5EB7`…）
**全是 `AND #$BF`（清 bit6）**，找不到任何置位的地方。

实测也印证了这一点：在"静止 LOGO"那段时间，trace 里 `$03F1` **一直是 00**，
按下 (5,3)（输入）时 `$EF10`（写 `$C7` 那条）**一次都没有命中**——
固件此刻根本不做键位识别，所以"输入"认不出来，只能靠 Y/N 两条线。

这条是"按输入进主菜单"卡住的直接原因，下一步要查：

1. `$03F1` bit6 到底在哪里被置起来（可能是"算出地址再存"的写法，
   也可能被 `$03F1` 相关的位操作替代）；
2. 或者：真机上进入 2×6 主菜单是不是走 Y/N 某一条线而不是"输入"。

### 10.1 补充：`$03F1` bit6 确实没有置位点，常规扫描在另一条支路

把 `$03F1` 的全部 7 个写入点都看了：

| 位置 | 动作 |
|---|---|
| bank 02 `$52B4` | `AND #$BF`（清 bit6） |
| bank 03 `$8469`、`$9988` | `AND #$BF`（清 bit6） |
| bank 0x0D `$4440` | `AND #$7F`（清 **bit7**） |
| bank 0x0D `$444B` | `ORA #$80`（置 **bit7**） |
| bank 0x10 `$4BE2`、`$5EB7` | `AND #$BF`（清 bit6） |

⇒ **bit6 只在多处被清、从没被置**，所以 `$EAD8` 那条"特殊扫描"实际上不会走；
走的是 `$EADD → $EC23` 这条**常规扫描**。它也照样产出"新键"：

```
$ECA1  LDA $0A2D / CMP $0A2E / BNE ...
$ECAE  CMP $040A / BEQ $ED01
$ECB3  STA $040A
$ECB6  ORA #$80
$ECB8  STA $C7          ; ★ 常规扫描同样写 $C7 = 键值|$80（新键）
```

（它按 6 行循环：驱动表 `$EAB2` = `01 07 0D 13 19 1F`，基准键值表
`$EAB8` = `00 16 22 25 17 0F 1B`，每行用 `JSR $EFB5` 读回列号。）

### 10.2 实测：按住时间太短会被"漏掉"

7.0 s 按下 (5,3) 150 ms，扫描下一次跑到已经是 7.81 s（`$EC23`/`$EFB5` 命中），
**按键已经松开了**，所以 `$ECB8`（真正的"认出键"）从 5.2 s 之后再没命中过。
换成 1500 ms 长按再试，动画会短暂变慢，但**仍然进不到 2×6 主菜单**

## 11. ★ 键扫描的完整结构（2026-09-27）：一个由 `$C8` 轮转的状态机

把 `$EC23` 后面的流程连起来读，终于看清了：

```
$EC23  (入口) ... 先处理 $1C、port0 bit2、$040B
$EC3B  JSR $ED24                     ; 配置 0x3A/0x3C（GPC）
$EC3E  LDX #$FF
$EC40  INX / CPX #$06 / BEQ $EC55
$EC45  LDA $EAB2,X / ORA #$40 / STA $1C   ; 写行码
$EC4C  JSR $EFB5                     ; 延时（LDY #$2D 空转）
$EC4F  LDA $1C / AND #$20 / BEQ $EC40 ; ★ 读 $1C 的 bit5（BCP 脚）
$EC55  LDA $EAB8,X ...               ; 命中行 → 取该行基准键值
$EC8C  STA $0A2D,Y ...               ; 三取二去抖($0A2D/$0A2E/$0A2F)
$ECB3  STA $040A
$ECB6  ORA #$80
$ECB8  STA $C7                       ; ★ 常规路径也能产出"新键"
...
$ED01  JMP $ED46
$ED46  LDA #$8A / BIT $1E / ... / STA $1C
$EDC6  INC $C8                       ; ★ 关键：轮转计数器
$EDC8  LDA $C8 / CMP #$0A / BCC ... / LDA #0 / STA $C8   ; $C8 在 0..9 循环
$EDD2  CMP #$08 / BCC $EE3C          ; $C8 < 8  → 走 port1 驱动的那8行
$EDD6  SBC #$08 / TAX                ; $C8 = 8/9 → X = 0/1
$EDF4  LDA $EFB3,X / STA $1E         ; 驱动 port6 → 产出键值 $EE3A[X]
...
$EE3C  (X = $C8 = 0..7)              ; ★ 每次只扫"一行"
$EE57  LDA $F035,X / STA $09         ; 用表 $F035 驱动 port1
$EE5C  LDA $08 / AND #$F1 / STA $C9  ; 读 port0
$EE62  LDA $1E ...                   ; 读 port6
$EE7D  PLA / EOR #$FF / TAY
$EE80  EOR $BF,X / BEQ $EE8B         ; 与上一次比较（去抖）
$EE8C  TYA / BIT $03F1 / BVS $EE95   ; ★ bit6 只决定**用哪张解码表**
$EE92  JMP $EEF6                     ; bit6=0 → 用 $EF32 表
$EE95  ...                           ; bit6=1 → 用 $EF73 表
$EF09  LDA $EF32,X / BMI $EF2C       ; ★ 查表得键值
$EF0E  ORA #$80 / STA $C7            ; ★ $C7 = 键值 | $80（新键）
```

**两个重要更正：**

1. `$03F1` bit6 **不是"要不要扫描"的开关**，而是**选哪张解码表**
   （`$EF73` 还是 `$EF32`）。扫描一直都在跑。
2. 扫描是**一次只扫一行**的：`$C8` 每被调用一次就 +1，在 0..9 里循环，
   `$C8 = 0..7` 各驱动一行（表 `$F035`），`$C8 = 8/9` 走 port6 分支。
   ⇒ **扫完整个键盘要 8 次调用**。

## 14. ★ 键盘扫描的驱动源 = **timebase 中断**（2026-09-27，关键）

IRQ 处理程序的入口（bank 0 `$EA5E` 一带）是：

```
$EA94  LDA $01          ; ★ $01 = 中断状态寄存器（读一次会把低 6 位清掉）
$EA96  STA $BE
$EA98  BIT $F039        ; $F039 是 ROM 里的常量 0x08 —— 起"掩码"作用
$EA9B  BEQ $EAA0        ; (A & 0x08) == 0 → 不扫键
$EA9D  JSR $EABF        ; ★ A 的 bit3 置位时才调用键盘扫描
```

（`BIT` 的 Z 由 `A & M` 决定，所以真正的条件是 **`$01` bit3 = 1**；
`$F039` 只是 ROM 里的常数 0x08。）

模拟器里置这一位的只有一处：

```c
void setIrqTimeBase() { ioReg[io01_int_status] |= INT_TIME_BASE; }   // INT_TIME_BASE = 8 → bit3
```

调用它的地方（`cpu_loop_new.cpp`）：

```c
if(nc2000mode||nc3000mode||nc1020mode){
    if(trigger_x_times_per_s(185)){
        if (timeBaseEnable()) {          // = (ioReg[0x04] & 0x0F) != 0
            setIrqTimeBase();
            cpu->set_irq_pending();
        }
    }
}
```

而 PC1000 分支里有一句注释把这个机制说得很明白：
> `//timebase中断为4ms一次，主要用于键盘扫描`

⇒ **NC3000 的键盘扫描就是靠这个 185Hz 的 timebase 中断在跑**，
每中断一次扫描状态机（`$C8`）走一步。

## 15. 实测：这一状态里扫描频率只有 ~14Hz（快了 13 倍才对）

在"静止 LOGO"状态用 trace 采样 `$C8`（每扫一次 +1）：

```
$C8 = 05 → 01 → 08 → 05 → 01 → 07 → 04     （500ms 内约 7 次）
```

⇒ 约 **14 次/秒**，而一次完整键盘扫描要 `$C8` 走 10 步，
所以**扫完一遍要 ~0.7 秒**（与实测 `$EC23` 两次命中间隔 5.2s→7.81s 的现象吻合）。
按一下键（150ms）非常容易被整轮扫掉；`--hold 1500` 也只能覆盖两三轮。

理论频率应该是 185Hz（`trigger_x_times_per_s(185)`），摊到 10 步是 **54ms 一轮**。

**下一步**：查为什么这一状态里 timebase 只跑到 ~14Hz。最可疑的两点：

1. 模拟器的 `g_irq` 是**一个布尔量**，多个中断源会被合并成一次 ——
   185Hz 的 timebase 在固件长时间关中断的循环里会被"压缩"掉；
2. `timeBaseEnable()` 用的 `ioReg[0x04] & 0x0F` 与固件实际写的时间基准位
   是否一致（NC3000 的 `$04` 定义可能和 NC2000 不同）。

## 16. ★ 实测数据（2026-09-27）：谁都没丢，是**扫描本身没认出键**

先纠正上面第 15 节"只有 14Hz"的说法 —— 那是 trace 采样 `$C8` 的错觉。
新增 `--count <pc>` 精确计数后（9 秒仿真）：

```
irq stats: timebase_fired=652 irq_pending=659 irq_taken=658 timebase_gate_fail=1019
count $EA5E = 658      ; IRQ 入口
count $EA6B = 658
count $EA94 = 658
count $EA9D = 651      ; JSR 键盘扫描
count $EABF = 651
count $EAD8 = 651
count $EC23 = 651      ; ★ 扫描体：651 次 / 9s = 72Hz
count $ECB8 = 1        ; ★ "认出键"只发生 1 次（就是 4.2s 那次按 N）
```

几件事同时确定：

1. **timebase 触发率完全正确**：652 + 1019 = 1671 次 / 9s ≈ **185Hz** ✓，
   `timebase_gate_fail` 的 1019 次几乎都在前 5 秒 —— 因为开头固件写了
   `$04 = 0`（pc=`$C481`，"停 timer0"），按手册 `$04` 的 b3~b0 就是 TBC，
   **0000 = OFF**，所以那时 timebase 本来就该停；到 `$42D2` 处写 `$04 = 0x0C`
   之后就一直在跑。
2. 中断链路**没有丢**：658 个 IRQ → 651 次扫描调用（差 7 次是别的分支）。
3. **但扫描一次都没认出键**：`$ECB8`（常规路径写出 `$C7`）只有 1 次，
   `$EF10`（另一条解码路径）在这轮里 **0 次**。

## 17. 原因：`$1C` 的 bit5 是"这一组有键"，不实现它扫描就永远认不出键

常规扫描每轮做的事：

```
$EC3E  LDX #$FF
$EC40  INX / CPX #$06 / BEQ $EC55
$EC45  LDA $EAB2,X / ORA #$40 / STA $1C    ; 探针序列 $EAB2 = 01 07 0D 13 19 1F
$EC4C  JSR $EFB5                            ; 延时
$EC4F  LDA $1C / AND #$20 / BEQ $EC40       ; ★ 读 $1C 的 bit5
$EC55  LDA $EAB8,X                          ; 基准键值表 = 00 16 22 25 17 0F 1B
```

模拟器里 `$1C`（`io1C_batt_detect`）**只对 nc1020/nc2000 当电池检测**实现，
NC3000 下读回来就是写进去的值 → bit5 永远 0 → 6 次探针全部落空，
`X` 走到 6 拿到 `$EAB8[6] = 0x1B` —— 这解释了那唯一一次 `$C7 = 0x9B`（=跳出）。

所以 **必须把 `$1C` bit5 建模出来**；但它低 5 位的**分组编码还没解开**
（我试过"任意键都置 bit5"，结果固件把任何键都解成第 0 组，
Y/N 对话框直接错乱，已回退）。

## 19. ★★★ 2026-09-27：找到并修掉真正的键盘 bug（`port6` 读回从不更新）

### 19.1 病灶

`NekoDriverIO.cpp` 里 `ReadPort6EX()` 返回的是：

```c
static BYTE r1e_port6_ID = 0xFF;      // ← 初始化成 0xFF 之后，全工程再没有第二个赋值点
BYTE ReadPort6EX(BYTE read){ UpdateKeypadRegisters(); return r1e_port6_ID; }
```

也就是说 **读 port6 永远返回 0xFF**（注释里那句"hack, 主要是为了骗 nc3000 的按键
运行起来"就是它在自白）。而固件的主扫描（bank 0 `$EE3C`）是这么取按键的：

```
$EE4D  LDA #$00 / STA $09 / STA $1E      ; port6 全 0
$EE57  LDA $F035,X / STA $09             ; ★ port1 逐行驱动，表 $F035 = 80 40 20 10 08 04 02 01
$EE5C  LDA $08 / AND #$F1 / STA $C9      ; 读 port0{0,4,5,6,7}
$EE62  LDA $1E / ASL A / ASL A / AND #$0C ; 读 port6{0,1} → 字节的 bit2,3
$EE68  ORA $C9
$EE80  EOR $BF,X / BEQ $EE8B             ; 和上一轮采样比较

$EF09  LDA $EF32,X / ... / ORA #$80 / STA $C7
```

port6 恒为 0xFF ⇒ 那半边键盘（矩阵列 0..3）**永远检不出来**；

### 19.2 修法（已提交）

在 `UpdateKeypadRegisters()` 里补上 port6 的"读回传导"：
port1 某一行被驱动时，按下的键把自己的列线接到该行，于是 **port6 对应位读到驱动电平**：

```c
if (nc3000mode) {
    unsigned char recv = 0, recv_lo = 0;
    for (int y = 0; y < 8; y++) {
        if (!(port1control & (1u << y))) continue;   /* port1 bit y 是输出 */
        for (int c = 0; c < 4; c++) {
            if (!keypadmatrix[y][c]) continue;
            if (port1data & (1u << y)) recv    |= (1u << c);
            else                       recv_lo |= (1u << c);
        }
    }
    r1e_port6_ID = (unsigned char)((w1e_port6_OL | recv) & ~recv_lo);
}
```

## 24. ★★★★ 2026-09-27：找到根因并修好 —— **BRK 压栈少了一个字节**

### 24.1 症状与定位过程

1. 和 Lee 版对照：Lee 版**按住**"输入"就能进 2×6 菜单（轻敲无效，因为要过
   三取二去抖），我们这边按住 3 秒也只会进"时间"程序 → 说明差异在**状态**。
2. 用环形记录追"进网络"那段 RAM 代码（`$414B`）的来源，一路追到：

```
$832A~$8336 处执行 → $8330/$8333 是 00 00 00（BRK/INT）→ 远调用跳板 $E9C7 → $414B
```

3. 而 `$832A` 在 **bank3 是图形数据**，在 **bank0 才是代码**：

| 位置 | 内容 |
|---|---|
| bank0 `$8310` | `a5 3a c9 15 d0 16 ad 08 34 85 00 …` = **代码** |
| bank3 `$8310` | `00 00 00 00 55 5f 1f eb 7c …` = **图形** |
| 我们 CPU 当时看到的 | **bank3 那份** ❌ |

⇒ 远调用返回时 bank 没恢复到 bank0，于是"返回到数据区"→ 撞上 `00`（BRK）→
这个假 INT 把机器带进了"进网络"的代码。**这就是开机预设成网络、
按输入落到时间程序的真正源头。**

### 24.2 根因：`xBRK()` 压的是 PC+1，硬件是 PC+2

`ansi/w65c02macro.h`：

```c
#define xBRK()\
{\
    mPC++;\            // ★ 错：标准 6502 的 BRK 压入 PC+2
    PUSH(mPC>>8);\
    PUSH(mPC&0xff);\
    PUSH(PS()|0x10);\
    ...
```

文曲星的 `INT idx bank`（三字节）正是靠"BRK 压 PC+2 + 处理程序用固定偏移
`$0104,X`/`$0105,X` 读回 bank/roa"这套约定工作的。少压一个字节 ⇒
**每次 INT 返回时 bank/地址都偏一个字节**，平时大多能"侥幸"跑过去，
但一旦跨 bank 就返回到错误 bank 的数据区。

### 24.3 修法

```c
    mPC += 2;      // 与真实 6502 一致
```

（只改这一处；`$E9C7` 那套跳板不用动。）

## 25. ★★★ 2026-09-27（续）：`$1C` 建模 + 启动器可导航 —— 全部打通

### 25.1 症状：菜单出现后被一个"假的跳出键"踢掉

用户指出"**和按住时长无关，真机按住不放也停在系统菜单页**"。按这条线索细看
`$C7` 轨迹（50ms 采样）：

```
8400-8850  按住输入时 $C7=00（已吃掉的键）
8900       松手
8950       $C7=1B  ← ★ 假的"跳出(0x1B)"就在松手那一刻冒出来
9000+      $C7=1B  → 启动器被"跳出"，随后进了时间程序
```

`0x1B` 正是 `$EC45` 那 6 次 `$1C` 探测**全部落空**走到 X=6 时的兜底值
（`$EAB8[6] = 0x1B`）。

### 25.2 `$1C` 的真语义（读代码读出来的）

```
$EC3E LDX #$FF
$EC40 INX / CPX #$06 / BEQ $EC55
$EC45 LDA $EAB2,X / ORA #$40 / STA $1C    ; 41 47 4D 53 59 5F
$EC4C JSR $EFB5                            ; 延时
$EC4F LDA $1C / AND #$20 / BEQ $EC40       ; bit5=0 → 继续下一组
$EC55 LDA $EAB8,X                          ; 命中组 → 键值
$EC58 BNE $EC5D / JMP $ECF1                ; ★ X=0 时 $EAB8[0]=$00 → "没有键"分支
```

* **X=0（写 0x41）是"无特殊键"通道，极性相反：bit5=1 表示"空闲"**；
* X=1..5（写 0x47/4D/53/59/5F）才是"第 k 组有键"；
* 组键值见 `$EAB8`：X=1→`$16(→)`、X=2→`$22`、X=3→`$25`、X=4→`$17(←)`、X=5→`$0F`；
* 其它写入值（如 `0xC0`）是**电池检测**，必须原样返回（否则固件会报"电池电力已不足"，
  这条实测踩过：bank0x0C `$8079` 那段就是"写 0x5F 等键 → 关机"的等待例程）。

`io_new.cpp` 的实现：

```c
if(address==0x1c){
    uint8_t v = ioReg[address], code = v & 0x7F;
    uint8_t out = v & ~0x20;
    bool right = keypadmatrix[7][1], left = keypadmatrix[7][7];
    switch (code) {
        case 0x41: if (!(right||left)) out |= 0x20; break;  /* 无特殊键 */
        case 0x47: if (right) out |= 0x20; break;          /* → */
        case 0x53: if (left)  out |= 0x20; break;          /* ← */
        default: break;                                     /* 侧键等暂未建模 */
    }
    return out;
}
```

## 23. ★ 用户指正（2026-09-27）：那串 `2D 2D 2D…` 是"文件加载错误"提示

把 bank 3 `$9E59` 起的那串读到 `0x00` 为止，是：

```
--------------------    文件加载错误      请重新升级此文件
                      --------------------======下载辞典======
```

（后面紧跟"下载辞典"）。**用户判断正确**：这是
**"按热键后去 NAND 的 sysdir 里找不到对应程序"**时的提示，
所以 `$9DF9` 那 12 个入口**不是主菜单本体**，而是 **"加载第 N 号程序"** 的入口。

同时这段确实是 sysdir 加载模块：

```
$9C2D  "/sysdir/xinhua"          ← 字面量
$9C3C  LDA $5C2C,X / STA $088C,X ; 把 16 字节文件名模板拷到 $088C
$9DB2  ～12 项 × 6 字节的图标表（每项 36 字节 = 24x12 点阵，指针步长 0x24）
$9D34  菜单/加载入口：$0400=0x2D、$03E4/5=$A5 $5A
$9DF9  12 个"设 $03E3=N 再 JMP $5A0A"的入口（=加载第 N 号程序）
```

⇒ `$03E3` 的 12 个值（`08 0A 04 09 0B 01 00 02 03 06 07 05`）
就是 **12 个可加载程序的功能码**，恰好对上 sysdir 里那批程序
（time / other / calculator / change / namecard / game / hero / txt_view / zijian …）。

### 23.1 由此得到的结论

* 按热键 = "把 `$03E3` 设成该功能码 → 去 sysdir 加载对应程序"（我们实测
  PDA→名片/记事/行程、计算→计算器、时间→时钟日历、英汉/AHD/剑桥→三个辞典 ✓）。
* 固件里"输入确认"那段是把 `$03E3` **硬编码成 0**，所以两边都落到 0 号程序；
  我们这边 0 号显示的是时钟（= 时间程序），而真机按输入应该是 **2×6 启动器菜单**。
* 剩下要查清的：**0 号到底是"时间程序"还是"启动器菜单"**，
  以及启动器菜单是不是驻留在 NOR 的另一段（或者是 sysdir 里某个程序画的）。

### 又试了一次"忠实模型"，仍然开不了机

这一版按"8 条列线 × 8 条行线、按键把行线接到列线电平"实现，并且按上一节的
时序规则给 bit0/bit2。结果是**连开机都过不去**。

矛盾点在固件的比较方式上：

```
STA $08 (写出一列)  →  LDA $09 / AND #$F0 / EOR <刚写的值> / BEQ 无键
```

——它要求**无键时读回值就等于刚写出去的值**。如果行线只是"浮空/下拉"，读回应该是 0，
永远不等于写出的 0x10/0x20/…，固件会把每一列都判成"有键"。所以
**port0 与 port1 的电学关系不是我假设的那样**（很可能是共享管脚的同一组线，
或者是"写出去的电平会被硬拉回来"），这一层得另外查手册的管脚复用表才能定。

在没搞清这一层之前，任何"忠实模型"都会把开机流程带坏——这已经是第三次验证。
**因此建议：键盘先维持现状（能开机、能进菜单、字母与功能键可用），
把数字键这一块单列成"需要查 SPDC1064 管脚复用表"的任务。**

1. ~~把 `ReadPort6EX` 换成真正的 port6 感应模型~~ ✅ 已完成，见第 4 节。
2. **先弄清 ON 键在固件里到底怎么被检测**（独立引脚？KBI 中断？还是矩阵里
   某个可检测的位置），再上忠实模型——否则会连带弄坏启动。
3. 给 port6 那 4 列补上正确的行映射（目前都解成 ESC）。
4. 给 port0 的互补驱动加"拉低"通路，消掉第 5~7 行的串键。
5. 全部对齐后，把 `items3000` 里那 7 个机型专用键按实测坐标落位。
6. ON/OFF 暂时保留现状（见下）：F12 走矩阵 (0,0) + 热复位，能把机器完全启动到主菜单
   （91 个代码页、`sys_key_proc` 两万多次）；而把固件认的 `ONOFF(4,0)` 递过去，它会
   "醒来又立刻睡回去"。等 port6 模型修好后再回头收拾这一条。

### 27.6 顶排热键在固件里是怎么变成 `$03E3` 的（"再按一次"的出处）

> ⚠️ **更正（2026-09-27 晚）**：本小节第一版把这件事记在 bank 3 `$4538/$4576` 那段
> （表 `$4628/$4632/$463A`）上。加了 `--watch-write` 之后**实测那段根本不执行**
> （`--count 4594/463C/41CA` 全是 0），真正干活的是 **BIOS `$D62F`–`$D6F0`**。

用 `--watch-write 03e3` 抓到：按 (5,0) 时，`$03E3=06` 是 **PC=`$D6D0`** 写进去的
（bank 窗口 `bs=03`、A=06）。把这段反汇编就一目了然：

```
$D67D: LDA $C7 / AND #$7F / STA $C7   ; 取主扫解出的键值
$D683: CMP #$18 / BNE / JMP $E00C     ; 0x18 = 开/关 → 直接走关机
$D68A: CMP #$22 / BEQ $D6B1           ; 录音
$D68E: CMP #$0F / BEQ $D6B1           ; 发音暂停
$D692: CMP #$25 / BEQ $D6B1           ; 复读
$D696: CMP #$26 / BEQ $D6B1           ; 快/慢
$D69A: CMP #$27 / BEQ $D6B1           ; 跟读
$D6B1: CMP #$22 / BEQ $D6F6           ; 录音 → 清 $0408/$0406 + INT $060B
$D6B5: CMP #$21 / BEQ $D6F1           ; 红外事件
$D6B9: CMP #$0D / BCS $D6EE           ; ≥0x0D 的其他键：原样返回
$D6BD: STA $C7
$D6BF: CMP $03E3                      ; ★ 和"当前功能"比
$D6C2: BNE $D6CB
$D6C4: CMP #$0C / BEQ $D6D0           ; 网络不参与复用
$D6C8: SEC / ADC #$00                 ; ★★ 相等 → A = A + 1（主功能变副功能）
$D6D0: STA $03E3                      ; ← 就是这里写 $03E3
```

所以"同一个键按一次进主功能、再按一次进副功能"= **键值和当前 `$03E3` 相等就 +1**，
第三次又因为 `$03E3` 已经等于键值+1 而不相等 → 回到主功能，天然形成两档循环。
`$03E3` 的偶/奇成对（00/01、02/03、04/05、06/07、08/09、0A/0B）正好对上 12 个功能：

| 偶 | 奇 | 功能对 |
|---|---|---|
| 0x00 | 0x01 | 时间 / 系统 |
| 0x02 | 0x03 | 计算 / 换算 |
| 0x04 | 0x05 | PDA(名片) / 游戏 |
| 0x06 | 0x07 | 英汉 / 汉英 |
| 0x08 | 0x09 | AHD / 词库 |
| 0x0A | 0x0B | 剑桥 / 学习 |

### 27.7 主键值表就是 BIOS `$EF32`（这次把它整张读出来了）

主扫（bank 0 `$EAE0` 起，走 `$F035` 逐条驱动 port1）最后是这样查表的
（`$EEFD`–`$EF09`）：索引 = **列组×8 + 命中位**，列组来自驱动到的那条行线，
命中位来自读回字节里被拉动的位（`$EE5C`：读回字节 = port0{0,4..7} + port6{0,1}→bit{2,3}）。

```
         col0    col1    col2    col3    col4    col5    col6    col7
bit7     17←     20      2E .    30      19      12      1A      0C 网络
bit6     13      6D m    6E n    62 b    76      63      78      04 PDA
bit5     6B k    6A j    68 h    67 g    66      64      73      02 计算
bit4     69 i    75 u    79 y    74 t    72      65      77      00 时间
bit3     16→     0E 录音 0D 输入 70 p    15↓     14↑     6C 'l'  18 开/关
bit2     25 复读 26      0F 播放 27 跟读 1F      1E      1D      1C
bit1     FF      FF      FF      FF      FF      FF      FF      FF
bit0     0A      08      06      18      00      02      04      0C
```

（这张表可以直接对模拟器 `keypadmatrix[y][x]` 的落位做校验：列组 = 7−y，
命中位 ↔ x：x=0→bit0、x=1→bit3(port6 bit1)、x=2→bit2(port6 bit0)、x=4..7→bit4..7。）

## 29. ★ 2026-09-27（深夜）：**侧面"红外接收"键（0x21）接通了**

### 29.1 之前为什么接不上

上一轮把 `0x21` 记成"应该是红外硬件载波产生、两张表里都没有"。**这个判断是错的**，
真正的原因有两个：

1. **键值带 bit7**。固件写 `$C7` 时是 `LDA $EE3A,X / ORA #$80 / STA $C7`，
   所以 `0x21` 实际以 **`0xA1`** 的形态出现（录音同理是 `0xA2`），
   按 `0x21` 去两张表里搜当然搜不到。
2. **它走的是"第二段扫描"的 port6 bit3，读回在 port0**，而模拟器只按"主扫的两列 port6"
   （bit0/bit1）建模，bit2/bit3 根本没人管。

### 29.2 固件里的真实通路（bank 0 `$ED76`–`$EDCC`）

主扫的列计数器 `$C8` 是 **0..9 共 10 个槽位**，`<8` 走键盘 8 列，`≥8` 就是两个侧键：

```
$ED86: SEC / SBC #$08 → X                ; X=0 → 槽位8(录音列)，X=1 → 槽位9(红外列)
$ED9E: LDA #$00 / STA $1E                ; port6 = 0
$EDA4: LDA $EFB3,X / STA $1E             ; $EFB3 = 04 08 → port6 bit2 / bit3
$EDA9: LDA $08 / AND #$F1 / PHA          ; ★ 读的是 port0，掩码 $F1
$EDBF: PLA / EOR #$FF / TAY / EOR $CA,X  ; 和上次状态比，有变化？
$EDC7: STY $CA,X / TAY / AND $CA,X / BEQ RTS   ; 仍然全 1（无键）就返回
$EDCF: LDA $EE3A,X / ORA #$80 / STA $C7  ; ★ $EE3A = { 22 21 } → 0xA2 / 0xA1
```

即：**这两个侧键把 port6 的列线（bit2 / bit3）短接到 port0 的一条读回线上，按下时该线被拉高**。
`$EE3A = {22, 21}` 正好是"录音 / 红外"，顺序和用户说的"从左到右：录音、红外接收"一致。

键值出去之后：`$D6B1 CMP #$22 → $D6F6`（录音：清 `$0408/$0406` + `INT $060B`）、
`$D6B5 CMP #$21 → $D6F1`（红外：`STA $C7` 后并回 `$D6CB` 的"和当前功能比较"逻辑）→
bank 3 `$9A21 CMP #$21 → JMP $5CAD`（红外接收处理）。

### 29.3 模拟器侧改动（`NekoDriverIO.cpp` 的 `UpdateKeypadRegisters()`）

```cpp
if (nc3000mode) {
    unsigned char side = 0;
    if (w1e_port6_OL == 0x04) { if (keypadmatrix[0][3]) side = 1; }  /* 录音列 */
    else if (w1e_port6_OL == 0x08) { if (keypadmatrix[3][3]) side = 1; } /* 红外列 */
    if (side) port0data |= 0x01;     /* 掩码 $F1 里的 bit0：idle 0，按下 1 */
}
```

矩阵落位沿用旧约定：**录音 = `(0,3)`（原来就有，走 `$1C` 组）、红外接收 = `(3,3)`（原来是个空占位）**。
只在 `port6 = 0x04/0x08` 时才注入，所以主扫（`port6 = 0x00`）完全不受影响。
