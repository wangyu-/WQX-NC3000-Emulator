# 视听教材 `.vnt` 文件格式分析（NC3000）

结论先行：**同一套教材分发的"高品质 / 一般品质"两份 `.vnt` 是同一条音频的两种编码。**

| | 容器头 | 编解码器 | 码率 |
|---|---|---|---|
| 高品质 | `07 80` + 流 | **A1600**（`0x8007`） | 16 000 bps |
| 一般品质 | `u32 长度` + `08 00` + 流 | **S200**（`0x0008`） | **2 000 bps** |

## 1. 全库统计（1156 个 `.vnt`）

样本：`info/视听教材/**` 共 **1156** 个 `.vnt`，其中

- 高品质 **570** 个：开头两字节恒为 `0x8007`；
- 一般品质 **586** 个：偏移 0 是 `u32` 长度 = 文件长度 − 4，偏移 4 的两字节恒为
  **`0x0008`**（586/586 全部一致）。

### 1.1 高品质 = 纯 A1600 流

```
片段一 高品质: 07 80 00 00 00 00 00 00 00 00 18 11 11 11 18 11 11 11 ...
```

- 没有 `.a16` 那样的 4 字节长度前缀，文件本身就是编解码器输入流，首字是 A1600 的
  参数字 `0x8007`。
- 把整文件从偏移 0 喂给 `host/s200_probe.exe <vnt> <out.wav> 0x40`（`0x99 0x40`
  → `[0x04CE] = 1` = A1600）即可正常出声，验证脚本见 §4。
- 同一目录下不同文件的前 98 字节曾完全一致，那是编码器冷启动的 lead-in（8 字节
  参数 + 两帧 44 字节的静音码流），换目录后公共前缀只剩 `0x8007` 两字节。

### 1.2 一般品质 = `[u32 长度][u16 参数][流]`

```
片段一 一般品质: 9f 77 00 00 | 08 00 | de 74 31 42 00 d2 e4 fe 42 00 ...
                 ~~~ 30623 = 30627-4 ~~~   ~~~ 参数字 0x0008 ~~~
场景一 一般品质: 2b 5e 01 00 | 08 00 | de 74 31 42 00 6b da ea 42 00 ...
                 ~~~ 89643 = 89647-4 ~~~
```

这个 `[u32 字节长度][u16 参数]` 的头部，和 **Sunplus 官方 SACM S200 语音样本**完全同构：

```
S200 SDK: spce061a\ref\gpce063_samples\S200_f2_3360.bin      (原 gpce063/demoCode/S200/voice/f2_3360.bin)
          5f 0f 00 00 | 0b 00 | f4 ee 45 47 ...
          ~~~ 3935 = 3939-4 ~~~ 参数 0x000B
```

## 2. 两条决定性证据

### 2.1 码率恰好是 A1600 的 1/8 ⇒ 2 000 bps

对 568 组「同一内容的高/低品质」配对比较编解码负载字节数：

```
比值均值 0.124996   最小 0.124968   最大 0.125017   标准差 0.000007
```

即低品质码率 = 16 000 / 8 = **2 000 bps**。这与 Sunplus 的命名规律一致
（`S480`≈4.8 k、`S720`≈7.2 k、`S240`≈2.4 k、**`S200` = 2.0 k**），
而不是 S240/S480/S720/S600。

### 2.2 061 固件里的 S200 内核能直接解析这个头部（实测）

NC3000 的 `061.dat` 里嵌了 Sunplus 的 **S200 内核**（字节级指纹匹配
`SACM_S200_*`，见 `spce061a/docs/NC3000-061协议对照.md`）。相关入口：

| 用途 | 地址 | 说明 |
|---|---|---|
| 流头解析 | `0x8256`（`0x8254` 先 `r1 = [0x04C0]`） | 读 4 个字设置解码器状态 |
| 编解码器初始化 | `0xC8C6` → `[0x04CE]==2` → `call 0x826F` | 由音频 TimerA FIQ 调用 |
| 每帧解码 | `0x82C6`（体在 `0x8339`） | 由 `0xC95D` 分发 |
| 配置表 | `0x994D`（11 项，每项 16 字） | 由参数字 − 1 索引 |

头部解析的实际算式（`0x8256`–`0x8266`）：

```
r2 = w0 ; r3 = w1 ; r3 = r3 lsr 1 ; r2 = r2 ror 1   ; 带进位的 32 位右移
[0x04C3] = r2 ; [0x04C4] = r3                       ; = (w0:w1) >> 1 = 字节数/2
[0x04D2] = w2 - 1                                    ; 配置表索引
[0x04E3] = w3                                        ; 第一个数据字
[0x04C0] = r1                                        ; 数据指针 = 流 + 8
```

实测（`tools/rom061.js` + `spce061a/host/s200_kern.c`）：

| 输入 | `[0x04C3]` | `[0x04D2]` 配置索引 | `[0x04D4]` 帧长 |
|---|---|---|---|
| `.vnt` 一般品质 场景一（参数 `0x0008`） | `0xAF15` = 89643/2 ✓ | **7**（表项 `0x990D`，基准字 `0x00A0`） | 320 / 72 … |
| SDK `f2_3360.bin`（参数 `0x000B`） | `0x07AF` = 3935/2 ✓ | **10**（表项 `0x993D`，基准字 `0x0064`） | 帧长可变 |

两者的头部公式、配置索引范围（0–10）、可变帧长行为完全一致 ⇒
**一般品质 `.vnt` 与 Sunplus 官方 S200 语音文件是同一种编码容器**。

## 3. 设备侧怎么选到它

主控通过 `INT`/BIOS 入口 `$FAE3`（文件偏移 `0x7AE3`，汇编为
`PHA; LDA #$99; JSR $FB1C; PLA; JSR $FB1C; RTS`）发送 `0x99 <参数>`，
061 在 `0xCE3F`–`0xCE58` 把参数映射成 `[0x04CE]`：

| `0x99` 参数 | `[0x04CE]` | 编解码器 |
|---|---|---|
| `0x00` | 3 | MS01（音乐） |
| **`0x10`** | **2** | **S200** ← 一般品质教材 |
| `0x20` | 0 | S480 系 |
| `0x21` | 4 | S600（NC3000 单词发音用这个） |
| `0x22` | 5 | S600-1 |
| 其它 | 1 | A1600 ← 高品质教材 / `.a16` |

主控固件里 `0x99` 只出现在 `$FAE3`（通用）、`$FE2A`（`0x99 0x00` = MS01）和
单词发音的 `0x99 0x21`；`0x10` 由教材播放程序（下载到 NAND 的播放器）传入。

## 5. 还没做完的部分

`s200_kern.c` 已经能把 S200 内核完整驱动起来（头部解析、初始化、逐帧解码
都正常：每帧消耗 2–3 个输入字，帧长 320/72 个样本可变），但**合成输出还是接近 0**：

- 逆滤波后的激励确实被写进了 `0x0000–0x013F`（320 字，与 `[0x04D4]` 帧长吻合），
  但它看起来像白噪声——那是残差，不是 PCM；
- LPC 合成结果应当写在 `0x0541` 起（见 `0x8772: [r1] = r4`，`r1 = [0x06DC] + 0x0541`），
  实测那里只有 ~0x24 的残留值，说明合成用的系数/状态还没被正确装载；
- 真机上这些状态由 **TimerA 音频 FIQ**（`0xC438`–`0xC4E0`）维护：FIQ 先
  `0xC8C6`（编解码器初始化）再走 `0xC8FA` 的解码分发，最后把样本搬到 DAC
  (`P_DAC2 = 0x7016`)。直接调用内核绕过了这一层，所以还差状态。

所以：**格式判定（S200, 2000 bps）证据已经闭环；一般品质的实际出声还差
把 FIQ 那一层补上。**
