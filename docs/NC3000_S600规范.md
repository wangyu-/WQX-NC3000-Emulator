## 1. Receiving Format（Table 3, p17）

一个"字"（word）= **16 bit = ID(4 bit) + Parameter(12 bit)**，主机按
**低字节先发、高字节后发**的顺序写数据口（§13 Volume 的例子：先写 `VolumeData`，
再写 `0x90`；即 word = `0x90NN`）。15 个字/帧。

### 1.1 数据包（15 个）

| # | Package | ID (B15..B12) | 有效参数位 | 名称/说明 |
|---|---|---|---|---|
| 0 | Package(0) | 0000 | B10..B0（11） | Byte0，B11 = X |
| 1 | Package(1) | 0001 | B10..B0（11） | Byte1，B11 = X |
| 2 | Package(2) | 0010 | B11..B0（12） | Byte2 |
| 3 | Package(3) | 0011 | B11..B8（4，帧头）+ B7..B0（8） | Subframe0；高 4 位是**子帧头** |
| 4 | Package(4) | 0100 | B9..B0（10） | Subframe0，B11/B10 = X |
| 5 | Package(5) | 0101 | B9..B0（10） | Subframe0 |
| 6 | Package(6) | 0011 | **5 bit**（note 2） | Subframe1，B11..B8 = X |
| 7 | Package(7) | 0100 | B9..B0（10） | Subframe1 |
| 8 | Package(8) | 0101 | B9..B0（10） | Subframe1 |
| 9 | Package(9) | 0011 | B7..B0（8） | Subframe2 |
| 10 | Package(10) | 0100 | B9..B0（10） | Subframe2 |
| 11 | Package(11) | 0101 | B9..B0（10） | Subframe2 |
| 12 | Package(12) | 0011 | **5 bit**（note 2） | Subframe3 |
| 13 | Package(13) | 0100 | B9..B0（10） | Subframe3 |
| 14 | Package(14) | 0101 | B9..B0（10） | Subframe3 |

> ID 序列 = `0,1,2,3,4,5` 循环；**每个子帧的首包（P3/P6/P9/P12）用 ID 3**。
> `X` = don't care（不存）。

### 1.2 控制字（ID 1110 之前的那批）

| Data Mode | ID | 参数 | 备注 |
|---|---|---|---|
| Filter option | 0110 | `3*` | 3* = Filter enabled(默认) / disabled(命令 6001) |
| Not Defined | 0111 | — | |
| Sleep | 1000 | `4*` | 4* = Sleep command |
| Volume | 1001 | `5*`(B11..B8) + `6*`(B7..B0) | 5* = 整数部分（b8~b9，b10~b11 不用），6* = 小数部分 b0~b7 |
| TTS synthesis mode | 1010 | `7*` | 7* = 1 SACM_S600 decoder / 2 word(syllable) synthesis / 3 PCM data out |
| Fast sleep | 1011 | `8*` | 8* = Fast sleep command（命令 B000） |
| TTS synthesis parameters | 1100 | `9*` + `10*` | 9* = 0001 音节结束 / 0011 单词结束 / 0010 设置音节头偏移 / 0100 设置音节尾偏移 / 1000 取帧号设定音节长度 |
| Not Defined | 1101 | — | |
| Not Defined | 1110 | — | |
| Speech End | 1111 | `11*` | 11* = End of speech code |

### 1.3 Notes（p18 原文）

1. `When d11 is 0, then Subframe0 is unvoiced.` / `d10 … Subframe1` / `d9 … Subframe2` / `d8 … Subframe3`
   —— 即子帧头 4 位 `d11..d8` 就是 P3 的 B11..B8。
2. `When subframe# is 0 or 2, then word is 8-bit.` `When subframe# is 1 or 3, then word is 5-bit.`
   —— **子帧 1/3 的字只有 5 位**（子帧 0/2 是 8 位）。这一条决定了 144 bit 的账能对上（见 §2）。
3. Filter enabled (Default) / Filter disabled (Command, 6001)
4. Sleep command
5. Volume control integer part, b8~b9, b10~b11 don't care
6. Volume control fraction part, b0~b7
7. 1: SACM_S600 decoder / 2: word(syllable) synthesis / 3: PCM data out
8. Fast sleep command. (Command, B000)
9. 0001: end of syllable / 0011: end of word / 0010: set syllable wave head offset /
   0100: set syllable wave tail offset / 1000: get frame number to set syllable length
10. （手册上缺 10* 的正文，Table 3 里它和 9* 一起出现在 TTS synthesis parameters 行）
11. End of speech code.

## 2. Packing Format（18 字节/帧）与位账

手册 p20 的图给出前两个字节的布局（原文标注）：

```
        B7   B6   B5   B4 | B3   B2   B1   B0
byte1  Package3_B11..B8   | Package0_B3..B0
byte2  Package1_B0        | Package0_B10..B4
```

p20 §7.1 的样例代码同样说明一个包的参数是 `(byte2 << 4) | (byte1 & 0x0F)`
（先取一字节的低半字节 = 参数低 4 位，再取下一字节 = 参数高位部分），
而同一字节的高半字节是 `SubFrame_Header`。

**位账（这条把布局钉死了）**：

```
帧头 4 bit（= P3 的 B11..B8）+ 各包有效位 140 bit = 144 bit = 18 字节 ✓
  11 + 11 + 12 + 8 + 10 + 10 + 5 + 10 + 10 + 8 + 10 + 10 + 5 + 10 + 10 = 140
```

（若按"每包 12 bit 全存"是 4+180 = 184 bit = 23 字节，与 18 字节矛盾；
若把 P6/P12 也当 8 bit 则是 150 bit，也对不上。只有上面这一种配法 = 144。）

也就是说：**Packing = 帧头 4 bit + 每个包"去掉 X 列"的有效位**，位流连续排布，
X 列不占空间（因此后续字段会往前移）。

### 2.1 .vnt 容器实测（ks100，339 个文件）

| 实测项 | 结果 |
|---|---|
| 文件长度 | **339/339 都是 18 的整数倍**（如 683568 = 18×37976、715356 = 18×35742… ） |
| 帧首 4 bit | **全部 0xF**（抽查 76953 帧，`0xF` 100%）→ 就是 P3 的 B11..B8（4 个子帧都"voiced"） |
| 帧尾 | 文件末尾是一段**完全相同的填充帧**重复（a1-12：`FD 56 DD B6 6D 26 00 00 03 00 00 CE 04 00 60 00 00 C0`） |
| 位分布 | 除帧首 4 bit 外，其余 140 bit 在高位统计上接近随机（压缩码流的正常表现） |

> 旧的"`偏移 +4 = 0x21` ⇒ S600"这条依据**不成立**：逐文件抽查偏移 4 的字节是
> `2D / AD / 21 / 6D / 23 …`（多为 0x2D），只是碰巧有个文件是 0x21。
> 真正站得住的判据是"长度 ≡ 0 (mod 18)" + "帧首恒 0xF"。

### 2.2 与 S200/A1600 容器对比

`info\视听教材\*.vnt`（A1600/S200）是另一套容器：`u32 长度 | u16 配置(0x0008) | 流`
（例：场景一.vnt = `2B 5E 01 00 | 08 00 | …`，0x15E2B = 89643 = 文件长度 − 4）。
两套容器结构完全不同，别混用。

## 4. 未定项（下一步要证的）

> **2026-09-24 晚更新：位序已经用 061 固件反汇编定案了，见下面的 §4.2。**
> 结论是——**NC3000（061）这条路根本不需要 18B→15W**：061 的 codec 4 直接吃
> **18 字节原帧**，位序是"**每字节从 bit0 往 bit7、字节按序**"。Table 3 的
> 15 字 Receiving Format 是给 PC2880H 的 SPDS104A 芯片用的另一种表示。

> 重要前提：`nibble` 与 `msb` 两种序**不改变字段边界**（哪几个流位属于哪个包是定死的），
> 只改变"一个包内部这几位各自算 B 的第几位"。所以已经确定的部分比看上去多得多。

1. **包内位序还有一个自由量**：手册 p20 的图把 byte2 画成
   `[Package1_B0][Package0_B10..B4]`，而"低半字节先 + 高位部分 MSB 先"的连续位流会
   写成 `[Package0_B10..B4][Package1_?]`——两者差 1 bit（图里那个 `P1_B0` 正好落在
   P0 的 B11（don't care）位置上）。目前按样例代码取 `nibble`，`msb` 作为备选，
   **必须用解码结果二选一**（见 2）。

   > 已试过的两个统计判据都**不足以定论**（记录下来避免重复劳动）：
   > - 帧间变化量（2×10³ 帧）：`nibble` 在 P2/P3/P9/P10/P14 更平滑，`msb` 在 P5/P7/P8/P12/P13 更平滑；
   > - 位稳定性（P(与上一帧同位相同)）：只有 P0/P1/P2 三包支持"前 4 位更不稳 = 低半字节先"，
   >   其余包互相矛盾。
   > 结论：参数本身变化太快，**必须等解码器**。
2. **P6/P12 的 5 bit 取哪 5 位**：note 2 只说"5-bit"，没说位置。默认按
   "低半字节 + 剩余 1 位（B3..B0, B4）"处理，备选是"低 5 位 MSB 先（B4..B0）"。
3. **P6/P12 的 5 bit 与"子帧 1/3 是 5-bit"的对应**：目前按 note 2 的字面理解
   （子帧 1、3 → 5 bit），这也是唯一能让位账 = 144 的读法，但最好再用解码器确认。
4. **解码器本身**：061 固件 codec 4 的入口（`0x9EA3` / `0xD225`）还没反完。
   反完之后就可以把本工具产出的 15 字流喂进去，用"听起来对不对"直接判定上面 1–3。

### 4.1 判定顺序（建议）

1. 反 `0xC8C6` 分发里 codec 4 那一支（`[0x0713]=0x14` → `0x9EA3` → 每块 `0xD225`），
   把 15 个字的**入参布局**（哪几个字进哪个系数、哪个是 pitch/gain）读出来；
2. 用 2–3 帧真实数据，把 `order=nibble` / `order=msb` 两种解出来的 15 字分别喂进去，
   看哪种能出**连续、有基音**的音频；
3. 定稿后写进本文档，并把 `s600_unpack.py` 的默认值锁死。

## 4.2 【已定案】061 侧 S600 的真实输入格式（固件反汇编）

061 固件（`spce061a\rom\061.dat`，基址 `0x8200`；反汇编工装 `tools\unspdis.py`，
已与既有 dump 逐行核对）里的链路：

```
0xC8C6  编解码器分派：[0x04CE] 索引 → 
          0 → 0x9EA3(init) / 0x9ED6(块)
          1 → 0xB5D6 / 0xB5E6        (A1600)
          2 → 0x8254 / 0x82C6        (S200)
          3 → 0xAADD / 0xAB0E
          4 → [0x0713]=0x14; 0x9EA3 / 0xD225   ★ S600（NC3000 单词）
          5 → 0x9EA3 / 0xA694
块入口：0xC94B 起 0xC962 → call 0xD225
0xD225 → 0xD1F2(环初始化) → 0xA694 → 0xA8B6(每子帧) / 0xA6B7(每帧开头)
```

关键代码读出来的**事实**（不是推断）：

| 地址 | 内容 |
|---|---|
| `0xA6B7` | 每帧**读 9 个字**（`bp=0..8`，每个字调 `0xA08F` 两次），存到 `[0x04B5+i]` |
| `0xA08F` | 从环指针 `[0x04C0]` 读一个字，**先返回低字节、再返回高字节**（两次调用合起来就是一个字） |
| `0xD1BF` | codec 4 的环初始化：`[0x04C3] = 9`（**槽 = 9 个字**），`[0x04C4] = 9 × 帧数` |
| `0xA71B(w)` | 取一个 w 位的字段；内部调 `0xA706` |
| `0xA706` | 读当前字的 **bit0**（LSB），再把字右移 1 —— **字内低位在前** |
| `0xA74C` | 把累计器还原成字段值：**先读到的位当字段的 MSB** |

也就是说：**载荷 = 144 bit 的位流，取位顺序是"字节 0 的 bit0 → bit7，然后字节 1 …"**，
字节顺序和文件里一致（`0xA08F` 的低/高字节只是把字拆开再拼回，不换序）。

### 4.3 字段表（合计正好 144 bit）

**帧级字段（在子帧 0 时取一次，`0xA8C9` 起）**

| 序 | 宽度 | 去处 | 说明 |
|---|---|---|---|
| 1 | 3 | `[0x03B3]` | |
| 2 | 1 | `[0x03B4]` 低位 | |
| 3 | 4 | `[0x04A5]` | **子帧头/voiced 标志**：bit3=sf0、bit2=sf1、bit1=sf2、bit0=sf3（0=unvoiced，对应 Table 3 的 note 1） |
| 4 | 3 | `[0x03B4] |= v<<1` | 与序 2 合成一个 4 位量 |
| 5 | 4 | `[0x03B5]` | |
| 6 | 4 | `[0x03B6]` | |
| 7 | 4 | `[0x03B7]` | |
| 8–12 | 3 ×5 | `[0x03B8]`…`[0x03BC]` | |

合计 3+1+4+3+4+4+4+3+3+3+3+3 = **38 bit**。

**每个子帧（4 次，`0xA945` 起）**

| 序 | 宽度 | 去处 | 说明 |
|---|---|---|---|
| 13 | **8（sf0/sf2）或 5（sf1/sf3）** | `[0x0386]` | ★ 这就是 Table 3 note 2 的"8-bit / 5-bit word"，`0xA949` 按子帧奇偶选择 |
| 14 | 9 | `[0x04A7]` | 送 `0xA760` 做码本搜索 |
| 15 | 1 | — | |
| 16 | 4 | `[0x0394]`（表 `0xA4C1`） | voiced 路径（`0xA77E`） |
| 17 | 4 | `[0x0390]`（表 `0xA970`） | |
| 18 | 1 | | |
| 19 | 1 | | |
|  | 1+4+**4**+1+1 = **11** | | voiced |

unvoiced 路径（`0xA7AA`，子帧头对应位为 0 时）宽度是 **1,4,5,1 = 11**。

**总账：38 + (8+9+11) + (5+9+11) + (8+9+11) + (5+9+11) = 38 + 28+25+28+25 = 144 bit = 18 字节 ✔**

### 4.4 直接结论

* **NC3000（061）不需要做 18B→15W**：把 `.vnt` 的 18 字节帧原样、按序喂给 DSP 即可
  （环槽 9 个字 = 18 字节、每帧读 9 个字、字段总和 144 bit，三条独立证据互相印证）。
  `docs\NC3000_S600规范.md` §1–§3 的 Table 3/15 字格式是**给 PC2880H 的 SPDS104A 用**的。
* 这也解释了为什么之前喂"15 字节 / 3+15 拆分"都不出声：**拆分假设是错的**。
* 校验工装：`tools\s600_fields.py`（`show` 打印一帧的全部字段，`stats` 统计标志位分布）；
  在 37976 + 20000 帧真实数据上**每帧都恰好消耗 144 bit**，且字段 3 恒为 `0xF`，
  与"帧首字节高半字节恒 0xF"的实测吻合。
* 注意：这批 ks100 素材的 voiced 标志**恒为 0xF**（12 万帧里没有 0），所以
  "unvoiced 路径"（1,4,5,1）在真实数据里还没被触发过，等有素材再验。

### 4.5 模拟器实测（2026-09-24，`nc3000_word.c` mode 9）

按 §4.4 的结论把**整帧 18 字节**用 `0x22 <len=18> <payload>` 发给 061（`0x33` 是固定
15 字节，装不下整帧），输入用 ks100 `a13-20.vnt` 第 2000 帧起的 120 帧真实语音。

结果（`build\word.exe build\word_rec.bin build\word_mode9.wav 9 build\t_frames.vnt 0x21`）：

| 观察 | 值 | 含义 |
|---|---|---|
| `[0x04CE]` | 4 | codec 4 选中 ✔ |
| DAC 样本数 | 954 | **FIQ 确实在跑**，约等于 2 帧 ×480（20 kHz）✔ |
| 样本值 | 951 个恒为 `+32`，其余 0/−32768 | 输出是直流 = 解到的是空数据 |
| `[0x04C3]/[0x04C4]` | 0000 / 0000 | **codec 4 的环从没被初始化**（0xD1BF 没跑） |
| `[0x04C0]` | 0006 | 读指针一直停在环基址（0xC986 的 wrap 值） |
| 暂存缓冲 `[0x075A]` | 0x072E = 0x072A+4 | 只有表头 1 + 记录 3 字节**进来了**；18 字节的流**没进这个缓冲** |

结论：**在这份 061 固件里，codec 4 的"环初始化 + 流喂入"这两段确实没被接上**
（与之前"启动链是死代码"的判断一致）。数据格式已经对了，卡点转移到固件侧：

1. `0xD1BF`（环初始化）要跑起来才会把 `[0x04C3]=9`、`[0x04C4]=9×帧数` 设上；
   它挂在 `[0x0000]` bit7（"环已满"）那条分支上，而那条分支要"解码器先跑起来"才置位 ——
   死循环。要么在探针里**手工把环指针/边界补齐**（像 mode 7 那样强设），
   要么把 18 字节直接写进环的物理地址段再放行 FIQ。
2. 还需要确认 **codec 4 的环在 RAM 的具体位置**（`0xC986` 的 wrap 值 0x0006 是读指针的
   回卷地址，但 `0x0006+9×帧数` 会盖到 0x010A/0x019F/0x037B 这些解码器自己的变量，
   所以真实缓冲要么在 DS 段、要么长度受限，需要下一步确认）。
3. 之后才是"喂真实语音 → 听声音 → 与 PC2880H 单词数据对拍"。

### 4.6 环的物理位置【已确认】+ mode 10 直接注入实验

**环就在 RAM 从第 6 个字开始**，证据两条（互相独立）：

1. `0xC524-C528`（音频引擎启动例程里）：
   ```
   C524: r1 = 0x0006
   C526: [0x04C0] = r1     ; 读指针 = 6
   C528: [0x04C8] = r1     ; 环尾指针 = 6
   ```
   回卷分支 `0xC983-C988` 也是 `[0x04C7]=1; [0x04C0]=6`。
2. **mode 9 实测**：灌流之后 `[0x04C0]` 从 6 走到 `0x0018` = 24，即**消费了 18 个字 = 2 帧**
   （`[0x04C5]=0x12` 也正好是 18）——说明解码器确实是从 RAM[6..] 取的数，
   只不过那里当时全是 0（所以输出恒为 +32 的直流）。

顺带纠正一条：`[0x04C3]/[0x04C4]` **不是写指针**，而是**环的容量**
（`0xD1E2/D1E4` 写 `9` 和 `9×帧数`；`0xC909-C90B` 拿读计数跟它们比来判断"够一帧了"），
而 `0xC6A0` 这个"推进写计数"的例程对 codec 4 **直接 return**（`0xC6A2-C6A3`）。

**mode 10（直接把 120 帧按 9 字/帧写进 RAM[6..]，再手工设 `04CE=4`/`0713=14`/
`078E=072B`/`0790=0` 等）结果**：`pcm = 1` —— **音频引擎根本没启动**
（`[0x04C0]` 停在 6、`[0x0790]` 停在 0）。对比 mode 9 的 954 个样本，
说明**"FIQ 跑起来"是被 `0x22` 流命令触发的**，不是靠数据就位。

所以剩下要查的**唯一一件事**：061 收到 `0x22/0x33` 之后把载荷写到哪个地址、
又是怎么推进环指针的（我们已知它**没**写进 RAM[6..]，也没写进 `0x072A` 暂存区，
后者只有表头+记录共 4 字节）。找到这段就能把"数据进场"接上；
接上之后，`0xD225`/`0xA694` 这条解码链已经全部读通，可以直接验证音频。

> 线索：`0x22`(STREAM_CMD1) 与 `0x33`(STREAM_CMD2) 的主机侧入口在 `nc3000_dsp.c`
> 注释里记的是 `$FCB6` / `$FC7D`（主控 ROM 里的服务例程）；061 侧的接收解析器还没定位到
> ——`out\061_disasm_full.txt` 里按 `P_UART_DATA(0x7000)` 只搜到 `0xCB2E/CB30` 两处写，
> 说明接收端要么用间接寻址、要么挂在别的端口，下一步从这里入手。

### 4.7 【突破】S600 出声音了（mode 9 + 真实语音段）

用"标记载荷 + 全 RAM 扫描"（`nc3000_word.c` **mode 11**）一步定位：

```
发 18 字节 A0 A1 A2 … AF A0 A1 →
  ram[00A0] = A000  ram[00A1] = A2A1  ram[00A2] = A4A3  … ram[00A8] = A0AF
```

即 **`0x22 <18>` 的载荷被存成 9 个小端 16 位字，落在 RAM[0x00A0]**。
而解码器的读指针 `[0x04C0]` 回卷值是 **6**，两者差 0x9A —— 所以
**环基址 = RAM[0x9A]，`[0x04C0]` 是"环内偏移"**（`0x9A + 6 = 0xA0`，
正好是第一帧的落点）。这同时解释了 `[0x0728] = 0xF6`（环尾，0xC69B 会 `[0x04C8] = [0x0728]`）
——**环只有 0xA0..0xF6 约 86 个字 ≈ 9 帧，是个小环，靠主机持续补数据**。

于是 mode 9（整帧 18 字节走 `0x22`）用**真实语音段**重跑：

| 输入段 | DAC 样本数 | 读指针 | 已消费 |
|---|---|---|---|
| `a13-20.vnt` 第 10000 帧起 120 帧 | 1906 | `04C0=0006` | `04C5=0x12`(18 字) |
| `a13-20.vnt` 第 20000 帧起 120 帧 | 6703 | `04C0=004E` | `04C5=0x48`(72 字) |

输出 WAV 实测：**样本值有 6867 种不同取值**，中段是平滑波形
（`-488 -496 -504 -504 -512 -512 …`），不再是直流 —— **S600 解码链路通了** ✔

> 待收尾：输出里有明显的限幅（±32767 各约 6.5k 个样本），需要查音量/定标
> （`0x44` 音量寄存器、`[0x0001]`，以及 `0xC742` 播放 FIQ 里的 `<<3 + 0x20`）；
> 另外环太小（≈9 帧），探针的节奏没有跟着补数据，所以要听完一整句需要按
> "边解码边补"的真实节奏重写喂数循环。

### 4.8 【接收链路已完整读通】噪音的原因锁定在"半字节状态机"

听感是噪音 ⇒ 载荷进环的**对齐**有问题。这一轮把 061 的接收链整条读出来了
（全部有地址）：

```
0x7022 = 数据口状态（bit6 = 主机有数据）；0x7023 = 数据口
  0xC88A/C88F  端口服务：test [0x7022] bit6 → r1 = [0x7023] → call 0xCC23
  0xCC23..     收字节状态机（[0x0714] 状态 / [0x0715] 计数 / [0x0716] 期望长度）
  0xCC7A       ★ 把收到的字节依次存到 RAM[0x0718 + [0x0715]]
  0xCC83       r3 == [0x0716]（收满）→ call 0xCD71
  0xCD71       ★★ 打包：两字节一个环字
                 [r3]   = 第 1 个字节（低字节）
                 [r3++] = 第 2 个字节<<8 | 低字节     ← 小端，写入后指针 +1 字
               [0x0727] = 半字状态（bit0=1 表示"下一个字节要放高字节"）
               [0x0728] = 环写指针（地址！）
  0xCCE9       收满后的收尾（清状态位 / 重新武装）
  0xCD1E       ★ 命令初始化：`[0x0727] = 2`（下一个字节另起一个字）
               `[0x0729] = 0`、`[0x0728] = 0x072A`  ← **环写指针初值 = 0x072A**
```

即：**主机字节流是连续的，DSP 把它按"低字节在前"两两打包成环字**；
`[0x0727]` 这个半字状态会跨包保留 —— **只要流的字节数是奇数，
后面所有帧就会整体错位半个字 = 1 字节，解出来就是噪音**。
实测：单发一帧 18 字节后 `[0x0715]=0x12`(18) ✓、`[0x0716]=0`、
`[0x0727]` 从 2 变成 0x38，`[0x0728]` 从 0x072A 变成 6 —— 说明
**收满一"包"之后状态被重置、写指针回到环基址 6（= 0x9A+6 = 0xA0）**，
所以解码器读的那个环（`[0x04C0]` 作为 `0x9A` 基址的偏移）是**第二级缓冲**，
由收包完成后的例程填充；`mode 11` 看到的"载荷落在 0xA0、且首字节跑到高字节"
正是这一级缓冲的对齐现象。

**下一步（按性价比）：**
1. 把 `0x0727`/`0x0728`/`0x0715`/`0x0716` 在**每一包前后**打出来（探针里加 4 个
   `printf`），确认半字状态在包边界的值；目标：让每帧 18 字节总是从"字起点"开始
   （必要时在前面补 1 个哑字节或把两帧合成 36 字节一包发）。
2. 对齐修好后，再用同样的"真实语音段 → WAV"流程听声音；
   若仍不对，则问题在字段表（§4.3）而不是对齐。

### 4.9 单帧落点实测（mode 14）

发**一帧**（`t_f2.vnt` 的 frame0 = `FA 43 54 4E 21 4B 00 26 6F 01 46 C8 89 E9 49 3A AF 12`，
18 字节）之后：

```
dec ring 0x009A+22 = 0x43FA   ← 正是 frame0 前两字节 FA 43 的小端打包（低字节 FA）
其余 0x9A..0xAF 全 0；staging 0x072A 也全 0（收满后被搬走并复位）
```

即**一帧 18 字节被正确地打包成 9 个小端字，落在 `0x9A+22 = 0xB0`**。
若把 `[0x04C0] = 6` 理解成"以 0xAA 为基址的字偏移"，则 `0xAA+6 = 0xB0` ✔
——**解码环基址很可能是 RAM[0x00AA]，`[0x04C0]` 是相对基址的字偏移**
（`0xA08F` 用 `ds:` 前缀读，真实芯片上 DS 段很可能就是这段缓冲的映射）。

> 于是"噪音"的最可能原因就是**基址/偏移的换算差 1 个字（2 字节）或 1 个字节**：
> 只要解码器读的起点比打包起点偏一点，每帧 144 bit 的字段边界就整体错位，
> 解出来正好是噪音。下一步：把环基址确认成常量（在 `0xA08F` 触发时抓一次
> `ds` 段寄存器和 `[0x04C0]`），再让打包起点与之严格对齐。

### 4.10 【噪音根因定案】解码环在 RAM[6..]，主机数据却进了 staging

在 `0xA09B`（`r2 = ds:[r1]`，即真正读环的那条）做定点抓取（`nc3000_word.c` mode 15）：

```
hit: sr=0040  ds=00  [04C0]=0006 -> addr=000006   ram6=0000  ramb0=4E54  ...
hit: sr=0040  ds=00  [04C0]=0007 -> addr=000007   ...
（[04C0] 逐字 +1）
```

* **DS = 0** ⇒ 有效地址就是普通 RAM ⇒ **解码环 = RAM[0x0006..]**（之前担心的 DS 段
  映射不存在，`[0x04C0]` 就是字地址）。
* 同一时刻**主机数据在 0xB0**（`ramb0 = 0x4E54` = 该帧第 3/4 字节的小端打包）——
  也就是说 **0x22 流把帧打包进了 staging 区（`[0x0718]` → `0xCD71` → 写指针
  `[0x0728]`，初值 0x072A 由 `0xCD1E` 设定），根本没进解码环 RAM[6..]**。

于是现象全部解释通：

| 跑法 | 解码器读到 | 输出 |
|---|---|---|
| mode 9/12（真流 + 真语音） | RAM[6..] 里的**残留垃圾** | 有波形但是**噪音** |
| mode 16（把 `[0x0728]` 强设成 6） | 全是 0 | 恒为 +32（静音） |
| mode 17（只注入 RAM[6..]、不发流） | — | `pcm=1`，**音频引擎没启动** |

**结论（根因）**：`0x22` 流负责"启动引擎 + 收数据到 staging"，但
"staging → 解码环 RAM[6..]"这一步在这份固件里没接上（与 §4.5 的"死代码"判断一致）。
所以听到的是解码器拿垃圾数据解出来的噪音。

**下一步（把这一步补上就能验证整条链）**：探针里把两件事合并——
① 照 mode 9 用 `0x22` 逐帧发（启动引擎）；② 每发完一帧，把刚打包好的 9 个字
从 staging 复制到 `RAM[6 + 9k]` 并把 `[0x04C8]`（环尾）跟上。
若声音干净，则 §4.3 的字段表和"18 字节原样"这一整套数据模型就全部验证成立；
剩下的才是音量定标（限幅）和喂数节奏。

### 4.11 mode 18（流 + 搬运）结果：数据打包是对的，阻塞点在 staging 的"消费者"

`mode 18` = 逐帧 `0x22`（启动引擎）+ 定位刚打包的 9 个字并搬到 `RAM[6+9k]`。

**好消息（这一条很重要）**：第一帧**逐字节正确**地进了打包区：

```
staging dump: … 43FA 4E54 4B21 2600 016F C846 (E989 3A49 12AF 还没到)
want        :    43FA 4E54 4B21 2600 016F C846  E989 3A49 12AF
```

即 **"18 字节原样 → 两字节小端打包成 9 个字"这条链路完全正确**，
与 §4.3 的字段表结合起来就是完整的 S600 数据模型。

**坏消息**：从第 10 帧左右开始，`0x9A..0x200` 里再也找不到新帧的字 —— 因为
staging 是个**小环形缓冲**（`[0x0727]` 半字状态 + `[0x0728]` 写指针 + `[0x0729]`
倒计数），必须由"消费者"及时取走；而那个消费者（把 staging  drain 进解码环
`RAM[6..]`）在这份固件里**不存在**，于是缓冲区写满、新帧被丢弃/覆盖，
解码器读到的就是新旧混杂的数据 → 仍然是噪音（本次 119003 样本 / 42487 个削顶）。

**两条可选收尾路线：**

* **A（混合式，最快）**：只发**一帧** `0x22` 把音频引擎踢起来，
  之后**不再发流**，直接按帧把 9 个字写进 `RAM[6..]` 并把环尾 `[0x04C8]`
  和容量 `[0x04C3]/[0x04C4]` 管好，让 FIQ 自己按节拍消费。
  这样可以完全绕开 staging。
* **B（纯解码器工装）**：跳过固件的流/环机制，直接构造 `[0x0713]=0x14`、
  记录表、`RAM[6..]` 与环指针，然后**自己调 `0xD225`**（或让 FIQ 调）逐帧解码
  ——字段表和入口地址都已经读通，这条更"干净"，适合将来做成离线的 S600 解码器。

### 4.12 mode 19/20：A 路线通了"管道"，但输出仍是噪音 ⇒ 疑点收敛到字段解释

`mode 19`（只发一帧 `0x22` 踢引擎 → 之后**直接**把 9 字/帧写进 `RAM[6..]`，
绕开 staging）：

```
after record: 04CE=0004 0713=0000
kicked:       pcm=2     0713=0014        ← 音频引擎起来了 ✔
ring[6]=43FA ring[7]=4E54  (frame0 FA 43 54 4E)  ← 送进解码器的正是真帧 ✔
mode 19 done: pcm=11310 04C0=0069 04C5=0075      ← 消费了约 13 帧 ✔
```

但 WAV 仍是噪音（7353 种取值、24166 个削顶、中段恒为 32）。
也就是说：**"数据送到解码器嘴边"这一段已经完全打通且逐字节可验证**，
剩下的差异只可能在**参数解释**（§4.3 的字段表/位序）或**合成器状态**。

`mode 20`（在 mode 19 基础上把每个字节位序翻转后再送）**连引擎都踢不起来**
（`pcm=1`、`0713=0`）——反过来说明**未翻转的字节流才是固件"认得"的形态**，
字节级位序翻转这条假设可以排除。

**下一步（针对字段解释）：**
1. 在 `0xA6B7` 之后 dump `[0x04B5..0x04BD]`（解码器实际装进暂存的 9 个字），
   与"帧字节小端打包"逐字比对 → 先证明"解码器看到的就是我们算的"。
2. 若第 1 步一致，则改 **ROM 镜像**做一次判决性实验：把 `0xA706` 的
   "读 bit0 + 右移"临时改成"读 bit15 + 左移"（即 MSB-first），重跑同一段音频；
   哪种出语音、哪种出噪音，就把 §4.3 的位序一次定死。
3. 之后再看合成器入口的参数量程（0xA0F9/0xA23F/0xA7C3/0xA806/0xA895/0xA34C）。

### 4.13 【已证实】格式与位序都正确 + 正确的喂数器

**判决性实验（mode 22）**：文件末尾那段重复的填充帧（应为静音），喂进去看输出：

| 喂法 | 输出 |
|---|---|
| **原样**（固件按 LSB-first 读） | 954 样本、**只有 3 种取值、恒为 +32 = 静音** ✔ |
| 每个 16 位字再位翻转（= MSB-first） | 954 样本、同样静音（对该帧无区分度） |
| 每两个字交换（big-endian 字序） | 153888 样本、8158 种取值 = 噪音 ✗ |

**结论：`.vnt` 的 18 字节原样、两字节小端打包、固件 LSB-first 读取 —— 这套是
正确的**（静音帧解出静音）。所以前面听到的噪音**不是格式问题，是喂数节奏问题**
（解码器在环里读到了重复/错位的字）。

**mode 23（正确的喂数器）**：4 槽环形缓冲在 `RAM[6..]`，随 `[0x04C0]` 前进自动补
下一帧（"边解码边补"）。

```
kicked: pcm=2 0713=0014
mode 23 done: pcm=143939  fed=118/120  04C0=000F 04C5=0012
```

输出中段是**真正的波形**（`-648 -1696 -2304 -3544 -5288 -5752 -3064 2600 8392
10624 7640 1320`），包络有起伏（起始 1495 → 32 静音 → 874/1004 → 稳定 ~300），
但**削顶严重**（44324/143939 ≈ 31%，峰值 RMS 29172）。

**剩余的就是最早交代的"限幅"**：与 S200 那条线完全同源 —— 播放 FIQ `0xC742` 里的
`<<3 + 0x20` 和音量寄存器 `[0x0001]`（模拟器里一直停在 `0x8000` 满档）。
所以下一步就是查 `0x44` 音量命令是否走到 `0xC562`、并把 `[0x0001]` 设成合理档位。

（954 样本 ≈ 1.08 帧 @36.79 kHz；§4.13 说静音帧也是 954 ⇒ 停机发生在解码器/握手那一侧。）

**(4) 位序疑点（下一步的判决点）**：把 a13-20.vnt 的第 200–1200 帧（真实语音段，不是开头
那 59 个重复填充帧）按两种位序解字段，统计 4000 个子帧：

| 位序 | `voiced_flags` 取值数 | `pitch9` 非零率 | `gain` 非零率 |
|---|---|---|---|
| **LSB-first**（§4.13 的结论） | **1**（恒为 15） | 74% | 71% |
| **MSB-first** | 14 | 93% | 75% |

语音一定有清音/浊音交替，**1000 帧里 `voiced_flags` 只有一种取值是不合理的**；MSB-first 才有
起伏。所以 §4.13 "位序已定案（LSB-first）"的结论**很可能不成立** —— 那一节用"文件末尾的填充帧
解出静音"来证明位序，但填充帧对两种位序都没有区分度（我们这次也看到：真实文件开头 59 帧是
重复填充帧，解出来正好是全 0 参数）。

**⇒ 下一步（照 §4.12 第 2 条做，这是唯一判决性的实验）**：把 ROM 镜像里 `0xA706` 的
"读 bit0 + 右移"临时改成"读 bit15 + 左移"（MSB-first），重跑同一段真实音频：
- 若**出语音** ⇒ 位序是 MSB-first，`.vnt` 的 18 字节需要按位翻转后再喂（或改写 §4.3 的字段表）；
- 若**仍是噪音/停机** ⇒ LSB-first 成立，疑点转回"解码器字段量程"（§4.12 第 3 条）。

顺带：`build\word.exe` 的 mode 23 现在支持 `argv[6]` = 强制 `[0x0001]`（0 = 不改），
便于把"电平"与"解码"两个变量分开。

### 4.15 【2026-09-25】主控侧到底发什么音量（"第一件"已查完）

在 `info\NC3KSYSNOR.nor` 里把 S600 单词播放这条链读完了（bank 映射：
`文件偏移 = 0x8000*bank + (CPU地址 - 0x4000)`，bank0 基址 0x8000）：

**单词播放入口 CPU `$9A95`（bank 0x0B，文件偏移 0x5DA95）**：

```asm
9a95  LDX #$ff
9a97  JSR $9E3D          ; 等 061 就绪
9a9f  LDA $03E9          ; ← 音量"档位"
9aa2  JSR $E099          ; = BIOS $FAEE → 发 0x44 <A>
9aaf  LDA $03EA ; JSR $E0C9   ; 0x55 语速
9abf  LDA #$99 ; ... ; LDA #$21 ; ...   ; 0x99 0x21 → 选 codec 4（S600）
9afa  LDA #$11 ; ... ; LDA #$01 ; ... ; TXA  ; 0x11 0x01 <count>
9b27  LDA #$11 ; ... ; LDA #$03 ; ...   ; 0x11 0x03 <记录>（每个音节一条）
```

**`$03E9` 是什么**：

- 音量加键处理 `$82CB`（bank 0x0B）：`INC $03E9` → `CMP #$0F; BCC`（≥15 就 `LDA #$01`）
  → 立刻 `LDA $03E9; JSR $E099`（发全档）。**所以档位范围是 1..14。**
- `SetVolume` 陷阱 `$B595`（bank 9）：同样读 `$03E9`、≥15 钳到 1，然后发 `0x44 <$03E9>`。
- 061 自己的表（ROM `0xC6B2`）是**线性**的 `档位 × 0x1000` ⇒ **增益 = 档位/16**，
  也就是可选增益 1/16 ~ 14/16；模拟器里 `[0x0001]=0x8000` 正好等于**档位 8 = 0.5**。

**另一个新发现（握手时发半档）**：bank 0 的 `0xBB 0x0A` 握手处理 `$FDF0`：

```asm
fe13  LDA $03E9 ; CLC ; ADC #$01 ; LSR A ; JSR $FAEE   ; 发 0x44 <($03E9+1)/2>
```

即**链路建立后先发"半档"**（档位 8 → 4 = 增益 0.25），而**单词播放开始时再发全档**。
⇒ 我们的宿主模型 `nc3000_dsp.c` 的 `n3_link()` 目前**没有**这一步，是个（次要的）保真缺口。

**结论（重要，别走错路）**：S600 不存在某个"正确的固定音量档位"——设备用的是**用户设置**，
中档就是 0.5。既然真机在 0.5 下听起来正常，而我们的解码在 0.5 下削顶 28%，那说明
**我们的 S600 解码输出电平偏大（约 2 倍），音量只是遮羞布**。所以：

- ❌ 不要用"把 `[0x0001]` 调到 0x4000"当作 S600 的修复（那只是把电平压回去，掩盖解码问题）；
- ✅ 应继续查 §4.3 字段表/量程（尤其 **gain 字段**）与位序，让解码在档位 8（增益 0.5）下
  自然落在限幅器之内。

**位序的第三条判据（新，倾向 LSB-first）**：在同一段 t_f2 上，音量固定 0.5，把注入帧逐字节
位翻转（MSB-first）：

| 位序 | RMS | 满量程写 |
|---|---|---|
| LSB-first | 21362 | 40888（28.4%） |
| MSB-first | 26006 | 63710（**44.3%**） |

⇒ MSB-first 电平更离谱。三条判据互相矛盾（`voiced_flags` 分布支持 MSB-first，电平支持
LSB-first），所以**位序仍未定案**，§4.12 的 ROM 补丁实验仍然必要；但可以先从"gain 字段量程"
入手（§4.12 第 3 条），因为它同时能解释"电平偏大 2 倍"。

**已做的第一步（2026-09-25，等价但更便宜的做法）**：给 mode 23 加 `argv[7]`，把**注入解码环的
帧**逐字节位翻转（固件按 bit0 先读 ⇒ 翻转后它看到的就是 MSB-first），**踢引擎那一帧保持原样**
（§4.12 记录位翻转会让引擎起不来）。a13-20.vnt 偏移 300 帧的 120 帧切片：

```
LSB-first  + 音量默认  : pcm=954  fed=118/120
MSB-first  + 音量默认  : pcm=954  fed=118/120
LSB-first  + 音量 0x4000: pcm=954  fed=118/120
MSB-first  + 音量 0x4000: pcm=954  fed=118/120
```

⇒ **位序翻转不改变"提前停机"**，所以停机不是位序造成的；同时注意 `fed=118/120` 说明**解码器
一直在消费**（环在前进），只有**播放 FIQ 在 954 个样本后停了**（≈1 帧）。即"解码器停了"这个
说法要修正为**"FIQ 的握手/门控停了"**——下一步应该去查 S600 这条解码路径里
`[0x0000]` bit10/bit11（`0xC546` 那套半缓冲握手）是由谁设置的、S200 有而 S600 没有的那一步
是什么。位序统计疑点（上表）仍待 §4.12 的 ROM 补丁实验最终裁决。

### 4.16 【2026-09-25 重大更正】真正的传输方式找到了：`0x33`+15 字节块

**A. 先看主控到底怎么发数据**（bank 0x0B 的 `$9CAA-$9D50`，S600 音节数据发送例程）：

```asm
9caa  LDA $06e8 ; ... ASL/ROL ×3 + 原值 + ASL   ; 记录里的 count → 字节数 = count × 18
9cd8  JSR $9D51                                 ; 取源地址（celp_data 里该音节的偏移）
9cdd  JSR $9E3D                                 ; 等 061 就绪
9ce5  LDA #$33 ; JSR $9DAA                      ; ★ 发 0x33
9cf1  LDA $0280,X ; JSR $9DAA ; INX ; CPX #$0f ; BCC  → 连发 **15 字节**
9d01  $06e8 -= 15 …
9d0f  … 剩余 > 15 → 再发一个 0x33 块；剩余 ≤ 15 → 走下面
9d2c  LDA #$22 ; JSR $9DAA                      ; ★ 尾部用 0x22
9d36  LDA $06e8 ; JSR $9DAA                     ; 长度
9d3e  LDA $0280,X … 发完剩余字节
```

**所以真实传输 = 若干个 `0x33` + 15 字节块，最后剩 ≤15 字节时改成 `0x22 <len>` + 剩余字节。**
（之前所有探针用的 `0x22 <18>` **不是**主机会发的东西。）

**B. 为什么 `0x22 <18>` 会把播放搞停（已逐字追踪证实）**：

061 的包暂存环在 `0x0718`，**只有 16 字节**（`0x0718..0x0727`，正好容下 `0x33` 的 16 字节包）。
发 18 字节的 `0x22` 包时，包的**最后两个字节**会写进 `[0x0728]/[0x0729]` —— 而那正是
**暂存目标指针**。门控追踪（新加的 `wr_trace`）实测：

```
#24 [0728] pc=CD4D value=0006      ← 记录路径把暂存指针设成 6 ✔
#28 [0728] pc=CC7F value=0000      ← 18 字节包的第 17 字节（ks100 帧的 00）把它清零 ✘
#29 [0000] pc=CD87 value=00FD      ← 于是载荷被拷到地址 0，踩了门字 [0x0000]
#30 [0000] pc=CD90 value=56FD      ← 门字里出现帧的前两字节（FD 56）→ b10=1
#11 [0000] pc=C7A2 value=64FD      ← FIQ 在半缓冲回绕处清 b12 → 停机
```

对照组 `t_f2.vnt`：帧尾是 `AF 12` → 指针变成 0x12AF（无害）→ 播放照跑（143939 样本）。
**这就是"真实内容只放 1 帧、合成文件能跑满"的全部原因**，与位序、与音量都无关。

**C. 按真实传输重跑（探针新增 mode 27）**：

```
mode 27: 120 frames (2160 bytes) as 0x33 blocks of 15
mode 27 done: pcm=5588 fed=2160/2160 0000=1210 04C0=0021 04C5=003F
  word samples=41035  peak=32768  rms=12141
```

包络（`a13-20.vnt` 前 120 帧，前 59 帧是重复填充帧）：

| 时间 | RMS | 峰值 | 满量程写 |
|---|---|---|---|
| 0.00–1.50 s | 0 | 32 | 0 | ← 填充帧解出**静音** ✔ |
| **2.25–3.90 s** | 1480~4500 | 9176~13144 | **0** | ← **真实语音，干净、不削顶** ✔ |
| 4.00 s 之后 | 27000 | 32767 | 有 | ← 流结束后的尾巴 |

⇒ **两个重要更正**：
1. **"061 固件缺'暂存环→解码环'的消费者"这个结论是错的**（§4.11/§4.13）：消费者存在且可用，
   只要按真实传输（`0x33` 块）喂，就会消费并出声。
2. **"S600 在增益 0.5 下必然削顶"也是错的**（§4.14）：真实语音段在默认 `[0x0001]=0x8000`
   下峰值只有 13144（40% 满量程）、**零削顶** ⇒ 音量根本不用动，之前的 28% 削顶是
   "喂数方式错误导致解码器状态崩掉"的后果。

**D. 还剩下的问题**：纯语音切片（a13-20 的第 200–799 帧，600 帧）出来仍是响亮噪音：

**(1) WAV 标称速率写错了（这就是"听起来慢了很多倍"的原因）**：mode 27 播放期间固件的
TimerA 是 `0xFD64` → **36,790 Hz**（打印实测），但 `write_wav` 是在**排空阶段之后**才取速率，
那时固件已经把 TimerA 改成空闲档 `0xF3FF` → **7,997 Hz**，于是文件被按 7,997 Hz 写头 ⇒
播放比真实慢 **4.6 倍**。判据：同一段样本按 7,997 Hz 标注时包络调制只有 **0.57 Hz**
（正常语音 2–6 Hz），按 36,790 Hz 标注则是 **2.62 Hz** ✔。
⇒ 出试听件必须**显式写 36,790 Hz**（`build\s600_试听_正确速率.wav`）。

**(2) 喂数配速会改变结果，但还没配对**：mode 27 新增 `argv[7]` = 每个 15 字节块等待的
DAC 样本数（15 字节 = 15/18 帧 = 20 ms ≈ 736 样本 @36,790 Hz）。实测：

⇒ 长度对了、内容质量还没对。干净段的样本区间在两种情况下都落在 **13k–31k**（≈18,500 样本），

下一步应查"解码环需要几帧的 lead、以及 `0x33` 块（15 字节，不是 18 的整数倍）与帧边界的相位关系"。

⇒ **S600 的解码链本身是对的**（格式、位序、字段表、激励/基音全部正确）。

   按 9 字/帧把数据直接填进解码环并驱动解码器，抓 DAC 出 WAV —— S200 侧的 `s200_map`/`vnt2wav`

### 4.17 【2026-09-25】直驱工装第一版：把"剩余问题"量化清楚了

**(a) 解码器的输入机制（新的事实，工装的关键）**：`0xA08F`（每帧 9 字的字节读取器）就是

```asm
a099  r1 = [0x04C0]      ; ← 解码器的字节流指针
a09b  r2 = ds:[r1]       ; 取一个字节
a09c  r1 += 1
a09d  [0x04C0] = r1
```

⇒ codec 4 的解码器**直接从 `[0x04C0]` 指向的字节流读**，每帧 18 字节（小端，`0xA6B7` 组装 9 字）。
所以"喂数据"的本质就是维护这个指针。

**(b) 这套流水线是"即时窗口"设计，缓冲极小**：在一次**健康**的 mode 27 运行里周期性采样，
`[0x04C0]` **只在 RAM 6..0x21 之间摆动**（≈2 帧），`[0x04C8]` 是"有效数据末尾"——
也就是说主机必须在解码器快要读完时**恰好**把下一块送到，早了会覆盖、晚了会读到垃圾。

**(c) 芯片的 ready 线在起作用，但挡的不是音频速率**：给 mode 27 加计数后，投喂 131 帧期间
`n3_busy`（= 061 的 ready 线）把主机挡了 **45,246** 次 ⇒ 主从握手是活的；但同一段时间里
DAC 只产出了 **6,256** 个样本（内容需要 ≈115,700）⇒ **主机仍比播放快约 18 倍**，
数据堆进小窗口后被覆盖 ⇒ 解码器读到被冲掉的数据 ⇒ 同一批填充帧有时是静音、有时是噪音。

**(d) 三种喂法都试过了**：

| 喂法 | 结果 |
|---|---|
| 全速（只靠 ready 线） | 长度短（80k 样本）、前段静音、后端噪音 |
| 按 DAC 时间配速（每 15 字节等 736 样本） | **总长度正确**（119k ≈ 内容 3.14 s），但 0.5 s 后转噪音 |
| 按解码器消费配速（lead=0/18/36 字节） | 长度正确但**几乎全静音**（解码器被饿死） |
| mode 28 直填窗口（预充 40 帧后自己当搬运工） | 解码器指针跑出我假设的环（`[0x04C0]` 到 0x047D）⇒ 说明环的真实边界还没搞对 |

**(e) 下一步（最稳的一条）**：**内核工装**——不碰包/窗口机械，直接：
1. `0x9EA3` 初始化（`[0x0713]=0x14`）；
2. 每帧把 18 字节放在一块空闲 RAM，`[0x04C0]` 指向它；
3. 直接 `call 0xD225`（解码一块）；
4. 抓**解码器输出缓冲**（不是 DAC）；S200 侧的 `s200_map` 就是这么拿到 0.9911 的。
   为此下一步要先在 mode 27 里量出"解码器输出写到哪"（对 0x019F..0x0400 做写入直方图）。

### 4.18 【2026-09-25】工装第一版：管道摸清，收割点还差一步

**(a) 解码器输出→播放缓冲的"转移"找到了**（与 S200 的 `0x8496` 同构）：

```asm
c0b1  r1 = [0x04D4]      ; 源（解码器的输出缓冲指针）
c0b3  r2 = [0x04C2]      ; 目标（g_filter_out）
c0b5  r2 = r2 + [0x04D3]
c0be  r4 = [r1++] ; [r2++] = r4 ; c0c0 cmp r2,r3 ; jne c0be
c0d1  r4 = [r1++] ; [r2++] = r4 ; c0d2 cmp r2,r3     ← 回绕段
```

**(b) 播放缓冲与每帧样本数（写入直方图实测）**：`0x019F..0x031F` = 384 字节
= **192 样本/帧**（24 ms @ 8 kHz ✓），写入 PC 就是 `0xC0C0/0xC0D2`；
而 FIQ 的读指针 `[0x04C1]` 实测一直落在 `0x1A3..0x30F`（**就在这个区间里** ✓）。
⇒ **S600 解码输出 = 192 样本/帧、8 kHz**（这也解释了"192×4=768 个 DAC 样本/帧、
36,790 Hz 下正好 24 ms"）。

**(c) mode 29 内核工装第一版（已能跑，但收割点不对）**：引擎照样先用真实协议启动，
然后**自己 `call 0xD225`**（帧放在固件的暂存窗口 `0x0718`，`[0x04C0]` 指向它）：

```
mode 29: 131 frames, 60 via real packets, then 71 x call 0xD225
  after start: 0713=0014 04CE=0004 04D4=06B3 04CD=00EE 04C2=028D pcm=1794
  first frame: 192 samples harvested
mode 29 done: calls=71 harvested=13632 (192.0 samples/frame)
```

机制通了（71 次调用、每次 192 样本 ✓），但**内容是错的**：`0xD225` 只解码，
**不会执行转移**（转移是 worker 在解码之后另调的），而 `[0x04D4]` 指向的是
`0x06B3`（061 的变量区），所以收割到的是一段"半常数"信号。

**⇒ 下一轮的确切动作（二选一，推荐 ①）**：
1. **改调 worker 入口**（`0xC94B`/`0xC962`，它 = 读输入 + `call 0xD225` + 转移发布），
   然后收割 `pc=0xC0C0/0xC0D2` 的写入 —— 这就是 `s200_map` 的等价物，
   一次性拿到"解码 + 发布"的完整样本流；
2. 或者先跟出"谁调用 `0xC0B1` 那段转移"（往上找它的入口），在 mode 29 里手动补一次调用。
   `pc=C0C0/C0D2` 的写入就是每帧 192 个样本，顺序即时间顺序。

### 4.19 【2026-09-25】发布链路找齐了；工装收割仍差"上下文"

**(a) 谁调用发布/转移（扫描全部 `call`/`pc=` 目标得到）**：

| 调用点 | 目标 | 说明 |
|---|---|---|
| `0xC668` | `0xC035` | **codec 分派块**（`0xC662` 起，`[0x04CE]`≠2/3 时走这里）——**S600 走这条** |
| `0xC4AA` | `0xC023` | 音频缓冲初始化路径（`0xC4B0–0xC4ED`） |

而 `0xC035` 里 `C03E/C040` 把转移的源指针设成 **`[0x04D4] = 0x0657`**（固定缓冲），
再经 `0xC0B1→0xC0BE/0xC0D0` 把样本搬到 `[0x04C2]+[0x04D3]`（播放缓冲 `0x019F..0x031F`
= 192 样本/帧 @8 kHz）。

**(b) mode 29 现在的形态**：真实协议启动引擎 → 每帧手动 `call 0xD225`（解码）+
手动 `call 0xC035`（发布；返回判定改用**栈指针回位**，因为它的流程会经跳转表跑掉）→
收割 `pc=0xC0C0/0xC0D2` 的写入。结果：

```
mode 29 done: calls=71 harvested=16932 (238.0 samples/frame)   ← 稳定了
rate=9916 n=16932 rms=28844 peak=32768 rails=11747 (69%)
```

收割数量稳定了（238/帧），但**内容是削顶的噪音** ⇒ `0xC035` 在工装里的**上下文/参数不对**
（它依赖 `[0x04D1]`/`[0x04D3]`/`[0x04C2]`/`[0x04CD]`/`[0x0002]` 这一组状态，
而且真实路径里它是由 `0xC662` 那个分派块在 FIQ 握手后调用的）。

**(c) 下一轮的确切动作**：
1. 在**健康的 mode 27** 运行里挂钩 `0xC668`（发布调用点），把每次调用时的
   `[0x04D1] [0x04D3] [0x04C2] [0x04CD] [0x04D4] [0x0002]` 与"本次调用中转移的写入次数"
   打印出来 —— 拿到"发布前的正确上下文 + 每帧的写入条数（应为 192）"；
2. 在 mode 29 里先把这组状态复现（或在解码后调用 `0xC662` 那个分派块本身，让固件自己发布），
   再收割转移写入 ⇒ 每帧恰好 192 个样本，顺序即时间顺序。

### 4.20 【2026-09-25】发布上下文实测：**每帧 238 样本**（还有 rate 的更正）

挂钩 `0xC668`（发布调用点）在健康运行里的实测（`build\log_pub.txt`）：

```

[pub#2] 04C2=028D 04D1=0024 04D3=00EE 04D4=06B3  transfer_writes=238
[pub#3] 04C2=019F 04D1=0036 04D3=00EE 04D4=06A1  transfer_writes=238
[pub#4] 04C2=028D 04D1=0048 04D3=00EE 04D4=068F  transfer_writes=240

三条硬结论：
1. **每帧 238 个样本**（`[0x04D3] = 0xEE` = 238 常量）⇒ S600 的帧长是 **238 样本/24 ms
   ≈ 9.92 kHz**（不是 8 kHz！之前按 192 算的那次是错的）；
2. `[0x04D4]`（解码器输出指针）每帧 **−0x12 (18)** ⇒ 解码输出写在**向下生长**的缓冲里；
3. `[0x04D1]`（播放缓冲内偏移）每帧 **+0x12**，`[0x04C2]` 在 0x019F/0x028D 间交替
   ⇒ 双缓冲（每半 0xEE = 238 字节）。

**mode 29/30 的收割数量已经和这个一致**（mode 29: 238.0/帧 ✓），所以**收割机制没问题**；
剩下的是**解码输入**：

```

  harvested=23822 (183.2/帧) rate=7635 Hz  rms=21010 rails=8752

⇒ **固件自己"发布"出来的流也是坏的**（不只是 DAC 那段），而且**配速方式不同、坏法不同**：
不配速时解码器被喂不饱（几乎不出声），DAC 配速时长度对了但内容坏。
这与 §4.16(c) 的结论一致：**卡点就是"包→小窗口→解码器"的喂数时序/相位**。
而我们模型里的 ready 线语义可能与真机不同（真机是"解码器吃完上一块才放行"），
这是下一轮要校准的点。

### 4.21 【2026-09-25】ready 线语义定案；输入字节流已排除

**(a) ready/忙线 = 严格的一字节一手握（读固件代码 + 实测跳变）**：

| PC | 动作 | 值 |
|---|---|---|
| `0xCC4F` | **置忙**（收到一个字节） | `[0x7006] \|= 0x4000` |
| `0xCC05` / `0xCC10` / `0xCC13` / `0xCC1C` | **放行**（该字节已消费） | `[0x7006] &= ~0x4000` |

之前**就按字节节奏翻转 ⇒ 它只反映"解析器字节级状态"，不反映音频进度。

**(b) 逐字节握手喂数没有改善**：给 mode 30 加"每字节等 ready"（`argv[9]`）后，
结果与不配速完全一样（`harvested=3572`，只解了约 15 帧）⇒ **解码器才是瓶颈**：
它跟不上字节级握手的速率，所以主机必须按**内容速率**配速（DAC 配速那档长度才是对的）。

**(c) 解码器输入字节流已排除嫌疑**：挂钩字节读取器 `0xA08F` 的两条路径计数

```

  [dec] read_path=900 cache_path=900 (0381=005B 037F=0000)
```

两条路径**均衡**（低字节/高字节交替）⇒ **送进解码器的字节流是完整且有序的**。
（先前"只读到偶数号字节"是日志只挂了 `0xA09C` 一条路径造成的误判。）

**⇒ 现在三件事都已排除**：输入字节流 ✓、收割机制 ✓、播放/DAC 环节（mode 30 绕开了）✓。
剩下的只能是**帧的相位/边界**（18 字节帧在流里的起点）或**跨帧状态**。
下一轮的决定性实验：**同一帧**分别用"固件自己的路径"（mode 27 的启动阶段）和
"工装的手动调用"（mode 29）解一次，比较发布出来的 238 个样本是否逐样本相同 ——
相同则说明工装是对的、而"坏"只是我们对内容的预期错了；不同则说明手动调用的上下文还缺东西。

### 4.22 【2026-09-25】"发布流 vs DAC 流"对拍：播放链路无罪，且**解码是时序敏感的**

把 mode 30 的排空阶段拉长到与 mode 27 同级（`budget<150M`、5M 无新增即停），
同一配置（都是不配速）下收割"固件发布的流"，再与 mode 27 的 DAC 流按"每帧 RMS"对齐：

```
harvested = 20120 样本（154.8/帧，84.5 帧）
mode 27 的 DAC 流 = 130 帧
每帧 RMS 包络相关 = +0.848；两边的"坏段"数值几乎一样（29,000 vs 27,000 RMS）
```

**结论一**：发布流与 DAC 流**一致**（同样的坏法）⇒ **播放链路无罪**，问题在解码。
**结论二（更重要）**：同一切片在 mode 27 与 mode 30 里"哪几帧解对"**不一样** ——
mode 27 那次在样本 12.8k–31.3k（≈第 14.5–35 帧）是**干净语音**（用户已确认），
而 mode 30 同样的帧区间是静音、坏段从第 35 帧才开始。
⇒ **解码结果是时序敏感的**（同一配置、微小差别就换一批帧解对）——
这是典型的**喂数与解码之间的竞争**，与 §4.16(c)/§4.21 的判断一致。

**⇒ 下一轮的确切动作**：把"喂数"做成**逐字节跟随**的精确生产者 —— 不再按"块"补，
而是每执行若干条指令就读一次 `[0x04C0]`，一旦它前进（解码器消费了字节）就立刻把
对应的下一批字节补进去，始终保持 1~2 帧的 lead（`[0x04C8]` 同步更新）。
mode 29/30 已经具备全部零件，只需把补数循环细化到字节级。

### 4.24 【2026-09-25 收尾】环语义补齐、工装仍不成立、ROM 通路是时序敏感的

**(a) 环的语义补齐（本轮最后的静态结论）**：`0xCB4D` 是"**环压实**"例程 ——

**(b) 工装（mode 29/30/31）试了 8 种改法，全部仍解出垃圾**：手动调 `0xD225`、

```
[mon] it=100 pos= 750 04C0=0018 04C5=0009 04C8=0006 0728=011E 0000=3010 busy=1 pcm= 740
[mon] it=200 pos=1500 04C0=000F 04C5=002D 04C8=00FA 0728=011E 0000=1210 busy=1 pcm=3235
[mon] it=300 pos=2250 04C0=0006 04C5=0048 04C8=00FA 0728=0108 0000=3010 busy=1 pcm=5798
[mon] it=440 pos=3300 04C0=0021 04C5=0063 04C8=00FA 0728=011E 0000=3210 busy=1 pcm=9562
```

读出来的事实：

1. **流水线真的在跑**：`[0x04C5]`（消费计数）每 20 次迭代涨 9 字节，`[0x04C0]` 在
   `6/0xF/0x18/0x21` 之间正常滚动，门字在 `1210/3010/3210` 之间正常握手，pcm 持续增长；
2. **但消费速率 ≈ 1 字节/1422 条指令**，而内容速率要求 **18 字节/24 ms ≈ 1 字节/65000 条指令**
   ⇒ **主机喂数比内容快约 46 倍** ⇒ 流水线（环/播放缓冲）必然溢出 ⇒ 输出是噪音；
3. **每次采样 `busy` 都是 1**：ready 线长时间是"忙"，而主机喂数循环的等待上限只有
   **400 次迭代（25,600 条指令）**，超时就照样发 ⇒ 节流根本没生效。

**⇒ 下一轮的第一件事（最可能的解）**：把主机的喂数改成**真正的"等 ready 才发"、不设短超时**
（真机 6502 的 `$9DAA → JSR $9E3D` 就是死等），即把 `for (k = 0; k < 400 && n3_busy(...); k++)`
改成长等待（或直到 ready），再跑同样的 301 帧用例 —— 判据：`[0x04C5]` 的增速应降到
**≈1 字节/65,000 条指令**，且输出从"噪音"变成结构化的静音+语音。

附带发现：**配速那几次 FIQ 的播放路径从没执行**（`C7AE/C784` 计数为 0），DAC 的样本来自
另一条直写路径 ⇒ 那些运行的"噪音"**不是解码失败**（是没被发布的数据），前面的归因要按此修正。

---

## 4.28 【2026-09-25 ★ 定案 ★】S600 ROM 通路的根因与修复：**主机喂数没有真正等 ready 线**

按 §4.27 的判据动手：把喂数循环里对 ready 线的等待从

```c
    for (k = 0; k < 400 && n3_busy(&link); k++) n3_run_steps(&link, 64);   /* ← 25 600 条就超时 */
```

改成**真等**（上限提到 2,000,000 次，等价真机 `$9DAA → JSR $9E3D` 的死等，
并用 `argv[20]` 可覆盖上限），同一批用例重跑：

| 用例 | 修复前 | 修复后 |
|---|---|---|
| 0–300 帧（301 帧） | rms 15898、**rails 10123**、`[0x04C5]` 只走到 0xA2 | rms 1395、**rails 1**、`[0x04C5]=0x08F7`、包络 241→2670/1909/979/63 |
| 文件头 131 帧 | rms 21262、rails 32426 | rms 1217、**rails 1**、包络 241→2670/1799 |
| 中间音节 p646（120 帧） | rms 21608、rails 34324 | rms 1734、**rails 1**、包络 241/0/1799/1114/3507/1610 |
| 中间音节 h158（120 帧） | rms 21253、rails 32426 | rms 1612、**rails 1**、包络 241/0/0/542/2435/3191 |

**根因**：主机的喂数等待有 400 次迭代（≈25,600 条指令）的短超时，而 ready 线在流水线
繁忙时会长时间保持"忙" ⇒ 超时后主机照发 ⇒ **实际喂数速率约为内容速率的 46 倍**
（实测 §4.27）⇒ 环/播放缓冲被覆盖 ⇒ 解码输出成片削顶噪音。
**真机 6502 的字节发送是死等 ready 线的**（`$9DAA → JSR $9E3D`，无超时），所以真机不会被这个
竞争打中——**这是宿主模型的保真度缺陷，不是固件问题**。

**修复**：`spce061a\host\nc3000_word.c` 里 S600 各模式的 ready 等待上限从 400 提到
2,000,000（`argv[20]` 可覆盖）。修复后各音节 **rails 全部降到 1 次**（起播那一拍），
包络呈"静音 + 语音段"的正常结构，RMS 落在 1.2k~1.8k（与用户确认过的干净段同量级）。

**试听件**：`spce061a\build\s600_试听_修复后_音节1.wav`（p646）、`…_音节2.wav`（h158），
各按内容长度 2.88 s 裁剪、按 36,790 Hz 标注。

**遗留（次要）**：
1. 输出末尾仍有一段"流结束后"的尾巴（§4.16(d) 同源），按内容长度裁掉即可；
2. `mode 29–31` 的手动工装尚未用这个修复重测（可能也有同样的等待问题）；
3. ready 等待上限做成 `argv` 后，建议下次把 S600 各模式的 header/record 等待也一并改为长等待。

### 4.29 【2026-09-25】S600 提取工具上线：`tools\s600vnt2wav.ps1`

把修复沉淀成工具（对标 S200 的 `vnt2wav.ps1`）：

```powershell
.\tools\s600vnt2wav.ps1 out\ks100_head600.vnt out\ks100_head600_s600.wav
# → decoding 600 frames in 8 chunks (<= 200 frames each)
#   wrote … 529800 samples, 14.4 s @ 36790 Hz, RMS 1815.7
```

做法：
1. 按**填充段**（≥3 个连续相同帧）把 .vnt 切成每块 ≤200 帧的切片（每块自带静音头）；
2. 每块调 `word.exe <slice> <wav> 27 <slice> 0x21 <帧数> 0 …`（走已修好的 ROM 通路）；
3. 按内容长度 `帧数 × 0.024 s × 36790 Hz` 裁剪（丢掉流结束后的尾巴），短的部分补静音；
4. 拼接输出 36,790 Hz 单声道 WAV。

实测（`a13-20.vnt` 前 600 帧）：**529,800 样本 / 14.40 s（= 600×24 ms ✔）、RMS 1816、
满量程 **8** 次（8 块各一次起播瞬态）、包络呈"静音 + 句子"结构** ✔。
耗时约 **5.5 s/块**（600 帧 ≈ 44 s）⇒ 15 分钟的整本教材约需 1 小时量级，适合批处理。

**残留**：每块起播的那一拍（每块 1 次满量程）与块边界的轻微不连续；如需更平滑可以在
块间做 1~2 ms 交叉淡化（未实现）。

### 4.30 【2026-09-25】"每句结尾啪一声"已修：块首/块尾淡入淡出

用户试听后反馈"每句句子读到结尾都会有啪的一声"。原因就是 §4.29 的**分块接缝**：
每块恰好在句子结束处断开、直接拼接 ⇒ 波形阶跃 ⇒ 啪声（另外手工裁剪试听件时的硬切同理）。

修复（`tools\s600vnt2wav.ps1`）：每块 **块首 1 ms 线性淡入 + 块尾 3.5 ms 线性淡出**。

**验收（`a13-20.vnt` 前 600 帧、8 块）**：

```
每个接缝处的样本阶跃 = 0（块尾淡出到静音、块首从 0 起）；满量程写 8 → 0 次
峰值 32768 → 23640（不再削顶）；RMS 1811
整体最大阶跃 4504 @ t=9.061 s（在块内部，是语音本身的瞬态）
```

⇒ 句子结尾的啪声消失。注：**整段一次解码**（不分块）也能避免接缝，但实测一个 600 帧
（14.4 s）的单次运行 >10 分钟仍跑不完（ready 死等 + 解释器速度），所以保留分块 + 淡入淡出。

| 输入切片 | 结果 |
|---|---|
| 文件开头 120 帧（填充 1–94 + 语音 95–119）| 静音 ✓ + **干净语音**（用户已确认）|
| 中间音节 p158 / p646 / p812（各自带填充头）| 静音 ✓ + **语音段变 21k~27k RMS 噪音** ✗ |
| 上述音节前面再补上文件第 0 帧（头部帧）| 仍 ✗ |

⇒ **旧 mode 19 也不是可复现的 S600 提取路径**；"文件开头那次成功"与"中间音节失败"的差别
尚未定位（候选：解码器的跨帧状态、kick 帧内容、填充帧个数）。**本轮工作到此停止**。

```
mode 27: 600 frames → 178239 样本（4.84 s，而内容是 14.4 s）rms=23151 持续削顶
```

而"前面带 59 帧填充帧"的切片，语音部分只有约 1.4 s 是干净的。两种解释待验：
(i) 流必须从一个"音节起点/带填充头"的位置开始（解码器需要 warm-up 或状态对齐）；
(ii) 帧边界与 `0x33` 块（15 字节 = 3 帧的奇数字节数）的相位关系编码了状态。
⇒ 下一步：用 `sysdir/celp_data` 里**真正的音节记录**（`tools/celp_extract.js` 的输出，含
每条记录的起始/长度）去喂 mode 27，而不是自己切帧；这样流起点就是设备真实使用的起点。
