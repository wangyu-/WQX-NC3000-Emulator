## 1. Linux 命令行 A1600 播放器

### 编译

```bash
cd outputs/emulator
make                      # 需要 libasound2-dev（ALSA）
# 或者只要文件转换功能：
cc -O2 -o a1600play main_linux.c unsp.c a1600.c a1600_image.c
```

### 使用

```bash
./a1600play /abs/path/to/sound.a16            # 直接从声卡播放
./a1600play -o /tmp/out.wav /abs/path/x.a16   # 导出 WAV
./a1600play -r 16000 -o out.wav x.a16         # 指定输出采样率
```

输入是 SACM A1600 的 `.a16` 文件，文件头规则：

```
[u32 数据长度] [u16 参数] [比特流...]
                 └─ 固定形如 "xx 80"（小端字 = 0x80xx），xx = 04..09
                    码率索引 = xx - 4   （3 = 16 kbps = 2 bit/样本 @8 kHz）
```

`a1600_load()` 会做格式判断（`a1600_check()`）：

- 若开头 4 字节等于「文件长度 − 4」，就当作长度字段跳过；**否则认为文件已经从参数字开始**（可直接投喂去掉长度头的资源），实测两者解码结果完全一致。
- 参数字必须是 `0x80xx` 且 `04 ≤ xx ≤ 09`，否则返回 `-4`（播放器会打印 `not an A1600 stream - the parameter word must be "xx 80" with xx = 04..09`）。

实测边界与拒绝情况：

| 头部 | 结果 |
|---|---|
| `07 80`（正常文件） | 通过，索引 3，143 帧 / 18304 样本 |
| `07 80`（去掉长度头） | 通过，输出与正常文件**逐样本一致** |
| `04 80` | 通过，索引 0（码率最高 → 229 帧） |
| `09 80`（长文件，377 KB） | 通过，索引 5，**7862 帧 / 1,006,336 样本 / 125.79 s** |
| `0A 80` / `03 80` / `01 00` | 拒绝并给出提示 |

大文件不再有 53 KB 限制：`a1600_t` 用**滑动输入窗口**，解码时把未读完的尾部搬到窗口开头并更新内核的流指针（`[0x04C0]`），因此文件多大都能连续解码（MCU 端从 SD/Flash 分块读取用的是同一套逻辑）。WAV 也改成了**流式写**（先写头、结束时回填长度），可以输出任意长度。

### 验证结果（已经实测）

| 样本 | 帧数 | 样本数 | 时长 |
|---|---|---|---|
| `t09_a.a16` | 143 | 18304 | 2.29 s |
| `t09_b.a16` | 141 | 18048 | 2.26 s |
| `t09_c.a16` | 129 | 16512 | 2.06 s |

C 版输出与先前的 Python 参考实现**逐样本完全一致（18304/18304，最大差 0）**，而 Python 版的音频你已确认听感正确。

### 限制

- 只支持 `.a16`（A1600）。DVR1600 同算法但文件头参数约定可能不同。
- 单帧 128 样本（8 kHz、2~3 bit/样本，帧按码率档消耗 16~24 字）；若遇到帧长不同的版本需要按参数表调整。
- 输入窗口 0x0800-0x6FFF（53 KB），超出部分由滑动窗口自动补充，文件大小不再受限。

## 2. Linux 命令行 MS01 播放器（黑盒：直接跑凌阳的 MS01 引擎）

MS01 的乐谱（`.ms1` / `.BIN`）不用自己解析：SDK 例子 `chapter9 Audio/MS01`
给出了**已经链接好的可执行映像** `Debug/MS01.S37`（含 MS01 合成引擎 +
`Isr.asm` 的中断入口）。播放器把这份映像装进 µ'nSP 核心跑，把引擎写进
`P_DAC1/P_DAC2` 的数当成 PCM 取出来——和 A1600 播放器同一种打法。

### 两种构建（"乐曲槽"版 / 经典版）

| 构建 | 说明 |
|---|---|
| `make ms01play` | **乐曲槽版**：ROM 里只有库 + 20 个鼓点，乐曲从命令行给的文件载入槽里，大了就分段滑动 |
| `make ms01play-classic` | 经典版：SDK 那 12 首曲子仍烤在 ROM 里（鼓点要牺牲 LA1 才塞得下） |
| `make ms01play-nodrum` | 原样示例（无鼓点），做对照用 |

#### 乐曲槽版（推荐）

```bash
make ms01play
./ms01play ../ms01_songs/HK1.BIN -o HK1.wav      # 直接给 .ms1/.BIN 文件
./ms01play WINE1.BIN -o WINE1.wav                # 不带 -t 就播到曲子结束
./ms01play test.ms1 -o test.wav                  # 14 分 27 秒的超长曲子也能整曲导出
./ms01play LA1.BIN --slot-words 512 -t 40 -o x.wav   # 故意把槽开小，强制分段
```

- **默认时长**：不给 `-t` 就播到曲子结束（检测到 1 秒静音收尾，硬上限 2 小时）；
  要固定长度就 `-t 秒数`。以前默认是 30 秒，长曲子会被截断——这就是 `test.ms1` 只出 30 秒的原因。
- **奇数长度**：有些 `.BIN` 把最后一个字的填充字节去掉了（例如 `S31.BIN` 是 4327 字节，
  而镜像里是 4328 字节，多出来那个字节是 `0x00`）。加载器现在会补一个 `0x00` 并提示，
  补完与镜像逐字节一致（S31 用槽版和经典版对拍，输出完全相同）。

ROM 布局（`work/mk_ms01_lib.py` 生成 `ms01_lib.c`）：

| 地址 | 内容 |
|---|---|
| `0x8000-0x957B` | 库 + 用户代码 + 资源表 |
| `0x957C-0xC1FF` | **20 个鼓点** ADPCM + 描述符 + 鼓点表（33.8 KB） |
| `0xC200-0xFFF4` | **乐曲槽 15861 字（31.7 KB）**，运行时从文件填入 |

要点：

- **不再需要牺牲任何曲子**：乐谱不在 ROM 里了，LA1 也能正常播；
- 曲子按"每字一个条目"铺进槽（低字节=命令/音符，高字节=操作数），把资源表 12 项都指向槽，
  所以示例自己的选曲键也不会踩到野指针；
- **分段载入**：引擎的乐谱游标 `[0x0065]` 是严格单调的（`0x85A4` 只做 `+1`，
  只在 0xFFFF 回绕时改 bank），所以游标接近已载入区末尾时，把"游标之后的尾巴"搬到槽首、
  改写 `[0x0065]`，再补一段——和 A1600 播放器的滑动窗口是同一套做法；
- 乐谱结束**不靠 EA**（读字节那条路只按游标取、然后 +1），曲子自带 `0x3F` 结束符，
  所以分段不需要维护"结束地址"。

实测（对拍同一个二进制的经典版输出）：

| 场景 | 结果 |
|---|---|
| HK1（1199 字）整槽放 | 与经典版**逐字节一致**（985580 样本、1293 事件） |
| HK1 槽限 1024 字 | **逐字节一致** |
| HK1 槽限 **256 字**（≈1/5 曲子，强制 4 次滑动） | **逐字节一致** |
| LA1 / GREEN1 / WINE1 整槽 vs 槽限 512 字 | 两两**逐字节一致** |

#### 经典版

```bash
make ms01play-classic
./ms01play-classic -k -a -t 200 -o HK1.wav    # 用 ROM 里烤好的 HK1
./ms01play-classic -s 4 -t 20 -o g.wav        # 第 4 首（GREEN1）
```

示例曲目文件（12 首 `.BIN`）在 `outputs/ms01_songs/`，可以直接喂给乐曲槽版。

### 编译与使用（下面这些选项两个版本都有）

```bash
cd outputs/emulator
make ms01play            # 乐曲槽版（-DMS01_SLOT + ms01_lib.c）
make ms01play-classic    # 经典版（ms01_image_drums.c）

./ms01play ../ms01_songs/HK1.BIN -a -o HK1.wav       # 乐曲槽版：给文件就行
./ms01play-classic -k -a -o HK1.wav                  # 经典版：用 ROM 里烤好的
./ms01play-classic -s 0 -t 20 -o song0.wav           # 第 0 首（WISH1）放 20 秒
./ms01play ../ms01_songs/HK1.BIN -e events.txt -o out.wav  # 导出音符事件
./ms01play ../ms01_songs/HK1.BIN -v -o out.wav       # 每 0.25 s 打印内核状态
```

参数速查：

| 选项 | 含义 |
|---|---|
| `歌曲文件`（位置参数或 `--song 文件`） | 乐曲槽版必填：把 `.ms1/.BIN` 铺进 0xC200 的槽 |
| `--slot-words N` | 只在乐曲槽版：把可用槽缩小到 N 字，用来强制走分段路径做对拍 |
| `-k` | 经典版：把资源表 `_RES_Table` 第 0 项直接改写成 HK1 的数据（`0xCDA4..0xD253`） |
| `-s N` | 经典版：选第 N 首（0…11）：在固件跑到 `main`(0x933A) 时改 RAM `0x00C0`(`_SongIndex`)，例程随后自己调 `SACM_MS01_Play` |
| `-p` | 配合 `-s`，改成每个采样点都钉值（会让例程以为"选曲改变"而**反复重头播**，只用来快速看某首有没有鼓点） |
| `-i N` | 1 kHz 节拍中断（IRQ4）的频率，默认 1024；`-i 0` 关掉可以复现"只有一个长音"的老毛病 |
| `-t S` | 固定采样时长（秒）；**不给就播到曲子结束**（1 s 静音收尾，上限 2 h） |
| `-a` | 强制开启"静音收尾"检测（等价于不给 `-t` 时的默认行为） |
| `-e FILE` | 导出音符/乐器事件表（`t(s) / 类型 / 原始码 / 音名通道 / 乐谱指针`） |

### 关键：MS01 的定时/中断分工（这就是"只有一个长音"的根因）

从 SDK 源码 `Isr.asm`、`sacmV32.asm`、`spce.inc` 和 `MS01.map` 一一对出来的：

| 向量 | 槽位 | 触发源 | 处理函数 | 作用 |
|---|---|---|---|---|
| FIQ | `0xFFF6` | TimerA，Fosc/2 ÷ 1536 = **16 kHz** | `F_ISR_Service_SACM_MS01` | 6 通道 FM 合成 → 写 `P_DAC1/P_DAC2` |
| IRQ2 | `0xFFFA` | TimerB（鼓点采样率） | `F_IRQ2_Service_SACM_MS01` | ADPCM 鼓点 → 写 `P_DAC2` |
| IRQ4 | `0xFFFC` | **1 kHz 时基**（`C_IRQ4_1KHz` = `P_INT_Ctrl` b4 = `0x0010`） | `F_IRQ4_Service_SACM_MS01` | **递减 RAM `0x0067` 的节拍计数器** |

节拍计数器 `RAM 0x0067` 才是关键：

```
0x8345 SACM_MS01_ServiceLoop（例程主循环里调用）
   └ 0x8384: if ([0x00BC]&0x8000) return          ; 没在播就返回
             if (!([0x00BB]&0x8000)) return       ; 没在播就返回
             if ([0x0067] != 0) return            ; 本音符还没放够
             call 0x85B8                          ; 符长到了 -> 取下一个乐谱字节
   ...
0x8942 F_IRQ4_Service_SACM_MS01（1 kHz 中断）
   └ r1 = [0x0067]; if (r1==0) return; [0x0067] = r1-1     ; 每个 1 kHz 拍减一
```

也就是说：**IRQ4 不响，`0x0067` 永远不归零，乐谱指针就永远停在第一个音符上**，
听到的就是"开头响一下，然后拖成长音"。旧版播放器只按采样率打 FIQ（TimerA），
完全没有产生 1 kHz 的 IRQ4，所以卡在这里。

老版还有两个隐藏错误，一并修掉了：

1. **向量区放的是入口地址，不是跳转指令**。`0xFFF6` 处存的是 `0x805A`（FIQ 处理
   函数的地址），硬件是把 PC 直接设成这个值；旧代码把 PC 设成 `0xFFF6`，于是从
   向量表往下"当指令执行"，栈立刻跑飞（`sp=0xBDCA`、`pc=0x0000`）。
2. **ISR 的结束判据不对**。旧代码遇到第一个 `retf`(`0x9A90`) 就认定中断返回，但
   中断体里的 `call` 子程序也是用 `retf` 返回的，于是中断被打断在
   `call F_IRQ2_...` 中间，`P_INT_Clear`/`pop`/`reti` 都没执行。现在改成
   "跑到 `reti`(`0x9A98`) 为止"——`Isr.asm` 里每个中断入口都是以 `reti` 收尾的。

### 实测对照（同一首 HK1，20 秒）

| 配置 | 音符事件数 | 每秒 RMS |
|---|---|---|
| `-i 0`（老的坏行为） | **11**（只有开头那几个） | 4742 3404 3081 3109 3071 3157 3085 …（几乎平的一条，就是长音） |
| `-i 1024`（修好的） | **452** | 5204 4132 3812 4154 4293 5085 5372 5973 …（有起伏的曲子） |

输出取单路 DAC（FM 引擎对两个 DAC 锁存器写的是同一个样本，相加只会翻倍并削顶；
改成单路后峰值 32704、削顶样本 0 个）。

`outputs/pcm/HK1_MS01.wav` 是修好之后的完整导出：**61.60 s**，1293 个事件，
乐谱指针 `0xCDA4 → 0xD24F`（HK1 数据段末尾是 `0xD253`，最后一个字是 `0x3F01`，
也就是你说的 `0x3F` 结束标志），到末尾引擎自己停下来，尾部静音。

### 关于鼓点（ADPCM）

**默认构建 `ms01play` 已经带鼓点**（`ms01_image_drums.c`），`ms01play-nodrum`
是不带鼓点的原样示例，两个可以对比。

先把机制说清楚（这部分是从引擎反汇编 + SDK 的 `Resource.asm` 对出来的）：

| 环节 | 位置 | 说明 |
|---|---|---|
| 鼓点通道 | 通道 **0 和 1** | `0x8577 cmp r2,2 / jb 0x857B`：通道号 < 2 走 ADPCM，否则走 FM。这就是 `Isr.asm` 里 `_IRQ2` 注释的 "2ch drum sound" |
| 鼓点编号 | `instr & 0x7F` | 乐谱里的 `$2X,$8n…$93`（128…147）→ 鼓 0…19；SDK 新示例的表就是 `BD1,SD1,HT1,…`（见 `T_SACM_MS01_DrumTable`） |
| 取数据 | `0x8587` | `r3 = 鼓号 + T_SACM_MS01_DrumTable`；表项是**描述符指针**，描述符 4 个字：`sa, seg, ea, seg` |
| 启动 | `0x8630` | 置 RAM `0x3D`（bit0=在响，bit4 选通道）并 `call F_SP_IRQ2_ON` |
| 解码 | IRQ2 → `0x889B` | 4 个相位/拍，每拍取一个 4 bit 半字节；ch0 用 `[0x37]/[0x42]/[0x44]`，ch1 用 `[0x3A]/[0x43]/[0x45]` |
| 混音 | `0x893A` 写 RAM `0x41` | IRQ2 把鼓点样本写进 `[0x41]`；FIQ 在 `0x8876` 做 `r4 = r4 + [0x41]`，然后才写 DAC —— **鼓点和 FM 是在 `[0x41]` 这里相加的** |

所以示例缺的只是**数据**：它的 `T_SACM_MS01_DrumTable`(0x8045) 只有 1 个占位项
`0xFA00`，而 0xFA00 在映像里全是 0 —— 鼓点路径照跑（`[0x3D]` 每 5 秒被置 28 次），
但读到的全是 0，所以一直是静音。

补法（`work/mk_ms01_drums.py`）：把 20 个 `DRUM/*.ADP` 全部放进 ROM，
建好 20 项描述符表，再把引擎里两处 `+ 0x8045` 的立即数（`0x8147`、`0x8588`）
改指向新表。`.ADP` 就是 ROM 里的原始格式：061.dat 的 `0xD33D..F6BA` 里
20 个文件中有 19 个和它们**逐字节相同**。

空间账：空闲区只有 `0xE414..0xFFF4` = 14274 字节，20 个鼓点要 22378 字节，
差 8104 字节。所以**牺牲一首曲子的 ROM**：LA1 是最大的一首（`0x957C..0xA8D3`，
9904 字节），正好够。做法是把 LA1 的资源表项改成指向一个只含 `0x3F`
（就是 `;Song ended` 那个结束字节）的单字乐谱——选到 LA1 时立即结束、静音，
不会再拿鼓点数据当乐谱放噪音。最终布局：

| 区域 | 内容 |
|---|---|
| `0x957C..` | 鼓点 ADPCM（LA1 原来的位置 + 空闲区，共 22378 字节） |
| `0xA888..0xFCC3` | 20 个描述符（每鼓 4 字） |
| `0xFCC7..0xFCDA` | 20 项新鼓点表 |
| `0xFCDB` / `0xFCDC` | 缺失鼓点的静音字 / LA1 的单字结束谱 |

`--fit` 可以反过来：保留全部 12 首曲子，只装下能放下的 15 个鼓点。

实测（鼓点分量 = 带鼓点渲染 − 不带鼓点渲染）：

| 曲子 | 鼓点峰值 | 鼓点 RMS | 曲子 RMS |
|---|---|---|---|
| WISH1 | 20912 | 4316 | 4190 |
| DECK1 | 19328 | 4330 | 4123 |
| **HK1** | **17920**（8 秒片段 25120） | **2144**（8 秒片段 4130） | 4806 |
| ALA1 / LA1 / S31 / TW1 / 1231 | 13k～23k | 1.6k～2.4k | — |
| GREEN1 / PP1 / WINE1（60 秒窗口） | 10736 / 18240 / 12736 | 489 / 262 / 649 | 2748 / 3110 / 2352 |
| ALAINS | 0 | 0 | 这首谱子本来就没有鼓点 |

注意 GREEN1 / PP1 / WINE1 的鼓点**不在曲子开头**：它们前 8 秒是纯 FM，
只按 8 秒窗口对比会误判成"没有鼓点"（我一开始就踩了这个坑，后来把窗口拉到
60 秒、并数 `[0x3D]` 被置位的次数才看清）。

HK1 的鼓点分量听感上是一串带衰减包络的打击（10 ms 峰值包络：`7440 4848 1440
1200 1200 912 720 … 0 0 0` 然后下一击），间隔 ≈0.187 s，正好落在乐谱的音符网格上。
整曲 61.60 s、峰值 32704、**削顶 0 个**。

`outputs/pcm/HK1_MS01_with_drums.wav` 是带鼓点整曲，
`outputs/pcm/HK1_8s_drums_only.wav` 是前 8 秒**只有鼓点**的部分（相减得到），
可以直接听出鼓点有没有踩在拍子上。

**代价**：这份映像里 **LA1（第 6 首）不能播**了，选到它会立刻静音结束；
其余 11 首都能正常播放，且都有鼓点（ALAINS 本来就没有）。

### 鼓点音调（TimerB 速率）——已修

鼓点 ADPCM 通道**每个 IRQ2 只吃一个 4 bit 半字节**，而 IRQ2 就是 TimerB，
所以**鼓点的采样率 = TimerB 的溢出率**，和 FM/DAC 的 16 kHz 没有关系。

示例固件在初始化时写的是：

```
P_TimerB_Ctrl = 0x0003      ; 手册 6.4 表：source C = 011 = 8192 Hz
P_TimerB_Data = 0xFFFF      ; 周期 = 0x10000-0xFFFF = 1 个 tick
→ 鼓点采样率 = 8192 Hz
```

旧版播放器按输出采样率（16 kHz）每个点都打一次 IRQ2 —— **鼓点正好快 1.95 倍，音调高一个八度**，
而节拍完全不受影响（触发来自乐谱、走 1 kHz 的 IRQ4）。现在按寄存器算速率
（`timerb_rate()`，读到 `P_TimerB_Ctrl/Data` 就重算），用 Bresenham 累加器打 IRQ2。

实测（第一个鼓点，鼓点分量 = 带鼓点 − 不带鼓点）：

| 版本 | 10% 衰减时间 | 频谱主峰 |
|---|---|---|
| 旧（IRQ2 = 16 kHz） | 70 ms | 740 Hz |
| 现在（IRQ2 = 8192 Hz） | **140 ms** | **318 Hz** |

`--irq2-rate N` 可以强制鼓点速率做对照（`--irq2-rate 0` 等于关掉鼓点通道，
正好用来提取"只有鼓点"的分量）。

## 3. STM32F411：直接播 A1600（先出声的那条路）

`main_stm32_a1600.c` 不模拟整个 061.dat，而是直接用**从固件里抽出来的 A1600 内核**
（`a1600_image.c`，与 061.dat 里那份逐字节相同、桌面播放器已验证）在 µ'nSP 核心上解码，
把 8 kHz PCM 送到 I2S。上电就能出声，零协议风险。

### 为什么 128 KB 的 F411 放得下

桌面播放器要一整块 `0x10000` 字（**128 KB**）的 image 数组；F411 总共才 128 KB RAM。
所以给 `unsp_t` 加了一个"RAM 窗口"，把内存拆成：

| 区域 | 大小 | 位置 |
|---|---|---|
| `a1600_image[]`（内核 + FFT + 系数表） | 40 KB | **flash**（const，`rom_base = 0x8200`） |
| 压缩流滑动窗口 `window[]` | 8 KB | RAM（`unsp_t.win`，映射在 0x0800） |
| `unsp_t.ram`（0x0000-0x07FF） | 4 KB | RAM |
| 流式暂存 `stage[]` | 12 KB | RAM |
| I2S 双缓冲 256 样本 + UART 环 + 静音帧 | < 1.5 KB | RAM |

合计 **RAM ≈ 26 KB / 128 KB**，**flash ≈ 46 KB / 512 KB**（内核 40 KB + 内嵌片段 4.6 KB + 代码），
余量很足，想加大 `stage[]`（放更长的流）或换成 SD/FatFs 都够。

验证方式（宿主机）：`work/a1600_split_test.c` 用这个"flash 内核 + RAM 窗口"布局解码
`t09_a.a16`，输出与参考播放器**逐字节一致**；`work/a1600_stream_test.c` 再把 STM32 那套
12 KB 暂存 + 256 字节分块 + 头部剥离 + 搬移逻辑原样跑一遍，用你那个 377 KB 的 `1.a16`
（125.79 秒、1474 个块）对比，同样是**逐字节一致**。

### 上电行为

1. 复位后自动播放内嵌试听片段 `demo_a16.c`（就是 `t09_a.a16`，2.29 秒），默认循环。
2. 调试口 USART1（115200 8N1）命令：

   | 键 | 作用 |
   |---|---|
   | `p` | 重放内嵌片段 |
   | `s` | 停止 |
   | `l` | 循环开关 |
   | `S` | 统计（已解码帧数/静音帧/错误/播放秒数/流字节/溢出/码率索引/速度） |
   | `i` | 参数（内核字数、窗口大小、暂存大小、`a1600_check(demo)`、码率索引） |
   | `m` | 测解码速度：报告"每 200 ms 能解多少帧"，实时需要 62.5 帧/秒 |

3. 想放别的文件：用 USART2 流式送（协议见下），`work/stream_a16.py` 已经写好。

### 流式协议（USART2，波特率随你设，两边一致即可）

```
上位机 -> 'A' + u32 文件长度（小端）
固件   -> 0x06                      ; 每个能收的块发一次
上位机 -> 256 字节（最后一块可短）  ; 就是 .a16 文件的原始字节
... 循环到发完 ...
```

```bash
pip install pyserial
python work/stream_a16.py COM7 sound.a16          # Windows
python work/stream_a16.py /dev/ttyUSB0 sound.a16  # Linux
```

固件端会自动剥掉 .a16 前 4 个字节的长度字段、按 256 字节块收、边收边解码，
暂存满了会停止发 0x06（所以上位机必须等 ACK，不要直接 `cat`——直接 cat 短文件也能响，
但长文件会丢数据，`S` 里的 `stream overflows` 会涨）。

### 验证到什么程度

## 4. STM32F411 固件模拟器（跑整个 061.dat）

> **2026-09-22 更新**：`unsp.c` 里修掉了三个把"整机模拟"卡死的核心 bug
> （见文末"CPU 核的三个 bug"），并且新增了 `fwstream`（`main_linux_fwstream.c`）
> —— 在 PC 上用真实外设模型驱动 061.dat 自己的串口流协议。
> 协议本身（分帧/环形缓冲/打包/流控/收尾）已经逆完并写进
> `outputs/061_启动流程与串口协议.md` 第 5 章。

### 已实测/已确定的结论

- **0x8000-0x81FF 缺失可以忽略**：真正的复位入口是 `0xCB9F`（设栈 → 搬运 → `call 0x8205`）；CPU 用的中断向量区虽然 0xFFF5-0xFFFF 在 dump 里是空的，但固件自己在 **0xFC00** 存了一份 11 项向量表，模拟器启动时把它装进 `cpu.vec_area[]` 即可。
- **实时性可行**：A1600 解码 ≈ **17161 条指令/帧**（128 样本 = 16 ms）→ 约 1.07 M 指令/秒；音频 FIQ 中断体仅 11-15 条。合计约 1.3 M 模拟指令/秒，100 MHz 的 M4 有 3-5 倍余量。
- **开机握手已逆清楚（这一版修正过）**：`sub_823A`(0x823A) 是握手例程，它在
  `0x823E..0x8245` 自旋等 UART 环形缓冲里出现 **16 位字 `0x0ABB`**，应答 `0xFABB`，
  然后才跳进真正的主循环 `0x8232`。这个字由 UART 中断（`_IRQ7` → `0xC889` → `0xCC23`）
  把两个字节拼出来：`[0x0717] = ([0x0717] ror 8) | byte<<8`，所以**字节顺序是 `0xBB` 先、`0x0A` 后**
  （`0xAB,0x0A` 会拼成 `0x0AAB`，永远等不到——旧版本注入的就是错的那组）。
  握手字节必须在固件初始化**之后**才发（固件在 `0xCB0E` 会清环形缓冲），所以现在是在
  检测到 PC 落在 `0x823E..0x8245` 时才注入。`unsp.c` 的 CPU 核心配合真实外设模型，
  发完这两个字节就走到 `0xCFE0`。
- **开机流程已经走通（现在真的进主循环了）**：握手命令之后还要再发一个字。
  `0x8222` 从环形缓冲取字：`0x0FCC` 是 `DEBUG_CMD`（回 `0xCCFF` 继续等），**其它任何字
  都直接进主循环 `0x8232`**。所以我们发 `START_MS01`（0x99 0x00）。
  实测：reset → 72501 条指令进主循环，固件回 `0xBB 0xFA`（= `LINK_ACK_CMD`）。
- **两个模型 bug（它们各自都能把启动链掐死）**：
  1. `P_IOx_Data` 读回值错。固件在 `0xCFE0` 发每个字节前会等 **IOB2 为低**
     （`test [0x7005],0x04`）。IOB2 被固件配成**输入**，而旧模型读回的是**输出锁存**，
     锁存里正好有 0x0404 → b2=1 → 永远等不到。现在按真实端口建模：
     `读取 = (锁存 & 方向) | (外部电平 & ~方向)`，并加了 `spce_set_io_a/b()` 让上位机
     拉外部电平。
  2. TimerA 的 source B 选择位读错了。手册里 source A 的 `110` 是"常量 0"（停表），
     但 **source B 的 `110` 是"常量 1"（让 source A 通过）**。固件写的是
     `P_TimerA_Ctrl = 0x0030`（source A = Fosc/2，source B = 常量 1），旧代码按"停表"
     处理，于是 TimerA 一动不动、音频 FIQ 一次都不来。修好后 TimerA 正常计数。
- **UART 中断模型修正**：`_IRQ7` 不受 `P_INT_Ctrl` 控制，由 `P_UART_Command1` 的 b7
  (RxIntEn) / b6 (TxIntEn) 使能，电平触发；已在 `spce061a.c` 里实现
  （`spce_uart_rx()` + `spce_poll_irq()`，后者要放在指令循环里每步调用）。
  另外 `P_INT_Ctrl` 只管"哪几个中断源被允许"，**不能再拿它去写 CPU 的全局
   `enable_irq/enable_fiq`**（那是 `INT ON/OFF` 指令的事）。旧代码在固件写
  `P_INT_Ctrl=0x2000`（只开 FIQ_TMA）时顺手把 IRQ 全局关了，UART 中断就此失效。
- **DAC 极性修正**：片上 DAC 是无符号的（0x8000 = 中点），I2S 要的是以 0 为中心的有符号
  PCM，所以推环前减 0x8000。旧代码直接 `(int16_t)value`，0x8000 会变成 −32768 的直流。
- **采样率跟随固件**：`spce_dac_sample_rate()` 按固件的 TimerA 重载值算它当前的采样率
  （`Fosc/2 / (0x10000 - reload)`）。主循环按这个比例决定每个输出样本打几次音频中断，
  所以固件从 8 kHz 切到 16 kHz 也不会变成半速播放。
- **`P_INT_Ctrl` 位定义修正**：旧的常量写错了（把 `FIQ_TMA` 当成 0x4000、IRQ 使能只认
  低 9 位，漏掉TimerB 的 `0x0400`）。现在按手册第 7 章的表：`FIQ_PWM 0x8000`、
  `IRQ0_PWM 0x4000`、`FIQ_TMA 0x2000`、`IRQ1_TMA 0x1000`、`FIQ_TMB 0x0800`、
  `IRQ2_TMB 0x0400`、`IRQ3_EXT2 0x0200`、`IRQ3_EXT1 0x0100`、`IRQ3_KEY 0x0080`、
  `IRQ4_1KHz 0x0010`。定时器时钟源也按手册的表实现了（TimerA = source A AND source B，
  TimerB = source C；`0x0003` 是 8192 Hz，`0x0030` 是 Fosc/2）。

### 实时策略（重要）

不按模拟时钟节拍（F411 无法逐周期模拟 49 MHz 的 µ'nSP），而是让**固件自己的 TimerA 驱动音频**：`spce_tick()` 用真实的指令周期数递减 TimerA，TimerA 溢出触发 FIQ → 固件把样本写进 `P_DAC1/P_DAC2` → 外设模型推入音频环形缓冲 → I2S DMA 取走。这样音质与实机一致，且只要模拟器平均速度高于实时需求就不会断音（余量 3-5 倍）。

### 两个串口的分工（重要）

| 串口 | 角色 | 说明 |
|---|---|---|
| **USART1** | **调试口** | 本程序自己的日志（启动、统计、错误）+ 命令台（见下表） |
| **USART2** | **接 061 模拟器的串口** | 固件写 `P_UART_Data`(0x7023) → 进 256 字节环形缓冲 → 中断发送；上位机发来的字节 → 中断接收 → 直接塞进模拟的接收 FIFO。**波特率自动跟随固件**：固件写 `P_UART_BaudScalarLow/High`(0x7024/0x7025) 时，模型按 `Baud = (Fosc/4)/Scale`（24.576/20.48MHz 时是 `(Fosc/2)/Scale`）算出真值并重新配置 USART2 |

这样：USB-TTL 接 USART2 就能和"芯片"对话（真实外设或 PC 终端都行），而调试信息不会和固件协议混在一起。`auto_handshake` 默认打开（裸板也能进主循环）；接真实设备时把它设为 0，或用调试口发 `i` 手动注入。

### 命令台（调试口 USART1，115200 8N1）

| 键 | 作用 |
|---|---|
| `h` | 帮助 |
| `i` | 发握手/链路命令 `0xBB 0x0A`（`DATA_LINK_CMD`） |
| `p` | 发 `START_MS01_CMD` = `0x99 0x00` |
| `o` / `a` / `u` | 发 `STOP_CMD`(0xAA00) / `PAUSE_CMD`(0xAA04) / `RESUME_CMD`(0xAA05) |
| `c` / `d` / `t` | 发 `DATA_CHK_CMD`(0xBB0B) / `DEBUG_CMD`(0xCC0F) / `TEST_CMD`(0xCC05) |
| `A` | 开关自动开机（默认开：检测到固件在握手自旋时自动发链路命令，收到应答后再发 `0x99 0x00`） |
| `r` | 复位模拟器（PC ← 0xCB9F，重新走一遍开机） |
| `s` | 统计：样本/帧/音频环溢出/音频中断次数/**固件当前采样率**/固件 PC/开机状态/模拟波特率/接收队列/指令总数/实测指令速率 |
| `b` / `m` | 显示模拟 UART 波特率 / 跑一次速度测试 |

命令常量与字节顺序取自上位机的 `V6100_061.h`（`Communicate with 061 system command`）。

### CubeMX 配置要求

- **I2S2**：Master TX、Philips、16 bit、**8 kHz**、DMA1 Stream4 循环模式、半传输+传输完成中断（对齐固件的 8 kHz 采样）

| 信号 | F411 引脚 |
|---|---|

### 使用

1. 用 CubeMX 生成工程，把 `unsp.c`、`spce061a.c`、`firmware_061.c`、`main_stm32.c` 加入并调用 `emulator_init()` 启动（`main()` 里已有示例）。
2. 烧写后调试口会打印入口信息，然后**自动开机**：链路命令 → 收到 `0xBB 0xFA` → 发 `0x99 0x00` →
   `boot complete, firmware in main loop`。此时固件已经在跑它自己的主循环，并会打印它检测到的采样率。
3. 之后可以用调试口的 `p/o/a/u` 发播放控制命令，或者把 USART2 接到真实上位机，让它按 `V6100_061.h` 的协议驱动"芯片"。
4. 音频从 I2S 输出（固件写 DAC1/DAC2 的样本都会进入 I2S 流）。

## 5. `fwstream`：在 PC 上按 061.dat 自己的串口协议喂流

```bash
cd outputs/emulator
make fwstream
./fwstream SONG.a16 out.wav [max_steps] [byte_gap] [end_mode] [fire_every] [pkt_mode] [block_pkts]
# ★ 能对上参考解码器的那条命令（把 A1600 的 .a16 喂给"芯片"，录 P_DAC2 成 WAV）：
./fwstream ~/t09_a.a16 out.wav 600000000 40 4 0 1 1000000
```

它做的是**上位机的活儿**：握手 `0xBB 0x0A` → `0x99 0x40`（START_A1600）→
把 `.a16`（去掉前 4 字节长度）按 `STREAM_CMD1/2` 包发进去 → `0xAA 0x02`（END_CMD），
然后按固件当前采样率敲 TimerA FIQ，把 `P_DAC2`(0x7016) 的样本写成 WAV。

参数含义：

| 参数 | 说明 |
|---|---|
| `byte_gap` | 每两个字节之间空多少条模拟指令（默认 40；现在每字节都按固件解析器状态握手，这个值只当兜底） |
| `end_mode` | **4 = 第一块（40 包）发完补一发 `0xAA 0x02`** ← 正确用法；1/2 是文件发完才发（会卡住，留着对照） |
| `fire_every` | 每多少条模拟指令敲一次音频 FIQ；**0 = 不注入，用芯片自己的 TimerA** ← 正确用法 |
| `pkt_mode` | 0 = `0x33` + 15 字节负载；1 = `0x22` + 长度字节 + 14 字节负载（**整块对齐用**） |
| `block_pkts` | 一个"块"发多少包（40 = 40×14B = 560B = 280 字，正好一个环）；给个大数（如 1000000）等于不做块节流，靠握手就够了 |

实测产出：`outputs/pcm/fwstream_t09a.wav` —— 061.dat **自己**解码、从 `P_DAC2` 出来的
2.64 秒音频（31958 Hz，84309 个样本，RMS ≈ 10544，包络是正常的语音形状）。
这是"固件真的在解码并在出声"的直接证据；但它**不是**逐样本正确的整曲，
原因见下一节。

### 这一轮新查清的三条协议规则

1. **`END_CMD`(`0xAA 0x02`) 必须在数据开始流动之后发，不能等到文件结束。**
   它置的 `[0x0000]` bit7 同时把两件事打开：
   `0xC699` 的 `[0x04C8] = [0x0728]`（让解码器看到新装进环的数据）和
   `0xC6A0`（把"新到了多少字"累加进解码器的阈值 `[0x04C3]/[0x04C4]`）。
   只在文件末尾发 END_CMD，整个流期间 `[0x04C8]` 就不动，解码器吃到
   `[0x04C0] == [0x04C8]` 就停住 —— 这正是上一轮"卡在中途"的直接原因。
   反过来，**太早发也不行**：`0xC92A` 那段是"累加器 ≥ 阈值就收尾"，
   一开始阈值为 0，bit7 一置位就立刻收尾。正确时机是**第一块数据发完之后**。
2. **宿主绝对不能在一个包的中间停住。** 固件重新装填环时要走
   `0xCB4D → 0xCD42 → 0xCD02 → 0xCD18`，而 `0xCD18` 是"等字节解析器回到状态 0"；
   半截包永远到不了状态 0。宿主一停、固件一等，就是死锁
   （实测现象：`[0x0714] = 0x8003`、`[0x0715] < [0x0716]`、`rx_fifo = 0`）。
3. **`0x22 + 14 字节` 才是能把环正好填满的形式**（40 包 = 280 字 = `[0x0729]` 配额），
   而且每次都在整字边界结束；`0x33`(15 字节)会留下半字。

### 实测状态：通了

`fwstream` 现在把 `.a16` 完整喂进 061.dat 并解出**和参考一致**的音频：

- 零丢失（`uart rx drops = 0`），全程 `[0x0713..0x0729]` / `[0x04C0..0x04C8]` 自洽；
- **芯片自己的 TimerA** 以 32 kHz 驱动音频 FIQ，不用宿主注入；
- 内核帧输出 0x011E 的 128 个样本**逐帧等于参考解码器**（见上一节）；
- 整段相关系数 **0.9927**，录音在 `outputs/pcm/fwstream_t09a.wav`。

所以 `fwstream` 现在已经是一个**可用的"把 .a16 喂给真固件"的参考上位机**：
先握手、`0x99 0x40` 启动、按 `0x22`+14 字节整块发数据、第一块后补一发
`0xAA 0x02` 开解码门，之后每字节按固件解析器状态握手式推进。
同样的三条规则已经体现在 STM32 那条路上（`spce_timer_fire_audio` 也用同一份
`unsp.c`/`spce061a.c`，`FIR_MOV` 一修，MCU 端的整机模拟也才第一次真正解对）。

### CPU 核 / 外设模型里的五个 bug（这一版才修掉）

它们在 `unsp.c` / `unsp.h` 里，**只影响"用 unsp_interrupt() 走真向量表"的整机模拟**；
`main_linux.c` / `main_linux_ms01.c` 那两个播放器自己发向量、从不调用
`unsp_interrupt()`，所以走 `int_active == 0` 的兼容分支，输出逐字节不变
（已回归验证：A1600 播放器对同一个 `.a16` 的输出与修改前完全一致）。

1. `cpu->vec_area[index & 10]` —— `10` 是十进制 `0b1010`，`& 10` 会把 bit0 抹掉，
   于是 **FIQ(1) 跳到 BREAK 向量、IRQ0(3) 跳到 RESET 向量**……
   现象是"音频 FIQ 跑进了 UART 中断服务程序"。应写 `index & 15`。
2. `retf` 无条件清 `in_fiq/in_irq`。061.dat 的 UART 中断处理程序里
   （`0xC889 push` → `call 0xCC23` → `0xC893 pop` → `0xC894 reti`）中间的 `retf`
   只是**子程序返回**，旧代码把它中断结束，电平触发的 UART 中断立刻重入：
   **每收一个字节漏 2 个字栈**，栈一路压低，最后踩进 `0x0713..0x0764`
   （字节暂存区 / 打包器状态 / 命令环）和环缓冲。现在按层记录进入时的 SP，
   `retf` 只有在栈回到该层入口时才算这一层结束。
3. FIQ 不能抢占 IRQ。32 kHz 的音频 FIQ 几乎总撞在 UART 中断里，
   旧代码"在中断里就拒绝一切中断"，于是 **FIQ 全被丢弃**（实测 `fiq entries=0`），
   一个 DAC 样本都写不出来。真芯片上 FIQ 优先于 IRQ，已改成 FIQ 可抢占 IRQ。
4. `spce061a.c` 里 **TimerA/TimerB 在"还没溢出"那条分支上把计数写反了**：
   `m->timer_a_count = count - ticks;`。溢出判断用的是
   `period = 0x10000 - count`（**向上**计数到 0x10000 overflow），
   所以这条分支必须是 `count + ticks`。写反以后计数器一路往下跑、预加载值
   `0xFCFF` 再也不回来、"剩余周期"越算越大 —— 音频 FIQ 从每 1538 条指令一次
   变成几百万条一次。修好之后：**60M 条指令里 FIQ 触发 38856 次 ≈ 每 1544 条一次**，
   正好等于 `Fosc/2 / (0x10000-0xFCFF) = 32 kHz` 的预期值。这条一修，
   模拟器就可以**用芯片自己的 TimerA 驱动音频**（`fwstream ... 0 ...`，
   `fire_every=0`），不用宿主去猜节奏。
5. **中断入口不该动 `FIR_MOV`**。旧代码在每层中断入口都写 `cpu->fir_mov = 1`，
   而 `FIR_MOV` 是"`MR = [Rx]*[Ry]` 内积之后自动搬移输入缓冲"的开关：
   061.dat 自己在启动时明确关掉它（`0xC41F: fir_mov off`），
   而 A1600 内核里有 **4 条**这种内积（`0xBA9A/0xBAB0/0xBAF3/0xBB1D`），
   必须在关掉的状态下跑。旧代码每来一次中断就把它打开，
   于是内核的滤波器历史被悄悄搬移，解出来的波形完全不同 ——
   这是最后一个"数据、状态、模式全都对、波形却不对"的隐藏开关。
   （独立播放器从不进中断，所以它们一直是好的；`a1600play` 修前修后逐字节一致。）

### 第 5 条修好之后：对上了

```
fn 0x011E 的 128 个样本，逐帧对比
  ref  frame 0: FFFF 0004 FFF3 FFF1 FFF7 FFFE 000A 002F
  fw   frame 0: FFFF 0004 FFF3 FFF1 FFF7 FFFE 000A 002F   ✓ 完全一致
  ref  frame 1: 01B5 070D 01EA 01F6 F91B FB28 FBAA F527
  fw   frame 1: 01B5 070D 01EA 01F6 F91B FB28 FBAA F527   ✓ 完全一致
（两边的流指针都从 base+2 开始，每帧 +0x10 = 16 字，位率索引 [0x0793] 都是 3）

整段音频（把固件 32 kHz 输出 4 倍抽取后和参考 8 kHz 逐样本相关）：
  最佳对齐 18.6 ms，相关系数 0.9927
```

也就是说：**061.dat 现在能按自己的串口流协议收下 `.a16`、用自己的解码器
解出和参考完全一致的 8 kHz PCM、并从 P_DAC2 出声**。

### 限制与注意

- **固件是"流式声音模块"**：它自己不带曲子（061.dat 里只有 A1600/S200 内核和鼓点，没有 MS01 内核，
  也没有乐谱），放音要由上位机**把压缩数据流发给它**——`V6100_061.h` 里的
  `STREAM_CMD1 0x22 / STREAM_CMD2 0x33 / VOLUME_CMD 0x44 / SPEED_CMD 0x55 / PITCH0/1 / VOICE_CMD`
  就是这条流的包头。所以现在能做到：**开机、进主循环、按协议收发命令**；
  要真的出声，还差把 A1600 数据按它的分包格式喂进去（包格式在固件的 UART 中断
  分发器 `0xCC23 → 表 0xCB89` 里，还没逆完；`STREAM_CMD2_LEN=0x0F` 提示包长 15 字节）。
  另外固件的音频 FIQ 只在"真的有流要放"时才 `fiq on`（`0xC546` 里看状态字 `[0x0000]` 的
  bit11 0x0800），所以静音时 I2S 上就是一条静音流，这是正常的。
- 只模拟了固件实际访问的外设（22 个寄存器）。按键/ADC 输入目前是常量，需要按现象补模型。
  现在可以用 `spce_set_io_a/b()` 拉引脚电平，用 `io_trace` 钩子看固件在写哪些寄存器
  （`work/fw_smoke.c` 就是这么把启动链逆出来的）。
- `0x7555` flash 控制器未实现（固件不写 flash）。
- I2S 时钟精度直接决定音调；若听感偏快/偏慢，检查 PLLI2S 配置是否真为 8 kHz。
- 本机没有 F411 实物，这一段只做了**语法检查（tcc + 桩头文件）和宿主机上同芯逻辑的验证**，
  没有上板实测。
