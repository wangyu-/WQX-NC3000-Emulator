# MS01 播放器：为什么只有开头一声，以及修了什么

> 结论：**MS01 的"曲长推进"靠 1 kHz 的 IRQ4 中断递减 RAM `0x0067` 的节拍计数器，
> 而这个中断以前根本没有被触发**。计数器不归零，主循环里的
> `SACM_MS01_ServiceLoop` 就永远不取下一个乐谱字节，于是听到的就是
> "第一个音符响一下 → 一直拖长"。另外还有两个隐藏错误（向量区语义、ISR 结束判据）
> 一并修掉了。修好后 `HK1.ms1` 能完整播完 **61.62 s**。

## 1. 素材与做法

| 素材 | 用途 |
|---|---|
| `chapter9 Audio/MS01/Debug/MS01.S37` | 已经链接好的**可执行映像**（MS01 合成引擎 + `Isr.asm` 的中断入口 + 12 首曲子） |
| `Debug/MS01.map` | 符号表：`_RESET`、`_FIQ`、`_IRQ2/_IRQ4`、`_RES_x_BIN_SA/EA`、`T_SACM_MS01_*` |
| `Isr.asm` / `sacmV32.asm` / `spce.inc` | 中断分工、定时器初值、`P_INT_Ctrl` 的位定义 |
| `HK1.ms1`（用户提供） | 与映像里 `0xCDA4..0xD253` 的那首 **逐字节相同** |

做法是"黑盒"：不解析 MS01 乐谱格式，直接把映像丢进 µ'nSP 核心跑，
让引擎自己解码合成，把写进 `P_DAC1/P_DAC2` 的数当 PCM 取出来
（`outputs/emulator/main_linux_ms01.c`）。

## 2. 中断分工（从源码对照出来的）

| 向量 | 槽位 | 触发源 | 处理函数 | 作用 |
|---|---|---|---|---|
| FIQ | `0xFFF6` | TimerA，Fosc/2 ÷ 1536 = **16 kHz** | `F_ISR_Service_SACM_MS01`（`0x8865`） | 6 通道 FM 合成 → `P_DAC1/P_DAC2` |
| IRQ2 | `0xFFFA` | TimerB（鼓点采样率） | `F_IRQ2_Service_SACM_MS01`（`0x889B`） | ADPCM 鼓点 → `P_DAC2` |
| IRQ4 | `0xFFFC` | **1 kHz 时基**（`C_IRQ4_1KHz` = `P_INT_Ctrl` b4 = `0x0010`） | `F_IRQ4_Service_SACM_MS01`（`0x8942`） | **递减 RAM `0x0067`** |

例程开机时 `F_SP_PlayMode3_`（`DAC_16K`）一次性写：

```
P_DAC_Ctrl   = 0x00A8
P_TimerA_Data= 0xF9FF          ; 0x10000-0xF9FF = 0x600 = 1536, 24.576MHz/1536 = 16 kHz
P_INT_Ctrl   = C_FIQ_TMA | C_IRQ2_TMB | C_IRQ4_1KHz = 0x2000|0x0400|0x0010 = 0x2410
```

## 3. 卡住的真正原因

把节拍相关的三段代码连起来（都是反汇编原文）：

```
0x8345  SACM_MS01_ServiceLoop:            ; 例程主循环 while(1) 里每轮都调
0x8346    call 0x8384
0x8384    r1 = [0x00BC]; if (b15) return  ; 没在播
0x8387    r1 = [0x00BB]; if (!b15) return ; 没在播
0x838B    r1 = [0x0067]; if (r1 != 0) return    ; ★ 本音符还没放够 -> 什么都不做
0x838F    call 0x85B8                    ; ★ 符长到了 -> 取下一个乐谱字节
          ... 按字节类别用 0x8C91 的跳表分发（音符/乐器/命令） ...

0x8942  F_IRQ4_Service_SACM_MS01:         ; 1 kHz 中断体
          r1 = [0x0067]                  ; 读计数器
          if (r1 == 0) retf              ; 已经是 0 就返回
          r1 -= 1; [0x0067] = r1         ; ★ 每个 1 kHz 拍减一
```

`0x0067` 是"当前音符还剩多少个 1 kHz 拍"。**没有 IRQ4，它就永远不归零，
`0x85B8` 永远不会被调用**，乐谱指针停在第 6 个字上——这就是"只有一个长音"。

旧播放器只按输出采样率打 FIQ（TimerA），压根没产生 1 kHz 事件，所以卡死在这里。

## 4. 顺手修掉的两个隐藏错误

### 4.1 向量区放的是**入口地址**，不是跳转指令

MS01 映像里 `0xFFF5..0xFFFF` 是：

```
FFF5:8063  FFF6:805A  FFF7:807D  FFF8:8063  FFF9:8063  FFFA:8066
FFFB:806F  FFFC:8072  FFFD:807A  FFFE:807A  FFFF:807A
```

对应 `_BREAK/_FIQ/_RESET/_IRQ0..7`，值是**处理函数地址**（`_FIQ=0x805A`、
`_IRQ4=0x8072`）。硬件是把 PC 直接设成这个值。旧代码写成 `PC = 0xFFF6`，
于是从向量表往下"当指令执行"，栈立刻跑飞（实测 `sp=0xBDCA`、`pc=0x0000`，
2 个采样点就把 RAM 写乱）。

### 4.2 ISR 的结束判据应该是 `reti`，不是第一个 `retf`

`Isr.asm` 里每个中断入口都以 `reti` 收尾，但中断体内部会 `call` 子程序，
那些子程序是用 `retf` 返回的。旧代码遇到第一个 `retf` 就认定"中断结束"，
导致 `P_INT_Clear`/`pop`/`reti` 都没执行（比如 IRQ2 里
`call F_USER_MS01_GetAdpcmData_Ch0` 一返回就被切断）。
现在改成"跑到 `reti`(0x9A98) 为止"。

## 5. 实测证据

### 5.1 同一首 HK1、同样 20 秒，只切换 IRQ4

```
$ ms01play -k -i 0    -t 20 -o bug_off.wav      # 复现老毛病
$ ms01play -k -i 1024 -t 20 -o bug_on.wav       # 修好以后
```

| 配置 | 音符/乐器事件数 | 每秒 RMS（20 秒） |
|---|---|---|
| `-i 0` | **11** | 4742 3404 3081 3109 3071 3157 3085 3148 3009 3153 3088 3201 … |
| `-i 1024` | **452** | 5204 4132 3812 4154 4293 5085 5372 5973 6123 6450 6392 6737 … |

关掉 IRQ4 时 RMS 平得像一条直线（就是那个长音），打开后才有音乐该有的起伏。

（另外把输出从 "DAC1+DAC2 相加" 改成取单路：FM 引擎对两个 DAC 锁存器写的是**同一个**
样本，相加只会让电平翻倍并且削顶——改之前 61 秒里有大量 `±32768` 的削顶样本，
现在峰值 32704、削顶 0 个。）

### 5.2 完整曲长与结束标志

```
$ ms01play -k -a -t 200 -e HK1_MS01_events.txt -o HK1_MS01.wav
wrote HK1_MS01.wav: 985580 samples (61.60 s)
fiq=985581 irq2=985581 irq4=63077 dac_writes=1970722 events=1293 adpcm=0
```

事件表里乐谱指针 `ptr` 从 `0xCDA4` 一路走到 **`0xD24F`**，而 HK1 的数据段是
`0xCDA4..0xD253`（1200 个字）。最后一个字是 `0x3F01`，低字节 `0x01`、高字节
`0x3F`——就是你说的**结束标志**。引擎吃完这个字之后音量包络归零、输出静音，
`-a` 因此在 61.62 s 收尾（0.5 s 静音判据）。

音符事件样例（`HK1_MS01_events.txt`）：

```
  0.0457  INSTR raw=0x4193  ch1 instr147  ptr=0xCDA6
  0.0458  INSTR raw=0x4207  ch2 instr7    ptr=0xCDA8
  0.0461  NOTE  raw=0x0111  ch1 C2        ptr=0xCDB3
  0.0462  NOTE  raw=0x01AC  ch2 B3        ptr=0xCDB4
  0.4209  INSTR raw=0x4192  ch1 instr146  ptr=0xCDB7
  0.4211  NOTE  raw=0x0111  ch1 C2        ptr=0xCDBB
```

音符间隔 ≈ 0.187 s，与 `[0x0067]` 的初值（如 `0xAF`=175 拍 / 1024 Hz ≈ 0.171 s）吻合。

### 5.3 频谱抽查

对渲染结果做 FFT，主峰落在 660 / 988 / 1318 / 1480 Hz 这类位置（E5、B5、E6、F#6
的谐波区），在正常音乐音域内。

## 6. 鼓点（ADPCM）——已补上

### 6.1 机制（从引擎反汇编 + SDK 的 Resource.asm 对出来）

| 环节 | 位置 | 说明 |
|---|---|---|
| 鼓点通道 | 通道 **0 和 1** | `0x8576 cmp r2,2` / `0x8577 jb 0x857B`：通道号 < 2 走 ADPCM，≥2 走 FM。正是 `Isr.asm` 里 `_IRQ2` 注释的 "2ch drum sound" |
| 鼓点编号 | `instr & 0x7F`（`0x8585`） | 乐谱 `$28..$2D` 后跟 `$80..$93`（128…147）→ 鼓 0…19 |
| 鼓点表 | `T_SACM_MS01_DrumTable`(0x8045) | 表项 = **描述符指针**；描述符 4 个字 `sa, seg, ea, seg`（与曲子的资源表同格式） |
| 启动 | `0x8630` | 置 RAM `0x3D`（bit0=正在响，bit4 选哪个通道）并 `call F_SP_IRQ2_ON`(0x92C1) |
| 解码 | IRQ2 → `0x889B` | `([0x3D]>>2)&3` 选 4 个相位，每拍取一个 4 bit 半字节；ch0 用 `[0x37]/[0x42]/[0x44]`，ch1 用 `[0x3A]/[0x43]/[0x45]`；步长表 `0x8C09` |
| 输出/混音 | `0x893A..0x8941` | 鼓点样本写进 RAM **`0x41`**；FM 侧在 `0x8876` 做 `r4 = r4 + [0x41]` 才写 DAC —— **鼓点与 FM 的混合点就是 `[0x41]`** |

### 6.2 原来为什么没声

示例映像的 `T_SACM_MS01_DrumTable`(0x8045) 只有 **1 个占位项 `0xFA00`**，而 0xFA00
在那份映像里全是 0。鼓点路径其实一直在跑（`[0x3D]` 5 秒内被置位 28 次、
IRQ2 的解码相位也被走到），只是读到的数据全是 0 → 静音。所以缺的是**资源**，
不是代码。

### 6.3 补法

`work/mk_ms01_drums.py`：

1. 把 20 个 `MS01/DRUM/*.ADP` 原样放进 ROM——`.ADP` 就是 ROM 原始格式，
   061.dat 的 `0xD33D..0xF6BA` 里 20 个文件有 19 个与之逐字节相同；
2. 建 20 个描述符 + 20 项新鼓点表；
3. 把引擎里两处 `+ 0x8045` 的立即数（字地址 `0x8147`、`0x8588`）改成新表地址；
4. 输出 `outputs/emulator/ms01_image_drums.c`。

空间不够，于是**牺牲 LA1**：空闲区 `0xE414..0xFFF4` 只有 14274 字节，
20 个鼓点要 22378 字节，差 8104；LA1 是最大的一首（`0x957C..0xA8D3`，
9904 字节），正好补上。它的资源表项被改成指向一个只含 `0x3F`（`;Song ended`）
的单字乐谱，选到 LA1 会立即静音结束，而不是把鼓点数据当乐谱放噪音。

最终布局：ADPCM 数据从 `0x957C` 起铺到空闲区；描述符 `0xA888..0xFCC3`；
新鼓点表 `0xFCC7..0xFCDA`；静音字 `0xFCDB`；LA1 的结束谱 `0xFCDC`。
`--fit` 可切回"保留 12 首曲子、只装 15 个鼓点"的保守版本。

### 6.4 实测

鼓点分量 = 带鼓点渲染 − 不带鼓点渲染：

| 曲子 | 鼓点峰值 | 鼓点 RMS |
|---|---|---|
| WISH1 | 20912 | 4316 |
| DECK1 | 19328 | 4330 |
| **HK1** | 17920 | 2144 |
| ALA1 / LA1 / S31 / TW1 / 1231 | 13k～23k | 1.6k～2.4k |
| GREEN1 / PP1 / WINE1（60 秒窗口） | 10736 / 18240 / 12736 | 489 / 262 / 649 |
| ALAINS | 0 | 0（这首谱子本来就没有鼓点） |

踩过的坑：GREEN1 / PP1 / WINE1 的鼓点不在开头，前 8 秒是纯 FM；只按 8 秒窗口
对比会误判成"没有鼓点"。把窗口拉到 60 秒、并数 `[0x3D]` 被置位的次数之后，
三首都能看到鼓点（`[0x3D]` 每首被置位 2400～12500 次）。

HK1 的鼓点分量有清楚的打击包络（10 ms 峰值包络 `7440 4848 1440 1200 1200 912
720 … 0` 再下一击），间隔 ≈0.187 s，与音符网格一致。带鼓点整曲仍是 61.60 s、
峰值 32704、削顶 0 个。

顺带修了一个选曲 bug：以前是**每个采样点**都把 `_SongIndex` 钉成 N，例程因此认为
选曲变了而反复重头播；现在改成等固件跑到 `main`(0x933A) 时写一次（`-s N`），
`-p` 才保留旧的钉值行为。

## 7. 乐曲槽：ROM 只放鼓点，乐曲运行时载入

用户提的方案（ROM 里只留鼓点、乐曲由命令行给出、放不下就分段载入）能成立，
靠的是两条反汇编结论：

| 结论 | 证据 |
|---|---|
| 乐谱游标 `[0x0065]` **严格单调**，只 +1 | `0x85A4`：`r2 = [0x0065]; r2 += 1; [0x0065] = r2`，只在 0xFFFF 回绕时把 `[0x0066]`（bank 字段）`+= 0x400`；没有回跳 |
| 乐谱结束**不靠 EA**，靠乐谱自己的 `0x3F` | 读字节 `0x85B8` 只按 `[0x65]` 取值（`ds:[r1]`），推进靠 `0x85A4`，**全程没有任何和 EA 的比较** |

所以：

- ROM 里的 12 首曲子全删掉也没关系（引擎只通过资源表 `0x8009` 找曲子）；
- 腾出来的空间（`0x957C-0xFFF4`，27257 字）足够放**全部 20 个鼓点**（11189 字）
  **再加一个 15861 字（31.7 KB）的乐曲槽**——**不用再牺牲 LA1 了**；
- 分段载入就是对游标做滑动窗口（同 A1600 的做法）：游标接近已载入区尾部时，
  把"游标之后的尾巴"搬到槽首、改写 `[0x0065]`、再补一段。

实现与验证（`work/mk_ms01_lib.py` + `main_linux_ms01.c -DMS01_SLOT`）：

| 场景 | 结果 |
|---|---|
| HK1 整槽 vs 经典版（曲子烤在 ROM 里） | **逐字节一致**（993582 样本 / 1297 事件，2026-09-22 复测） |
| HK1 + 槽限 1024 字 | **逐字节一致** |
| HK1 + 槽限 256 字（1199 字的曲子，强制多次滑动） | **逐字节一致** |
| LA1 / GREEN1 / WINE1：整槽 vs 槽限 512 字 | 两两**逐字节一致** |

> 复测命令（经典版里 HK1 是第 5 首）：
> ```
> ./ms01play      ../ms01_songs/HK1.BIN -o a.wav
> ./ms01play-classic -s 5                -o b.wav
> ```
> 注：本报告早期版本写的 `985580 样本 / 1293 事件` 是"鼓点音调修好之前"的数；
> 修掉鼓点采样率后整曲变成 `993582 样本 / 1297 事件`（≈62.1 s），两个构建仍然逐字节一致。
>
> 另外 2026-09-22 给 `unsp.c` 修了三个只影响"整机模拟"的中断模型 bug
> （向量索引 `&10`、`retf` 误释放中断锁、FIQ 不能抢占 IRQ，见
> `outputs/emulator/README.md`）。这两个播放器自己发中断向量、从不调用
> `unsp_interrupt()`，走的是 `int_active==0` 的兼容分支，所以输出**逐字节不变**
> （已回归验证：A1600 播放器对同一个 `.a16` 的输出与修改前完全一致）。

顺带修掉的坑：滑动之前必须判断"文件是否已经全部载入"，否则曲子尾部会被搬空
（第一版就踩了这个，HK1 少了 0.19 秒、少一个事件，加上判断后逐字节一致）。

### 7.1 鼓点音调偏高（已修）

现象：鼓点节拍准确但音调高、像"低采样数据用高采样率播出来"。

原因：**鼓点的采样率不是 DAC 速率，而是 TimerB（IRQ2）的溢出率**——
鼓点通道每个 IRQ2 只取一个 4 bit 半字节（相位 `([0x3D]>>2)&3` 走 4 拍、第 4 拍才推进
`[0x37]`），而 IRQ2 挂的是 TimerB。示例固件写的是：

```
P_TimerB_Ctrl = 0x0003   ; 手册 6.4：source C = 011 = 8192 Hz
P_TimerB_Data = 0xFFFF   ; 周期 = 1 tick
⇒ 鼓点 8192 Hz
```

旧播放器图省事，按输出采样率 16 kHz 每个采样点都打一次 IRQ2，于是鼓点**快了 1.95 倍**
（音调高一个八度）；而节拍完全正常，因为触发来自乐谱、走的是 1 kHz 的 IRQ4。

修法：`timerb_rate()` 按 `P_TimerB_Ctrl` 的 source C 表 + `0x10000-P_TimerB_Data` 算速率
（读到这两个寄存器就重算），再用 Bresenham 累加器打 IRQ2。也可以用 `--irq2-rate N` 强制。

实测（第一个鼓点的鼓点分量，10% 衰减时间 / 频谱主峰）：

| 版本 | 衰减 | 主峰 |
|---|---|---|
| IRQ2 = 16 kHz（旧） | 70 ms | 740 Hz |
| IRQ2 = 8192 Hz（现在） | **140 ms** | **318 Hz** |

## 8. 复现命令

```bash
cd outputs/emulator
cc -O2 -o ms01play main_linux_ms01.c unsp.c ms01_image.c

./ms01play-classic -k -a -t 200 -e events.txt -o HK1.wav   # 完整 HK1 + 事件表
./ms01play -i 0 -t 20 -o bug.wav                   # 复现"只有一个长音"
./ms01play -s 0 -t 20 -o song0.wav                 # 第 0 首（WISH1）
./ms01play -v -o out.wav                           # 每 0.25 s 打印内核状态
```

`ms01_image.c` 由 `work/mk_ms01_image.py` 从 `MS01.S37` 生成；
反汇编用 `work/ms01_dis.py <十六进制入口> [条数]`。
