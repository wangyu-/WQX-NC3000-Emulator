# 061.dat 固件：启动流程与串口协议（实测 + 反汇编）

> 命令常量来自上位机头文件 `V6100_061.h`（"Communicate with 061 system command"），
> 固件侧的地址/分支来自对 061.dat 的反汇编，整条链路在 `work/fw_smoke.c`
> （宿主机 + 真实外设模型）里跑通并复现。

## 1. 开机握手（复位 → 主循环）

| 步骤 | 固件在做什么 | 上位机要做什么 |
|---|---|---|
| 1 | `0xCB9F` 复位入口 → 清 RAM → `call 0x8205`（C 运行时）→ `call 0xCB2B`（IO 初始化） | — |
| 2 | `call 0x823A` 握手例程：`call 0xCB0B`（UART 初始化 + `irq on`）后，在 **`0x823E..0x8245`** 自旋等环形缓冲里出现 16 位字 **`0x0ABB`** | 发 **`0xBB` 然后 `0x0A`**（= `DATA_LINK_CMD 0xbb0a`） |
| 3 | 收到后 `0x8246: r1 = 0xFABB; call 0xCFC8` → 从 UART 发两个字节 | 收 **`0xBB 0xFA`**（= `LINK_ACK_CMD 0xbbfa`） |
| 4 | 回到 `0x821F..0x8228`：循环 `call 0xCDC4` 从环形缓冲取字；`word == 0x0FCC` → 回 `0xCCFF` 并继续等，**其它任何字** → 跳 `0x8232` | 发一个"非 0x0FCC"的命令字，例如 **`0x99 0x00`**（`START_MS01_CMD`） |
| 5 | `0x8232` 主循环：`call 0xCE0D`（命令分发）→ `call 0xC5E5`（状态机）→ 循环 | 之后按协议发命令/数据 |

实测（宿主机 + 真实外设模型）：**72501 条指令**进入主循环，固件回 `0xBB 0xFA`。
握手字节必须在固件初始化**之后**发（固件在 `0xCB0E` 会清环形缓冲）。

### 字节顺序规则

UART 中断（`_IRQ7` → `0xC889` → `0xCC23`）把两个字节拼成一个 16 位字：

```
[0x0717] = (([0x0717] ror 8) & 0x00FF) | (byte << 8)
```

也就是 **先发的字节是低字节**。所以头文件里的 `0xbb0a`（"send 0bbh 0ah"）在固件里
被比较的值是 **0x0ABB**；`DEBUG_CMD 0xcc0f`（"send 0cch 0fh"）在固件里是 **0x0FCC**。

## 2. 主循环的命令分发

```
0xCE0D: r1 = [0x0000]                  ; 状态字
        若 (bit10 & bit15) 都置位 -> 走 0xCEC8（调试/更新模式）
0xCE17: call 0xCDB3                    ; 从环形缓冲取一个字（0 表示空）
        若为 0 -> retf
        高字节 -> r2
        低 4 位 -> 查表 0xCB72          ; ★ 命令表，用第一个字节的低 4 位索引
        pc = 表项
```

命令表 `0xCB72`（16 项）：

| 低位 | 处理 | 含义 |
|---|---|---|
| 0-3 | `0xCE24` | 忽略 |
| 4-8 | `0xCE26/0xCE2B/0xCE30/0xCE35/0xCE3A` | 调 `0xC562/0xC568/0xC56B/0xC56E/0xC571`（写 `[0x0001..0x0005]`，参数类） |
| **9** | **`0xCE3F`** | **`0x99 xx` 启动**：`r1 = 3/2/0/5/4/1` 按第二字节（`00`=MS01、`10`=S200、`20`=S480、`22`=S600-1、`21`=S600-2、其它=1），`call 0xC574` 写格式号 `[0x04CE]`，然后写 `P_DAC1=0`、`P_DAC_Ctrl=0x00A8`、TimerA 重载、`P_INT_Ctrl=0x2000` |
| A | `0xCE7B` | `0xAA xx` 组：再查表 `0xCB7F`（`00`=停止…`04`=暂停 `0xCF34`、`05`=恢复 `0xCF3F`） |
| B/C/E/F | `0xCF5A/0xCF89/0xCEB6/0xCF2A` | 其它控制 |
| D | `0xCE80` | `0xCC xx` 组（调试/测试/升级） |

对应的上位机命令（`V6100_061.h`，按"先发高字节"的顺序）：

```
0x99 0x00  START_MS01_CMD    0x99 0x10  START_S200_CMD   0x99 0x20  START_S480_CMD
0x99 0x21  START_S600_CMD    0x99 0x22  START_S600_CMD1  0x99 0x40  START_A1600_CMD
0x99 0x80..0x85  START_ENC10K..24K_CMD
0xAA 0x00  STOP_CMD    0xAA 0x01 SLEEP_CMD   0xAA 0x02 END_CMD   0xAA 0x03 END_ACK_CMD
0xAA 0x04  PAUSE_CMD   0xAA 0x05 RESUME_CMD
0xBB 0x0A  DATA_LINK_CMD  -> 应答 0xBB 0xFA  LINK_ACK_CMD
0xBB 0x0B  DATA_CHK_CMD   -> 应答 0xBB 0xFB(正常)/0xBB 0xFC(错)
0xCC 0x0F  DEBUG_CMD      -> 应答 0xCC 0xFF
0xCC 0x05  TEST_CMD       -> 应答 0xCC 0xF5
0xCC 0x0A  UPD_CMD        -> 应答 0xCC 0xFA      0xCC 0x0B UPDEND_CMD -> 0xCC 0xFB/0xFC
流包头（无应答）：0x11 TTS / 0x22 STREAM1 / 0x33 STREAM2 / 0x44 VOLUME
                  0x55 SPEED / 0x66 PITCH0 / 0x77 PITCH1 / 0x88 VOICE
常量：STREAM_CMD2_LEN = 0x0F（15 字节）
```

## 3. 输入引脚 / 硬件流控

发每个字节前固件会等在 `0xCFE0`：

```
CFE0: [P_Watchdog_Clear] = 1
CFE3: r1 = [P_IOB_Data] (0x7005)
CFE5: test r1, 0x04
CFE6: jne 0xCFE0          ; ★ 只要 IOB2 还是高就继续等
CFE7: retf
```

固件把 IOB2 配成**输入**（`P_IOB_Dir = 0xC400`），所以这一位必须由外部（或模型）拉低。
注意：读 `P_IOB_Data` 得到的是**引脚电平**，不是输出锁存——
`读取 = (锁存 & 方向) | (外部电平 & ~方向)`。模型里搞错这一点会让这个循环永远出不来。

## 4. 音频路径

- 音频中断：**TimerA FIQ**（`P_INT_Ctrl = 0x2000` = `FIQ_TMA`），入口 `0xC742`；
  定时器 `P_TimerA_Ctrl = 0x0030`（CKA = Fosc/2，CKB = 常量 1——注意 source B 的
  `110` 是"常量 1"，不是 source A 那种"常量 0 停表"）。
- 采样率 = `Fosc/2 / (0x10000 - P_TimerA_Data)`；出厂路径写 `0xF3FF`（8 kHz），
  切到 MS01 格式后写 `0xFE7F`（≈63.8 kHz，说明那个分支是给"高速取样/编码"用的）。
- DAC 是**无符号**的（`0x8000` = 中点），I2S 要用有符号 PCM，所以推环前减 `0x8000`。
- **FIQ 不是一直开着的**：`0xC546` 只在状态字 `[0x0000]` 的 bit11 (`0x0800`) 置位时才
  `fiq on`。这颗固件是**流式解码器**——只有真的有数据流要放时才开音频中断，
  静音时 I2S 上就是静音流。

## 5. 数据流的包格式（已逆完）

固件里没有曲子（061.dat 只有 A1600/S200 内核 + 鼓点，没有 MS01 内核和乐谱），
放音必须由上位机把压缩数据流喂进来。包头的分帧在 UART 中断那条路上：

```
0xCC23: r2 = (byte & 0x38) << 4 | [0x0714]      ; 累积一个"头"
        test r2, 0x8000
        0 -> 0xCC31（两字节拼字：0x0ABB 握手 / 0x0BBB 校验…）
        1 -> r3 = r2 & 7 ; pc = 表[0xCB89][r3]   ; 8 个分支
```

表 `0xCB89`：`0:CC45 1:CC54 2:CC63 3:CC7A 4:CC8F 5:CCA6 6:CCBB 7:CCC5`，
其中 `0xCC54` 已经把"高字节 + `[0x0717]`"拼成字推进环形缓冲（`call 0xCDDE`）。
### 5.1 包类型：`高位半字节 == 低位半字节` 的字节是"包头"

状态 0（`[0x0714]` 的 bit15 置位、低 3 位 = 0）时，`0xCC45` 做：

```
CC45: r3 = byte >> 4 ; r4 = byte & 0x0F
      if (r3 != r4) r3 = 0            ; 不等于就用表项 0
      r3 += 0xCB8F ; pc = [r3]        ; 表 0xCB8F
```

表 `0xCB8F`：`0:CCBB 1:CCC5 2:CCCC 3:CCD3 4..F:CCE0`

| 包头 | 分支 | 含义 |
|---|---|---|
| `0x11` | `0xCCC5` | TTS 类：一个长度字节 + 那么长的负载（去 `0xCDCE`） |
| `0x22` | `0xCCCC` | STREAM_CMD1：一个长度字节 + 负载（`0xCC63`→`0xCC7A`，打包用 `0xCD71`） |
| `0x33` | `0xCCD3` | **STREAM_CMD2：固定 15 字节负载**（`[0x0716] = 0x0F` = 头文件里的 `STREAM_CMD2_LEN`） |
| `0x44`…`0xFF` | `0xCCE0` | 当作"两字节值"的低字节：存进 `[0x0717]`，下一个字节来齐后拼成 16 位字推进命令环形缓冲 |
| 其它 | `0xCCBB` | 置 `[0x0727]` bit6，走收尾 |

`0x44`…`0x88` 正好就是头文件里的 `VOLUME_CMD/SPEED_CMD/PITCH0/PITCH1/VOICE_CMD`——
主循环按命令字低 4 位分发到 `0xC562/0xC568/0xC56B/0xC56E/0xC571`，分别写
`[0x0001]`…`[0x0005]` ✓。

### 5.2 负载去处：RAM `0x0006` 起的环形缓冲（280 字 = 560 字节）

15 字节负载先攒到暂存区 `0x0718`，再由 `0xCD71` **按 2 字节/字**打进环形缓冲：

```
CD71: r3 = [0x0728]          ; 环形缓冲写指针（绝对地址）
      r4 = [0x0727]          ; bit0 = 半个字未填满
      bp = [0x0729]          ; 剩余配额（按"字"计）
      循环：从 0x0718 取字节 → [r3] = 低字节 / [r3++] = (高字节<<8)|低字节
            每打包 1 个字 [0x0729] -= 1
CFA 结束：配额到 0 → [0x0727] |= 2   ; "一整块就绪"
```

实测（早期用 `work/fw_stream2.c` 发一包可识别的 15 字节；当时打包器已经被
`0xCD42` 重新装填到 `0x0006`）：

```
0006: 2211 4433 6655 8877 AA99 CCBB EEDD 00FF      ← 负载原样落在 RAM 0x0006
[0x04C0]=0006  [0x04C8]=0006  [0x0728]=0006  [0x0729]=0118
```

⚠️ 这个"落到 `0x0006`"是**有条件的**：`0xCD42` 只有在
`0xCD02 → 0xCD18` 等到字节解析器回到状态 0 之后才会执行。
如果宿主一直在发字节，`0xCD18` 就出不来，`[0x0728]` 会停在复位值 `0x072A`，
这时负载只堆在暂存区 `0x0718..`、打包器写到 `0x072A` 起（也就是**别的格式**
用的那块），环 `0x0006` 一直是空的。用 `work/fw_trace.c` 监视 `0x0006`
可以明确看到这一点（"一直发"的几种节流模式下它**一次都没被写过**）。
这正好说明 5.4.2 那条"宿主必须在块边界上停一下"是**协议要求**，不是优化。

#### 5.2.1 三个缓冲的区别（早期分析在这里踩过坑）

| 缓冲区 | 地址 | 大小 | 谁写 | 谁读 |
|---|---|---|---|---|
| **解码器输入环** | RAM `0x0006..0x011D` | 280 字 = 560 字节 | 打包器 `0xCD71`（2 字节/字） | A1600 内核，游标 `[0x04C0]` |
| **字节暂存区** | RAM `0x0718..0x0726` | 15 字（**一个字节一个字**） | 字节解析器 `0xCC7A` | 打包器 `0xCD71` / 裸字搬运 `0xCDCE` |
| **命令环** | RAM `0x075B..0x0762` | 8 字（一个 16 位命令字） | `0xCDDE` | 命令分发 `0xCE0D`，指针 `[0x0763]/[0x0764]` |

另外还有一套**给别的格式用的**暂存区从 RAM `0x072A` 开始，写指针也是 `[0x0728]`
（`0xCD1E`/`0xCD33` 把它初始化成 `0x072A`，`0xCDCE` 用 `[0x075A]` 当写指针）。
`0x072A` 只在"非 A1600 流"下有效——**A1600 播放监督在 `0xC46D` 会调用 `0xCB4D`
把打包器的写指针重新指到 `[0x04C0]`**，所以 A1600 的负载确实落在 `0x0006` 起的环里。
（早期版本把 `0x072A` 误读成"6"，以为写指针会"绕回 6"，其实是 `0xCB4D` 做的**环内搬移**。）

`0xCB4D` 本身是一个"把环压实"的例程：

```
CB4D: r1 = [0x04C0]
      if (r1 == 0x0006) -> 什么都不做
      if (r1 >= 0x011E) r1 = 0x0006      ; 指针越界就回到环首
      else  把 [0x04C0..0x011E) 这段字搬到 0x0006 起（memmove 到环首）
CB64: [0x04C8] = [0x04C0]
      r2 = 0x011E - [0x04C0]
      call 0xCD42                        ; ★ 给打包器重新装填：写指针=读指针，配额=剩余字数
      [0x04C0] = 0x0006
```

所以每个"块"的边界不是固定地址，而是**当前读指针**：`0xCD42` 之后
`[0x0728] = [0x04C0]`、`[0x0729] = 0x011E - [0x04C0]`（按字计的配额）。
配额减到 0 时 `0xCD71` 置 `[0x0727]` bit1 = **"整块就绪"**。

也就是：

- **环形缓冲 = RAM `0x0006`..`0x011D`（280 字 = 560 字节比特流）**，`0x011E` 是排他末尾；
- **写指针 `[0x0728]`、读指针 `[0x04C0]`、可用末尾 `[0x04C8]` 都是这个区域里的绝对地址**；
- **配额 `[0x0729]` 按"字"递减**，从 `0x118`(=280) 开始，到 0 表示这一块收满；
- 负载内容就是 **A1600 比特流本身**（从 `.a16` 的参数字 `xx 80` 开始；含不含前 4 字节长度见 5.4）。

### 5.3 启动：等一整块 → 初始化 → 点亮"流运行中"

`0x99 0x40`（START_A1600）最后会 `call 0xC437`，那就是**播放监督**：

```
C46F: 循环: [P_Watchdog_Clear]=1 ; call 0xCE0D（跑命令分发）
            if ([0x0000] & 0x0080) 跳出
            call 0xCDAF ; if (r1==0) 继续循环      ; 查 [0x0727] bit1 = "整块就绪"
C486: call 0xC8AC            ; A1600 初始化（解析流头：参数字、码率…）
C49E: [0x04C8] = [0x0728]    ; 把"可用末尾"对齐到写指针
C4A2: call 0xC8C6            ; 按格式号分派音频任务
C4AC: 清输出环 0x019F..0x029E，[0x04C1] = 0x019F
C4E7: [0x0000] |= 0x3300            ; ★ bit8/bit9 = "解码触发 + 输出环相位"
C4ED: fiq on                        ; ★ 到这里音频 FIQ 才打开
```

⚠️ 订正：`[0x0000] |= 0x0800`（bit11 = "直接播放中"）、`[P_TimerA_Data] = 0xFCFF`
（32 kHz）、`[0x04C7] = 1`、`[0x04C0] = [0x04C8] = 0x0006` 这几条属于**另一条启动路径
`0x4EF`**（`0x99` 的参数字节 ≥ 0x80 时走它，`0xCE6E: call 0xC4EF`）。
`0x99 0x40`（START_A1600）参数是 0x40 < 0x80，走的是**流式监督** `0xC437`：
它先 `call 0xC546`（此时 bit11 还是 0，于是把 `[0x0000]` 整个清零），
等第一块就绪后初始化、清输出环、最后 `[0x0000] |= 0x3300` + `fiq on` 返回主循环，
由主循环的 `0xC657` 管家例程继续推进解码。**bit11 在 A1600 流式路径上始终是 0**
（早期把它当"流运行中"指示器是错的）。

实测（`work/fw_trace.c` / `outputs/emulator/fwstream`）：

- 喂 `t09_a.a16` 时环形缓冲会稳定填满：`[0x0728]=0x011E`、`[0x0729]=0`、
  `[0x0727]=0x0002`（整块就绪）；
- 启动代码确实跑过：`[0x04C1]=0x019F`（输出环基址）、`TimerA=0xFCFF`（≈32 kHz）、
  `[0x0000]=0x3190`（bit4 + bit7 + bit8 + bit12 + bit13 ✓）都能在 RAM 里看到；
- 音频 FIQ 真的在跑、真的在写 DAC：`P_DAC2` 的写入次数与 FIQ 次数一一对应
  （1 样本 / 1 次 TimerA FIQ），录出来是 RMS≈10544 的真声音。

⚠️ 早期版本把"每收一个字节栈掉 2 个字"当成固件自己的问题，实际是模拟器
`retf` 误释放中断锁导致的（见第 6 章第 2 条）。修好后最低 SP 稳定在 `0x07AF` 附近，
离环形缓冲（`0x011D`）很远，`[0x0000]` 也不再被踩。

### 5.4 流控与收尾

#### 5.4.1 IOB14 的真实含义

`P_IOB_Buffer` 的 bit14 在固件里是"**字节解析器还在忙**"的指示，同时也是给上位机的节拍信号：

- `0xCC4B`：每收到一个**包头**就把 IOB14 置高（`r4 |= 0x4000; [0x7006] = r4`）——
  表示"我正在收一包"；
- `0xCCE9`（`sub_CCE9`）：收尾时如果 `[0x0727]` bit2 没置位就清低 IOB14；
- `0xCD02`：`[0x0728]` 那种"重新装填"的场合先置高 IOB14、延时 `0x320` 个循环，
  再用 `0xCD18` **等字节解析器回到状态 0**（`[0x0714] & 7 == 0`）才返回。

所以 IOB14 不是简单的一根"要数据"线，而是"解析器忙碌/已空闲"的观察点。
早期把它当成"发下一块"的握手，方向搞反了。

#### 5.4.2 固件自己在主循环里管流控（关键）

主循环是 `0x8232: 喂狗 → call 0xCE0D（命令分发）→ call 0xC5E5 → 循环`。
`0xC5E5` 按状态字分路：

```
C5E5: r1 = [0x0000]
      if (r1 & 0x0800) -> 0xC5EC     ; bit11 = "直接播放中"
      else             -> 0xC657     ; ★ 流式播放的管家例程
```

`0xC657` 这段就是流控本体（`0xC657..0xC69F`）：

```
C657: if (!(r1 & 0x0010)) retf        ; bit4："音频任务可以跑"
C65A: if (!(r1 & 0x0100)) retf        ; bit8：一次性触发位
C65E: [0x0000] &= ~0x0100             ; 清掉 bit8（表示这一拍已处理）
C662: if ([0x04CE] == 2 || 3) call 0xC8F8   ; 格式 2/3 的解码推进
      else                    call 0xC035   ; ★ 格式 1（A1600）的解码推进
C67B: [0x0000] ^= 0x0200              ; 翻转 bit9（输出环双缓冲相位）
C682: r1 = 0x011E - [0x0728] + [0x04C0]      ; ★ 环内空闲字数
C688: if (r1 <= 0x20) goto C694
C68C: if (!([0x0727] & 2)) goto C694          ; 整块就绪？
C690: call 0xC6A0 ; call 0xCB4D              ; ★ 压实 + 重新装填打包器
C694: if ([0x0000] & 0x0080) {                ; bit7 = 解码门
C699:     call 0xC6A0 ; [0x04C8] = [0x0728]   ; 把"可用末尾"推到写指针
      }
```

**结论**：上位机不需要（也不应该）自己算块边界——固件在空闲字数超过 `0x20`
且"整块就绪"时自己调用 `0xCB4D` 重新装填。上位机只要做到两条：

1. **不要超过 `0xCD71` 的配额**（否则会覆盖暂存区，见 5.4.3）；
2. **不要在解析器还在收包时插命令**（`0xAA 0x02` 之类必须等在包边界上）。

#### 5.4.3 包头长度必须让"块"对齐

`0xCD71` 是"2 字节 = 1 字"的打包器，它的相位记在 `[0x0727]` bit0，跨包保留；
配额记在 `[0x0729]`（按字）。两个必然后果：

- **包负载最好是偶数长度**。`0x33`（固定 15 字节）跨包时相位翻转，
  最后一个字节会以"半个字"的形式挂在环里等下一包的第一个字节——本身合法，
  但一旦这个半字正好卡在配额边界上，`0xCD71` 就会提前退出，把剩余字节搬回暂存区
  而**不更新暂存计数 `[0x0715]`**，下一个包就会从 `0x0718+[0x0715]` 继续写，
  越过 `0x0726` 踩到 `[0x0727]/[0x0728]/[0x0729]`。这就是早期"多发一拍就把 RAM 写坏"的真正原因。
- 因此"用 15 字节包凑满 560 字节"是**凑不出来的**（560 = 37×15 + 5）。
  560 能被 14 整除（40×14）也能被 20 整除（28×20），所以实际可用的对齐方式是
  **`0x22`（STREAM_CMD1，带长度字节）用 14 字节负载**，正好 40 包 = 280 字 = 一个整块。

实测：用 `0x22 + 14B` 发第一包后 `[0x0728]` 从 `6` 走到 `0xD`、`[0x0729]` 从 `0x118`
减到 `0x111`（= 280-7），相位 `[0x0727]` bit0 回到 0——完全符合上面的模型。

#### 5.4.4 收尾

- 流放完时固件在 `0xC946` 发 `0xAA 0x00`（= `STOP_CMD`）给上位机，作为"放完了"的通知；
- 上位机也可以主动发 `0xAA 0x00`：`0xCE80` 会 `[0x04CE] = 0`（回到空闲格式）、
  调 `0xC546` 收拾状态、`call 0xCD33` 复位打包器，再回一个 `0xAA`。

### 5.5 解码门 bit7 与 `END_CMD`（订正 + 第二轮补完）

`[0x0000]` 的 bit7 是流式解码的使能位，两处置位：

| 位置 | 触发 |
|---|---|
| `0xC918`（format 4 / fft64 分支） | 固件自己置位 |
| `0xCF2D`（`0xAA,0x02` 的处理器 = **`END_CMD`**） | 主机发 `0xAA,0x02` 时置位 |

`0xAA` 的命令表在 `0xCB7F`，用**第二个字节**索引
（`0xCE7B: r2 = r2 + 0xCB7F; pc = [r2]`，其中 `r2` 是命令字的高字节）：

| 第二字节 | 处理 | 含义 |
|---|---|---|
| `0x00` | `0xCE80` | **STOP**：`[0x04CE]=0`、收拾状态、复位打包器、回 `0xAA` |
| `0x01` | `0xCEB6` | `[0x0797]=1`（速率/模式） |
| `0x02` | `0xCF2A` | **END**：`[0x0000] |= 0x0080`（解码门） |
| `0x03` | `0xCF13` | END_ACK：bit10 未置位则置 bit7+bit14，否则回 `0xAA` |
| `0x04` | `0xCF34` | PAUSE（清 `0xC577`） |
| `0x05` | `0xCF3F` | RESUME（`0xC583`） |
| `0x06` | `0xCEB0` | `[0x0797]=0` |
| `0x07` | `0xCF4A` | `P_IOB_Buffer \|= 0x8000` |

⚠️ 订正：早期版本把 `0xC8F8` 当成"A1600 解码器"、把 `bit7` 当成"A1600 解码门"。
实际 `0xC8F8` 只服务 **format 2/3**；**format 1（也就是 `0x99 0x40` = START_A1600）
走的是 `0xC035`**（见 5.4.2 的 `C662`）。所以 `0xAA 0x02` 对 A1600 的作用是
置状态字的 bit7，而 `bit7` 在 `0xC694` 那段里被用来把 `[0x04C8]` 推到写指针——
也就是"**让解码器可以看到新装进来的数据**"。它仍然是必须发的，但作用点是
`0xC694`，不是 `0xC8F8` 里的那道门。

#### 5.5.1 bit7 同时管两件事 —— 所以 `END_CMD` 的时机很关键

`0xC694` 那段（主循环管家 `0xC657` 的尾巴）在 **bit7 置位时**做两件事：

```
C694: if (!([0x0000] & 0x0080)) retf        ; bit7 是门
C699: call 0xC6A0
      C6A0: r3 = [0x0728] - [0x04C8]        ; 这一轮新到了多少字
            r3 += [0x04C3] ; [0x04C4] += carry
            [0x04C3]:[0x04C4] = r3          ; ★ 抬高解码器的"可解码量"阈值
C69D: [0x04C8] = [0x0728]                   ; ★ 把"可用末尾"推到写指针
```

而 `0xC8F8` 的解码推进是"累加器 `[0x04C5]:[0x04C6]` 超过阈值
`[0x04C3]:[0x04C4]` 就算把现有数据解完了"，那时再看 bit7 决定收尾还是继续等。
于是：

| `END_CMD` 发送时机 | 结果（实测） |
|---|---|
| **只在文件末尾发** | 整个流期间 bit7 = 0 → `[0x04C8]` 永远是启动时那个值 → 解码器吃到 `[0x04C0] == [0x04C8]` 就停住（上一轮"卡在中途"的直接原因） |
| **START 之后立刻发**（还没发数据） | 阈值为 0 → 第一次解码就"已解完" → `0xC932` 置 bit10、清 bit12（音频立刻关），而且 `fiq on` 都白搭。实测：2504 次 FIQ 只写出 2 个 DAC 样本；但**环里确实拿到了正确的数据**（`8007 7899 7686 5765 7777 EBAE C56F 8BE9`，正是 `.a16` 去掉前 4 字节后的头 8 个字） |
| **第一块数据发完之后发** | ✅ 阈值随数据增长、`[0x04C8]` 跟着 `[0x0728]` 走、bit12 保持、FIQ 持续写 DAC |

所以正确用法是：`0x99 0x40`(START) → 发第一块（40 包 × 14 字节 = 280 字）
→ `0xAA 0x02`(END_CMD) → **继续发后面的块**。这样 bit7 一直是 1，
每轮管家例程都把新到的字数加进阈值、并把可用末尾推上去。

### 5.6 现在的状态（诚实版）

**已经逆完并逐条实测的**：

1. 握手、命令表、命令字节序、`0x99/0xAA/0xBB/0xCC` 各命令的含义；
2. 包分帧：`0x11/0x22/0x33/0x44..0xFF` 的含义，`STREAM_CMD1` 带长度字节、
   `STREAM_CMD2` 固定 15 字节负载，命令字 = `(第二字节 << 8) | 包头字节`；
3. 三个缓冲区（5.2.1）：解码输入环 `0x0006..0x011D`(280 字)、
   **一个字节一个字的**字节暂存区 `0x0718..0x0726`、命令环 `0x075B..0x0762`；
   写指针 `[0x0728]`、读指针 `[0x04C0]`、可用末尾 `[0x04C8]`、配额 `[0x0729]`（按字）、
   相位 `[0x0727]` bit0、忙位 bit1/bit2；
4. 打包：`0xCD71` = 2 字节/字，跨包保留相位；配额到 0 置"整块就绪"；
   配额边界上的剩余字节由 `0xCDA8` 搬回暂存区（但**不会**更新 `[0x0715]`，
   所以包长度必须让块对齐，见 5.4.3）；
5. 重新装填：`0xC46D → 0xCB4D`（把环压实到 `0x0006`）→ `0xCD42`
   （写指针 = 读指针，配额 = `0x011E - 读指针`）；主循环 `0xC682` 也会按同样的条件自动重装；
6. 启动：块满 → 播放监督 `0xC437` → 格式相关初始化 → `TimerA = 0xFCFF`(≈32 kHz)、
   输出环 `0x019F`（双缓冲，相位 bit9）、`fiq on`；
7. 状态字 `[0x0000]` 的位含义：bit4 = 音频任务可跑、bit7 = 解码门（`0xAA 0x02`）、
   bit8 = 解码触发（管家例程清它）、bit9 = 输出环相位、bit11 = "直接播放中"
   （`0xC5E5` 用它选 `0xC657` 流式管家 vs `0xC5EC` 直接播放）、bit12 = 音频输出使能；
8. 收尾：`0xAA 0x00` = STOP（`[0x04CE]=0`、复位打包器），固件放完时自己也会发。

**能跑通的**（`outputs/emulator/main_linux_fwstream.c`，宿主机 + 完整外设模型）：

```

  ★ 固件把流打进环、跑它自己的解码器、从 P_DAC2 输出真声音

        129884 个 DAC 样本（4.06 s）、uart rx drops = 0、
        [0x04C0] 从头走到尾再绕回 0x0006、[0x04C8] 跟着 [0x0728]、

  录音：outputs/pcm/fwstream_t09a.wav（4.06 s / 129884 样本 / 31958 Hz）
```

#### 5.6.1 这一轮新查清的三条协议规则

1. **`END_CMD` 要在"第一块数据之后"发**（见 5.5.1）—— 这是整件事的关键。
2. **宿主绝不能在一个包的中间停住**：固件重新装填环时要走
   `0xCB4D → 0xCD42 → 0xCD02 → 0xCD18`，而 `0xCD18` 是"等字节解析器回到状态 0"，
   半截包永远到不了状态 0 → 宿主等固件、固件等宿主，死锁。
   实测死锁现场：`[0x0714] = 0x8003`（状态 3）、`[0x0715] < [0x0716]`、
   接收 FIFO 空、`enable_irq = 1`、`d = 0/0/0`。
3. **`0x22` + 14 字节才是能正好填满一块的形式**（40 包 = 280 字 = 配额
   `0x011E-0x0006`），且每包都落在整字边界；`0x33`(15 字节)会留半个字，
   在配额边界上还会触发 5.4.3 说的 `[0x0715]` 陈旧 bug。

**结果：对上了。**

```

  fw   frame 0: FFFF 0004 FFF3 FFF1 FFF7 FFFE 000A 002F    ✓ 完全一致
  ref  frame 1: 01B5 070D 01EA 01F6 F91B FB28 FBAA F527
  fw   frame 1: 01B5 070D 01EA 01F6 F91B FB28 FBAA F527    ✓ 完全一致
```

也就是说 061.dat 现在能**按自己的串口流协议收下 `.a16`、用自己的解码器解出
和参考完全一致的 8 kHz PCM、并从 P_DAC2 出声**。最后卡住的那一处不是协议，
而是模拟器 CPU 核的第 5 个 bug（见第 6 章第 5 条：中断入口不该动 `FIR_MOV`）。

## 6. 这次为了跑通固件修掉的五个核心 bug

前三个在 `outputs/emulator/unsp.c` / `unsp.h` 里，是"固件永远跑不过 100 个字节"
的真正原因；第四个在 `spce061a.c`（定时器）。它们**不影响**
`main_linux_ms01.c` / `main_linux.c` 那两个独立播放器
（它们自己发向量、从不调用 `unsp_interrupt()`，所以走的是兼容分支；
A1600 播放器修前修后逐字节一致，已回归验证）。

1. **中断向量索引写成十进制 `10`**：`cpu->vec_area[index & 10]`。
   `10` 是 `0b1010`，`& 10` 会把 bit0 抹掉，于是 `FIQ(1)` 落到 `vec_area[0]`（BREAK）、
   `IRQ0(3)` 落到 `vec_area[2]`（RESET）……实测现象就是"TimerA 音频 FIQ 跑的是 UART 中断服务程序"。
   改成 `index & 15`。
2. **`retf` 无条件释放中断锁**：061.dat 的 UART 中断处理程序
   （`0xC889: push r1,bp` → `call 0xCC23` 解析 → `0xC893: pop` → `0xC894: reti`）
   里面的 `retf` 只是**从子程序返回**，但旧代码把它当成"中断结束"，
   于是电平触发的 UART 中断立刻重入，**每收一个字节漏 2 个字栈**；
   栈从 `0x07FF` 一路走低，最后踩进 `0x0713..0x0764` 这一片
   （字节暂存区、打包器状态、命令环）和环缓冲 `0x0006..`，
   固件就"先能出声、然后莫名复位/PC 跑飞"。
   现在用 `int_depth` / `int_sp[]` 记录每层中断的进入栈指针，
   `retf` 只有在栈回到该层进入点时才算这一层结束（`reti` 按层弹）。
3. **FIQ 不能抢占 IRQ**：旧代码里"只要在中断里就拒绝一切中断"，
   而 32 kHz 的音频 FIQ 几乎总是撞在 UART 中断里，于是 **FIQ 被整片丢弃**，
   连一个 DAC 样本都写不出来（实测 `fiq entries=0`）。
   真芯片上 FIQ 优先于 IRQ：现在 FIQ 可以抢占 IRQ 处理程序，IRQ 仍然互斥。

4. **TimerA/TimerB 在"还没溢出"那条分支上把计数写反了**：
   `m->timer_a_count = count - ticks;`。溢出判断用的是 `period = 0x10000 - count`
   （**向上**计数到 0x10000 溢出），所以这条分支必须是 `count + ticks`。
   写反之后计数器一路往下跑、预加载值 `0xFCFF` 再也不回来、"剩余周期"越算越大，
   音频 FIQ 从每 1538 条指令一次变成**几百万条指令一次**（实测 60M 条指令里
   只触发个位数到十几次）。修好后 **60M 条指令里 FIQ 触发 38856 次 ≈
   每 1544 条一次**，正好等于 `Fosc/2 / (0x10000-0xFCFF) = 32 kHz`；
   于是可以**用芯片自己的 TimerA 驱动音频**，不用宿主去猜节奏。

5. **中断入口不该动 `FIR_MOV`**（`unsp.c` 的 `take_interrupt`）。旧代码在每层中断
   入口都写 `cpu->fir_mov = 1`，而 `FIR_MOV` 是"`MR = [Rx]*[Ry]` 内积之后
   **自动搬移输入缓冲**"的开关：061.dat 自己在启动时明确关掉它
   （`0xC41F: fir_mov off`，就在 `sub_C41D` 里），而 A1600 内核有 **4 条**
   这种内积（`0xBA9A/0xBAB0/0xBAF3/0xBB1D`），必须在关掉的状态下跑。
   旧代码每来一次中断就把它打开，内核的滤波器历史被悄悄搬移 ——
   于是"输入字节一致、内核状态一致、模式一致，波形却完全不同"
   （frame 0 出来是 `FFFF 0000 0007 FFFD ...` 而不是 `FFFF 0004 FFF3 FFF1 ...`）。
   去掉这一行后逐帧完全一致。独立播放器从不进中断，所以它们一直是好的。

另外 `spce061a.c` 的 UART 中断是**电平触发**（FIFO 非空 + `P_UART_Command1` b7），
所以宿主必须每指令调用一次 `spce_poll_irq()`；这一点早先已经修好，这次没有再动。
