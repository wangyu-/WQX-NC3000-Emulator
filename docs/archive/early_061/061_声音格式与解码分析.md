## 1. 方法：库指纹匹配

SACM 的 `.lib` 是 Sunplus 目标库（头部 `SunplusLib 1.0`），内部由 15 个 `SunplusObj` 模块组成，每个模块带**完整符号名**：

```
module  0  A1600_Kernel.asm        module  4  DVR1600_Kernel_v5.2.1.asm
module  1  fft64.asm               module  5  fft64.asm
module  2  SACM_A1600_Decode.asm   module  6  SACM_DVR1600_Decode.asm
module  3  SACM_A1600_API.asm      module  7  SACM_DVR1600_API.asm
module  8  S720_Kernel.asm  9 SACM_S720_Decode.asm  10 SACM_S720_API.asm
module 11  MS01_kernel.asm 12 Drum.asm 13 SACM_MS01_Decode.asm 14 SACM_MS01_API.asm
```

每个模块 = 模块头 + 9 个段描述符（CODE/DATA/TEXT/IRAM/…，含段大小）+ 符号表 + 段数据。我用两种指纹把库和固件对齐：

1. **结构指纹**：把指令文本归一化（掩掉立即数/地址）后做长序列匹配 —— 能发现"同一编译版本"的代码；
2. **字节指纹**：锚定 8 字完全相同序列再容错延伸（允许 ~12% 字不同，即重定位过的绝对地址）—— 判定"真的是同一段代码"。

> 这一步很关键：结构指纹会把**共享模板**的不同编解码器判成同一个（我一开始就被 S200 误报过），字节指纹才能定案。

## 2. 固件里到底有哪些格式

### 2.1 字节级确认存在的代码

| 库/模块 | 固件地址 | 字节相同字数 |
|---|---|---|
| **SACM A1600 V4.1.5 / D10 的 `A1600_Kernel.asm`** | `0xB626-0xC0C3` 一带 | 1253 / **1313** |
| **`fft64.asm`（64 点 FFT，A1600 专用）** | `0xCFE8-0xD1E0` | **505** |
| SACM_DVR1600 的 `DVR1600_Kernel_v5.2.1.asm`（与 A1600 同一算法内核） | 同上 `0xBBA3-0xC0C3` | 1313 |
| SACM_S200 V4.1.4 的 `SACM_S200_Kernel.asm` | `0x849C-0x84F0`、`0x8824-0x8A5C` | **654** |

结论：**固件里同时链接了两套语音编解码内核（A1600 系 + S200 系）以及 A1600 的 FFT**。`SACM_A1600_Decode/API`、`SACM_MS01_*`、`SACM_S720_*` 的**包装层代码不在固件里**（产品自己实现了缓冲/播放层）。

### 2.2 固件里嵌入的声音资源

- **MS01 鼓点整套**：GPCE063 包 `MS01/DRUM/*.ADP` 里 20 个鼓点有 **19 个字节级完整嵌入**固件：

  | 鼓点 | ROM 地址 | 鼓点 | ROM 地址 |
  |---|---|---|---|
  | OHT1 | 0xD33D | HAP1 | 0xF2CC |
  | LT | 0xD874 | HT1 | 0xF39D |
  | CYM1 | 0xDB72 | BD1 | 0xF469 |
  | HTM | 0xDE66 | CHT1 | 0xF52B |
  | LFT | 0xE138 | CBL | 0xF5BC |
  | HFT | 0xE3F4 | PHT1 | 0xF643 |
  | LBQ | 0xE6A4 | CBH | 0xF6BA |
  | LB | 0xE8D4 | SD1 | 0xF0F2 |
  | JB1 | 0xEB04 | HB | 0xED16 |
  | HBQ | 0xEF04 | CC | **未出现**（唯一缺失，可能是镲片太大被裁掉） |

- 配套的**鼓点指针表**在 ROM `0xCA97-0xCAE1`（19 个鼓点的起始地址 + 长度/属性字段），说明固件自带一套鼓点播放引擎。
- SDK 里的 `.a16` 语音样本、MS01 的歌曲文件（`.POP/.BIN`）**没有**出现在固件中 —— 产品用的是自己的曲库。

### 2.3 产品的音频引擎（格式分派）

固件在 `0xC8C6-0xC8E8` 按 RAM `[0x04CE]` 的"格式 ID"分派到不同解码器：

| ID | 解码函数 | 归属 |
|---|---|---|
| 0 | `0x9EA3` | 产品自带（PCM/其它） |
| **1** | **`0xB5D6` / `0xB5E6`** | **A1600 内核** |
| **2** | **`0x826F` / `0x82C6`** | **S200 内核** |
| 3 | `0xAADD` | 产品自带 |
| 4 | `0xD1BF`（fft64 入口） | A1600 的另一条路径 |
| 5 | `0x9EA3`（带参数 0x14） | 产品自带 |

解码服务例程在 `0xC8FE-0xC9D0`：维护环形缓冲（写指针 `[0x04C5]/[0x04C6]`、边界 `[0x04C3]/[0x04C4]`、每次解码产出的样本数 `[0x04C7]`），按需调用对应解码器，并用 `P_Watchdog_Clear` 喂狗。

## 3. `.a16` 容器格式（实测）

```
偏移 0..3 : u32  数据长度（= 文件长度 - 4）
偏移 4..5 : u16  参数：低字节 - 4 = 码率/模式索引
偏移 6... : 压缩比特流（每帧 256 bit = 32 字节；128 个样本/帧；2 bit/样本 @ 8 kHz = 16 kbps）
```

实测：`t09_a.a16`（4582 B）：参数 `0x8007` → 低字节 7 → 索引 3；`(4576 字节 ÷ 32) = 143 帧`；`143 × 128 = 18304 样本 = 2.29 s @8 kHz`，与文件长度完全自洽。

> 注：SACM_D10 文档里 `BITRATE_10K..24K` 常数标注为"DVR1600 Only"，即 **A1600 播放时码率由文件头自带**，与上面实测一致。

## 4. A1600 解码器在固件里的接口（逆向结果）

| 入口 | 作用 | 关键变量 |
|---|---|---|
| `0xB5D4` | 清内核工作区（0x043D-0x04BC） | — |
| `0xB5D6` | 初始化：解析文件头、选参数表 | `[0x04C0]` 输入流指针；结果 `[0x0793]`=码率索引、`[0x043C]`=参数表指针、`[0x047F]`=首数据字 |
| `0xB5E6` | **解码一帧**（产品按需调用） | 输出/工作缓冲 `[0x0439]` = RAM `0x011E`，128 个字/帧 |
| `0xB5CB` / `0xB5D0` | 模式设置（`[0x043A]`/`[0x043B]`） | — |
| `0xB88F` | 帧处理：`0xB9C6`（解包→谱）→ `0xBA90`（合成） | 参数表 `0xBD83`、系数表 `0xBE83/0xBC83`、FFT `0xCFE8/0xD113` |

解码数据流：`[0x04C0]` 逐字读入 → 比特解包（`0xB71D`/`0xB745` 等）→ 频域重建 → **64 点 FFT 的逆变换（`0xD113`）** → 两级点积滤波（`MR = [Rd]*[Rs], ss, 2`，即 µ'nSP 的**内积指令**，系数表在 `0xBC83/0xBD83/0xBE83`）→ 饱和限幅（±0x7FD0）→ 写回 `0x011E` 起的 128 字缓冲。

## 5. A1600 → PCM 工具

### 5.1 做法

与其"照着反汇编重写算法"，我写了**µ'nSP 解释器**直接跑固件里那份已链接好的解码器（指令语义取自 MAME `unsp` 核心；MAME 未实现的 MULS 内积按《SPCE061A 编程手册》3.3.6 节实现：n 项点积 + 指针推进 + FIR_MOV 数据移位）。

```
python unspemu.py        # 解释器（可单独用于跑固件任意函数）
python a1600_decode.py <输入.a16> <输出.wav>
```

解释器已通过单元测试（加减/借位/符号/移位标志位）并成功执行真实固件：清 RAM 循环、上电延时、外设初始化、进入握手循环，以及**完整的 A1600 解码流程**。

### 5.2 验证

对 GPCE063 包里的三个 A1600 样本解码：

| 样本 | 帧数 | 样本数 | 时长 | 峰值 |
|---|---|---|---|---|
| `t09_a.a16` | 143 | 18304 | 2.29 s | 31267 |
| `t09_b.a16` | 141 | 18048 | 2.26 s | 29047 |
| `t09_c.a16` | 129 | 16512 | 2.06 s | 31005 |

自洽性检验：帧数 × 32 字节 = 数据长度（误差 0）；样本数 = 帧数 × 128；相邻样本相关性 0.5~0.9（第 0~1 帧是重叠相加的预热帧）。**可直接播放 `pcm/*.wav` 做主观校验。**

### 5.3 已知限制

1. `MULS`（内积）在 MAME 里未实现，我按手册实现；若听感异常，优先核对这条指令的符号模式（`ss/us`）与指针推进方式。
2. 工具只解码 `.a16`（A1600）。同一内核也能解 DVR1600 格式（同算法），但 DVR 系产品的文件头参数约定可能不同。
3. SACM_D10 自带的那批示例（`Sound1.A16` 等）参数为 `0x0001`，不满足本内核"低字节-4"的索引约定，未能解出 —— 应为更早版本 SunAudior 的产物，需要另定映射。

## 6. 与你原判断的对照

| 你的判断 | 核实结果 |
|---|---|
| SACM_D10 的四种格式都在 061.dat 里 | **部分成立**：A1600 的**内核 + FFT 完整存在且可用**；MS01 的**鼓点数据整套存在**（但 MS01 引擎代码不是 SDK 版本）；DVR1600 只共享 A1600 内核代码；**S720 未发现**。另外固件里还有 **S200**（GPCE063 包）的内核代码，且它是被产品实际调用的语音编解码器之一。 |

| 希望能做 A1600→PCM 工具 | **已完成**：见 `a1600_decode.py`，并已产出可用 WAV（建议试听后确认音质）。 |

## 7. 建议的下一步

1. **试听 `pcm/t09_a.wav`**：如果内容清晰可辨，说明解码链路正确，只需再补 DVR1600/S200 的文件头约定即可覆盖其余格式；如果有杂音，我们从 MULS 语义入手（这是唯一"未实现参考"的指令）。
2. 用同一套解释器把 **S200 内核**（`0x826F`/`0x82C6`）也跑起来，即可支持固件里第二种实际使用的语音格式。
3. 鼓点 ADPCM（`0xD33D` 起）解码工具化：鼓点是 MS01 的 ADPCM 鼓采样，解码后可直接用于还原/替换音色。
