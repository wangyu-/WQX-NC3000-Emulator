## 1. 系统概况（已确认）

* 主控 SPDC1064（6502 兼容核）+ 语音协处理 SPCE061A（µ'nSP ISA 1.3）+ 1 MB NOR + 64 MB NAND + 160×80 单色 LCD + 串口。
* NOR 结构、BANK 映射、INT（BRK）中断机制：见 `docs\NC3KSYSNOR_结构分析.md`。
* 主控 ↔ 061 的串口协议（0xBB 握手 / 0x99 选解码器 / 0x44 音量 / 0x33+15B 与 0x22 包 / 0xAA 停止）：
  见 `docs\NC3000_LAVAX与语音播放协议.md` 第 1–4 节；宿主侧模型在
  `spce061a\host\nc3000_dsp.c`，函数注释逐条对应 bank0 的 BIOS 例程地址（`$FABE/$FB1C/$FB49/$F9E9/$FAE3/$FAEE/$FC7D/$FCB6`）。
* 061 侧 `0x99` 参数 → 解码器映射：
  `0x00`→3(MS01)、`0x10`→2(**S200**)、`0x20`→0、`0x21`→4(**S600/单词**)、`0x22`→5、其它→1(**A1600**)。

## 2. 已经完成并验证的部分

### 2.1 A1600 ✅ 逐样本验证通过

* 解码器在 061 固件 bank9（`0xB5D0` 附近），模拟器输出与官方参考 WAV **相关系数 1.000000**。
* 容器：`07 80` + 流（`xx 80`，xx = 04..09）。
* 相关文档：`docs\NC3000_VNT视听教材格式分析.md`、`docs\NC3000_LAVAX与语音播放协议.md` 第 1–8 节。

### 2.2 S200 ✅ 解码器验证通过 + 提取通路可用

**验证数据（对官方 `info\双语OK编辑工具\S200.exe` 的参照）：**

| 指标 | 结果 |
|---|---|
| 500 帧逐帧能量包络相关系数 | **0.9911** |
| 响帧波形相关系数 | **0.95 ~ 0.98**（lag = −9 样本）|
| 静音帧 | 模拟器 RMS 1~2，与官方数字静音一致 |
| 电平 | 约为 PC 参考工具的 0.63 倍（设备 DAC 通路另有 ×8 与音量控制）|

* 容器：`u32 长度 | u16 配置(0x0008) | 流`；帧 = 40 bit（字段宽 8/8/8/7/6/3）、8 kHz、160 样本/帧。
* 数据通路（已逐段实测）：
  ```
  0x82C6 读参数 → 0x8339/0x86B9 码本 → 0x8704 激励合成(写 0x0541+idx)
    → 0x83A8 四个子帧的 11 抽头 IIR(原地) → 0x8496 转移(×2+饱和) → [0x04C2]
    → 0xC742 播放 FIQ(4× 插值 + 音量 + 限幅 + DAC)
  ```
* **提取工具（推荐用法）**：
  ```powershell
  .\tools\vnt2wav.ps1 <一般品质.vnt> [输出.wav]
  ```
  内部走"直驱通路"（逐帧直接调 `0x82C6`，自己按固件时序喂流），
  源程序 `spce061a\host\s200_map.c`，实测 59.5 s 素材 RMS 792 / 峰值 10520，**听感正常**。

### 2.3 模拟器 ROM 协议通路（串口喂数据）—— 修掉两个真 bug

1. **流头必须一次发 8 字节**：内核 `0x8254` 读 **4 个字**（`u32 长度`、`u16 配置`、**然后是第一个数据字**）。
   原来探针分两次发（6 字节头 + 后续数据），解析时第 4 个字为 0 → 位流整体错位。
   改为一次发 8 字节后 RAM 实测为 `02F1 0000 0008 74DE`，与期望逐字一致。
2. **S200 不能给音频 FIQ 上 hold**：`nc3000_dsp.c` 的 `audio_pace()` 里"到半缓冲末尾就 hold FIQ"是当年为 A1600 调的；
   S200 的补数据由同一个 FIQ 驱动，hold 会把服务饿死 → 播放缓冲边写边读（撕读）。
   实测（20 帧纯静音）railing DAC 写：`no_hold=0` → **494**，`no_hold=1` → **1**。
   现在 `s200_probe` 对 S200 默认 `no_hold=1`。

修完后 ROM 通路的**解码输出**与直驱通路逐项一致（激励缓冲 ±1、`0503/0504/0507/04F4/06DA/06DB/06DC` 全同）。

## 3. 正在进行 / 未完成

### 3.1 串口通路的"播放输出"还差音量一环 ⚠️ —— ✅ 已于 2026-09-25 晚定案

> **根因不是音量/增益，而是模拟器的中断没有保存移位缓冲 `SB`**（`emu\unsp.c`）：
> 音频 FIQ 的 `MULS` 会把 S200 内核正在用的 `SB` 清零，导致 LPC 滤波器发散、输出饱和。
> 修好后 `lrc_800.s20` 全 188 帧 ROM 通路与参照**逐帧包络相关 0.9986**、满量程写
> 12898 → **1**，A1600 回归仍 1.000000。完整证据链与复核命令见
> `docs\交接文档_20260925.md` §2.3。下面这段保留为当时的排查记录。

* 现象：真实语音 4 s 有 **1965 次** DAC 满量程写（静音时只有 1 次），包络相关系数因此掉到 0.36。
* 原因已定位：`0xC769` 是**限幅器**（插值结果 ≥`0x0FFC`→钳 `0x7FDF`，≤`-0x1000`→钳 `0x8000`，再 `<<3+0x20` 输出），
  而 `[0x0001]`（音量寄存器）在模拟器里**一直停在 `0x8000`（=1.0 满档）**。
* 真正的音量写入点（全固件唯一一处写 `[0x0001]`）：
  ```
  0xC562: r1 = r1 + 0xC6B2   ; 音量表
  0xC564: r1 = [r1]
  0xC565: [0x0001] = r1
  ```
  唯一调用点 `0xCE27`，属于 `0xCE19` 那个"写寄存器 = 低半字节选寄存器 / 高字节为值"的分发器（16 项跳转表在 `0xCB72`）。
* **待办**：把参数位置写对（共 20 个 argv，音量在 `argv[20]`），在 `n3_volume()` 前后各打一次 `[0x0001]`，
  确认 `0x44` 命令有没有走到 `0xC562`；若没有就查 `0xCC23` 的字节级状态机（跳转表 `0xCB89`/`0xCB8F`）。
  > 注：上一轮"音量无论填几都是 0x8000"的结论**不可信**——那次命令行参数错位，实际发的是档位 0。
* 关闭与结束判定：`0xC546`（FIQ 回绕时调用）测 `[0x0000]` 的 **bit11(0x0800)**，
  没有就 `[0x0000]=0` 直接停播。探针测试台原本在第 40 块人为发 END，会造成"播到一半停"，
  需要 `no_end40=1` 或用"喂到流尾"的方式。

### 3.2 S600 —— 规范已齐备，只差实现 🟡（当前主线）

材料：`info\PC2880H.nor`、`info\PC2880H.nand`（该机型 DSP 是定制 SPDS104，**只支持 S600 播放**，其单词发音数据即标准 S600，可作黄金参照）；
`info\SPDS104A PROGRAMMING GUIDE.pdf`、`info\Speech Synthesis User Manual.pdf`。

> **2026-09-24 更新：Table 3 已逐位核准，18B→15W 转换器已写好。**
> 全文见 **`docs\NC3000_S600规范.md`**；工装 `tools\s600_unpack.py`（`frame` / `dump` / `check`）。
> 要点：帧 = 帧头 4 bit + 各包有效位 140 bit = 144 bit = 18 字节（位账唯一解）；
> P6/P12 是 5 bit（note 2）；`.vnt` 长度 339/339 ≡ 0 (mod 18)、帧首 4 bit 恒 `0xF`。
> 剩下的是**包内位序**二选一（`nibble`/`msb`），要用解码器判定。
>
> **2026-09-24 晚：位序已定案（反 061 固件），而且推翻了"NC3000 需要 18B→15W"这个前提。**
> 061 的 codec 4（`0x99 0x21`）链路：`0xC8C6` → `0x9EA3`(init, `[0x0713]=0x14`) /
> **`0xD225`(每块)** → `0xA694` → `0xA8B6`(每子帧) + `0xA6B7`(每帧开头读 **9 个字** = 18 字节)。
> 取位顺序是 **"字节 x 的 bit0→bit7，字节按序"**（`0xA706` 读的是字的 bit0 再右移）。
> 字段表合计 **38 + (8/5 + 9 + 11)×4 = 144 bit**，与 18 字节严丝合缝；
> 其中"8/5"就是 Table 3 的 note 2。工装 `tools\s600_fields.py`（12 万帧实测每帧都恰好 144 bit，
> 帧头字段恒 `0xF`，与"帧首字节高半字节恒 0xF"吻合）。
> **所以 Table 3 的 15 字 Receiving Format 是给 PC2880H 的 SPDS104A 芯片的；
> NC3000 只需要把 `.vnt` 的 18 字节帧原样喂给 061。**

**从官方文档挖到的 S600 规范（全部有出处）：**

> "长度 ≡ 0 (mod 18)" + "帧首恒 0xF"，见 `docs\NC3000_S600规范.md` §2.1。

## 5. 踩过的坑（务必避免重复）

1. **不要用单一全局 lag 比对长音频**：素材里常有大片数字静音，全段相关系数会被静音段淹没
   （本例 S200 从 0.95 被拉低到 0.154）。正确做法：**逐帧包络** + 每帧单独找 lag。
2. **小心输出文件被覆盖**：一连串参数扫描会反复覆盖 `out\s200_emu_021F.pcm`，
   之后跑短帧数又会把它截短，"静音段有底噪"这种结论其实是污染数据。正式跑之前先删旧文件。
3. **PowerShell 读 16-bit PCM 必须显式 `[int]` 转换**：`[byte] -shl 8` 会溢出，
   把 `ff ff`（−1）读成 255，直接误导了整整一轮分析。
4. **`.vnt` 里的 `07 80` 不能只靠两字节判断**：`a1600play.exe` 只校验头两字节，
   683 KB 的随机数据里命中 32 次 `07 80`，全部被"解码成功"（每段恰好 625 帧 = 切片长度/32）。判断 A1600 必须加更强约束。
5. **中文路径尽量用变量传**：这台机器的 shell 传中文参数时好时坏，`Get-ChildItem` 结果放进变量再传更稳。
6. **文件名/字符集**：NC3000 是 GBK，PC2880H 是 Big5，别混。

### 2.3 真正的病因：模拟器中断没保存移位缓冲 `SB`（**已修复**）

失败现象（`lrc_800.s20` 全 188 帧、按真实协议**边喂边放**）：

```
直驱 : RMS  1677  峰值 10060   railing      0
ROM  : RMS 13066  峰值 32767   railing  12898   ← 间歇性、整段级损坏
```

逐步排除（每一步都是实测）：

1. **位流没送错**：把 ROM 通路逐帧喂给解码器的参数（`PC=0x8339` 时的 `RAM 0x04E5..0x04F1`）
   与直驱通路逐帧对拍，前 15 帧**完全相同**（`03BF/0005`、`03BF/000A`、`03D7/0292`、
   `03EF/051B`、`016F/107D`…）⇒ 参数（= 位流解码结果）一致。
2. **不是算力**：内核每帧只用 ~38k 指令，实时预算是 984k（160 样本 × 4 × 1538）。
   DAC 写 : FIR 环补充 = 精确 **4.00**；UART 零丢字节、零溢出。
3. **不是"中断那一刻"本身**：S200 内核全程跑在**主循环上下文**（IRQ/FIQ 内 0 条）；
   UART IRQ 1031 次**没有一次**命中内核窗口；FIQ 命中内核 11664 次，但 8 帧素材同样
   命中 482 次却完全正常。
4. **是 FIQ 的 `MULS` 清掉了内核正在用的 `SB`**：
   - `0xC765` 的 `MR = [r2]*[bp], ss, 8` 是 MULS，按 MAME/我们的核会 `SB = 0`；
   - 手册《第 3 章 3.4.5 移位操作》写明 LSL/LSR/ASL/… **把移出的位放进 SB 寄存器**，
     S200 内核的可变移位例程（`0x8905/0x8994`，单元测试 `build\s200_shift.exe` 全过）靠它接力；
   - 音频 FIQ 每帧要打断内核 ~25 次，**只要一次撞在移位序列中间**，LPC 滤波器状态就发散
     → 输出饱和到 ±0x7FDF/∓0x8000（正好是 `0x8496` 那个"×2+饱和"转移的钳位常数）。
   - 实测：把 `SB` 也纳入中断现场保护后，`railing 12898 → 1`。

**修复**（`spce061a\emu\unsp.h` + `emu\unsp.c`）：`unsp_t` 增加 `int_sb[UNSP_INT_MAX]`，
`take_interrupt()` 随 PC/SR 一起记录当前 `cpu->sb`，`reti`（以及 RETF 逐层退出）时恢复。
依据：MAME 中 `SB` 是 FR 寄存器的一个字段（`fr>>7 & 0xf`，与 `BNK/FRA/FIR_MOV/IRQ/FIQ 使能`
同在一个 FR 里），而中断硬件会把 FR 压栈 —— 固件正是按这个前提写的。

### 3.11 ✅ S600 已定案（2026-09-25 晚）——根因是宿主模型没真等 ready 线

**现象**：同一切片有时解对、有时全坏；输出"静音段夹 21k~27k RMS 噪音"。
**定位**（细粒度监视器）：主机喂数**约 1 字节/1422 条指令**，而内容速率需要
**1 字节/65000 条指令** ⇒ **喂数快约 46 倍** ⇒ 环/播放缓冲被覆盖 ⇒ 成片削顶。
**根因**：`nc3000_word.c` 里等待 061 ready 线的循环上限只有 **400 次迭代（25,600 条指令）**，
超时就照样发；而 ready 线在流水线繁忙时长时间为"忙" ⇒ 节流形同虚设。
**真机 6502 的字节发送是死等 ready 线的**（`$9DAA → JSR $9E3D`，无超时），所以这是
**宿主模型的保真度缺陷**，不是固件/解码问题。

**修复**：S600 各模式的 ready 等待上限 400 → 2,000,000（`argv[20]` 可覆盖）。
**验证（4 个用例，全部 rails 从 1 万+ 降到 1；包络恢复"静音 + 语音"结构）**：

| 用例 | 修复前 | 修复后 |
|---|---|---|
| 0–300 帧（301 帧） | rms 15898 / rails 10123 | rms 1395 / **rails 1** |
| 文件头 131 帧 | rms 21262 / rails 32426 | rms 1217 / **rails 1** |
| 中间音节 p646 | rms 21608 / rails 34324 | rms 1734 / **rails 1** |
| 中间音节 h158 | rms 21253 / rails 32426 | rms 1612 / **rails 1** |

**试听件**：`spce061a\build\s600_试听_修复后_音节1.wav`、`…_音节2.wav`（按 36,790 Hz 标注、

### 3.13 ✅ NC3000 单词数据找到了：celp_data 本身就是 S600 码流（2026-09-25 深夜）

**勘误**：`docs\NC3000_单词发音数据.md` §1 那条 `nand_deinterleave 0x2AAB000` 的起点
**没落在 528 字节页边界上**（`0x2AAB000 mod 528 = 400`），每个 512 字节窗口都掺进
16 字节冗余区 ⇒ 之前所有「没有 0xF 帧头 / 5 字节记录 / 偏移表」的结论都建立在被

- 先从整片 NAND 按 528→512 去交织成逻辑镜像（`out\nc3000_full.bin`，52,150,272 字节）；
- inode 表在镜像开头；sysdir 目录区在逻辑 `0x31B8180`，能直接读出

- `celp_data` = inode 26，首块 2506 → 逻辑 `0x2728000`，**整条是 18 字节/帧的 S600 码流**，
  从文件 **偏移 10** 开始；每 16 KB 块最优相位按 −4 递变（`16384 mod 18 = 4`），
  这正是「跨块连续」的指纹；
- 走已修好的 ROM 通路（mode 27，`0x99 0x21`）解码 3 处各 300 帧：`pcm≈248477`、
  满量程 1 次、频谱带限到 ~3.5 kHz（与听感确认过的 ks100 产物同一形状）。

## 5. 本轮新增的坑（务必避免）

1. **别用"18 步长 + 首半字节 0xF"当 S600 判据**：`0xFF` 填充区会完美满足它（我在 `多國會話\*.dic` 上因此误报过 1250 段"S600"）。
2. **`0xFF`/`0x00` 填充会污染统计**：判"某格式是否存在"必须排除全 `0xFF` 的样本。
3. **`.dic` 的关系**：`多國會話\*.dic` 是**纯 Big5 文本短语书**（无音频）；`有声书\**\*.dic` = 16 字节文本字段 + **A1600 音频块**（`07 80` 容器）；`TTS2DIC.exe` 是 `*.TTS → *.TTS.DIC` 编译器。
4. **音量/斜坡/节拍三个杠杆对 S200 的削顶全部无效**（见 §2.2），别再重复试。
5. **探针的 `argv` 是位置参数**：`fire_every` 在第 5 位（默认 1538，别填 40）；填错会让人误解成"速率错"。
6. **`有聲會話.bin` 是可执行程序**，不是语音数据（已确认）。
7. **比较 ROM 通路与直驱参照时，重采样率必须是 31958.39 Hz，不能按 32000 算**，
   而且**必须逐窗（甚至逐帧）单独找 lag**：否则 3.3 s 就漂 32 个样本，长段比较会得出
   "相关系数 0.36/0.45"这种假结论。上一轮"相关掉到 0.36"就是这么来的。
8. **统计"满量程写/railing"必须区分内容区与流结束后的尾巴**：8 帧素材的 171 次满量程写里
   有 170 次落在播放结束后的尾巴上，内容区一次都没有。
9. **改动 `emu\unsp.c` 的中断路径要极其小心**：`SB`（移位缓冲，是 FR 的一部分）必须随
   中断保存/恢复（本轮已修，见 §2.3）；`MULS` 会清 `SB`，而 S200 内核依赖它接力。
10. **不要用 `spce061a\host\s200_probe.c` 的 `build\s200_probeD…Q.exe`**：那是本轮调试
    过程中的中间产物（已作废，源码为准），现行构建是 `build\s200_probeC.exe`。

### 4.2 "词号 → 音频记录"那一层的语义

* `ahd_celp[词号]` 给出一个 0..14,908 的数（`FFFF` = 无发音），

* 按 §9.1 的语义（bit6=还有下一音节）走链，能走出**多音节的词**，
  例：`celp idx 25208 → record 761 → 2 音节 (V=268,FC=9)+(V=595,FC=5)`；
  但也有"两条记录 V 相同"的怪例（24844 → 1829/28 + 1829/6），说明
  **表值可能不是"该词第一条记录"**（也许是累计位置，或以 5 字节为单位的位置）。
* 下一步：拿 `dict_entries` 已知拼写的词（如 `doorknob` #24848、`dopant` #24869、
  `dracaena` #25208）**听感验收** —— 这几个词音节数是已知的
  （door-knob=2、do-pant=2、drac-ae-na=3），用它反推"表值 → 记录"的确切含义。

### 4.3 常用词的拼写（含 `apple`）需要解压码表

词头是压缩数据：常用词用短码，生僻词用 `F0 xx` 逐字母转义。现在我们已经有了
**每个词条的词头字节范围 + 词号 + 字母序 + 27,283 个已知拼写的锚点**，
这给反解码表提供了上一轮没有的强约束：
* 同一码在多个词头里出现 ⇒ 它的串必须同时适合那些位置；
* 码的**顺序**必须与词表（`out/tables_guess.json` 那套）一致；
* 词头两端都是字节对齐的转义/`F0 04`，所以**词头的位长已知**，
  可能的码序列是有限的组合（4/12/16/20/16/21 bit）。
* 判据仍是"解出来通顺 + 词号对得上"（可用 `find <拼写>` 直接校验）。

### 6.1 第一次试听失败 ⇒ 定位到**记录区是两层寻址**（工具已修）

第一次给出的 4 个 WAV 用户反馈"读音都不对"。复查固件（`tools/dis6502.js` 反汇编）
后找到原因：**记录区不是平铺的 `celp_data+0x284000+5N`**，而是按 **32 KB 页**寻址：

```
bank0B $9722：用 24 位键在 $9993 起的 3 字节升序页表里找"页号"（表项-1 >= 键）
bank0B $97F0：cluster = 0x0A6B + 页号*2 + (偏移>>14)  ，偏移仍取 $240000 那张 u16 表
bank0B $9D51：音频按 15 字节块读（对应主控 0x33+15 字节的传输块），偏移每次 +15
```

* 页表就在 NOR 里：`info/NC3KSYSNOR.nor` 偏移 **0x5D993**（bank 0x0B 的 `$9993`），
  3 字节小端、升序、步长 ~1.57~1.73 K，首项 1569、次项 3293 ……（共 80+ 项）。
* `celp_data+0x240000` 那张 u16 表的每一项 = **页内描述符**（`偏移>>14` 占高 2 位、
  低 14 位是页内偏移），所有值都是 5 的倍数 ✓。
* 独立验证帧号语义：记录里的 `V` 取 `字节 = 10 + 18*V` 时，字节高半字节为 `0xF`
  的比例 **75.7%**，与全流基线 72.6% 一致；取 `V*2`/`V` 则只有 10~14% ⇒
  **V 就是 18 字节/帧的 S600 帧号**，之前的帧提取是对的，错的是"哪几条记录"。

`tools/nc3000_word_audio.py` 已按上面的两层寻址重写并重新生成试听件
（`dreadlocks` 2 音节/0.35 s、`dopant` 2 音节/0.41 s、`apple候选_cb` 1 音节/0.87 s、
`apple候选_ahd` 2 音节/0.43 s）。判据仍是"听出来是哪个词"：

* `dreadlocks`/`dopant` 若念对 ⇒ 链路成立，`apple` 只差"词号选对"；
* 若仍是**别的话音** ⇒ 说明 `celp 表的下标 ≠ 词典词号`（还差固件 trie 给出的
  24 位键那一层）；
* 若是**噪音/静音** ⇒ 说明"记录 → 帧"还有单位问题（下一处要查的是 $9CAA 的
  `FC×18` 与 $9D51 的 15 字节块如何拼成帧）。

### 7.1 发音索引结构（源码注释 + 代码，逐条对上）

```
每词 3 字节（24 位）：值 = 二级索引的下标*3；bit23 = 1 表示 TTS 发音（此机型不播）
二级索引（TV_INDEX.BIN）：成对的 24 位偏移 → 音频数据的 [起始, 结束)
数据文件（TV_DATA.BIN）：S200 容器（实测 "54 00 00 00 | 04 00 | 流"）
TTS 数据块结构（源码注释原文）：
    音节数              1 Byte
    第n音节: 帧偏移   17 bit (bit0..16)
             字节长度  7 bit (bit17..23)
             样点头    8 bit (bit24..31)
             样点尾    8 bit (bit32..39)
```

**这就是 celp_data 里那张 5 字节记录表的字段含义** —— 注意它和
`NC3000_单词发音数据.md` §9.1 的读法不同：**帧偏移是 b2 的 bit0（不是 bit7），
那 7 bit 是"字节长度"而不是"帧数"**；所以之前按 §9.1 解出来的 V/FC/more
都是错的（这解释了为什么放出来的音频不对）。

### 7.2 顺带确认的规模

* `AHD_WORD_COUNT = 95703`（源码）——我用 `tools/dict_entries.py` 在 NC3000 的
  inode 9 上枚举出 **95,684 个词条**，差 19 个 ⇒ **枚举方法正确**、两部机器的 AHD
  是同一部词典（词序应一致）。
* `DICT_CAM.BIN` / `CAM_IDX.BIN`(44498×3) ⇒ **inode 8 = 剑桥词典**，
  对应 `cb_celp`（Cambridge）；`GGV_IDX.BIN`(76966×3) ⇒ `wqx_celp`。
* `TRUEVOICE_MAX_BYTES = 600`（单个真人发音词的音频上限）。

### 7.3 可直接验证的样例（NC3001）

已按上面的结构从 `AHD_IDX.BIN → TV_INDEX.BIN → TV_DATA.BIN` 取出词 #110 的音频
（1.2 s，`out\NC3001_词110_应为aberrated.wav`；NC3000 侧的词号 #110 = `aberrated`）。
听感若对上，就说明"索引结构"这一层已经定死，接下来只是把 NC3000 的
"词号 → 记录块"对上（下一步：把 `word_ID` 的 3 字节记录按"bit23 = TTS 标志 +
值×N 查下级表"的语义重新验一遍）。

### 7.4 实测反馈（重要）

* NC3001 词 #110 放出来用户听到的是 **"ABC"**，而 NC3000 侧 #110 = `aberrated`
  ⇒ **两部机器的 AHD 不是同一版**，词号不能互相照搬。
* NC3001 的词典音频比正常语速慢（音调正常）⇒ 容器配置 `0x0004` 对应的播放速率
  与官方 `.s20` 不同（速率先搁置，不影响索引结构结论）。
* NC3000 侧本轮排除的映射（都不成立）：
  1. `ahd/wqx/cb_celp[词号]` 直接当记录下标（平铺 `0x284000+5N`）；
  2. 经页表 + `0x240000` 描述符再取记录（字段 V/L 大量越界）；
  3. `[T[k], T[k+1])` 当"成对偏移"取一段记录（条数与音节数只有 22% 吻合）；
  4. 记录块 = `[音节数 1B][n×5B]`（首字节与音节数无关）；
  5. 索引取"词号 / 发音序号"× `ahd/wqx/cb` × 值×1/2/3（全部 <1%）。
* 因此 NC3000 与 NC3001 的**索引宽窄不同**（NC3000 的 `ahd_celp` 是**每词 2 字节**，
  NC3001 的 `AHD_IDX.BIN` 是**每词 3 字节**），不能照搬。

### 7.5 下一步（NC3000）

回到固件里那条**已经读通**的路：`trie → $94/$95/$96（3 字节键） → 页表 → 记录`。
也就是说"拼写 → 音频"缺的是 **trie（字母索引）** 这一层，而它就在
`0xC0000..0xE0000` 的 12 字节节点表（或 ROM 里 9 字节节点）里。下一轮就把它走通。
