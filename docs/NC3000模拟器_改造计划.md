## 0. 结论先说：这个"改造"到底要做多少事

拆开看，NC2000 → NC3000 的差别集中在 **5 个部件**，其中 4 个在模拟器里都只是"换参数"级别，
只有 **语音协处理器** 是真正要重写的部分：

| 部件 | NC2000 | NC3000 | 模拟器改动量 |
|---|---|---|---|
| 主控 CPU | SPDC1024（6502 兼容） | SPDC1064（6502 兼容） | 中（内存映射/bank 规则，已有半成品） |
| 内存/中断 | 24K+32K RAM、BRK 3 字节跨 bank 调用 | 同架构，窗口划分不同 | 中（`mem.cpp` 的 `nc3000mode` 分支） |
| NOR | 512KB | 1MB（本机 dump 只有 17×32KB） | 小（`nor.cpp`） |
| NAND | 32MB，页 528B | 64MB，页 528B | 小（`nand.cpp` 已按 `CLE/ALE` 位分支） |
| LCD | 160×80 + SPLD803A | 160×80，显存在 `0x19C0`（`A19C0 LCD_MEMORY`） | 小（`CopyLcdBuffer` 已按 `0x19C0`） |
| 键盘 | QWERTY 矩阵 | 另一套矩阵 | 小（`key_new.cpp` 已有 `items3000`） |
| **语音** | **SPDS104A**（并行口 0x30-0x33） | **SPCE061A**（走主控 UART `0x3A-0x3D` + 握手线 IO `0x0E` bit4） | **大**，但**已有现成成果可用** |

**关键有利条件**：本仓库 `spce061a/` 下已经有一台**经过验证的 SPCE061A 模拟器**
（µ'nSP CPU 核 + 外设 + 真机 061 固件），A1600/S200/S600/MS01 四条语音链路都跑通了，
而且 `docs/SPCE061A模拟器_使用指南.md` §4 已经写好了"接进文曲星模拟器"的两条路线。
也就是说：**语音这一块不是从零开始，是接线。**

## 1. 已经查清的事实（本轮实测，不是推测）

### 1.1 源码缺口

上游源码**故意没有发布** `dsp/` 目录（SPDS104A 语音核，源自 Lee 的 Pc1000emux），
但 `CMakeLists.txt` 引用了 `dsp/dsp.cpp` → **原始压缩包无法编译**。
NC3000 根本不用 SPDS104A，所以我们用一个**空壳 `dsp/dsp.cpp`** 补齐接口
（只保留 `reset()/write()/dspMode/callback` 这些调用点用到的符号），
NC3000 的语音走新的 061 通道。原始 NC2000/1020 模式随之失去声音，但保留可运行。

### 1.3 ROM 预处理（`tools/nc3000_rom_prep.ps1`）

两个 dump 都要转换才能喂给模拟器，脚本已写好并有自检：

* **NOR**：dump 是"CPU 窗口顺序"，bank≥1 的上下 16 KB 是**对调**的；模拟器要的是
  **芯片顺序**。脚本按 bank 拆开、对 bank≥1 交换上下半区，再补 0xFF 到 1 MB。
  校验：复位向量读出来是 `FFF4`（与 `NC3KSYSNOR_结构分析.md` 一致）。
* **NAND**：**528 B 页**（512 数据 + 16 spare），而且 dump **本身就是"设备第 64 页起"**
  （第 0 字节就是 inode 1 的记录）——所以它等价于模拟器的 `<rom>.nand`，**不能再砍 64 页**。

  > ⚠️ 这里踩过两次坑，都是"错位 64 页（33,792 字节）"：
  > ① 早期以为 dump 是"纯 512 数据页"而重新封装；② 后来又按"含前 64 页"切掉 64 页当
  > `.nand0`。后果都是固件在"闪存中有数据 清除吗？选 N"之后挂不上文件系统，
  > **掉进它自己的调试监视器（屏幕只剩一个 `>`）**。
  > 脚本现在会自己判断（看首字节是不是 `01 00` + `A8 A8`）：
  > 是 ⇒ 原样当 `.nand`，`.nand0` 写 64 页 `FF`（签名由模拟器 `nand.cpp` 自己写）；
  > 否 ⇒ 按老办法切 `.nand0` + `.nand`。

```powershell
powershell -File tools\nc3000_rom_prep.ps1          # -> roms/nc3000.nor .nand0 .nand
```

### 1.4 固件**已经能跑起来**（本轮最大进展）

`src_nc3000/headless/main_headless.cpp` 是为此写的无窗口测试台：跑固件、统计
PC 直方图、统计每个 IO 口的读写次数、dump LCD 成 BMP。

实测（`--ms 8000`）：

```
after boot: PC=FFF4 ...                       <- 复位向量正确
instructions=12,253,071  distinct PC pages=45  BRK/INT=11
first INT/BRK calls:
   C11B -> 03 00    C128 -> 1D 03    C242 -> 10 03   403D -> 29 05
   48D3 -> 03 C0    48D6 -> 04 C0    48D9 -> 2A C7   48F1 -> 19 C7
   E0FF -> 29 C7    E110 -> 1D 03    E1D8 -> 23 05
```

也就是说：**跨 bank 的 `INT <idx> <bank>` 机制、bank 切换、NOR 读取、NAND 读取
（`$39` 有 34 次读）、LCD 控制器配置、定时器都已经在跑**，45 个不同的代码页被执行过。

### 1.5 卡在哪：等 061

同一份实测的 IO 访问统计：

```
$3A r=92     w=116     <- UART 数据
$3B r=9947   w=8       <- UART 状态（发送就绪）
$3C r=135317 w=1142    <- bit4 = "收到字节"（固件在这里死等）
$3D r=131    w=146     <- UART bank 选择
$30..$33    0 次       <- NC2000 的 SPDS104A 口，NC3000 固件完全不碰
```

`$3C` 被轮询 13.5 万次、`$3B` 近 1 万次 ⇒ 固件在**等一字节 061 的应答**；
同时 `$FB80-$FB83`（BIOS 里的延时循环，被 `$FB73` 调用）占了 13.4% 的执行时间。

对照 `info/NC3000_trap.txt`/`common.txt` 和 `spce061a/docs/NC3000-061协议对照.md`：
主控 BIOS 的 `$FB1C`(发字节) / `$FB49`(收字节，等 `$3C` bit4) / `$FB8C`(061 口初始化) /
`$FC41`+`$FC5F`(0x33+15B / 0x22+len 推数据) 正是文档里那条 **0xBB 握手 / 0x99 选解码器 /
0x33·0x22 推流** 的链路，物理通道就是 **`0x3A-0x3D` 这个 UART**，握手线是 **IO `0x0E` bit4**。

> 顺带排除一个弯路：`common.txt` 里 `A0030 DSP_STAT/DSP_CNTL`、`A0031 DSP_DATAR`、
> `A0032/A0033` 那组符号是 **NC2000 时代（SPDS104A 并行口）的遗留**，
> NC3000 固件在 8 秒里对 `0x30-0x33` 的访问次数是 **0**。NC3000 的 061 走 UART。

**所以"下一步"非常明确：把 `spce061a/` 这台 061 模拟器接到主控的 UART 上。**

### 阶段 4/5 的实测结果（本轮）

**061 已经接通，协议握手与真机一致**（`--dsp-trace` 抓到的字节流）：

```
[6502>061] BB 0A      ->  [061>6502] BB FA     # 握手
[6502>061] AA 00      ->  [061>6502] AA 00     # 停止带应答
[6502>061] AA 01                                # 睡眠（之后必须重新握手）
[6502>061] BB 0A      ->  [061>6502] BB FA     # 再次握手，与文档规则一致

**但固件之后不是卡死，而是"睡着了"**：跑满 5 秒后 PC 冻结在 `$E371`、`IO 0x05=0xFF`
（`cks=7`，主控停振）、`g_wai` 置位——正是真机"没按键就待机"的状态。

| 执行过的代码页 | 45 | **91** |
| `INT <idx> <bank>` 次数 | 11 | **63,227** |
| 061 收发字节 | 12 / 8 | 78 / 52 |
| 屏幕 | 全白 | **有画面**（见下） |

## 4. 第二轮（阶段 5/6）：显示与键盘

### 4.1 两个真正的 bug（都不是"没实现"，而是"实现错了"）

**① NAND dump 的页大小是 528 字节，不是 512。**

`info/NC3KSYSNAND.nand` 本身就**带 16 字节 spare**（512+16=528），而我第一版
`tools/nc3000_rom_prep.ps1` 把它当成"纯数据、无 spare"，又按 528 重新封装了一遍
——等于**整个镜像每页错位 16 字节**。

判据（现在脚本里已写成断言）：

```
按 512 分页：文件长度 % 512 = 2   （不是整数，说明页长不是 512）
按 528 分页：文件长度 % 528 = 2   且  页 1 的数据区开头 = 11 00 = inode #17 的编号
```

按 528 分页后，inode 表就是干净的 32 字节一条记录；按 512 分页则每 512 字节就多出
16 字节垃圾。**修正后 `roms/nc3000.nand` 不再"重新封装"，只按 64 页拆出 `.nand0`。**

**② NC3000 的 LCD 极性与 NC2000 相反。**

NC2000 的约定是"显存某位 = 1 → 该点黑"。NC3000 是反的：按 NC2000 的极性渲染出来，
主菜单是"黑底白字"而且**看不到文字**（因为字是按相反的位画的，全糊在一起）。
在 `CopyLcdBuffer()` 里对 `nc3000mode` 取反后，画面变成正常的**白底黑字**（白像素占 74%）。

> 这两条合起来的教训：**先怀疑"实现错了"，再怀疑"没实现"**——两处一修，固件立刻就能用了。

| 开关 | 用途 |
|---|---|

| `--lcd-seq <ms> <前缀>` | 每隔 N 毫秒导一张 BMP，用文件哈希对比就能看出屏幕的每次变化 |
| `--dsp-trace` | 打印 6502 ↔ 061 的每个字节 |

**INT 调用直方图**是最有用的一招：本轮统计出

```
INT $C00A = sys_key_proc    60,978 次   ← 主循环在扫键盘
INT $0505 = __NANDReadBytes  1,847 次
```

看到 `sys_key_proc` 占绝对多数，就能断定"固件没卡，是在等按键"，不用再猜。
（`info/NC3000_trap.txt` 里 `C00A //sys_key_proc` 就是名字来源。）

### 阶段 4 的实现要点（已经写好的接线方案）

1. 把 `spce061a/emu/{unsp.c,spce061a.c,firmware_061.c}` 与
   `spce061a/host/nc3000_dsp.c` 编进 `src_nc3000`（C99，用 gcc 单独编译成 .o 再链接）。
2. 新文件 `src_nc3000/spce061_bridge.cpp`：对外只暴露 4 个动作
   —— 写 `0x3A`（= 主控发一字节给 061）、读 `0x3A`（= 取 061 发来的一字节）、
   读 `0x3B/0x3C` 状态位、读 `0x0E` bit4（ready 线）。
3. `io_new.cpp` 里对 `nc3000mode` 把 `0x3A-0x3D` 从"PC 串口/红外"改接到 061；
   `0x0E` 的 bit4 由 `nc3_busy()` 驱动（忙=1）。
4. 每个时间片给 061 跑一段指令（`n3_run_steps`），并遵守使用指南 §6 的时序规则
   （发前等 ready、一次最多一个环 560B、不要发半个包、收字节一字节一手握）。

### 需要遵守的"坑"清单（来自 `docs/SPCE061A模拟器_使用指南.md` §6）

* 发数据前必须等 IOB14 变低；一次最多填满一个环（280 字 = 560B）。
* 不能发半个包（`0x33+15` / `0x22+len+payload` 要发完）。
* `0xAA 0x01`（睡眠）之后必须重新 `0xBB 0x0A` 握手。
* 顺序必须是：先 stop/idle → 再 `0x44` 音量 / `0x55` 速度 → 最后 `0x99` 选解码器。
* 主控读端口要读**引脚电平**而不是输出锁存（061 的 flow-control 会死循环）。
* 听感验收必须用**当前源码现编的 exe**（历史 exe 会冻结当年的 bug）。

## 5. 第三轮（阶段 7）：声音输出

### 5.1 做了什么

把 061 解码出来的 PCM 接进了模拟器原本的 SDL 混音器：

| 位置 | 改动 |
|---|---|
| `spce061_bridge.{h,cpp}` | 新增 `nc3_dsp_audio()`（取 PCM）、`nc3_dsp_sample_rate()`（固件 TimerA 定的采样率） |
| `sound.cpp` | 新增 061 流队列 + 独立的线性重采样器（按固件的采样率算比例），与蜂鸣器、NC2000 的 DSP 三路相加后限幅 |
| `nc2000.cpp` | 061 的配速从 `主控周期/2` 改成 **`主控周期×5`**（061 晶振 49.152MHz ÷ 主控 10.24MHz = 4.8），并让 `fire_every = 51.2M / 采样率`，这样音频节拍与固件写的 TimerA 一致 |
| `sound.cpp` | 空闲（没有流）时把 061 的配速压到 3000 条/毫秒，避免白烧 CPU |
| `--dump-audio <file.wav>` | 无窗口下把混音结果录成 44.1kHz WAV（本机没有声卡也能验收） |

### 5.2 怎么验证的（不依赖固件 UI）

固件要在"词典→发音"这种路径下才会给 061 发播放命令，而键位还没核对完，所以加了一条
**直接驱动 061 的测试通道** `--dsp-play <ms> <帧文件>`：它按真机主控的顺序
（`0x99 0x21` 选 S600 → `0x11` TTS 头/记录 → 每帧 `0x22 <18>`）把一段已验证能出声的
帧流灌给 061，**每 24ms 一帧、并且等 ready 线**。

```powershell
cd src_nc3000
.\nc3000_headless.exe ..\roms\nc3000 --ms 16000 `
    --dsp-play 2000 "..\spce061a\build\word_ahd\ahd_celp_first15.bin" `
    --dump-audio ..\out\nc3000\audio_061.wav
```

实测结果（`audio_061.wav`，44.1kHz）：

| 区间 | RMS | 非零样本 |
|---|---|---|
| 0–2 s（还没开播） | 303 | 2% |
| 3 s | 25,402 | 99% |
| 4 s | 25,234 | 99% |
| 5 s | 26,486 | 100% |
| 6 s | 25,157 | 99% |
| 7 s | 25,191 | 91% |

对照上一线程用独立工具做的参照 `spce061a/build/word_ahd/ahd_celp.wav`
（RMS 6,951、99.3% 非零）：**同一量级、连续有声**，说明
「061 解码 → 桥接 → 混音 → WAV」这条链是通的。

> 还没做精细定标的两点：
> 1. 我这条测试通道是"驱动一次 357 帧"，出来的时长（~5.5 s）比标称的 8.57 s 短，
>    语速偏快——这是 **测试喂帧方式** 的事（真机由主控按 6000bps 卡节奏），
>    不是混音器的问题；等键位通了走固件自己的播放路径再对比一次。
> 2. 满量程处仍是 ±32767（061 侧限幅），和上一线程的结论一致，属于音量定标范畴。

**不播放时是安静的**：同样跑 20 秒但不带 `--dsp-play`，WAV 里只有 990 个非零样本
（按键蜂鸣），没有噪声。

## 6. 第四轮（阶段 6）：按键矩阵实测

> ⚠️ 这一轮（第四轮）当时**还没找到真正的键盘 bug**，下面写的"下一步"在后面的
> 第六、九、十三轮才陆续完成。**键盘的最终结论看 `docs/NC3000_键盘.md`**；
> 完整的排查过程看 `docs/NC3000_按键矩阵实测.md`（日志）。

完整数据见 **`docs/NC3000_按键矩阵实测.md`**，这里只放当时的结论：

1. 反汇编出了固件的主扫程序（`INT $C00A = sys_key_proc` → `$D71D` → `$D753` → `$EAE0` 段）：
   它逐行驱动 port1（IO `0x09`），再读 port0（`0x08`）和 **port6（`0x1E`）**，
   查 `$EF73` 表得到键值，写进 `$C7`（bit7=1 表示无键）和 `$040A`；
   去抖历史在 `$0A2D/$0A2E/$0A2F`。
2. 新增工具 `--key-probe`：逐个按下 64 个矩阵位置，**读固件自己解出的键值**——
   不用猜，固件说了算。
3. 实测：**约 35/64 个位置解出的键值与模拟器现有键表完全一致**（字母、数字、
   F1–F4、方向、输入、跳出、空格、符号、中英数…）。剩下的全落在"感应线在 port6"
   的那几行上，因为 `NekoDriverIO.cpp` 里 port6 是抄 port0 的（作者自己写了
   `//// hack, 主要是为了骗nc3000的按键运行起来`）。
4. 所以下一步不是"改键表"，而是**把 port6 的感应线真正建模**，然后用 `--key-probe`
   复验"64 个位置互不相同"。
5. ON/OFF 暂按现状：F12 走矩阵 (0,0) + 热复位，能完全启动到主菜单；把固件认的
   `ONOFF(4,0)` 递过去它会"醒了又睡"（已实测），等 port6 修好再回头处理。

### 6.1 本轮进展与"ON 键"的坑

* 在 bank 0x10 找到**真正的键盘识别扫描**与两张列线表：
  port0 八条 `10 20 40 80 EF DF BF 7F`、port6 八条 `01 02 04 08 FE FD FB F7`，
  行线是 port1 —— 即 **16 列 × 4 行 = 64 键**。
* 据此实现了 **port6 的列线传导**（`Write1EPort6` + `UpdateKeypadRegisters`），
  一下把之前按不出来的字母都救回来了（r/t/g/n/j/a…），解出键值的位置从
  约 40/64 升到 **62/64**。
* 在 bank 3 `$4658` 找到**开关键/热键扫描**：它驱动 port1/port6 的列组，
  然后只读 **port0 的 bit0**（"有键按下"公共线）。这就是老模型里 (0,0)
  能唤醒的原因——它恰好拉的是这条线。
* 试过三版"更忠实"的模型（去掉老传导、加 port0→port1 电平传导、
  任意键拉 bit0），**都会把开机流程弄坏或让键位识别变差**，均已回退。
  原因：port0 bit0 在启动阶段还有别的用途，不能简单地"有键就拉高"。
  详见 `docs/NC3000_按键矩阵实测.md` 第 6 节。

再跳到 `$C245`，那里对照 `$0A99/$0A9A` 决定走 `INT $0311 warm_start` 还是冷启动。
实测这两个魔数在休眠前后都是 `A5 5A` / `00 00`，所以固件**自己走了 warm_start**，
不是我们模拟器的近似 —— 模拟器只负责"清掉 clk off 位 + 让 CPU 复位"，剩下的全是固件行为。

## 10. 第十轮（2026-09-27）：**声音的"噪音"根因找到并修掉**（两个真凶）

### 10.1 先分清"谁在响"（新工具）

| 工具 | 作用 |
|---|---|
| `--dump-061 <file.wav>` | 只录 **061 芯片的原始 DAC 输出**（不经过混音器、不含蜂鸣器），并且只保留"正在播放"的那段（空闲时 DAC 不产样本） |

| `--watch-write <addr>` | 谁写了某个内存地址（上一轮加的，这轮救场） |

| `NC3_SND_DEBUG=1` | 每 250 ms 打印混音器的 061 重采样状态（ratio/队列/计数） |

结论：用户在词典界面听到的"噪音"其实是**两样东西**：

1. **按键音**（固件本来就要响的）：BIOS `$E374`（跳表 `$E012`）往 P47 打 144 个脉冲 = 一声"哔"。
   实测每次按键一声、时长约 20 ms（`--io-watch 0x18` 能看到 `$E397/$E3A7` 交替写 `8F/0F`）。
   这是**正确行为**，不是 bug。
2. **单词发音被拉坏了** —— 这才是"噪音"。下面两条是真凶。

### 10.2 真凶 A：喂给 061 的包型错了（`0x22`+18 字节）

真机主控（bank 0x0B `$9CAA-$9D50`）发的是 **`0x33` + 15 字节块**，尾部不足 15 字节才用 `0x22 <len>`；
而 `--dsp-play`/桥接的测试通道一直发 **`0x22` + 18 字节**（一整帧）。
061 的暂存环只有 16 字节（`0x0718..0x0727`），18 字节会**踩掉暂存指针** `[0x0728]/[0x0729]`
（`docs/archive/交接文档_2026-09-24_09-26.md` 里源文件 `交接文档_20260925.md` 的 §3.8/§3.11
早就定案过，本轮才落到模拟器里）。

修法（`src_nc3000/spce061_bridge.cpp`）：按真机的字节流发 15 字节块，余量用 `0x22 <len>`，
并且**不要人为按 6000 bps 限速** —— 节流交给 061 的 ready 线（真机 6502 就是死等它）。

### 10.3 真凶 B：DAC 节拍被 UART 轮询"带快"了（本轮最关键）

原来的音频节拍是**按 061 执行了多少条指令**来点的：
`fire_every = 51.2M / 采样率`（`nc3000_dsp.c: audio_pace()`）。
可固件在等 061 应答时会走 `nc3_dsp_rx_ready()`，那里**额外**给 061 塞指令（`n3_run_steps(64)`）
——`$3C` 一次启动被轮询 **13.7 万次**，于是 061 实际跑的指令远多于"主控周期 × 5"，
DAC 也就跟着快。实测：

| | 20 ms 内产出的样本 | 折算采样率 |
|---|---|---|
| 修之前 | 1475 | **73,750 Hz（标称的 2 倍）** |
| 修之后 | 763 | **38,150 Hz ≈ 36,790 ✓** |

音频快一倍 + 混音器按 36,790 Hz 取样 ⇒ 波形被拉碎 ⇒ 听着就是噪音。

修法：

1. `spce061a/host/nc3000_dsp.{h,c}`：新增 `link->audio_off`，置 1 时 `audio_pace()` 不再自己点 DAC。
2. `src_nc3000/spce061_bridge.cpp`：`nc3_dsp_run(steps)` 里用**主控时基**算该出多少样本
   —— `samples = steps × 采样率 / 51.2M`（`steps` = 主控周期 × 5，不含 UART 轮询补的那些），
   再直接 `spce_timer_fire_audio()` 点这么多次。

这样 DAC 只跟"主控时间"走，和固件 TimerA 写的采样率严格一致。

```

27 帧（486 字节）就是 apple 的语音数据（在 `celp_data` 里能找到对应片段），
所以"发什么"是对的。问题在**发多快**和**061 跑多快**：

| 现象 | 根因 |
|---|---|
| 固件把 550 字节在 **同一毫秒** 灌完 | 忙线（IO 0x0E bit4）只在每个 1 ms 时间片末尾才刷新 ⇒ 固件轮询时看到的永远是"空闲" |
| 061 每帧只出 **637** 个样本（真机/参照工具是 **992**） | 061 的指令预算是"每片再加 UART 轮询那几步"，等于**跑得比真机快** ⇒ 解码器跑到 DAC 前面，语速加快+杂音 |

1. `nc3_dsp_ready()` / `nc3_dsp_write()` 里各给 061 补 24 条指令 —— 忙线于是**实时**，
   固件自然会等（实测那 550 字节从一个毫秒摊开到约 500 ms）；
2. 加 `g_slice_charged` 记账：这些补跑的指令**从本片的预算里扣**，
   `nc3_dsp_run()` 只补差额 ⇒ 061 每秒执行的指令数 = 主控周期 × 5（真机的 4.8~5 倍），
   而 DAC 样本数仍按主控时基算。

修完实测：

```

| 现成产物 | `roms/nc3000_dl/`（已经装好 音乐1/音乐2.mid 的 nor/nand） |

### 12.2 为什么卡了这么久：FS 的 inode 表是"日志式 + 双世代"的

实测出来的结构（`tools/nc3kfs.py` 是这轮写的解析/查询工具）：

```
inode 记录 = 32 字节，槽位 = (id - 1) * 0x20，记录以 A8 A8 结尾
  id(2) attr(2) st(1) date(4) time(5) cnt(2) ?(2) blk[4](8) 保留(4) A8A8(2)
  st: 0xC0=当前有效  0x40=已作废  0x80=过渡

NOR 里有两份 inode 表（世代轮流用）：
  0xFC000 起 = 新世代     0xFD000 起 = 老世代
  日志区从 0xFDBC0 / 0xFE000 往后追加新记录（追加一条"新 inode"，并把父目录那条改成 st=0x40）
NAND 侧还有一份副本：`.nand` 偏移 0x0000-0x3FFF（= FS 扇区 0x2 的前 31 页，第 32 页是根目录块）
```

所以一次"下载文件"是这样落盘的：

```
NAND：文件数据写到新扇区（本例 0xC95）、父目录新目录块（本例 0xC8D，条目在块内 +0x10）
NOR ：日志区追加 <新 inode 131 → 0xC95> 和 <inode 52(/midi) → 0xC8D>
      此时**还没生效**：记录没被整理，固件读表时看不到新 inode ⇒ 目录"空"
INT $051C：(InodeReclaimAll) 把日志整理成一份完整的新表（写到另一个世代），这时才真正生效
```

三个对照实验（都用 `--dump-lcd` 看"和弦音乐"的画面）：

| 实验 | NAND 里 inode 52 | NOR 里的记录 | 画面 |
|---|---|---|---|
| 只 `put` | 0xE2E | 日志里有 52→0xC8D（已提交）+ 131→0xC95（**没** A8A8 结尾）| 空目录 |
| `put` + 手工给 131 那条补 `A8 A8` | 0xE2E | 同上 | **音乐1.mid** |
| `put` + `INT $051C` | 0xE2E | 整理过的新表 | **音乐1.mid** ✅ |

### 12.3 与 Lee 版模拟器的对照（顺手解决的老疑问）

* Lee 模拟器的"**文件→虚拟硬盘**"对话框是它**自己实现**的一套 FS 读取器（不是跑固件），
  所以它能列出文件 ≠ 固件认得；里面的"碎片整理"就是同一类整理动作。
* 让用户用 Lee 模拟器下载过一次文件，它写出来的 `.nor/.nand` 与本模拟器 `put` 的结果
  **逐字节同构**：同样是"131→0xC95 的记录没有 A8 A8 结尾"⇒ 李版模拟器下载完也没有做整理，
  固件大概率同样看不到（这也反向印证了根因）。
* 顺带确认：固件自带的文件管理器不列 `.mid`（提示"此目录无可显示文件"），
  所以**验收要看"和弦音乐"的列表，而不是资源管理器**。

### 12.6 顺带记录：FS 的一些"实物尺寸"

| 关系 | 值 |
|---|---|
| FS 扇区 N ↔ NAND 设备页 | `page = 32 * N`（恒等，无坏块重映射） |
| `.nand` 文件偏移 | `(page - 64) * 528`（文件第 0 页 = 设备第 64 页；设备 0-63 页来自 `.nand0`） |
| 一个 FS 扇区 | 32 × 528 = 16896 字节 |
| 目录块格式 | `[16B 头(通常是 ".." 条目)][16B 条目]...`，条目 = 2B inode + 14B GBK 名（`00`/`FF` 填充），`FF FF` 结束；空目录整块全 `FF` |
| 目录块位置 | 就写在 inode 的 `blk[0]` 所指扇区的**页 0**；条目从 +0x10 开始 |

## 13. 第十三轮（2026-09-27 深夜）：**A —— 侧面"红外接收"键接通** ✅

（详细分析见 `docs/NC3000_按键矩阵实测.md` 第 29 节，这里只记结论与改动清单。）

### 13.1 根因

上一轮把 `0x21` 判成"红外硬件载波产生"，错了。真因两条：

1. 固件写 `$C7` 时是 `$EE3A[X] | 0x80`，所以红外键的**实际键值是 `0xA1`**（录音是 `0xA2`），
   按 `0x21` 搜表当然搜不到；
2. 它走的是主扫**列计数器 `$C8` 的槽位 8/9**（`$ED76`–`$EDCC`）：
   把 `$EFB3 = {04,08}` 写进 **port6($1E) 的 bit2/bit3**，然后**读 port0($08) & $F1**，
   有变化就 `LDA $EE3A,X`（`$EE3A = {22,21}`）→ `ORA #$80` → `$C7`。
   模拟器此前只建模 port6 的 bit0/bit1，bit2/bit3 没人管，所以怎么按都没反应。

### 13.2 改动

`NekoDriverIO.cpp::UpdateKeypadRegisters()` 末尾加一段：

```cpp
if (nc3000mode) {
    unsigned char side = 0;
    if (w1e_port6_OL == 0x04) { if (keypadmatrix[0][3]) side = 1; }      /* 录音列 → 0xA2 */
    else if (w1e_port6_OL == 0x08) { if (keypadmatrix[3][3]) side = 1; } /* 红外列 → 0xA1 */
    if (side) port0data |= 0x01;
}
```

只在固件驱动那两条列线时才注入，主扫（`port6 = 0`）不受影响。

### 13.3 实测

| 项 | 结果 |
|---|---|
| 键值 | `(3,3)` → `$C7 = A1`（PC=`$EE24`，固件自己写的）→ 掩掉 bit7 变 `0x21`（PC=`$D681`）|
| 功能 | `$03E3 = 0x21`（PC=`$D6D0`）→ 画面出现 **"搜索通讯设备…"**（= 红外接收模式）|
| 回归 | 和弦音乐列表仍在（`out/nc3000/seq_reg/midi_list.bmp`）；顶排热键 0C/04/02 照旧 |
| 证据 | `out/nc3000/seq_ir/f_19000.bmp` |

### 13.4 新工具

* `--io-rwatch <port>`：记录某个 IO 口的**读**（带 PC 和寄存器），本轮靠它看到
  "侧键扫描时 port0 读到 0x00"，从而确定要注入的是"拉高"而不是"拉低"。
* `tools/sweep_keys.ps1`：穷举 128 个矩阵坐标，直接打印固件解出的 `$C7` 与写入点。

⇒ **剩下的只有 E（0.5% 时基漂移）。**

## 14. 第十四轮（2026-09-27 深夜）：**E —— 时基漂移修掉** ✅

### 14.1 现象

GUI 的主循环是"**一个真实毫秒跑一片 `RunTimeSlice(1)`**"（`main.cpp`：
`expected_tick += SLICE_INTERVAL` + `SDL_Delay`），而 `RunTimeSlice(1)` 想要
`CYCLES_MS = 10240` 个周期。但它是这么写的：

```cpp
while (cycles < target_cycles) cpu_run3();   // cpu_run3 里固定跑 cpu_batch(默认 64) 个周期
```

"凑够就停"⇒ 每片平均**多跑 ~25 周期**。实测：

| 时刻 | cycles | 折算周期/毫秒 |
|---|---|---|
| 5000 ms | 51,351,627 | 10270.3 |
| 10000 ms | 102,676,564 | 10265.0 |
| 15000 ms | 154,001,242 | 10264.9 |

也就是模拟出来的时间比真实时间**快 0.24%**（长跑 1 小时，文曲星时钟会快 ~9 秒）。
这个量级听不出来（所以上一轮判为"听感不可辨"），但它是真的在漂。

### 14.2 修法：跨片补偿（`nc2000.cpp`）

```cpp
static int64_t cycle_carry = 0;      /* 上一片多走的周期，这一片扣回来 */
...
void RunTimeSlice(uint32_t time_slice) {
    uint32_t new_cycles = time_slice * CYCLES_MS;   /* × speed_multiplier 之后… */
    if (cycle_carry > 0) new_cycles -= min(cycle_carry, new_cycles);
    else if (cycle_carry < 0) new_cycles += -cycle_carry;
    ...
    while (cycles < target) cpu_run3();
    cycle_carry = (实际走的周期) - (本来该走的周期);
}
```

只动"这一片要跑多少周期"，不碰 CPU 批量、不碰 DSP 分发，所以音频路径完全不变。

### 14.3 实测

| 时刻 | cycles | 周期/毫秒 |
|---|---|---|
| 5000 ms | 51,210,263 | 10242.1（含第一片的启动余量）|
| 10000 ms | 102,410,241 | **10240.00** |
| 15000 ms | 153,610,299 | **10240.00** |
| 60001 片 | 614,410,274 | 期望 614,410,240，**只差 34 个周期**（0.0000055%）|

### 14.4 回归（声音逐字节对拍）

同一条命令（`nc3000_dl` → 网络 → ↓↓↓ → 输入 → 输入 播放音乐1）跑 60 s，
把 061 的原始 DAC 流 dump 出来和**改动前**的那份对比：

```
raw061.bin（改前） 3,602,038 字节
raw061_new.bin（改后）3,602,038 字节
逐 16 位样本比较：1801019 / 1801019 完全一致（100.00%）
```

⇒ **时基修正没有动到音频**，两个目标同时成立。

## 16. 修一个"跑不起来"的问题（2026-09-27）：静态链接 + 启动脚本

### 16.1 现象

用户双击 `src_nc3000\nc3000.exe` 报：

```
无法定位程序输入点 clock_gettime64 于动态链接库
```

### 16.2 诊断

用 `objdump -p nc3000.exe` 看导入表，发现：

```
DLL Name: libgcc_s_seh-1.dll
DLL Name: libstdc++-6.dll
DLL Name: libwinpthread-1.dll
            060c5d00 <none> 000c clock_gettime64      ← 就是这个
            060c5d08 <none> 0055 pthread_mutex_destroy
            ...
DLL Name: SDL2.dll
```

也就是说 **`clock_gettime64` 是从 `libwinpthread-1.dll` 导入的**，而这个 DLL 我们**没有**
放在 exe 旁边（`build.ps1` 只复制了 `SDL2.dll`）。于是 Windows 按 exe 目录 → 系统目录 →
`PATH` 的顺序去搜，用户 `PATH` 上（Git for Windows / MSYS2 之类都带一份）那份**更旧的**
`libwinpthread-1.dll` 被加载，里面没有 `clock_gettime64` ⇒ 报错。

> 对照证据：`nc3000_headless.exe` 没有这个问题——它的 main 不调用 `clock_gettime`，
> 所以导入表里根本没有这个符号。

### 16.3 修法（两条一起上）

1. **静态链接 mingw 运行时**（`build.ps1`）：`-static -static-libgcc -static-libstdc++`。
   这样 `-static` 会让 ld 选**静态**的 `libSDL2.a`，于是再补上 SDL2 需要的系统库
   （`user32 gdi32 winmm imm32 ole32 oleaut32 uuid version advapi32 setupapi shell32 hid`），
   结果是 **exe 里连 SDL2.dll 也不需要了**：

   ```
   修好后的导入表：ADVAPI32 / GDI32 / IMM32 / KERNEL32 / ole32 / OLEAUT32 /
                   SETUPAPI / SHELL32 / USER32 / VERSION / WINMM
                   + api-ms-win-crt-*（UCRT，Win10+ 自带）
   ```

   不再有 `libwinpthread-1.dll`、`libstdc++-6.dll`、`libgcc_s_seh-1.dll`、`SDL2.dll`，
   `clock_gettime64` 也彻底消失。（代价：exe 从 17MB 变成 33MB。）

2. **`main.cpp` 不再用 `clock_gettime`**：改用 kernel32 的 `GetSystemTimeAsFileTime`
   （FILETIME 是 1601 起的 100ns 计数，换算成 Unix 毫秒）。这样即使以后改回动态链接，
   也不会有这个符号依赖。

### 16.4 附带：双击启动脚本 `run_nc3000.cmd`

直接双击 exe 还有第二个坑：模拟器要读**工作目录**下的 `resource/lcdstripe_*.bmp|json`，
而且 `--rom` 的默认路径是相对的，所以必须在 `src_nc3000` 目录里带 `--rom` 启动。
仓库根目录放了一个 `run_nc3000.cmd`：

```bat
set ROM=%~dp0roms\nc3000_dl\nc3000
cd /d "%~dp0src_nc3000"
nc3000.exe --nc3000 --rom "%ROM%"
```

（脚本特意写成**纯 ASCII**：中文注释在 GBK 代码页的 cmd 里会被拆成乱码命令。）
换 ROM 只改 `ROM=` 那一行。

而且**直接双击 `nc3000.exe` 现在也能跑**了，另外两处改动：

1. **不指定机型时默认按 NC3000 起**（`settings.cpp`，原来是默认 nc2000）。
   本仓库就是 NC3000 移植版，这样才对。
2. **ROM 自动探测**（`settings.cpp` 的 nc3000 分支）：默认路径
   `roms/nc3000` 不存在时，依次试
   `roms/nc3000` → `roms/nc3000_dl/nc3000` → `roms/lee2/nc3000` →
   `../roms/nc3000` → `../roms/nc3000_dl/nc3000` → `../roms/lee2/nc3000`，
   找到哪个用哪个（以本仓库产物 `nc3000_dl` 优先）。

### 16.5 验证

| 项 | 结果 |
|---|---|
| 导入表 | 只剩系统 DLL；`clock_gettime64` / `libwinpthread` 均消失 |
| GUI（`run_nc3000.cmd`） | 出现 NC3000 开机画面（"闪存中有数据 清除吗？"），窗口标题 `NC3000` |
| GUI（**直接双击 exe**，不带任何参数） | 同样正常起来（日志：`no mode specified, default to nc3000` + `rom auto-detected: ../roms/nc3000_dl/nc3000`）|

## 17. 用户报"按 N 进 debug 命令行"：**两个问题叠在一起**（2026-09-27）

用户现象："打开后按 N 键，系统没有进驻菜单，而是进 debug 命令行界面了"，并补充
"模拟器跑的系统没进系统菜单"。查下来是**两件互不相干的事**同时存在。

### 17.1 问题一：exe 自带的**控制台窗口**抢了键盘焦点（已修）

GUI 版原来是"控制台子系统"程序，双击时会**额外弹出一个黑窗口**（里面是模拟器的
printf 日志：`cycles per second is …` 之类）。实测：启动后**前台窗口是这个控制台**
（`FGClass=CASCADIA_HOSTING_WINDOW_CLASS`，标题就是 exe 路径），SDL 模拟器窗口在它后面。
于是用户按的键全进了那个黑窗口，模拟器一个键都收不到 ⇒ "系统没进菜单"，
而屏幕上那个带文字的黑窗口就被当成了 "debug 命令行界面"。

**修法**：

* `build.ps1` 给 GUI 目标加 **`-mwindows`**（Windows 窗口子系统）⇒ 不再有控制台窗口，
  只剩 SDL 窗口。要用日志时加参数 `--console`，`main()` 里会 `AllocConsole()` 再挂出来。
  （无头版 `nc3000_headless.exe` 保持控制台程序，命令行工具必须能打印。）
* `init_resource()` 里加 `SDL_RaiseWindow(window)`，保证启动时窗口在前台。
* 资源路径加兜底：`resource/` 找不到时再到 exe 所在目录找 `resource\`，方便搬走。

验证：`tools/win_enum.py nc3000.exe` 现在只列出 `SDL_app "NC3000"`，没有控制台窗口；
用 `tools/lee_win.ps1 sendkey`（带正确 scancode 的按键）走完
"N → 输入"，画面正常进入 2×6 主菜单。

> 附带修了一个调试工具的小坑：`SendMessage(WM_KEYDOWN)` 的 lParam 里**必须带 scancode**，
> 否则 SDL2 会把这个键翻译成别的 keycode（实测 scancode=0 时被当成 `` ` ``，
> 结果打开了模拟器内置命令行——这正是最初误判"按 N 会进命令行"的来源）。
> `tools/lee_win.ps1` 的 `sendkey` 现在会自己 `MapVirtualKey` 算 scancode。

### 17.2 问题二：**你自己的 NAND dump 被预处理脚本切错页**（已修，现已能开机）

修完问题一之后按 N 还是进不去菜单，用无头版对照才看清：**这是固件自己画的 `>` 界面**
（无头版 dump 出来的 LCD 里也是 `>`，而无头版根本不会画模拟器命令行）——也就是文曲星
固件在"闪存中有数据 清除吗？选 N"之后，因为**挂不上文件系统**而掉进了它自己的调试监视器。

原因在 `tools/nc3000_rom_prep.ps1`：

```
info/NC3KSYSNAND.nand 的第 0 字节 = 01 00 ba 80 c0 … a8 a8   ← 这已经是 inode 1 的记录
```

即这份 dump **本身就是从设备第 64 页开始**的（等价于模拟器的 `.nand`），
而脚本却按"含前 64 页"又切掉了 64 页（33,792 字节）当 `.nand0` ⇒ 整份镜像错位 64 页，
固件自然找不到文件系统。

**修法**：脚本现在先判断首字节是不是 inode 1 的记录
（`01 00` 且 +0x1E 处是 `A8 A8`）：

* 是 ⇒ 这份 dump 就是 `.nand`，原样使用；`.nand0` 写 64 页 `FF`
  （模拟器 `nand.cpp` 自己会写 `ggv nc3000` 签名）。
* 否 ⇒ 还是按老办法切成 `.nand0` + `.nand`。

重跑 `powershell -File tools\nc3000_rom_prep.ps1` 后，`roms/nc3000.nand` 开头就是
inode 表（`01 00 ba 80 c0…a8 a8`），无头版实测：

```
8s  : 授权画面（英美权威双授权）
24s : ★ 2×6 系统主菜单（英汉/AHD/剑桥/PDA/计算/时间 + 汉英/词库/学习/游戏/换算/系统）
```

顺带确认用户这份 dump **带的是用户自己机器的数据**：按 网络 键出来的是
`1.托福试题 2.有声读物 3.旅游全球话`（Lee 的参照 ROM 是 `应用程序/文书浏览/有声学习/和弦音乐/歌曲音乐`）；
061 固件也是从这份 NAND 里的 `升级061.bin` 加载的（日志 `[061] NAND 升级061.bin firmware`）。
> **注（2026-09-27 后已变）**：那只是当时的状态；现在默认改为 `061.dat`(283D，真机同款)，
> NAND 那份要 `NC3_DSP_NAND=1` 才切，见 §22.7。
热键 06 / 红外 21 在它上面同样解得出。

## 18. 第十九轮（2026-09-27）：用户报的四个小问题

### 18.1 "产品信息有误，请接洽代理商"（按输入进主菜单前那一屏）

**根因**：NC3000 把"产品信息"存在 **NOR 0xED000**（bank 0x1D，256 字节）：

```
金远见(6B) 'N' 'C' 机型(2B,小端) 'J' 01 00 00 00 4F 05 09 03 01 …
                ^^^^^^^^^^^^
                机型 = 型号的十进制值：NC2000=0x07D0、NC2600=0x0A28、NC3000=0x0BB8
```

而用户那份 `info/NC3KSYSNOR.nor` **只导出了 bank 0x00~0x10（0x88000 字节）**，
0xED000 这一块没被导出 ⇒ 固件读到全 `0xFF`，就在"按输入进主菜单"那一步弹这句提示
（提示之后它自己初始化默认值，所以还能继续进菜单）。

**定位方法**：先用 `tools/find_str.py` 找到提示串（bank 3 `$9D63`），
再做"混合实验"——把用户 NOR 的前 0x88000 与参照 ROM 的高区拼起来：

| 组合 | 提示 | 结论 |
|---|---|---|
| 用户 NOR + Lee NAND | **有** | 与 NAND 无关 |
| Lee NOR + 用户 NAND | 无 | |
| 用户低 17 bank + Lee 高区 | 无 | 问题在**高区** |
| 用户 NOR + 只补 Lee 的 `0xED000..0xED0FF` | **无** | 就是这一块 |

**修法**：`tools/nc3000_rom_prep.ps1` 现在会检查 dump 是否覆盖 0xED000：
没有（或全 FF）就**合成一块**（机型填 NC3000 = 0x0BB8），并打印提示。
真机那块里的序列号只有完整 dump 才能拿到——想还原就重新 dump bank 0x1D。

> 另：`nor.cpp` 里那套"用 0x78/0x90 命令读的 256 字节 info block"以前给 NC3000 也返回
> 2000 的机型码，现在改成 3000 了（启动路径上固件其实不读它，但系统测试菜单里会读）。

### 18.2 "按一次方向键，菜单跳两格"

**根因**：同一个键被**两条扫描通路各报一次**——`→` 由 `$1C` 组（PC=`$ECB8`）和主扫
（PC=`$EF10`）各产生一个键事件；`←`、`录音` 同理（录音还多一条 port6 槽位 8 的路）。

**实测**（`--watch-write 00c7`）：

```
按 (7,1) 一次  ->  $C7=0x96 @ECB8  →  0x16 @D681      （第一路）
                   $C7=0x96 @EF10  →  0x16 @D681      （第二路）⇒ 光标跳两格
```

**修法**：`io_new.cpp` 的 `$1C` 分支只保留**只有它能认**的复读（X=3）与发音暂停（X=5）；
→/←/录音 交给主扫与 port6 槽位。修完实测：按住 60/100/150/200/600 ms 都只移动一格 ✓。

### 18.3 默认带命令行窗口

GUI 版原来是 `-mwindows`（双击不弹控制台），用户希望**默认就能看日志**。
改成：默认 `AllocConsole()`，加 `--no-console` 才关掉；
`--console` 保留为兼容写法。控制台先出现、SDL 窗口随后 `SDL_RaiseWindow()` 提到最前，
所以**键盘焦点仍在模拟器窗口**（早期用控制台子系统时它抢焦点，正是"按 N 没反应"的假象来源）。

### 18.4 退出游戏后还有一段噪音（BGM 不停）

这条查得最久，最后发现是**三件事叠在一起**：

1. **061 的指令预算多给了 4%**：原代码按"主控周期 × 5"喂 061（真实晶振比是 49.152/10.24 = **4.8**）。
   实测 061 每秒产 **66,996** 个样本，而 DAC 只走 **63,833**，多出来的 5% 全堆在主机侧队列里。
2. **缺背压**：真机 DAC 的 FIFO 只有几个样本，解码器不可能跑到 DAC 前面；我们的队列被堆满
   （上限 24000 样本 ≈ 0.4 s），停止播放后这些"提前解码好的"样本还在放。
3. **停止瞬间重采样比变了 8 倍**：停止后 TimerA 从 63.8 kHz 改回 8 kHz，混音器跟着改比例，
   队列里那点残留被**慢放 8 倍** ⇒ 一段怪声（用户听到的"噪音"）。
   最后还有一下"啪"：061 固件用 **`0x0000` 表示"DAC 关/静音"**（整首歌里只出现在开头和停止时），
   而我们把无符号 DAC 值减 0x8000 转有符号，`0x0000` ⇒ **-32768 满量程**。

**修法**（三处 + 一处容错）：

| 位置 | 改动 |
|---|---|
| `nc2000.cpp` | 061 指令预算 `ran*5` → `ran*24/5`（精确 4.8）|
| `spce061_bridge.cpp` | **背压**：主机侧队列 > 3000 样本时按水位压缩 061 的指令预算（最少留 600 条服务 UART）；解码门 1→0 时把队列淡出清掉 |
| `sound.cpp` | 队列非空时不改重采样比（避免把旧样本按新速率拉伸）；新增 `dsp061_flush_queue()` |
| `spce061a.c` | 写 DAC `0x0000` 按**静音**处理（不再变成 -32768 尖峰）|

**实测**：

```
和弦音乐：退出后尾巴 2.78s → 0.06s（自然收尾，无爆音）
华容道 BGM：退出后尾巴 1.63s → 0（停止指令前就已经收干净）
主机侧音频队列：24000 样本（满仓）→ 0~1200 样本（≈0~19 ms），A/V 延迟顺带从 0.4s 降到十几 ms
061 产率：66,996/s → 64,130/s（与 DAC 的 63,833 基本持平）
```

> 顺带发现：词典发音的分段也变干净了（apple 现在和真机一样是 **2 段**，之前是 3 段）——
> 之前队列满仓时会**丢样本**，那才是"apple 听起来不对"的一部分原因。值得再实听一次。

## 19. 第二十轮（2026-09-27）：发音被放慢 + 蜂鸣器音调 —— **主频其实是 14.7456 MHz**

用户两条反馈：① 单词发音"像放慢了很多倍"；② 蜂鸣器音调偏低。查下来：
前一条是我上一轮引入的**回归**，后一条是**上游源码里一个一直存在的错误假设**。

### 19.1 发音被放慢 4.6 倍（回归，已修）

第 18.4 节修"停止时的怪声"时，我在 `sound.cpp` 里加了"队列非空就不更新重采样比"。
这条对停止收尾有帮助，但**太黏**：单词发音一开始队列里就有样本 ⇒ 比例一直停在空闲的
8 kHz（应为 36.8 kHz）⇒ 发音被**慢了 4.6 倍**。

**修法**：去掉锁比例，恢复"跟着 061 的 TimerA 走"；停止时的残留交给
`dsp061_flush_queue()`（解码门落下时淡出清掉）——它是按事件触发的，不会误伤正常播放。

实测（`--dump-audio` 的混音输出）：词典查 apple → 按发音键 ⇒ **0.370 s**（两段 0.14+0.23），
与 061 的原始流一致 ✓，游戏退出仍然没有尾巴 ✓。

### 19.2 蜂鸣器音调偏低 —— 主频少了 1.44 倍（本轮的关键发现）

蜂鸣器不是"采样率"问题：固件是用**软件延时循环**翻转 IO `0x18` bit7 来发声的，
所以它的频率**正比于 CPU 主频**。用新加的 `NC3_BEEP_TRACE=1` 打出来：

```
[beep] toggle ... (Δ=716, Δ=782, Δ=716, ...)   ← 半周期 ~750 周期，整周期 ≈ 1498 周期
```

而我们一直按 **10.24 MHz** 算 → 6.84 kHz（偏低）。翻 SPDC1064 手册才发现主频应该是
**14.7456 MHz**：

```
第 42 页 Operating mode：TEST[1:0]=01 → PLL(14.7456M)，这正是"正常运行模式"
第 43 页 CPU CLOCK SELECT：CKS=3 → CPU 直接用 OSC；固件开机就把 CKS 设成 3
```

10.24 MHz 是上游 NC2000 模拟器里 nc3000 分支的**猜测值**（≈ NC2000 的 5.12 MHz × 2），
结果**一切由 CPU 指令时间决定的东西都慢了 1.44 倍**——蜂鸣器最明显。

**改动**：

| 位置 | 改动 |
|---|---|
| `comm.cpp` | `CYCLES_SECOND` 的 nc3000 项：`10240*1000` → **`14745600`** |
| `nc2000.cpp` | 给 061 的指令预算：主控周期 × `24/5`(4.8) → × **`10/3`**（49.152/14.7456 精确值）|
| `spce061_bridge.cpp` | `N3_INSN_PER_SEC`：`51200000` → **`49152000`**（061 晶振 49.152 MHz，一周期一指令）|

**实测**：

```
cycles per second is 14745600
按键音主频 6900 Hz → 9900 Hz ✓（与真机同量级）
词典发音 0.370 s ✓ 不变（061 时钟没动，只是主控↔061 的比例换成了精确值）
顶排热键/输入/菜单、按键"按一次只走一格"、游戏 BGM 与退出收尾 —— 全部照旧 ✓
```

> 顺带修正了音频长度上那 4% 的老账：原来 `N3_INSN_PER_SEC=51.2M` 比真实值大 4%，
> 导致 DAC 点得比固件要求的采样率少 4%（这就是早先"bee 我们 511 ms vs 真机 483 ms"的由来）。
> 现在主控×10/3 = 49.152 M = 061 的真实指令率，firing 数与固件设的采样率**完全一致**。

## 20. 第二十一轮（2026-09-27）：**32 位 / WinXP 版 exe**

用户问："能不能把编译出的 exe 弄成支持 32 位 WinXP？"——能，但要**另起一套工具链**。

### 20.1 为什么原来那个 exe 在 XP 上必然不行

现有的 `nc3000.exe` 是 **x86-64 + UCRT**：

```
DLL Name: api-ms-win-crt-runtime-l1-1-0.dll
DLL Name: api-ms-win-crt-stdio-l1-1-0.dll
...
```

`api-ms-win-crt-*` = 通用 C 运行时（UCRT），**Win10 才自带**；XP 上连 64 位进程都跑不了。
所以"支持 XP"不是加个编译开关的事，三条硬门槛缺一不可：

| 门槛 | 原因 |
|---|---|
| **32 位（i686）** | XP 有 32 位版；64 位需要 XP x64（冷门且内核不同）|
| **链 `msvcrt.dll`** | XP 自带 msvcrt；UCRT 不在 XP 上 |
| **SDL2 ≤ 2.0.22** | 2.24 起官方放弃 XP 支持 |

### 20.2 工具链换了什么（都在 `toolchain/`，绿色免安装）

| 用途 | x64（原来） | 32 位 XP（新增） |
|---|---|---|
| 编译器 | `mingw64/mingw64`（UCRT，GCC 16.2.0）| `mingw32`（**i686 + msvcrt**，GCC 16.2.0）|
| SDL2 | `sdl2/SDL2-2.32.10`（x86_64）| `sdl2_xp/i686-w64-mingw32`（**2.0.22**）|

来源（都记在 `toolchain/_dl/`）：

```
winlibs-i686-posix-dwarf-gcc-16.2.0-mingw-w64msvcrt-14.0.0-r1.zip   (268 MB)
SDL2-devel-2.0.22-mingw.tar.gz                                     (14 MB)
```

> 下载踩的坑：`curl` 不带 `--ssl-no-revoke` 会在 schannel 上报
> `CRYPT_E_REVOCATION_OFFLINE`（国内网络常见），表现为**下载 0 字节 / 卡住不动**。
> 另外上一轮有个没退出的 curl 还在往 `_dl/mingw32.zip` 写，和这次的文件撞名了——
> 所以本次落盘先写 `.part`，成功后再改名。

### 20.3 `build.ps1 -XP`

```powershell
.\build.ps1 -XP            # -> nc3000_xp.exe
.\build.ps1 -XP -Headless  # -> nc3000_xp_headless.exe
```

脚本里按 `-XP` 切换：编译器目录、SDL2 目录、**中间产物目录 `obj_xp32/`**（32/64 位的 .o 绝对不能混）、
宏 `-D_WIN32_WINNT=0x0501 -DWINVER=0x0501`、默认输出名；并且**不再往源码目录拷 SDL2.dll**
（本来就是静态链，XP 版更不该混进一个 32 位 DLL）。

源码这边**一行都不用改**——整个代码里只有三处 Win32 API（`GetSystemTimeAsFileTime`、
`AllocConsole`、`freopen("CONOUT$")`），XP 全都有。

### 20.4 验证

```
pei-i386 ✓                      （PE32 32 位）
Subsystem = 2 (Windows GUI) ✓
MajorSubsystemVersion = 4.0 ✓   （4.0 才能被 XP 加载）
导入表只有：KERNEL32 USER32 GDI32 WINMM IMM32 ADVAPI32 SHELL32
            ole32 OLEAUT32 VERSION SETUPAPI msvcrt     ← 无 api-ms-win-crt-* ✓
```

逐条核对过 410 个导入函数，没有 XP 之后才有的（`GetTickCount64`、`FlsAlloc`、
`InitializeCriticalSectionEx`、`GetSystemTimePreciseAsFileTime`、SRW/条件变量那批…）**全都没有**。

功能等价性——**32 位无头版 vs 64 位无头版，同一串按键，逐帧液晶逐字节相同**：

```
开机（20 s，--press 4000 5 6）           : diff = 0 / 38454
主菜单 7 帧（每 2 s，--press 9000 5 1）  : 每帧 diff = 0，总计 0
```

GUI 版在 32 位下也实测能起窗口（`MainWindowTitle = "NC3000"`，进程稳定不退出）。

> 顺带确认了 `--press <ms> <y> <x>` 的坐标含义：**y=行 x=列，都是 0 基**。
> 所以"输入"键是 **(5,1)**（见 `NC3000_键盘.md` 的矩阵表）——之前有的复现命令里写的
> `--press 4000 5 6` 其实是 N/2 键，在 LOGO 画面上等于没按。

## 22. 第二十三轮（2026-09-27）：自测菜单 `9.SPCE061检测` 报 "SPCE061 ERR!" —— 两个根因

用户："按 **W+V+ON/OFF** 可以打开系统自测菜单，里面有一项 `9.SPCE061检测`，
当前运行后显示 `SPCE061 ERR!`"。

### 22.1 这一项到底在查什么（主控、061 两边都反汇编出来了）

**主控侧**（bank0 `$92FA` → INT `$1004` → bank16 `$7335`；`tools/dis6502.js`）：

```
$7335  画 "SPCE061 SRAM TEST:"
$7357  等 061 的 ready 线（$E093 → $FABE）
$7362  链路握手：发 BB 0A，等 BB FA              （$F9E9）
$736D  发 CC 0F，等 CC FF                        ; SRAM 测试开始
$73A3  发 CC 01，等 CC F1                        ; 读 SRAM（F1=通过，1F=失败）
$73DC  通过就画 "SPCE061 SRAM ok!!"，再画 "SPCE061 Check_Sum: … Version:"
$7428  发 BB 0B（数据校验）
       收 BB FB + 4 字节 → $0B00..$0B03          ; 收到别的字节 = 直接 ERR
       ★ 这里有个重试：第一个字节读超时就回 $7428 **重发 BB 0B**
$74FB  发 BB 00 → 收 2 字节（版本字）→ $0B04/$0B05
$7549  把 $0B00..$0B05 以十六进制填进画面，SEC 返回（进位=1 表示成功）
$7538  任何一环失败 → 画 "SPCE061 ERR!!"，CLC 返回
```

**061 侧**（NAND 里那版 284F；`tools/unspdis.py --rom out/升级061_denand.bin`）：

```
CF7E 处理 BB 0B：
        r3:r4 = Σ[0x8000..0x81FF] + Σ[0x8204..0xFBFF] + Σ[0xFFF5..0xFFFF]   (32 位字和)
        r1 = (r3==[0x8202] && r4==[0x8203]) ? FBBB : FCBB
        回 r1，再回 r3、r4
```

（`061.dat` 那版 283D 是**另一份代码**：只比较 `[0x8200]/[0x8201]` 与 `[0x8202]/[0x8203]`
两对是否相等——它的两对本来就相同，所以用 061.dat 时自检一直是 OK。）

### 22.2 根因一：NAND 里的 `升级061.bin` 是"待烧写映像"，校验和标头没填（已修）

用新写的探针 `spce061a/host/dsp_selftest.c`（不经过 6502，直接喂命令）实测：

| 映像 | 0x8200/0x8201 | 0x8202/0x8203 | `BB 0B` 的回答 |
|---|---|---|---|
| `061.dat`（283D） | `10F7 303B` | `10F7 303B` | **`BB FB`** + `10F7 303B` ✓ |
| `升级061.bin`（284F） | `0000 0000` | `793B 3131` | **`BB FC`** + 算出来的字和 ✗ |

284F 那版是**自己现算**一遍字和再和 `[0x8202]/[0x8203]` 比。而 `升级061.bin` 是
"升级用的映像文件"、不是任何一颗芯片的 flash dump：它**头两个字是留给烧写时填的 0**，
另外 `0x8000-0x81FF`（升级不重写、所以不在文件里）在我们这儿读出来是全 0，
算出来的字和自然对不上文件里那份期望值（那份期望值是在**真芯片的引导扇区**上算的，
而 061.dat 是另一台机器/另一版，代进去也对不上：实测 `313D 8893` vs `793B 3131`）。

**修法**（`src_nc3000/spce061_bridge.cpp` 的 `boot_fw()`）：按固件自己的算法把 32 位字和
重算一遍写回**两对**标头（写回的位置正好在求和区间之外，所以稳定）。
细节：`0xFFFF` 要按 0 算——模拟器里这个地址是 SACM 内核当 bank 用的 shadow 寄存器
（读回 0），而 flash 里那位是 `0xFFFF`，不抹平会正好差 `0xFFFF`（实测）。
只在"两对不一致"时动手，`061.dat` 不受影响。

> ⚠️ **2026-09-27 晚用户要求后，这段补写已改成默认关闭**（见 §22.9）：
> 默认**一个字节都不改**，只打印一行提示说明"自检会回 BB FC"；
> 想研究 284F"如果自检通过会显示什么"时才显式打开：
> `set NC3_DSP_FIX_HEADER=1`（配合 `NC3_DSP_NAND=1`）。默认固件 061.dat 两对本来就相等，两种情况都不受影响。

### 22.3 根因二：主控等回包只等 ~14 ms，我们的 061 被限速拖成 ~37 ms（已修）

修完标头以后第一轮握手全对（`BB 0B → BB FB`、`BB 00 → 4F 28`），但屏幕**还是 ERR**。
把 `--dsp-trace` 的字节流按时间对齐，问题一目了然：

```
43521  >BB 0B        ← 主控发命令
43535  >BB 0B        ← 14 ms 后没等到回包，重发（$7428 的重试）
43548  >BB 0B        ← 再重发
43562  >BB 0B        ← 再重发
43575  <BB FB EB 95 6A 30   ← 我们的 061 终于回了（慢了 ~53 ms）
43576  >BB 00        ← 主控读走的是**四条回包里的第一条**
43707  <BB           ← 于是"版本查询"读到的是第二条回包的开头，不是版本字
```

队列里堆了 4 份回包 ⇒ 后面每一步都读到陈旧字节 ⇒ 最终 ERR。

为什么慢：没有音频流时（解码门 `gate=0`）`nc3_dsp_run` 会把每片给 061 的指令数
限到 **3000 条**（061 核心是模拟器里最贵的一块，空闲时没必要全速跑）。可**命令回包
恰恰只在 `gate=0` 时发生**，于是这 3000 条的限速把"回包延迟"从真实芯片的 ~3 ms 拖到 ~37 ms。

**修法**（同上文件）：加一个"活跃窗口"——真的往 061 塞过字节、或从它那儿读到过字节，
之后 150 ms（主控周期计）内**不限速**；`nc3_dsp_rx_ready()` 在等回包时每次也让 061 多跑
512 条（原来是 64 条）。键盘扫描那些 `$3C` 轮询不写 `$3A`、队列也是空的，所以不受影响。
改完实测：**主控一次就把命令发完（不再重发）**，061 在 13 ms 内回包，总字节数
从 `sent=668 / recvd=576`（一堆重试垃圾）降到 `sent=24 / recvd=28`（干净的一轮）。

### 22.4 怎么验证"自检到底成没成"

`call` 那个调试桩是 `INT / CLC / BCC -6`，会**不停重复触发同一个 INT**，
而这一项每轮只要 ~250 ms、最终结果只闪现几毫秒 —— 所以直接 `call 04 10`
看到的永远是下一轮的中间画面（这也是最初误判"还是 ERR"的原因）。

新增 **`call1`** 命令：只触发一次 INT，把返回的进位记到 `$03F0`，然后原地自旋。

```powershell
.\nc3000_headless.exe <rom> --ms 33000 --hold 150 --press 4000 5 6 `
    --cmd-at 30000 "call1 04 10" --dump-ram 0x3F0 1 out\result.bin
# $03F0 = 0x01  ⇒ 进位=1 ⇒ SPCE061 自检成功
```

实测结果：

| 检查 | 结果 |
|---|---|
| `$03F0`（INT 返回进位） | **0x01 = 成功** |
| 画面 | `SPCE061 Check_Sum: eb 95 6a 30` / `Version: 4f 28`（= 284F）|
| 字节流 | `BB0A→BBFA`、`CC0F→CCFF`、`CC01→CCF1`、`BB0B→BBFB+4B`、`BB00→4F28`，一次过 |
| 回归：开机→游戏菜单 | ✅ 照旧 |
| 回归：词典发音（061 流 373 字节） | ✅ 照旧 |
| 回归：华容道 BGM | ✅ `rate=63833`、`dac fired=743558` |

### 22.5 怎么在模拟器里进自测菜单（这一步也踩过坑）

**按法是：先关机，然后按住 W+V 再按 ON/OFF**（用户原话）。两个坑：

  用默认 150 ms 的话 `--press 30000 1 4 --press 30100 3 6 --press 30300 4 0`
  里 W 早在 30150 就松开了 ⇒ 只会正常开机。实测 **`--hold 600`** 就能进菜单：

  ```powershell

      --press 26000 4 0 `                       # 先关机
      --press 30000 1 4 --press 30100 3 6 --press 30300 4 0   # 按住 W+V 再按 ON/OFF
  ```

  画面（`out/selftest/vd__31000.bmp`）：`1.自动检测 / 2.液晶检测 / 3.键盘检测 / 4.录放音检测 / 5.内存检测 …`
* 菜单里**直接按数字键**就运行对应项（按 `9` = 矩阵 (6,4) = U 键 → `9.SPCE061检测`）；
  按 `↓` 不是移动光标，而是会让菜单退出/机器重走一遍开机。

### 22.6 还差一步：走"真机那条路"时仍然是 ERR

从**主菜单**直接调 INT $1004 时自检通过（§22.4）。但从 **W+V+ON/OFF → 自测菜单 → 第 9 项**
走，屏幕仍然是 `SPCE061 ERR!!`。两边字节流一对比，差异很明确：

```
（直接调 INT：061 没被休眠过）
   BB 0A → BB FA      ✓
   CC 0F → CC FF      ✓      ← SRAM 测试开始

（真机那条路：开机/唤醒时主控先做过 BB0A → AA 00(停止+应答) → AA 01(休眠)）
   BB 0A → BB FA      ✓      ← 唤醒握手是应答的
   CC 0F → CC 0F      ✗      ← 少了 SRAM 测试该有的 FF
```

也就是说：**`AA 01` 休眠之后，我们这颗 061 虽然会应答唤醒握手，但状态没回到"能跑 SRAM 测试"**
（061 固件里 `CC 0F` 走的是两条不同分支，一条回 `CC FF`、一条回 `CC 0F`）。
下一步要在 284F 的休眠/唤醒处理里找那个状态变量（`AA 01` 处理程序 → 设置/清除的标志位），
对着真机行为补齐；或者拿真机这一项显示的 Check_Sum/Version 反推它到底走哪条分支。

### 22.7 真机读数拿到了 —— 结论翻转（2026-09-27 收尾）

用户把真机这一项的读数报了回来：

```
Check_Sum: f7 10 3b 30      → [0x8200]=0x10F7, [0x8201]=0x303B
Version:   3d 28            → [0x8204]=0x283D
```

**这正是 `spce061a/rom/061.dat`（出厂 283D）的头，一字节不差。** 说明：

1. **真机那颗 061 跑的是出厂固件，NAND 里的 `升级061.bin`(284F) 只是随机器带的升级包。**
   模拟器以前默认加载的是那份升级包 —— 换错了。现在 `g_use_nand = 0`（默认 061.dat），
   想研究 284F 用环境变量 `NC3_DSP_NAND=1`。
2. 换成 061.dat 之后，模拟器自检画面的读数与真机**完全一致**：
   `Check_Sum: f7 10 3b 30` / `Version: 3d 28`（截图 `out/selftest/r283__32750.bmp`），
   INT 返回进位 = 1。

### 22.8 剩下的 ERR 其实在固件里，不是模拟器的锅

把"真机那条路"的字节流和真机读数对上之后，剩下那点差异的解释很干脆：

* 283D 固件里 `CC 0F`（SRAM 测试开始）的处理程序**恒定**发 `r1 = 0x0FCC`，
  也就是回 **`CC 0F`**；
* 而主控 BIOS（bank16 `$7398`）读第二个字节后 `CMP #$ff`，要的是 **`CC FF`** ⇒ 必然走 ERR 分支。
* 对照其它同类子命令就能看出这行数字"不对劲"：`CC 05` 回 `CC F5`、`CC 06` 回 `CC F6`、
  `CC 01` 回 `CC F1`（都是 `0xF0|参数` 的高字节），只有 `CC 0F` 的高字节是 `0x0F` 而不是 `0xFF`。

**两份互不相干的同版本内核映像**（`spce061a/rom/061.dat` 和 `spce061a/emu/a1600_image.c`，
两者头都是 `10F7 303B` / `283D`）在那一处的字**都是 `0x0FCC`**，
所以这基本可以确定是**出厂固件/B​IOS 这一对本身的毛病**（真机自检第 9 项应该也是 ERR，
只是它照样把 Check_Sum/Version 显示出来）。

于是现在模拟器在两条路上的行为分别是：

| 走法 | 061 的 CC 0F 应答 | 自检结果 |
|---|---|---|
| **正常开机进系统菜单后再测**（真机用法） | `CC 0F`（与固件代码一致） | ERR —— **与真机一致** |
| 直接 `call1 04 10`（调试用，唤醒后立刻发命令） | `CC FF`（我们这边的解析时序恰好错开一位） | OK |

> 也就是说：**真机怎么显示，模拟器就怎么显示**；调试用的 `call1` 那条路反而"过于乐观"。
> 如果真机自检第 9 项显示的其实是 `SPCE061 OK!!!`（请用户再确认一下），
> 那说明真芯片 flash 里这一处是 `0xFFCC`（比我们手里的两份映像都新），
> 那就把映像里这一个字改成 `0xFFCC` 即可（一行改动）。

### 22.9 用户结论：真机是 OK；**这件事到此挂起，禁止"打补丁骗自己"**

> ⚠️ **2026-09-28 更正（见 §25）**：本节最后那句"剩下的 ERR 其实在固件里，不是模拟器的锅"
> **不成立**。真因是主控的 `IO 0x0E` bit3 = 061 复位线一直没建模（BIOS 在自测项开跑前会
> 脉冲一次复位）；补上之后自测第 9 项在模拟器里**正常通过**。本节"不许改映像/改流程糊过去"

用户指出（2026-09-27）：**"如果显示 ERR，那就不会显示 check sum 和 Version 了"** ——
这个判断和我们反汇编出来的代码完全一致：

```
$7398  SRAM 测试第二个字节必须 = FF
       失败 → JMP $7538  → 只画 "SPCE061 ERR!!"，**跳过** Check_Sum/Version 两行
       成功 → $73DC 画 "SPCE061 SRAM ok!!"，再画 "SPCE061 Check_Sum: … Version:"

所以真机屏幕上出现了 `Check_Sum: f7 10 3b 30` / `Version: 3d 28` ⇒ **真机这一项是 OK 的**

⇒ 结论：我们手里的两份 283D 映像（那一处都是 `0x0FCC`）与真芯片的 flash

**用户明确要求：这个问题先放起，不要靠改映像去"修"。** 理由很直白——那等于自己骗自己

## 23. 第二十四轮（2026-09-27）：播放和弦音乐时"中间有一小段突然变快" —— 音频队列被顶爆丢样

用户："加载带两首音乐的固件，开机后按网络进和弦音乐，两首都会出现：播放中间有一小段
（几秒）声音像是被加快了，随后又正常，会不会是缓冲区的问题？"

**是缓冲区的问题，而且位置就在 `dsp061_max_queue`。** 这次把 GUI 的音频队列曲线录下来了
（`out/music_bug/gui_log6.txt`，`NC3_SND_DEBUG=1` + `--no-console` 把 printf 重定向到文件）：

```
blk=1401  q=3307                     ← 正常播放，队列 ~3 k 样（≈50 ms）
blk=1426  q=15501  push+49249        ← 产率突然涨到 1.33 倍
blk=1451  q=24000  ovr+4152          ← 顶到 24000 上限，开始丢样本
blk=1476  q=24000  ovr+5282
blk=1501  q=24000  ovr+5747
blk=1526  q=23694  ovr+3870          ← 这一波共丢 ≈19000 样 ≈ 0.3 s 的音乐
```

**根因**：061 的采样跟着**模拟时间**产，声卡跟着**墙上时间**放，中间那个队列是缓冲；
而模拟器为了追进度会短时间全速跑（`main_loop` 里那套 ±300 ms 漂移逻辑：落后了就一路
flat-out 追到只落后 300 ms）。追赶的那一下产样比声卡快 ~1.33 倍 ⇒ 队列冲顶 ⇒
`drain_dsp061_audio()` 里 `size() >= dsp061_max_queue` 就把**新样本丢掉** ⇒
听感就是"音乐往前跳一下 / 快了几秒"，跳完队列被放掉又恢复正常。

**修法**（两处）：

| 位置 | 改动 |
|---|---|
| `main.cpp`（主循环） | **音频背压**：积压超过 ~47 ms 就 `SDL_Delay` 等声卡放掉一些，回到 ~24 ms 再继续跑。阈值按当前采样率折算（音乐/发音/空闲同一延迟量级），队列不降就立刻放弃（声卡没开/暂停时不会卡界面）|
| `sound.cpp` | `dsp061_max_queue` 24000（0.38 s）→ **32000（0.5 s）** 当最后一道保险（一次追赶最多瞬产 300 ms ≈ 19 k 样，原来的上限刚好会被顶爆）|

**验证**（同样按键序列，GUI 实测）：

| | 修前 | 修后 |
|---|---|---|
| 队列峰值 | 24000（顶格） | **9333** |
| 丢样总数 | ≈19000 | **0** |
| 稳态队列 | 涨到 15 k 再被丢 | ~3000 样（≈45 ms）|
| 音质 | 中间跳一段 | 连续（听感正常）|

回归：词典发音、华容道 BGM、音乐整曲、开机进菜单都照旧（发音那次 `overruns=0` 不变）。

> 小记：这次是靠"把 GUI 的 printf 重定向到文件 + 用 PostMessage 送按键"跑通的，
> 两个坑记一下：
> 1. GUI 默认 `AllocConsole()` 会把 stdout 抢到控制台窗口，抓日志要加 **`--no-console`**；
> 2. 给 SDL 窗口发方向键要把 lParam 的**扩展键位（bit24）**置上，否则 SDL 认不出来

### 24.2 更正 §21.3：`INT $0505` 不是"音乐推流"

§21.3 用"华容道 564 次 `INT $0505`、黑白棋 0 次"当决定性证据。这次在同一台机器上量：

| 状态 | `INT $0505` 次数 |
|---|---|
| 只停在游戏菜单（25 s，不进局） | **400** |
| 华容道 经典关卡（45 s） | 564 |
| 黑白棋 棋盘（45 s） | **1199** |

菜单里一次游戏都没进也有 400 次（≈16 次/秒），**说明 `$0505` 是周期性节拍/定时服务，

## 25. 第二十六轮（2026-09-28）：自测 `9.SPCE061检测` ERR **已解决** —— 根因是 `IO 0x0E bit3`（061 复位线）没建模

用户："翻篇，解决自测的问题吧"（§22.9 当时按用户要求挂起）。这一轮查到了真因，**§22.8/§22.9
那句"剩下的 ERR 其实是固件自己的毛病"作废**：固件里确实有回 `CC FF` 的分支，只是模拟器
一直没走到它——因为**主控给 061 的复位线（`IO 0x0E` bit3）我们从来没实现过**。

### 25.1 固件其实有两条 `CC 0F` 分支，走哪条取决于"复位后第一条命令"

`061.dat`（283D）里 `CC 0F` 只有一个地方回 `CC FF`，在**复位路径**上：

```
$8213  sp = 0x07FF
$821A  call $823A            ; 握手：循环 pop，直到拿到 0x0ABB，回 0xFABB
$821C  [0x0796] = 0
$821F  pet watchdog
$8222  call $CDC4            ; ★ PEEK（只看不取）
$8224  cmp r1, 0 ; je $821F  ; 队列空就继续等
$8226  cmp r1, 0x0FCC        ; ★ 是不是"CC 0F"这条命令
$8228  jne $8232             ; 不是 → 去主循环（一辈子出不来了）
$822E  r1 = 0xFFCC           ; ★ 是 → 回 CC FF
```

另一条在主循环派遣里（`$CB72` 跳表按命令字低 nibble 选，`[C]` → `$CC54` → 再派发 →
`$CF89` 的 `cmp r2,0x0F` / `je $CFB6` → `$CFB9 r1 = 0x0FCC` → 回 **`CC 0F`**）。

用新写的探针 `spce061a/host/wd_probe.c`（直接喂命令 + 看 PC/喂狗）实测，规律很干脆：

| 序列 | `CC 0F` 回答 |
|---|---|
| 复位 → `BB 0A` → `CC 0F`（`CC 0F` 是握手后第一条命令） | **`CC FF`** ✓ |
| 复位 → `BB 0A` → 任意别的命令 → … → `BB 0A` → `CC 0F` | `CC 0F` ✗ |
| 复位 → `BB 0A` → 干等一阵 → `BB 0A` → `CC 0F` | `CC 0F` ✗ |

也就是说：**只要 `CC 0F` 不是"复位后紧跟 `BB 0A` 的第一条命令"，固件就必然回 `CC 0F`**。
而主控 BIOS（bank16 `$7398`/`$739B` 反汇编）读第二个字节后是 `CMP #$FF`，不是 `$FF`
就直接 `JMP $7538`（只画 `SPCE061 ERR!!`，连 Check_Sum/Version 都不读）。

### 25.2 真机为什么 OK：BIOS 在自测前会把 061 **复位**一次

`--io-watch 0x0e` 抓主控对 `IO 0x0E` 的写（这次跑出来的原始记录）：

```
[io] t=26018ms  pc=$F972  $0E <- 00        ← 先关机
[io] t=26018ms  pc=$F97C  $0E <- 08
[io] t=30341ms  pc=$F972  $0E <- 00        ← W+V+ON/OFF 再开机
[io] t=30341ms  pc=$F97C  $0E <- 08
[io] t=33563ms  pc=$F972  $0E <- 00        ← ★ 启动自测第 9 项，紧跟一个 00→08 脉冲
[io] t=33563ms  pc=$F97C  $0E <- 08
```

那两行的代码（bank0，文件偏移 `$7970`/`$797A`，运行时 `$F972`/`$F97C`）：

```asm
LDA $0435 / AND #$F7 / STA $0E     ; bit3 = 0  ⇒ 拉住 061 复位
JSR $FB73                          ; 延时
LDA $0435 / ORA #$08 / STA $0E     ; bit3 = 1  ⇒ 放开复位（061 重启）
```

**所以 `IO 0x0E` 的位定义是：bit4 = 061 的 ready/busy（输入，早就建模了），
bit3 = 061 的 /RESET（输出，一直没建模）**。真机上自测项一开跑，061 被拉复位 → 重跑
`$821A` 握手 → `$821F` peek，紧接着的 `CC 0F` 才是"复位后第一条命令" ⇒ 回 `CC FF` ⇒ OK。
模拟器里这条写被当成普通端口值存进 `ioReg[]` 就没了，061 一直停在主循环 ⇒ ERR。

> 顺带解释了两个老疑问：
> * §22.4 那条 `call1 04 10` 为什么"莫名其妙是 OK"——因为那条路**从头到尾没发过
>   `AA 00`/`AA 01`**（`--dsp-trace` 里只有 `BB 0A → CC 0F → …`），061 还停在复位后的
>   握手循环里，`CC 0F` 恰好就是第一条命令。它不是"时序错开一位"，是真的走了正确的分支。
> * 自测菜单那条路为什么 ERR——菜单自己会先做 `BB 0A → AA 00 → AA 01`，把 061 踢进主循环。

### 25.3 改法（一行硬件行为，不是补丁）

`src_nc3000/io_new.cpp` 的 `io_v2_write()` 原来没有 `0x0E` 分支（落到 `default:
ioReg[address] = value`）。现在补上：

```cpp
case 0x0e: {
    uint8_t old = (uint8_t)ioReg[address];
    ioReg[address] = (uint8_t)(value & ~0x10);   /* bit4 是输入，别存 */
    if (!(old & 0x08) && (value & 0x08))
        nc3_dsp_boot();                          /* bit3 0→1 = 放开复位，061 重启 */
    return;
}
```
