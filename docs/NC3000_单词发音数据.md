## 1. 先把语音库从 NAND 里无损取出来

`celp_data`（Inode 26，313 块 = 5,128,192 字节）在物理 NAND 上的起点是 **`0x2AAB000`**
（前面整片是 `0xFF` 未用区）。按已确认的 528 字节页结构去交织：

```powershell
node tools/nand_deinterleave.js 0x2AAB000 0x4E4000 "" out/celp_data.bin
```

得到 **5,128,192 字节 = 313 × 16KB**，与 Inode 的块数**完全一致** —— 这本身就是
“起点 + 结构都取对了”的强证据（之前的 061 固件同样验证过这套去交织）。

## 2. 文件结构（实测）

```
0x00000 .. 0x44000   76 个“偏移表块”：每块从 0 开始递增到 <0x8000，块之间不连续
0x44000 .. 0x4E4000  74 个 64KB 数据段（74 × 65536 = 4,849,664 字节，正好等于数据区大小）
```

* 表项是 **16 位、单位 = 2 字节**：第 n 项的值就是该音节在对应 64KB 段里的**字偏移**。
  每个表块覆盖 **0x8000 个字 = 64KB**，正好对上 74 个 64KB 段。
* 相邻表项之差（= 音节长度）**全是 5 的倍数**，也就是音节长度都是 10 字节的整数倍；
  单音节长度范围大致 **10 ~ 100 字节**（实测最大 delta = 50 → 100 字节）。
* 表块以“值回落到 0”为界，共 76 个（比 74 个数据段多 1~2 个，应是首/末块的边界效应）。

`tools/celp_parse.js` 会打印 76 个表块的项数、最大值与统计：

```
block  0 @0x00000  entries= 1568  max=0x7fe4
block  1 @0x00c40  entries= 1724  max=0x7fdf
...
```

## 3. 主控侧把音节送给 061 的确切格式（从固件反汇编得到）

BANK0B（file 0x58000 起）的 `$9A95 / $9AFA / $9B27` 就是“放单词”的例程：

```
$9A95: LDA $03E9 -> JSR $E099 ($FAEE = 0x44 音量)
       LDA $03EA -> JSR $E0C9 ($FB01 = 0x55 速度)
$9ABF: 发 0x99
$9AC9: 发 0x21                     ; 选解码器：RAM [0x04CE] = 4
$9AD3: 遍历 RAM $06AC 起的记录表，数出记录条数 N
$9AFA: 发 0x11 0x01 N              ; “后面有 N 条记录”
$9B1F: 逐条:
        发 0x11 0x03 <记录第3字节> <记录第5字节&0x3F> <记录第4字节>
```

记录表（每条 6 字节）由 BANK0B `$9820-$995F` 生成，输入是**从文件读来的 5 字节**：

```
记录 = [ f(u0,u1,u2) 低 | 中 | 高 ,  u3 , u4 , g(u2) ]      f = 该 24 位值 × 5，g(u2)= (u2&0x3F)|((u2&0x40)<<1)
发送的 3 字节 = [ u3 , u2 & 0x3F , u4 ]
```

也就是：**文件里每 5 字节出一个“记录”，真正发给 061 的只有其中 3 个字节**。

## 4. 目前的回放结果（实测，不能说成功）

`spce061a/host/nc3000_word.c` 把上面这套字节序列打在**真实 061 固件**（`rom/061.dat`）上：

```
boot -> 0x823E: OK
link 0xBB0A: OK 0xBBFA
0x99 0x21 -> [0x04CE]=0004 (want 0004 = word codec), selected
sent 33/33 records; parser=8000      (解析器回到状态 0 → 帧格式被接受)
decoded 1 samples                    ← 没有出声
```

三种送法都试过（都**没有**产出音频）：

| 送法 | 结果 |
|---|---|
| `0x99 0x21` + `0x11 0x01/0x03` 记录（主控真实用法） | 记录全部被接受，只出 1 个 DAC 样本 |
| 同上 + `0xAA 0x02` 结束 | 同上 |
| `0x99 0x21` + `0x22` 流 / `0x33` 流块 | 只出 5 个样本，采样率还停在 755 Hz（说明解码器没被真正启动） |

结论：**“取数据 + 打包 + 传输”这一半已经打通且被固件接受；解码器侧还差一步**。
最可能的原因是脚本里那 5 字节记录的第 2 个字节（`u2 & 0x3F`，作为记录的 `cnt` 字段）
在真实数据里另有含义（例如帧计数/采样数），061 的 S600 解码器要看到合法的帧头才会出音频。

### 4.1 对照实验：问题不在“数据对不对”

把**已经验证能出声的 A1600 数据**（`testdata/t09_a.a16` 的比特流，共 1526 条记录）
用**同一条 word 路径**（`0x99 0x21` + `0x11 0x01/0x03`）喂进去，结果同样是 **1 个样本、没有声音**：

```
mode 0 / sent 1526/1526 records / decoded 1 samples
```

而同一份数据走 `0x99 0x40` + `0x33` 流块时能出 73042 个样本。两者对比说明：
**`0x11`（TTS/记录）这条路径在这份固件里并不会直接驱动 DAC 解码** ——
要么还缺一个“开始播放/开始合成”的触发（0xAA 系列或另一个 `0x99` 参数），
要么 `0x11` 的记录只是被缓存进另一个合成器缓冲，需要后续命令才启动。
所以目前的“听不到”不能归因于我从 NAND 里取出的数据。

另外：按“单位 = 2 字节”解释，单个音节的长度只有 10~100 字节（≈0.01~0.06 s @8kHz），
偏短，提示每个表项可能只是**一段更长的记录的起点**（记录的 `u0/u1` 两个字节很可能就是
“下一条记录”的链指针，见 BANK0B `$17F0` 里 `5*V + 0x0A5A` 的算法）。
这一条也需要下一步验证。

## 5. 下一步（建议顺序）

### 4.3 用探针把 `0x11` 载荷语义测出来了（本轮）

新增工装 `spce061a/host/word_probe.c`：只发一条记录，然后把解析器/合成器的所有单元打出来。

```
baseline          0716=0000 0727=0006 0728=072A 0729=0000 072A=0000 075A=072A 0763=075D
after 0x11 0x01 01  0716=0001 0718=0001 0728=0006 072A=0001 075A=072B
after 0x11 0x03 12 40 00
                    0715=0003 0716=0003 0718=0012 0719=0040 071A=0000 075A=072E
```

结论（实测，不是推测）：

* `0x11 0x01 N` / `0x11 0x03 a b c` 的载荷是**原始数据字节**，被依次塞进 DSP 侧
  **RAM `0x072A` 起的暂存缓冲**（两个字节打包成一个字），写指针在 `[0x075A]`：
  发 1 字节 → `075A = 072B`；发 3 字节 → `075A = 072E`（+3）✓
* 这个暂存缓冲**只有约 50 个字**（`0x072A`..`0x075B`）。所以**主机必须边发边等 DSP 消费**：
  我一次性灌 20 条记录（60 字节）会把它灌满，固件的反应就是**中止这条流**
  （`[0x04CE]` 被清成 0、PC 落到 `0xCE25`）——这正好解释了上一轮的“记录被接受但无声”。

### 4.4 为什么还是不出声：这份固件里 TTS 路径不启动音频引擎

* 音频引擎（TimerA FIQ）唯一的启动点：`sub_C89C` 写 `P_TIMERA_CTRL(0x700B)` /
  `P_INT_CTRL(0x7010)`，它只被 `0xC41E` 调用；
* 而 `0xC41E`（清 `[0x0000]`、清 `[0x04CE]`、再启动定时器 = “停止/空闲”）和
  单词码流的启动例程 `0xC438`（里面才调用索引 4 的 `0xD319`）在整个固件里
  **既没有 `call`、也没有 `pc =` 跳转、也不在 `0xFC00` 向量表里**（全库检索为 0 命中）；
* 对照：A1600 的初始化 `0xB5D6` 是被 `0xC8C6` 分派器正常调用的，所以 A1600 能出声；
  索引 4 在 `0xC8C6` 里只做到 `[0x0713]=0x14` + `call 0x9EA3`，而这一步要先有
  `[0x0000]` 的 bit7（“流已开始”），bit7 又只在**环形缓冲满**的那条分支里被置位——
  于是形成“解码器要先跑起来才会开始跑”的循环，实际结果就是永远不启动。

也就是说：**在这份 061 固件里，`0x11`（TTS/记录）这条路不会驱动 DAC**。
NC3000 的单词发音要么走**流式路径**（`0x99 0x21` + `0x33/0x22` 块，我试过，仍不出声，
说明 061 侧索引 4 的解码器对容器/数据还有要求），要么这条路径本来就是给别的机型准备的
（NC3000 的固件里同时保留了 TTS 记录和流式两套例程）。

建议下一步（按性价比）：

1. 把 061 侧 `0xD225`（索引 4 的每块解码）入口的**入参/环形缓冲格式**读清楚，
   或者用 061 自带的 4bit/ADPCM 参数反推容器头；
2. 用主控侧 `0xCJxx` 那个发 `0x33/0x22` 的例程（BANK0B `$9C41` 一带）确认
   NC3000 到底用哪条路放单词（它在 `$9CE7` 发 `0x33`、`$9D2E` 发 `0x22`）；
3. 真机抓一次串口（`0x3A/0x3B/0x3C`）就能直接判定，一台机器即可收尾。

### 4.5 关键结构：记录 = 描述表，音频 = `0x33/0x22` 流（本轮）

扫 `JSR $9CAA`（BANK0B 里那个发 `0x33`/`0x22` 的流式发送例程）得到唯一调用点：
**bank11 `$9BD7`** —— 也就是说它就在**同一条“放单词”例程里**，
紧跟在 `$9B79-$9BD4` 那段“遍历记录表”的代码后面。把两段连起来看：

```
$9A95  0x44/0x55 → 0x99 0x21 → 0x11 0x01 N → N × 0x11 0x03 <描述>
$9B79  遍历记录表：从每条记录里取出 24 位地址（×5 = 文件字节偏移）
                  和 6 位长度（[0x06E8]，u4 非 0 时再 +1）
$9BD7  call $9CAA  ← 流式发送：0x33 + 15 字节 / 最后 0x22 + 长度 + 数据
$9BF5  0xAA 0x03（等 0xAA 0x00）
$9C41  0xAA 0x01 睡眠 + 端口复位
```

配合 4.3 的实测（`0x11` 载荷只进约 50 个字的 DSP 暂存缓冲），可以确定：

> **`0x11 0x03` 记录不是音频本体，而是一张“流描述表”**
> （每条 = 文件偏移 + 长度），真正的压缩音频是用 `0x33`/`0x22` 流式发过去的，
> 数据由 `$9D51`（bank5 文件读例程）按描述表里的偏移从 `celp_data` 里读出来。

这样记录里那个“×5 的 24 位地址”和 `u2&0x3F` 的 6 位“长度”就都对上号了。

### 4.6 试过的五种主机侧组合（都不出声，问题在 061 侧）

| 组合 | 结果 |
|---|---|
| 只发记录（`0x11 0x01/0x03`） | 记录被收下，1 个样本 |
| 记录 + `0xAA 0x02` / `0xAA 0x03` | 同上 / 同上 |
| 只发 `0x22` 流 / 只发 `0x33` 流 | 5 个样本，采样率停在 755 Hz |
| **记录（描述表）+ `0x33/0x22` 流** | 1 个样本 |

五种组合下索引 4 的解码器（`0x9EA3` / `0xD225` / `0xD319`）**一次都没被调用**，
而同一台模拟器跑 A1600（`0x99 0x40` + `0x33` 流）能出 73042 个样本。
所以剩下的缺口在 061 侧“索引 4 怎么才算把流开起来”这一段。

### 4.7 索引 4 的启动链，以及“这条路是死代码”的证据（本轮）

从 disasm 读出的索引 4 启动链：

| 地址 | 内容 | 前置条件 |
|---|---|---|
| `0xC8F8` | 解码服务：推进环形缓冲；**它才会把 `[0x0000]` 的 bit7 置位** | 由 TimerA FIQ（`0xC109`）或 `0xC66B` 调用 |
| `0xC47D` | bit7 置位后进入：`[0x04CE]` 分派 | bit7 |
| `0xC489` → `0xD1BF` | **单词码流的环形缓冲初始化**：`[0x04C3]=9`、`[0x04C4]=9×N`（N 来自记录描述表） | 上一步 |
| `0xC4A2` → `0xC8C6` → `0x9EA3` | 索引 4 的编解码器初始化：`[0x0713] = 0x14` | 上一步 |
| `0xC962` → `0xD225` | 索引 4 的每块解码（出音频） | 上面都成立 |

`0xD1BF` 里 `[0x04C4] = 9 × N` 这一段正好印证了 4.5 的结论：**记录表就是用来定环大小的描述表**。

但这条链的**最前端是断的**：

* 唯一会写音频定时器控制寄存器 `P_TIMERA_CTRL(0x700B)` 的是 `sub_C89C`，它只被 `0xC41E` 调用；
* `0xC41E`（停止/空闲）和 `0xC438`（单词码流启动例程）在整颗固件里：
  **既没有 `call`、也没有 `pc =` 跳转、也不在 `0xFC00` 向量表里** ——
  直接按 16 位小端在映像里搜这两个地址，**命中 0 次**；
* 我手工把“环形缓冲已满”的 bit7 置起来（mode 6）也无效：固件反而把 `[0x04CE]` 清成 0；
* **两份 061 固件（`061.dat` 与 NAND 里那份）表现完全一样**（都是 1 个样本、`0713` 保持 0）。

也就是说：**这份 061 固件里 TTS/单词记录的启动路径是死代码**（编译时被裁掉或从未接入），
NC3000 的单词发音应该是走另一条流式路径（`0x99 0x21` + `0x33/0x22`），
或者 061 侧需要主机在 `0x99 0x21` 之前再做一次我还没找到的初始化。

下一轮要查的方向（最后一个未排查点）：
主控 `$9A8B` 那一步会调用 bank5 的文件读例程（`INT $0505/$0506/$051A/$051B`），
**这些例程内部是否也在往 0x3A/0x3D 写命令**（往 061 发“开始播放”之类的初始化）——
如果有，那就是我漏掉的触发；如果没有，就说明机器上单词发音确实走流式路径，
需要继续对 `0xD225` 的容器格式下功夫。

### 4.8 celp_data 的寻址方式全部解出来了（本轮，含与提取结果的对拍）

BANK0B 的三个前置例程（`$9722` / `$9771` / `$97F0`）把“音节 → 文件数据”这条路讲清楚了：

```
$9722  LDA #0→$0280; LDA #3; JSR $997A   ; 用 3 除：$0280/3 = 音节组号 k
       LDA $9993+3k,$9994+3k,$9995+3k → ($82,$83,$84)   ; 固件里的 3 字节表 = 该组的文件地址 V
$9771  V(=24 位,来自 $94/$95/$96) 左移 1 位后拆成
          [0x088A] = (2V)&0xFF   [0x088B] = ((2V)>>8)&0x3F   [0x0888] = (2V)>>14
          再给 [0x0888] 加 0x0A5A、[0x088C]=0、长度 [0x09D2]=2、目标 $f0/$f1
          INT $0505            ; ← 文件读：**从文件偏移 2V 处读 2 字节**
$9771  读回的 2 字节 ($0281,$0282) 与 0xFFFE/0xFFFF 比较 = **链表结束标记**
$97F0  取当前项的数据（长度 = [0x06E8]，即 u2&0x3F (+u4 标志)），偏移 = 5*V+0x0A6B
```

由此可确定：

1. **文件地址 = 16KB“簇” + 14 位簇内偏移**，即
   `簇号 = (2V)>>14 + 0x0A5A`、`簇内偏移 = (2V)&0x3FFF`；
   换算回**文件内偏移就是 `2V`**（因为基簇 0x0A5A 正好是文件的第 0 簇）。
2. **5 字节一格的“记录”其实是一条链表**：每项前 2 字节 = 下一项的文件地址（÷2），
   链尾是 `FFFE/FFFF`。这正好解释了为什么“按 2 字节步进读这个区域会得到单调递增的数列”
   —— 我们是在**沿链表走**，不是在读一张顺序表。
3. **基簇 0x0A5A 与物理偏移对拍成功**：
   `(0x0A5A - 2) × 16896 = 0x2AAB000` —— **与我从 NAND 里取出 celp_data 的起点完全一致**；
   而 061 固件那份（Inode 块 0xC30）同样是 `(0xC30-2)×16896 = 0x323DC00` ✓。
   也就是说：**之前那份 celp_data 的提取（起点、528 字节页结构、长度）是完全正确的**，
   只是我把“链表”误读成了“顺序表”。
4. 固件里 `$9993` 那张 3 字节表 = **各组链表的入口地址**，它的数值序列
   （0x621, 0xCDD, 0x1364, …）与我从文件里数出来的“表块起点”（0xC40, 0x19B8, 0x26C6… ÷2）
   一一对应（差 2 字节 = “链尾/链头”的 1 项），两边互为印证。

**下一步（已经非常明确）**：

1. 用链表语义重取一条真正的语音项：从固件 `$9993` 表某个入口开始，按
   “读 2 字节 → 得到下一项地址”走链，每项取长度 `u2&0x3F (+1)` 字节的数据；
2. 把这条链生成 `0x11 0x03` 描述项 + 对应的 `0x33/0x22` 流，喂进模拟器；
3. 观察 `[0x0713]` 是否变成 `0x14`、环形缓冲是否启动，然后出 WAV 试听。

### 4.9 链表语义的实测与“还差一步”（本轮末尾）

新增 `tools/celp_chain.js`（按 `[nextV(2)][u2][u3][u4]`、`nextV` = 偏移 2V 处的 LE16 走链）：

```
node tools/celp_chain.js out/celp_data.bin 0x0 12 dump
  #0 V=0x00000 off=0x000000 next=0x00000 ... → self loop
```

从 `V=0` 出发立刻自环，说明**“next 指针就在 2V 处”这一条我还没读对**：
文件开头是 `00 00 | 05 00 | 0A 00 | 14 00 | 1E 00 | 2D 00 …`，
按 2 字节步进读出来是 `0, 5, 0xA, 0x14, 0x1E, 0x2D …`（单调），
但把这 5 字节当成 `[next][u2][u3][u4]` 时：

* `V=0` → `next=0x0000`（自环）、`u2=0x05`：**u2 恰好等于下一个表值 5**；
* `V=5` → 起始偏移 `0x0A` → `next=0x000A`、`u2=0x14`：下一个表值是 `0x0A`，
  而 `u2=0x14` 对不上。

所以更可能是“**表项 = 描述符偏移，描述符里另外的字段才是下一项/长度**”，
或者描述符起点/字宽还有一处偏差（例如描述符 5 字节但表和描述符共用同一片区域，
需要按“表项 → 描述符 → 数据”三级来读）。下一步就按这个思路把 `V=0x620`
（第一组的入口，= 固件 `$9993` 表的第一项 0x621）附近的原始字节逐字节摊开，
把“表项 / next / 长度 / 数据起点”四个角色彻底对齐，再喂模拟器。

> 结论一句话：**文件寻址（2V、簇 0x0A5A）已经和提取结果对拍成功，剩下的只是
> “5 字节里哪个字段是什么”这最后一步**。

### 4.10 两级间接寻址解出来了（本轮）

把 `$9771` / `$97F0` 的字段运算逐位算了一遍：

| 步骤 | 计算 | 含义 |
|---|---|---|
| `$9771` | 读文件 **2 字节**，地址 = `簇(2V>>14) + 0x0A5A`、`簇内偏移 = (2V)&0x3FFF`、`长度=2` | 取回一个 **14 位偏移 + 2 位簇增量** 的值 |
| `$97F0` | `簇 = 0x0A6B + 2×index + (值>>6)`、`偏移 = 值 & 0x3FFF`、`长度 = 5` | 取回一个 **5 字节数据块** `[u0 u1 u2 u3 u4]` |
| `$9820-$995F` | 记录 = `[5×(u0\|u1<<8\|(u2&0x3F)<<16) 3 字节][u3][u4][g(u2)]` | 发送 `0x11 0x03 <u3> <u2&0x3F> <u4>` |

两个簇基常数的差正好等于数据区起点：

```
(0x0A6B - 0x0A5A) × 16384 = 17 × 16384 = 278,528 = 0x44000   ← celp_data 的数据区起点 ✓
```

所以：**表区（0x0 ~ 0x44000）里存的是“14 位簇内偏移 + 2 位簇增量”，
数据区（0x44000 起）里存的是 5 字节一块的数据，块内前 3 个字节又编码了下一块的位置**——
也就是**两级间接 + 块内链表**。

本轮用 `tools/celp_chunks.js` 按“下一块 = 5×V”试了几种基线（0 / 0x44000）和几个入口 V，
链条都只走 1~2 步就出界：

```
base=0x44000 V0=0xa  -> chunks=2 first=0x44032 last=0x4b1061
base=0x44000 V0=0x10 -> chunks=2 first=0x44050 last=0x411228
```

说明**“下一块地址”这一条还没算对**：大概率不是平坦的 `5×V`，而是要在
“簇 + 14 位偏移”的地址空间里做（增量是**相对当前簇**的，而不是文件内的平坦偏移）。
下一步就按这个改：`next = (cur_cluster + delta_of(5V) ) × 16384 + (5V & 0x3FFF)`，
再喂模拟器试听。

## 6. 勘误与重来：celp_data 之前是「错位 400 字节」取出来的（2026-09-25 晚，本轮）

### 6.1 错在哪

本文 §1 的提取命令是 `nand_deinterleave.js 0x2AAB000 …`。NAND 是 528 字节页
（512 数据 + 16 冗余），而 `0x2AAB000 mod 528 = 400` —— **起点没有落在页边界上**。
于是工具每个 512 字节窗口实际取的是 `data[400..512] + spare[16] + data[0..384]`：
每 512 字节被塞进 16 字节冗余区垃圾。

后果：数据被系统性打散，所以「没有 0xF 帧头」「表项差值是 5 的倍数」「5 字节记录」
这些结论全部建立在被破坏的字节流上。**不能再用。**

正确做法：先从整片 NAND 按页去交织成逻辑镜像，再按 inode 的块号取文件。
`tools/celp_frames.js` 已把这套流程固化（见 §6.4）。

```powershell
# 整片逻辑镜像（101856 页 × 512 = 52,150,272 字节）
python -c "import numpy as np;
raw=np.fromfile(r'info\NC3KSYSNAND.nand',dtype=np.uint8);
p=len(raw)//528; raw[:p*528].reshape(p,528)[:,:512].reshape(-1).tofile('out/nc3000_full.bin')"
```

### 6.2 对齐后 celp_data 是什么（实测）

逻辑镜像里 inode 表就在 0 号块开头（32 字节记录、末尾 `A8 A8`）。sysdir（inode 1）
的目录区在逻辑 `0x31B8180`，文件名是 GBK/ASCII，逐个对得上：

```
id=25 word_ID    4 块   64 KB
id=26 celp_data  313 块 5,128,192 B
id=27 ahd_celp   16 块
id=28 wqx_celp   20 块
id=29 cb_celp    16 块
id=31 世界.bin   229 块
id=38 拼音061.bin 4 块
id=47..51 zijian / celps / jinqu / hexuan / xinhua
```

`celp_data` 的首块 = 2506 → 逻辑 `0x2728000`，正好落在「全盘扫 18 字节 0xF 帧头」
命中区（`0x2720000..0x2960000`）里。对齐后：

* **celp_data 是一整条 18 字节/帧的 S600 码流**，从文件 **偏移 10**（10 字节文件头）开始；
  帧首字节高半字节 = 0xF（与 `a13-20.vnt` 同构）；
* 每 16 KB 块的最优相位按 **−4** 递变（10, 6, 2, 16, 12, 8, 4, 0, 14, …），
  而 `16384 mod 18 = 4` —— 这正是「码流跨块连续」的指纹，所以文件确实是
  **块连续**的一整条流，不是拼装出来的；
* 文件内部还有两段别的数据：约 `0x1E0000..0x240000` 是全 `0xFF` 未用区；
  `0x240000` 起是一张 16 位递增小步长的表（21620, 21635, 21645, 21660…，差值 10~20），
  再往后（`0x28xxxx` 起）是低帧密度的另一段数据 —— 这两段有待继续解读。

## 7. 「点名单词」这一轮的进展（2026-09-25 深夜）

### 7.1 文件系统先彻底理清（勘误 §6.1 的顺带收获）

* inode 记录（32 字节、末尾 `A8 A8`）里 `+18/+20/+22` 是前三个块号，
  **`+24` 不是第 4 个块，而是「起始块 + 块数」= 结束块号**（端指针）。
  实测：celp_data `blk[0]=2506, cnt=313, blk[3]=2819=2506+313` ✓；
  inode8 `99+768=867` ✓；word_ID `2501+4=2505` ✓。
  所以**这些文件都是连续块**，取文件 = `img[blk0*0x4000 : (blk0+cnt)*0x4000]`。
* sysdir 文件清单（逻辑 0x31B8180）：`word_ID(25) celp_data(26) ahd_celp(27)
  wqx_celp(28) cb_celp(29) midigame(30) 世界.bin(31) 拼音061.bin(38)
  zijian(47) celps(48) jinqu(49) hexuan(50) xinhua(51)`。
* `word_ID` 用正确块表重取后：7413 条 3 字节记录 `(flag, u16 LE)`，
  flag=1 段 5141 条、flag=2 段 2336 条（各自严格递增），之后 0xFF 填充，
  0xC000 起还有 16 KB 的 S600 帧数据。

### 7.2 主控固件里的「放单词」链（bank0B + bank0，已逐条读通）

| 地址 | 作用 |
|---|---|
| bank0B `$9A95` | 真·放音：等 ready → 发 `0x44` 音量 / `0x55` 语速 / `0x99 0x21` → 遍历 RAM `$06AC` 的 **6 字节记录表**（终止 = 记录第 5 字节 bit7）→ 发 `0x11 0x01 N`，再逐条 `0x11 0x03 <rec+3> <rec+5&0x3F> <rec+4>` |
| bank0B `$9CAA`/`$9DAA`/`$9E3D` | `0x33`+15 字节 / `0x22`+长度 的流式发送；**每次发字节前死等 ready 线**（§3.11 的根因就在这里） |
| bank0B `$9722` | 用 24 位键（`$94/$95/$96`）在 `$9993` 起的 3 字节升序表上定位**页号** → `$0280` |
| bank0B `$9771` | 由 `$94/$95/$96` 算描述符：**簇 = 0x0A5A + 键/8192，偏移 = (键 mod 8192)×2**（即键以 2 字节为单位、簇 = 16 KB） |
| bank0B `$97F0` | 由 `$0280/$0281/$0282` 算描述符（**簇基址 0x0A6B**），再用 `INT $0505` 读文件，**每步前进 5 字节**（⇒ 记录 = 5 字节） |
| bank0B `$981D..$9837` | 把读到的数据整理成 6 字节记录表（`$06AC` 起），记录第 6 字节 bit7 = 结束 |
| bank0 `$F2D4` 起 | 逻辑地址 → (簇, 偏移) 的分段映射（簇 4 / 0x0C22 …），供文件读例程用 |

⇒ 一句话：**单词的音频 = 一份「5 字节记录表」+ 「0x33/0x22 流」**，
记录里的 24 位地址以 2 字节为单位、按 16 KB 簇寻址；两条基簇分别是
`0x0A5A`（音频）与 `0x0A6B`（记录表）。按逻辑号换算，`0x0A5A` 落在
celp_data 的 **+0x240000**，`0x0A6B` 落在 **+0x284000** —— 都在这条文件的尾部区。

### 7.3 词典本体（inode 8，12.6 MB）的结构

```
0x000000..0x041050  24 位键表：66580 条，4 字节/条（[00][v24 LE]）
0x041050..0x054000  连排正文（英文词 + GBK 中文词/释义，带 0x04/0x12 之类控制码）
0x054000..0x0B4000  词条数据区（键指向这里；簇 120..144 = 0x78..0x90）
0x0B4000..          其它（含 6 字节结构，见 0x0B3F00 附近的 E4 00 …）
```

* 键的编码 = `[页号 8 位][页内偏移 14 位]`：页号 **0x78..0x90 = FS 簇 120..144**，
  页内偏移 0..0x3FFF；同一页内键**步长只有 3~8**（≈ 每个词条的字节数），

## 8. 判定实验（2026-09-26 凌晨，含**排除项**）

### 8.1 已排除 ①：word_ID 的值不是 S600 帧地址

若 word_ID 的 16 位值是以 2 字节为单位的 S600 帧地址，则每个段的 `value % 9`
必须是**同一常数**（帧=18 字节=9 个 2 字节单位）。实测（flag=1 段 5141 条、
flag=2 段 2336 条）9 个余数几乎均匀分布 ⇒ **不是**帧地址。
同一检验也否掉了「按字节地址（% 18 == 10）」「10 字节帧（% 10 == 0）」。

### 8.2 已排除 ②：celp_data 尾部的「5 字节记录 + 24 位 S600 地址」

对尾部数据区（0x279500 起，2.42 MB）按 5 字节记录、24 位地址做参数扫描
（9 个基点 × 0..63 字节偏移 × 5 种记录相位，每种 12 万条），
要求地址落在 S600 帧边界：最好也只有 **0.129**，而随机期望 0.111 ⇒ 不成立。

### 8.3 新增事实 ①：`ahd_celp` / `wqx_celp` / `cb_celp` 是**逐词映射表**

用「连续块」正确装配后（§7.1）：

| 文件 | 大小 | 16 位表项数 | FFFF（无发音） | 值域 | 递增步 | 前 12 个值 |
|---|---|---|---|---|---|---|
| ahd_celp | 262,144 | 131,072 | 47.5% | 0..14,908 | 94.5% | 5171,5172,5175,5176,5177,5178,5179,5181,5183,5184,5187,5191 |
| wqx_celp | 327,680 | 163,840 | 31.7% | 0..**14,908** | 96.6% | 5460,5461,5462,5464,5467,5469,… |
| cb_celp | 262,144 | 131,072 | 76.0% | 0..56,524 | 70.2% | 2292,2297,2303,2304,2314,2318,… |

* 表项数正好是 128 KB 的整数倍 ⇒ 每个文件 = 若干段「64K 个 16 位值」，
  与词典「英汉/汉英」两向（各 64K 词位）天然吻合；
* 值**单调递增、步长 1~5**、且 ahd 与 wqx 的**上界完全相同（14,908）**
  ⇒ 最自然的解释是：**表下标 = 词条序号，值 = 该词在「发音单元表」里的累计位置
  （步长 = 该词的音节数）**，ahd/wqx 共用同一套发音单元，cb 另有自己的一套。

### 8.4 新增事实 ②：celp_data 尾部是 69 张「发音单元目录」

* 0x240000 起共 **69 张表**，合计 **117,443 条**，每张覆盖一个段：
  值域 0..~32,750（≈ 32 KB），**相邻差值全是 5 的倍数**（= 5 字节粒度！），
  每张 272~1902 条（均值 1702）；表区结束于 0x279500，之后是 2.42 MB 数据区；
* 5 字节粒度与固件 `$97F0`「每步前进 5 字节」的记录读法**完全对上** ✓
  ⇒ 这 69 张表就是**发音单元的目录**（段 + 段内位置 + 长度，长度以 5 字节为单位），
  它是「词 → 发音」链上紧挨音频的那一层。

### 8.5 现在的模型（待验证的最后一环）

## 9. 记录格式与音频地址：从固件代码逐条读出来了（2026-09-26）

### 9.1 5 字节记录 = 一个音节（bank0B `$97F0` → `$9B84` → `$9CAA`/`$9D51`）

固件把文件里读到的 5 字节记录（b0..b4）整理成 6 字节 RAM 记录再播放。逐句还原：

| 字段 | 来源 | 含义 |
|---|---|---|
| 音频帧号 V | `((b2>>7)<<16) | (b1<<8) | b0` | 17 位，**S600 帧号** |
| 帧数 FC | `b2 & 0x3F`（`b4≠0` 时 +1） | 该音节的帧数 |
| 「后面还有」 | `b2 & 0x40` | 1 = 同一词还有下一音节 |
| 描述符 | `b3`、`b4` | 发给 061 的 (SO, EO)（即 TTS600 的 SO/FC/EO 三元组） |

关键的两处缩放/基址（都在代码里硬编码）：

* `$9CAA`：`FC ×18`（= 帧数 × 每帧 18 字节），且是先 ×9 再 ×2 —— **每帧就是 18 字节**；
* `$9D51`：音频描述符 = **簇 `0x09CA` + $061d**，偏移 = ($d5,$d4)；
  `0x09CA = 2506` **正好是 celp_data 的首块** ⇒ **音频地址是相对 celp_data 文件头的字节地址**，
  即 `音频字节 = V × 18`（+ 文件头的 10 字节）——**词典单词用的音频就是我们已经听到的那条
  S600 帧流**（前段 1.87 MB / 103,736 帧）✓✓；
* `$97F0`：记录区的描述符 = **簇 `0x0A6B` + 2×页号 + …**，偏移 = ($0281,$0282)；
  `0x0A6B = 2667` → celp_data + 0x284000。

**独立验证**：全镜像搜字节模式 `FD 06 07 00`（= V=1789/FC=7 的规整记录），
共 86 处，其中 **58 处在 image 块 0x29AC000、23 处在 0x29A8000** ——
而 `0x29AC000` 正是 celp_data+0x284000 ⇒ 记录区位置得到独立佐证 ✓。

### 9.2 因此「词 → 音频」的链路（已完整，只差一层换算）

```
词条序号 ──ahd/wqx/cb_celp 的 16 位表──▶ 累计记录序号（步长 = 该词音节数 = 记录条数）
        ──bank0B $9993 的 86 条页表（累计值，步长 ~1724）──▶ 页号 p
        ──记录区（簇 0x0A6B + 2p，偏移 = 页内位置）──▶ 若干条 5 字节记录
        ──每条记录：V×18 字节 = celp_data 里的 S600 帧，FC 帧──▶ 交给 061 播放
```

唯一还没定死的是「累计记录序号 → 页内位置」的换算比例（页表步长 1724 与 2 簇=32 KB
的容量对不上，怀疑页内位置以「记录条数 ×5 字节」还是「字节」为单位，或页不是 32 KB）。
下一步按 §9.3 直接拿一批词做**逐字节核对**即可定案。

```
;         数据地址是偏移地址, 从0开始, 使用时要加上4000h
```

`read_data` 的实现（逐句核对过）与我从 NC3000 固件逆出来的完全一致：

* `frame  = a2[2] & 0x3F`；`a2[2] & 0x40`（= last sign）左移成 bit7 一起存 → **它就是「还有下一音节」标志**；
* `head = a2[3]`、`tail = a2[4]` = 发给 DSP 的 **SO/EO**；
* `start = (a2[2]>>7)<<16 | a2[1]<<8 | a2[0]`（17 位**帧号**），随后 `start = start*16 + start*2 = start*18` ✓；
* 地址换算成 `bank : addr`：`speak_addr = (start*18 & 0x7FFF) + 0x4000`，
  `speak_bank = start*18 >> 15` ⇒ **音频按 32 KB BANK、窗口基址 0x4000 组织**；
* 结果按 **6 字节一条**写进 `VARADDR`（= NC3000 固件里 RAM `$06AC` 的 6 字节记录表）✓。

`play_word(intc[3])` 的入口是**单词 ID**（3 字节）；`find_addr` 用 `ID*2` 去读
**pron.addr**（2 字节/词，`FFFF`=无发音），`find_bank` 用 **pron.bank.tab**
（3 字节/BANK，值是每个 BANK 的起始单词 ID）定位数据 BANK。

## 11. ✅ 链条打通（2026-09-26，本轮）：`*_celp` 的值 = 记录序号

### 11.1 结论

```
词典词条序号 k
   └─(*_celp[word_id] = N)              该 2 字节表就是 NC2000 的 pron.addr
      └─ 记录表在 celp_data + 0x284000 + N×5 ，读 5 字节记录直到 b2 bit6=1
         · 记录 = [b0,b1,b2,b3,b4]：V = ((b2>>7)<<16)|(b1<<8)|b0 （17 位帧号）
           FC = b2&0x3F（帧数），last = b2 bit6，SO = b3，EO = b4
         └─ 音频帧 = celp_data 前段：第 f 帧 = 文件偏移 10 + 18×f
            （再把每帧交给 061，按 SO/FC/EO 播放）
```

### 11.2 判定证据（都是本轮实测）

1. **解析率**：把 `ahd_celp` 的非 FFFF 值按 `BASE + N×5` 读记录，
   86.0% 能解析出「V ≤ 103,736 且 1 ≤ FC ≤ 63」的记录表；
   随机偏移对照只有 33.0%（区域内）和 46.6%（0..1 MB 内）⇒ 公式成立；
2. **后缀共享结构**（最有力）：相邻词条的记录表互为后缀：

```
idx0 (5171) = [A, B]
idx1 (5172) = [B]                 ← 恰好是上一条去掉首记录
idx2 (5175) = [C, D, E, F]
idx3 (5176) = [D, E, F]
idx4 (5177) = [E, F]
idx5 (5178) = [F]
```

   这与「按字母序排列的词条共用尾部音节」完全一致，随机数据不可能出现；
3. **字段合法性**：FC ∈ 3..13 帧（72–312 ms/音节）、SO/EO ≤ 236

### 12.2 词典文件头部的「4 字节记录表」结构（本轮新实测）

对象：`out/file_ahddata.bin`（= inode 9，块 868..2051，0xD90000 起，19,398,656B）。

1. **文件开头 **0 .. 0x41050** 是一张密集表：66,580 条 4 字节记录，`b0 = 0x03`，

### 12.3 负结果（都做过，别再重复）

把「相邻两条记录之间」切段当作「一条记录的文本」，**没有一种对齐**能切出干净的词/短语：

| 试法 | 结果 |
|---|---|
| 常数平移 `c ∈ [-3000, +3000]`（含 ±20 逐字节看） | 切片永远是「任意位置的字串」，如 `.ÿÿµÄthe[I` `nf.]of` |
| 每记录累积修正 -1（假设一条一个被省掉的分隔符） | 同样不成词 |
| 偏移按 2/3/4 倍缩放 | 无改善 |
| 「首字母单调（字母序）」扫描全部 3,184 个 16KB 页 | 只有 0x55 填充页假命中，无真峰值 |
| 「切片全为字母」扫描 `c ∈ [-3000,+3000]` | 平坦 ~0.82，无峰 |

很可能就是 `INDEX.H` 里的「词频索引/词频数据」，和我们要的「拼写」不是同一层。

原因现在也清楚了：**9B 节点是 ROM 侧的运行时结构，不是这两个 .bin 里的静态布局**。

### 12.4 另外两条本轮读通的事实

* ROM 侧（bank 9）trie 走查已经读通，节点 = **9 字节 `[B0B1B2][B3B4B5][B6B7B8]`**
  （$73CF 起，每字符 `addr += (char-'a')*9` 后 `$09D2=9` 读 9 字节到 `$0D1D..$0D25`）：
  * `B0|B1|B2 == 0` ⇒ **叶子**：`$0D23/$0D24/$0D25(=B6B7B8) → $94/$95/$96`（**词 ID**），
    同时 `$0D20/$0D21/$0D22(=B3B4B5) → $0D13..$0D15` 经 `$718C` 换出地址；
  * 否则 **非叶子**：`$0D1D/$0D1E/$0D1F(=B0B1B2) → $0D13..$0D15` 经 `$718C` 换出新基址，
    `$0D83++` 回到 `$73CF` 继续下一个字符；
  * 另一处调用者 `$6CA3` 把 `B0B1B2` 存到 `$0D00-$0D02`、`B3B4B5` 换址后存到 `$0D03-$0D06`、
    `B6B7B8` 换址后存到 `$0D07-$0D0A`（⇒ 一个 9 字节节点里能塞下三个「物理地址」字段）。
  `$718C` 把 3 字节指针 `N` 拆成 `page = N>>14`、`offset = N&0x3FFF` 再加基址 `$0D16-$0D19`；
  物理读用 `$7526`：把 4 字节 `(off16, blk16)` 送 `BRK $05 $05`（bank5 `$4182 → $4AF3`，
  真正的 NAND 页读），`blk < 0x40` 直接读，否则 `blk -= 0x40; off += 1` 循环归一化。
* `info/NC3KSYSNOR.nor` 的 bank→文件偏移映射本轮自己核对过：`bank N` 从 `0x8000*N` 开始，
  CPU 窗口为 `0x4000-0xBFFF`（bank0 是 `0x8000-0xFFFF`）；每个 bank 开头 `60 EA` + 2 字节跳转表
  （第 idx 项在 `+2*idx`），`BRK 05 05` → bank5 `$4182`。反汇编脚本见
  `tools/dis6502.js`，本轮新增 `tools/dstrace.js`（追踪对 `$0D03..$0D0E`/`$0D16..$0D19` 的写）。

### 14.1 词条记录格式（实测）

### 14.3 `word_ID` 的语义定死了：**它就是 `ahd_celp` 的下标（+0x10000）**

（`v` 直接当下标只有 15% 命中，`v-0x1610C` 也只是数值巧合，`v-0x10000` 才是对的。）
⇒ **`word_ID[k] - 0x10000` = `ahd_celp` 的下标**，也就是该词的发音记录序号入口。

```

      →  celp_data + 0x284000 + N*5 起的 5 字节记录链（含 last 标志）
```

### 14.4 唯一剩下的一环：**词头 ↔ word_ID 的配对**

两边都是递增序列，但**数量不同**：词头 27,235 条、`word_ID` 7,413 条
（≈ 每 3.7 个词条一个发音 ID）。而且两边的排序基准不同：

* 压缩流里的词条 = **字母序**（§14.2 已证）；
* `ahd_celp` 的值单调递增、记录链互为后缀 ⇒ 发音表是**按词尾（逆拼写）排序**的
  （§11.2 的「相邻词条记录互为后缀」就是这么来的）。

所以配对要做一次「有序子序列对齐」。两条可执行的判据（建议按序做）：

1. **音节数对齐（纯数据可算）**：词条里 `F0 04` 之后就是**音标原文**（字面转义），
   AHD 音标用 `·`/`-`/`′` 标音节 ⇒ 数出每个词头的音节数；
   而 `ahd_celp[N] → celp_data+0x284000+N*5` 的记录链长度就是**音节数**。
   两边做一次 DP 对齐（词头序 → 发音 ID 序，音节数必须相等），即可定出 7,413 个配对。
2. **听感抽查**：挑几个靠前/靠后的词头，按候选配对放音让用户确认
   （本项目一贯的验证方式，一次两三个词就够定位）。

① 把词频表切出来 → 解出所有词头（含常用词）；② 用音节链长度与词头音节数做 DP 对齐；
③ 再用几个实听锚点校验。
