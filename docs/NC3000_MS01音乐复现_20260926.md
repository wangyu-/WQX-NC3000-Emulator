# NC3000 MS01 音乐：用固件自己的解码放出来（2026-09-26）

> **现状（2026-09-27）**：这条链路已经接进模拟器本体——给虚拟盘装上
> `sysdir/` 认可的 `/midi/音乐N.mid`（见 `tools/nc3k_put.ps1`）之后，
> "网络 → 和弦音乐"能列出曲目、选中即开始播放（061 收到流）。
> 本文是 MS01 的**格式/命令序列/坑**的参考，结论与第 6 节之后的内容仍然有效。
> 总览见 `docs/README.md`，加文件的机制见 `NC3000_NAND_文件系统分析.md` §8。

目标：在 SPCE061A 模拟器上，让 NC3000 的**固件**（`061.dat` / NAND 里的
`升级061.bin`）解码并播放原机的 MS01 音乐。

> 早期曾用 SDK 示例引擎（`emu/ms01_lib.c` = `MS01.S37` 链接映像）作为权宜方案，
> 现已**删除**：`emu/` 里只剩 `main_linux_ms01.c`，它让模拟器加载真机固件、按主控
> 时序喂乐谱（`build/ms01play.exe`）。

结论：**已经放通**。两套固件输出一致，音高随乐谱变化（195→392→887→997→259→440→523→174 Hz…），
换一首曲子输出即不同。

## 1. 音乐文件在哪、是什么格式

原机文件：`info/NC3000原机的midi.rar` → `音乐1.mid` … `音乐20.mid`
（解压副本：`out/midi_orig/NC3000原机的midi/`）

* 不是标准 MIDI（全盘搜不到 `MThd`/`MTrk`），是 **SACM_MS01 的原始乐谱流**。
* 每个文件真实长度 = NOR bank0 `$DEEC` 那张表的第 N 项
  （音乐1 = `0x042B` = 1067 字节），其后一律 `0xFF` 填到 16 KB（一个 NAND 块）。
* NOR bank0 `$DD78` 是 20 个 `/midi/音乐N.mid` 的指针表，`$DD51` 是播放入口。

## 2. 主机侧命令序列（从 NOR 反出来的）

```
0xBB 0x0A                    ; 链路握手，应答 0xBB 0xFA      ($FDE0/$F9E9)
0x44 <0..15>                 ; 音量                          ($FAEE)
0x55 <speed>                 ; 语速/节拍                     ($FB01)
0x99 0x00                    ; 选 MS01                       ($FE2A → $FE21)
0x33 <15 字节> × N           ; 乐谱正文                      ($FC7D)
0x22 <len> <payload>         ; 尾部                          ($FCB6)
```

## 3. 两个必须知道的坑（本次排查的核心）

### 3.1 DSP 会"等数据流建立"才启动解码（宿主只要按顺序喂即可）

DSP 侧的 `0x99` 处理程序走到 `0xC456` 会进入等待循环：

```
C456: r1 = 1; [0x7012] = 1        ; 喂狗
C459: call 0xCE1F                 ; 派发一个已入队的命令字节
C45B: r1 = [0x0000]; test 0x0080
C45F: jne  C464                   ; 出口 A: bit7 = "stream started"
C460: call 0xCDC1                 ; 出口 B: [0x0727] & 2
C463: je   C456
```

而 `0x99` 字节本身虽然会把 `[0x0727]` 置 2（`0xCD45`），紧接着
`0xC454 → 0xCB5F → 0xCD54`（以非零长度调用）又把它**清掉**了。实测的入口状态：

```
C452  04C0=011E  0727=0002     ; [0x04C0] = MS01 输入环基址
CB76  04C0=0006  0727=0002     ; 0x011E 不小于 0x011E → 直接把基址设成 6
CD54  04C0=0006  0727=0002
CB7F  04C0=0006  0727=0000     ; ← bit1 被清
[loop C456] ... 死等
```

**这个循环不是死等**：它每轮都调用 `0xCE1F` 派发已入队的命令字节，所以宿主
继续按正常时序喂 `0x33`/`0x22` 数据包，数据流一建立循环就会退出，随后
`0xC480` 的启动解码、`0xC8C6`（→ codec 3 = `0xAADD`）的 MS01 引擎初始化、
输出环 `0x019F`（长度 `[0x04CD]=0x140`）全部就位，引擎开始按 `[0x04C0]`
逐字推进读乐谱（自增发生在 `0xACCC`）。

> 排查记录：中途一度以为"必须在等待循环里**再发一次 `0x99`** 才能退出"，
> 那是**误判**——当时的对比用的是"抓所有外设写"的旧采集（见 3.2），两边比的是
> 垃圾数据。改成只抓 DAC2 后做对照实验：把重复的 `0x99` 去掉，输出 WAV
> **逐字节相同**（md5 `fe2a7036a955…`）。所以正确的宿主序列就是 NOR 里那套：
> `0x99 0x00` 之后直接喂数据，不需要任何额外命令。

顺带一个模型保真度验证：DSP 里 `0xCDAB: bp = [0x0729]` 紧跟 `0xCDAD: jne`
（跳过 `0xCDAE: r4 |= 0x02`），从字面看像是"依赖前一条 `r1 -= 1` 的 Z 标志"。
把模拟器的"加载指令是否更新 N/Z"改成**不更新**后，MS01 反而只能发出一个固定音
（788 Hz），说明 MAME 的行为（`ld` 更新 N/Z，本模型默认如此）才是对的。
该开关留在 `unsp_t.ld_sets_flags` 里当诊断用，默认值不变，A1600/S600 结果不变。

### 3.2 采样：只取 DAC2，并减掉 0x8000 中点

* `m.io_trace` 对**所有**外设写都会回调。不加过滤会把定时器/端口寄存器的值
  当样点录进 PCM，听起来就是刺耳方波。
* MS01 的输出在 **DAC2（`0x7016`）**；DAC1（`0x7015`）整个播放过程只写了 1 次。
* 片上 DAC 是无符号、`0x8000` 为中值，PCM 要 `value - 0x8000`。
* 采样率由固件自己的 TimerA 决定：MS01 重装值 `0xFE7F` → `Fosc/2/0x180`
  = **63833 Hz**（SDK 示例是 16 kHz，固件里 MS01 跑 4 倍）。WAV 要按这个速率写。

## 4. 引擎内部地图（NAND 固件地址；`061.dat` 同族，偏移约 +0x1F）

| 地址 | 作用 |
|---|---|
| `0xCE45` | `0x99 <param>` → 索引（`0x00`→3 = MS01，`0x10`→2 = S200，`0x21`→4 = S600，`0x40`→1 = A1600） |
| `0xC574` | `[0x04CE] = 索引` |
| `0xC8C6` | 编解码器初始化分派：`3 → call 0xAADD` |
| `0xAADD` | MS01 引擎初始化：状态块 RAM `0x0500–0x054F`，`[0x04CD]=0x140`，回调 `[0x0533]=0xB19E`、`[0x0534]=0xB2D9` |
| `0xD336` | MS01 的 TimerA 装载 `0xFE7F` + 开 TimerA FIQ（S600 走 `0xD34A`，A1600/S200 走 `0xC8A0`） |
| `0xC450/C452` | MS01 输入环基址 `[0x04C0] = 0x011E` |
| `0xC480` | 启动解码：设环描述符 → 引擎初始化 → 清 `0x019F..0x02DF` → 输出环指针 |
| `0xC773 → 0xAB0E → 0xAE47` | MS01 服务例程（codec 3 专用分支） |
| `0xACCC` | 乐谱读指针 `[0x04C0]` 自增处 |
| `0x0727` | bit1 = "数据流入驻"（`0xCDC1` 轮询）；bit0 = 半字节打包状态 |
| `0x0716/0x0718` | 命令数据暂存计数 / 暂存缓冲 |
| `0x075B..0x0762` | 命令字节队列（**只有 8 字节**，宿主发包要注意节奏） |

## 5. 复现

一键（推荐）：

```powershell
.\tools\nc3000_music2wav.ps1 1                      # 音乐1 整曲，out\NC3000_音乐1.wav
.\tools\nc3000_music2wav.ps1 2 -Seconds 8           # 只取前 8 秒
.\tools\nc3000_music2wav.ps1 1 -Firmware 061        # 换 061.dat 那份固件
```

手工：

```
set TCC=<...>\tcc.exe
cd spce061a

:: 播放器：模拟器加载真机固件 + 主控协议
%TCC% -O2 -I emu -I host -o build\ms01play.exe emu\main_linux_ms01.c ^
      host\nc3000_dsp.c emu\spce061a.c emu\unsp.c emu\firmware_061.c ^
      host\firmware_061_nand.c

build\ms01play.exe 1 out\音乐1.wav            :: 整曲（默认 061.dat）
build\ms01play.exe 1 out\音乐1_8s.wav -t 8    :: 只取 8 秒
build\ms01play.exe 1 out\音乐1_nand.wav -fw nand   :: 换 NAND 的 升级061.bin
build\ms01play.exe "..\out\midi_orig\NC3000原机的midi\音乐1.mid" out.wav

:: 诊断：-diag 打固件侧状态/中断/热点代码页，-pctrace <file> 录 PC 轨迹
```

## 6. 曲子有多长 / 结尾怎么判断

* **一首曲子有多长**（固件实测，整曲渲染自动收尾）：

  | 曲目 | 样点 @63833 Hz | 时长 | 收尾方式 |
  |---|---|---|---|
  | 音乐1 | 1,800,993 | 28.21 s | 曲终静音被探针捕获 |
  | 音乐2 | 2,932,490 | 45.94 s | 同上（`[end] no new samples for 60003840 instructions`） |

  早期还用 SDK 示例引擎放 90 s 做过对照：第 ~28.5 s 之后 RMS 归零，与固件侧 28.21 s
  吻合（那个引擎连同 `ms01_lib.c` 已经删掉，只留下一份对照 WAV）。

* 20 首的篇幅（早期用已删除的 SDK 引擎放 120 s 量得；`≥120` 表示那个演示外壳在
  120 秒内没停，而**固件侧是真的会停**——音乐2 就是 45.94 s 收尾。现在用
  `ms01play.exe` 可以逐首拿到固件实测长度）：

  | 曲目 | 乐谱字节 | 长度 s | 曲目 | 乐谱字节 | 长度 s |
  |---|---|---|---|---|---|
  | 音乐1 | 1067 | **28**（固件实测 28.21 ✓） | 音乐11 | 2199 | 42 |
  | 音乐2 | 742 | ≥120（固件实测 **45.94**） | 音乐12 | 786 | 29 |
  | 音乐3 | 1931 | 95 | 音乐13 | 1041 | ≥120 |
  | 音乐4 | 1501 | 30 | 音乐14 | 1250 | 62 |
  | 音乐5 | 964 | ≥120 | 音乐15 | 638 | 25 |
  | 音乐6 | 464 | 12 | 音乐16 | 666 | ≥120 |
  | 音乐7 | 566 | 13 | 音乐17 | 878 | ≥120 |
  | 音乐8 | 536 | ≥120 | 音乐18 | 1672 | 32 |
  | 音乐9 | 2812 | 79 | 音乐19 | 1189 | ≥120 |
  | 音乐10 | 433 | ≥120 | 音乐20 | 3427 | ≥120 |

  要拿到这些曲子的固件实测长度，用 `ms01play.exe <N> <out.wav>` 各跑一次整曲渲染
  （每首约 0.5~1 分钟机器时间），可以按需批量做。
* **DSP 引擎自己会判断结尾**：整曲放完后它**不再写 DAC2 样点**（用 2.4G 条指令
  去跑音乐1，样点数仍停在 1,800,993 不动，之后是静音，不会循环）。
* 早期"只放了一小段"不是缺结尾判断，而是**指令预算太小**。换算关系：
  **约 50M 条指令 = 1 秒 63833 Hz 音频**（实测 487M 条 → 9.86 s）；整曲约需 1.41G 条。
* `ms01play.exe` 带自动收尾：连续 6000 万条指令没有新样点就停，所以整曲跑完会自己
  结束，日志里出现
  `[end] no new samples for ... instructions - song finished`。

* `ms01_slot_music1.wav` —— **历史对照**：早期 SDK 示例引擎放的同一份乐谱

## 7. 短乐谱必须补齐（已解决）

一开始音乐6（464 字节）和音乐8（536 字节）**完全不出声**：`0x99` 处理程序卡在
`0xC456` 等待循环里，`[0x04CD]` 始终 0、启动解码 `0xC4DF` 从没执行、DAC2 零写入；
当时用 SDK 示例引擎做对照能正常放它们（`adpcm=0`，所以不是鼓的问题；那个引擎现已删除）。

逐指令 PC 轨迹 diff + 关键变量追踪定出了判据：

* `0xC456` 循环的出口是 `0xCDC1`（`[0x0727] & 2`）或 `[0x0000] bit7`；
* `[0x0727]` bit1 由解包器尾部 `0xCDB3` 写入的 `r4` 决定，而 `0xCDAD: jne` 测的是
  **刚加载出来的 `[0x0729]`**（`ld` 更新 Z——这条模型行为和 MAME 一致，见 §3）。
  也就是说：**配对计数器 `[0x0729]` 数到 0 才会置 bit1**；
* `[0x0729]` 由 `0xCB5F → 0xCD54` 初始化成 `0x118`（280 对 = **560 字节**），之后
  每解包一对减 1。实测归零次数：音乐1=5、音乐2/7=4（能放），音乐6/8=3（放不出来）；
  分界线正好是 560 字节（音乐7 = 566 刚好过线）。

**真机宿主是"按 RAM 缓冲区整块发送"**（NOR 的 `$FC5F` 泵按 `$0636/$0637` 的长度
从 `$2000` 缓冲区推，缓冲区里的余量就是填充），所以短乐谱天然被补齐。我们的探针
照做：剥掉 NAND 的 0xFF 填充后，**不足 640 字节的补 0x00**（`argv` 不变，日志里会
打印 `padded to 640 bytes …`）。修好后：

| 曲目 | 乐谱字节 | 补齐后 | 整曲时长 |
|---|---|---|---|
| 音乐6 | 464 | 640 | 12.31 s |
| 音乐8 | 536 | 640 | 15.90 s |
| 音乐10 | 433 | 640 | 14.6 s |
| 音乐5 | 964 | — | 15.1 s |

（注意：尾部用 `0xFF` 补齐不行——探针会把尾部 `0xFF` 当成 NAND 填充剥掉；用 `0x00`
或补在开头都可以。）

产物：`out/NC3000_音乐6_整曲.wav`、`out/NC3000_音乐8_整曲.wav`。

回归：`build\nc3000_conformance.exe testdata\t09_a.a16 build\conf.wav`
仍然是 **22 passed, 0 failed**、73042 样点（本次给模拟器加的 1 kHz 时基是
可选开关，默认关闭，不影响既有的 A1600/S600 结果）。
