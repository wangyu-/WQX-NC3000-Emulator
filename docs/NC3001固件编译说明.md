> ### 根因（实测确认）：`xasm16` 的宏临时文件落在"当前盘根目录"
> `xasm16` 是 2007 年的老 CRT 程序，宏展开用的 `tmpfile()` 会写进**当前驱动器根目录**。
> `C:\` 根目录对普通用户**不可写** → 展开到约 64 KB 时创建临时文件失败，
> 报 `No more tmp file can be used in macro processing!` 并连带 `A0007 undefined`。
> 这解释了全部现象：为什么只有 18 个宏展开量大的文件失败、为什么换参数/目录/`TMP` 都没用、
> 为什么以管理员运行 IDE 就能过（提权后 `C:\` 可写）。
>
> **不用提权的解法**：`subst` 一个空闲盘符指向"工作树与输出目录的公共父目录"
> （`subst Z: C:\Users\YYGSM\Documents\work`），让构建的**当前盘**变成可写的虚拟盘根。
> 脚本已自动做这件事（`RunMode` 会显示 `subst Z: -> ...`），并在结束时 `subst /d` 清理。
> 实测：`RichEdit/GUIEditHour/InputMethod/ViewTextExtend/LineEditForDic/GUIPullDownMenu`
> 在虚拟盘下全部 **0 error**。
>
> ### 链接也要按 IDE 的方式
> IDE 生成的 Makefile 链接规则是 `$(LD) -at <项目>.ary <项目>.TSK -initdata -initdata -body ...`，
> 而 `<项目>.ary`（`Obj:`×572 + `Lib:`×18 + `LibPath:` …）是 IDE 写在 `src\Debug\` 里的输入清单；
> 直接 `xlink16 <项目名>`（读 `.lik`）会报 `Error L0010: Cannot open ...\decrypt.tmp`。
> 脚本现在会把项目的 `.ary` 改写成本次输出目录的版本再交给 make 链接。
>
> ### KeyDecode.asm 的改动（用户完成，等价且更简洁）

> —— `?L_KeyScanReturn:` 本身就只有一条 `retf`，所以与原意完全一致；
> 脚本已不再对源码做任何补丁。

## 4. 两个真正的卡点

### 4.1 `xasm16` 的宏展开临时文件池（18 个文件）

**现象**：文件编到一半报
```
xxx.asm(412): No more tmp file can be used in macro processing!
xxx.asm(674): error A0007: '?L_SaveHourEnd_7_59248' undefined
```
即：宏处理器"临时文件"用光后，`#` 本地标号的替换号错乱，于是"自己 define 的标号自己找不到"。

**最小复现**（随便找台装了 3.0.4 的机器，把下面存成 GBK+LF 的 `.asm`，用
`xasm16 -t4 t64.asm` 跑，把 `M_E` 调用次数改一改）：

```asm
	.CODE
?L_Start:
	retf
M_E:	.MACRO	a1,a2,a3
	.IFMA	3
	cmp	r1,a1
	jne	?L_G#
	goto	a3
	.ELSE
	cmp	r1,a1
	jne	?L_G#
	goto	a2
	.ENDIF
?L_G#:
	.ENDM
	M_E 1,2,?L_Start          ← 这一行重复 N 次
```

| N | 结果 |
|---|---|
| 60 | 0 error |
| **63** | **0 error** |
| **64** | **2 error（No more tmp file + A0007）** |
| 100 / 200 | 同样报错 |

**这就是 18 个文件的病因**（宏调用次数 vs 结果，实测）：

| 文件 | 宏调用数 | 结果 |
|---|---|---|
| `Component\GUI\GUIDispTime.asm` | 44 | ✅ |
| `Component\GUI\GUIEditDay.asm` | 54 | ✅ |
| `Component\GUI\GUIEditMonthDay_Expand.asm` | 68 | ❌ |
| `Component\GUI\GUIEditTime.asm` | 78 | ❌ |
| `Component\InputMethod\InputMethod.asm` | 183 | ❌ |
| `Component\Editor\ViewTextExtend.asm` | 455 | ❌ |
| `Component\Editor\RichEdit.asm` | 986 | ❌ |

18 个失败文件（全部在 `Component\GUI`、`Component\Editor`、`Component\InputMethod`）：
`GUIEditCountDownTime.ASM, GUIEditDate.asm, GUIEditDate_Expand.asm, GUIEditDT_Expand.asm,
GUIEditHMS.asm, GUIEditHMS_Expand.asm, GUIEditHour.asm, GUIEditMonthDay_Expand.asm,
GUIEditTime.asm, GUIEditTime_Expand.asm, GUIPullDownMenu.asm, GUIPullDownMenu_Expand.asm,
GUITileMenu.ASM, ViewTextExtend.asm, LineEditForDic.asm, RichEdit.asm, RichFloatEdit.asm,
InputMethod.asm`（宏定义来自 `System\include\system\unSPMACRO.inc` 和 `Component\*\<xxx>_Self.inc`）。

**已排除的假设（都实测过，别再试）**：

| 假设 | 实验 | 结果 |
|---|---|---|
| 换行符（LF/CRLF） | 整棵树复制一份转成 CRLF 再编 | ❌ 同样卡在 64；**但**单文件混用 CRLF/LF 会直接引起 `parse error` |
| `TMP`/`TEMP` 目录脏或满 | 指向全新空目录再编 | ❌ 同样 |
| 选项 `-t3/-t4/-t5`、`-be`、`-d`、`-sr`、`-l`（列表文件） | 逐项试 | ❌ 都无关 |
| 与 `.IFMA` 有关 | 去掉条件的宏 100 次展开 | ✅ 通过（说明**只有带条件/`#` 的宏**吃名额，且名额不释放） |
| 是源码问题（有人改坏了文件） | 查 CVS：19 个文件最后修改都在 2006-05~07，早于 2006-12 的构建 | ❌ 源码就是当年能编过的那份 |

**⚠️ 2026-09-25 追加实测：换成 unSP IDE 2.3.2（xasm16 1.14.11）后，18 个文件报的还是同一个错，
阈值一模一样。** 用同一个最小宏（带 `.IFMA` + `#` 标号）分别在两套汇编器上跑：

| 调用次数 N | 3.0.4 / xasm16 1.14.13 | 2.3.2 / xasm16 1.14.11 |
|---|---|---|
| 60 | 0 error | 0 error |
| **63** | **0 error** | **0 error** |
| **64** | **2 error** | **2 error** |
| 100 / 128 / 200 / 256 / 300 | 报错 | 报错（错误数完全一致） |

同时实测排除：

| 假设 | 实验 | 结果 |
|---|---|---|
| 池子会因换 `.include` 文件而重置 | 主文件 include 3 个子文件各 40 次调用（共 120） | ❌ 一样爆池 |
| 池子会因切换 section 而重置 | `.CODE` 400 次 + 再 `.CODE`/`.TEXT` 400 次 | ❌ 一样爆（都停在第 643 行） |
| 池子是"次数"而非"体积" | 1 行体宏 640 次才爆，3 行体宏 219 次、6 行体 137 次、`.IFMA` 大宏 64 次 | → 池子按**展开出来的文本量**计，约等于"640 行展开文本" |
| 输出目录脏/满 | 空目录 vs 1097 文件目录 | ❌ 无关 |

结论：这是汇编器内部固定的临时文件缓冲，**与工具链版本无关**，也无法通过选项/目录/环境变量放大。
唯一可行的绕法是把大文件**拆成多个 `.obj`**（每次汇编各拿一份池子）——见 §6 选项 B。

### 4.2 `KeyDecode.asm` 的 A0174（1 个文件）

> **2026-09-25 已按用户要求直接改源码**：`info\NC3001\src\Component\KeyDecode\KeyDecode.asm`
> 第 112 行 `jmp ?L_KeyScanReturn` → `goto ?L_KeyScanReturn`（仅此一行，文件仍是 LF + GBK，
> 其余 3 处同目标的 `jmp` 保持原样）。改完 KeyDecode.obj 正常产出。

```
Component\KeyDecode\KeyDecode.asm(112): error A0174:
    After two effective words instructions should to be inserted in the branch instruction
```

第 110–112 行：
```asm
?L_GetCapitalASCII:
	r1 -= 0x0020
	jmp	?L_KeyScanReturn
```
后面直接是数据表 `T_NumberKeyBoard: .DW ...`（`.endp` 已在本过程末尾闭合）。

**最小复现**：
```asm
	.CODE
F1:
	r1 -= 0x0020
	jmp	F1
	.END
```
→ A0174。把 `.END` 换成**任意一条真实指令**（`retf`、`goto`、`jz` 都行）→ 0 error；
在 `jmp` 前后插 `nop` **不行**（汇编器不认 `nop` 算"有效指令"）。

**为什么当年能编过：** `unSP IDE 2.3.2\xasm16-Changelog.txt` 写得很清楚——

```
1.14.9 : 2006 November 6
    1. Under unSP ISA2.0 , assembler will report error message once encounter the pipeline
       hazard as followed:
       ...
       jxx L1
       .dw 0x1234
       ...
```

即 **A0174 是 1.14.9（2006-11-06）才引入的检查**。本机两套（1.14.11 / 1.14.13）都晚于它，所以都报错；
仓库自带的那套 2005 版 IDE（xasm16 应为 1.14.0~1.14.4，2005-04~10）不会有这个错。

**本地绕法**（脚本已自动做，改的是 `out\...\stage\patched\` 里的副本，`info\` 不动）：
把该行 `jmp ?L_KeyScanReturn` 换成 `goto ?L_KeyScanReturn`——
`goto` 是 2 字的 PC 赋值跳转，跳转目标/语义完全相同，汇编器接受（实测 0 error），
项目里其它地方（以及所有 `M_*` 宏）本来就大量使用 `goto`。

## 5. 复现时踩到的环境坑（很重要，别再踩）

### 5.1 PowerShell 7 的 UTF-8 控制台会把 GBK 命令行打成 `????`

* 现象：`resc` 报 `Can't open C:\...\Resource\Bmp\?????\???\ZhuanYe.RAW`，
  `make` 回显也是 `????`；但同一条命令手工敲又能成功。
* 根因：这些工具是 ANSI(CP936) 程序；PowerShell 7 把**控制台代码页设成 65001**，
  `cmd.exe`/`make.exe` 用它把 GBK 字节转 Unicode → 全变 `?`。
* 现象 2：**并行编译时**，排在最后的目标（本例是我追加的 4 条规则）会失败，而排前面的
  178 个中文路径资源能成功 —— 所以"能编过"和"编不过"看起来自相矛盾。
* 解决：脚本里对每个工具调用都把控制台代码页切到 936（`SetConsoleCP/SetConsoleOutputCP`），
  并且把中文路径的**输入**预先 staging 成 ASCII 名字（`out\nc3001_build\stage\`）。

### 5.2 其它

* `xasm16` 对**单个文件内 CRLF/LF 混用**会直接 `parse error` / `Can't define a macro inside another macro`，
  不要只转换某一行；仓库里这些 `.asm` 目前**全是 LF**，可以正常编（除了 §4.1 的限制）。
* `xlink16` 的用法是 `xlink16 <名字>`（自己补 `.lik`），不是 `-h`/`--help`。
* `info\TC2000\tools\ide\unSPIDE2.0.0.2.exe` 是 **InstallShield 包**：
  外层可以用 7z 拆出 `Disk1\data1.hdr/data1.cab/data2.cab`，
  但 **`data1.cab/data2.cab` 是 InstallShield 私有 CAB（ISc 格式）**，

## 6. 下一步（三选一，建议 A）

**A. 试仓库自带的那套 2005 版 IDE（最省事，也是"更对代"的工具链）**

`info\TC2000\tools\ide\unSPIDE2.0.0.2.exe`（2005-11-11）就是当年给这个项目用的 IDE——
`patch.bat` 里写明原厂路径 `C:\Program Files\Sunplus\unSP IDE 2.0.0.2\`。
它的 xasm16 早于 1.14.9，**KeyDecode 的 A0174 不会出现**；宏临时文件池的大小则值得实测（有可能更大，
也可能同样是 640 行展开文本）。

* 直接双击安装（和装 2.3.2 一样，30 秒），装完告诉我，我用 `-ToolchainRoot` 指过去重跑；

  `unshield`（GitHub 只有源码，本机有 TCC 可以自己编）——所以**手动安装是最快的**。

**B. 拆对象，绕开宏池（不换工具链，能编到 100%，但代码布局会变）** —— 原型已写好：`tools\nc3001\split_asm.ps1`

已实测跑通的部分（2.3.2 + 该脚本，产物在 `out\nc3001_build\split\<名字>\`）：

| 文件 | 段数 | 结果 |
|---|---|---|
| GUIEditHour / GUIEditDate / GUIEditTime / GUIEditHMS / GUIEditCountDownTime / GUIPullDownMenu_Expand / GUITileMenu / GUIEditMonthDay_Expand / GUIEditDT_Expand / GUIEditDate_Expand / GUIEditHMS_Expand / GUIEditTime_Expand / LineEditForDic | 2~9 | ✅ 0 error |
| RichEdit / ViewTextExtend / InputMethod / RichFloatEdit / GUIPullDownMenu | 3~11 | 🟡 还差最后一步，见下 |

脚本做的事：按「不可 fall-through 的标号 / `.ENDP`」切块 → 每块复制 header（`.INCLUDE`、局部 `.MACRO`、`.VDEF`）
→ 跨块符号自动补 `.PUBLIC`/`.EXTERNAL`、`?` 局部标号自动改名 → 跨块 `goto/jmp/条件跳转`
自动改写成 `call`+`retf` 尾调用（等价写法，因为汇编器不允许跳到别的 `.obj` 里的标号，报 A0145）。

**剩下的 4~5 个文件卡在两点**：
1. `M_FarJa/M_ZeroFarJmp/M_Case` 这类宏**展开出来**的跳转跨块了 —— 出错行是宏调用行，无法逐行改写，
   只能动宏定义（把宏体里的 `goto 参数` 一并改成 `call`+`retf`），每次调用都多一条 `call/retf`（语义等价、变慢）。
2. `.INCLUDE` 的文件里既有宏、又有 RAM 定义（如 `Editor_LV.inc` 的 `IW_KeyBoardStates: .DW 1`），
   复制到每个块会重复定义；需要把「纯宏/常量」和「数据定义」分开处理。

池子是"每次汇编一份"，所以把 18 个文件按 `.ENDP`/顶层标号边界切成多个 `.asm`（每个单独出一个 `.obj`），
再把新 `.obj` 加进 `.lik` 即可。可以做自动化：

1. 按汇编器报的行号贪心切块（每个块 < 1 个池）；
2. 头部（`.include`、局部 `.MACRO` 定义）复制到每个块，`.VAR` 声明只留第一块，其余块改成 `.EXTERNAL`；
3. 逐轮汇编，按 "undefined" 报错补 `.PUBLIC`/`.EXTERNAL`（跨块的 `?L_` 局部标号会自动改名为全局名）。

代价与风险：**对象数从 572 涨到 620+，链接后的代码布局/地址与当年不同**；而且该型号没有出厂镜像
（`info\NC3KSYSNOR.nor` 是另一个型号，不能比对），所以这条路只能保证"能链接、功能等价"，
无法保证与当年固件逐字节一致。预计 50~60 个新对象（18 个文件共 3190 次宏调用）。

**C. 维持现状**：把 **554/572（96.9%）** 当基线——
C 代码 100% 可编译、资源 100% 可编译，只有 18 个汇编文件需要拆或需要更老的汇编器。
