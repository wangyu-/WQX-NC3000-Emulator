## 3. ngpc.zip 里到底是什么

`ngpc.zip` = **Neo Geo Pocket 开发包**（NeoPop 模拟器 + NeoTile/NeoTracker 等），
其中 `ngpc/T900/` 就是一份**完整的 Toshiba T900 工具链**——正好是 V5100 需要的编译器家族：

```
BIN\  CC900.EXE(驱动) THC1.EXE(解析) THC2.EXE(代码生成) ASM900.EXE(汇编)
      MAC900.EXE(汇编驱动) TUMPL/TUAPP(宏/预处理) TULINK.EXE(链接)
      TULIB.EXE(库) TUCONV.EXE(对象转换) TUFAL.EXE(列表)
ETC\  *.ENV(版本) *.HLP(用法)
INCLUDE\  标准头 stdio.h/stdlib.h/string.h … 与 IO900*.H、CUSTOMIZ\C900_H\ (TLCS-900/H 寄存器定义)
LIB\  C900ML.LIB (large 模型 C 库) + LIB\SRC (库源码)
README\  版本/历史文档
```

版本（`-V` 实测）：

| 工具 | ngpc 版本 | 原厂版本 |
|---|---|---|
| CC900 (驱动) | 4.23 (1997) | 1.82 / Package **4.70** (2003) |
| THC1 (Parser) | 0.8o.02.16 | **1.8r.15** |
| THC2 (CodeGen) | 0.8n.04.11 | **1.8n.05.45.01** |
| ASM900 | **2.2d** | **2.2i** |
| TULINK | **2.0f** | **2.0l** |
| TULIB / TUCONV | 1.2g / 1.2e | — |

**两套工具版本相差 5~8 年，这就是后面所有问题的根源。**

## 4. 实测结论

### 4.1 工具链能在本机运行 ✅

所有 EXE 都是 32 位 PE（`machine=0x014C`），Win10/11 无需 XP 虚拟机。
唯一要求：`THOME` 指向 T900 根目录（否则驱动找不到 `.\etc\cc900.env`）。
（ngpc 包里 `IMPORTANT.TXT` 说“Win7 跑不了 thc1”，实测那是**用错工作目录**导致的。）

### 4.2 原厂 CC900.EXE 驱动在本机**必然**失败 —— 原因已定位 ✅

现象：
```
cc900-Fatal-116: cannot execute "…\T900\bin\thc1"
```

用 Frida 挂钩 `CreateProcessA` 抓到的原始参数：

```
lpApplicationName = "…\T900\bin\thc1.exe"     ← 文件确实存在
lpCommandLine     = "thc1 -z@"
lpEnvironment     = <113 字节的块>
     内容： [ " " ×5 | "C:\t9k_a1" | "<TEMP>" | "-g" | "-XO" | "-XM" | "<源码>" | "<临时目录>" ]
返回值 0，GetLastError = 87 (ERROR_INVALID_PARAMETER)
```

即：驱动用 `-z@` + **“把 argv 塞进环境块”** 的老技巧传参；Windows 10/11 的
`CreateProcessA` 会校验环境块（每个条目必须是 `NAME=VALUE`），这种“纯参数”条目
会被拒绝（实测：`A=1` 通过；`C:=1`、`" "`、`C:\t9k_a1`、`-g` 全部失败）。
这与 Windows 版本无关的“兼容性破坏”，**在本机无解，只能绕开驱动**。

**解决办法（已脚本化）**：直接按原厂三阶段调用
`THC1 → THC2 → ASM900`，见 `tools\v5100\cc900.ps1`。

顺带踩到的三个坑（脚本里都已处理）：

1. 源码/汇编必须是 **CRLF**，LF 会报 `ASM900-Fatal-152 : Illegal source file format`；
2. **ASM900 最多接受 4 个 `-I`**，第 5 个直接崩（exit=0xC0000005）；
3. `-O0` 只能给 THC2，THC1 会报 `Illegal option '-O0'`；THC1/THC2 需要 `-XO -XM`。

### 4.3 用这套工具链编译 SDK 源码 —— 成功 ✅

以 SDK 自带样例 `Gui_smulator\Application\aptest\demo.c` 验证（原厂 2006 年也编过它）：

```
THC1   -w1 -g -Xc -Xp2 -DPIC_PID=1 -I … -XS4 -Nb1 -XO -XM  demo.c  demo.i     → 0 error
THC2   -w1 -O0 -g -XS4 -Nb1 -XO -XM                         demo.i  demo.asm  → 0 error (477 KB)
ASM900 -w1 -g -I … -Nb3 -XE                                 demo.asm          → 0 error (264 KB)
```

| | 本次（T900 4.23/2.2d） | 原厂 2006（T900 4.70/2.2i） |
|---|---|---|
| `demo.asm` | 477,156 B | 481,465 B |
| `demo.rel` | ~265,000 B | 267,612 B |

再往下链接、`TUCONV -Fs24` 转 S 记录也都正常（只剩“系统符号未解析”这类正常提示，
因为没给系统 API 表/PIC 库）。

### 4.4 但**出厂系统目标文件链接不了** ❌（当前唯一硬阻塞）

```
$ tulink v6100.lcf -T900 c900ml.lib -la -w1 -ga relfile\*.rel -o output\v6100.abs -$
TULINK-Fatal-120: Bad object format in "relfile\caret.rel"( 0x00009cfa )
```

实测统计（347 个 `.rel` 逐个试）：

* **316 个可读**，**31 个报 Bad object format**；
* 失败名单（31 个，很多是核心模块）：
  `caret, dev_kbd, dev_pwr, dev_timer, dev_usb, direct, edit, evt_PCX, fcsel, fscmd,
   gui_init, library, Memory, mp3, online_fc, Os_start, sch, smd_common, smd_smilsub,
   sound, start, svcRTC, sys_table, uart_drv, usb_main, windlg, winevent, wininputbox,
   winmain, winuser, winxime`
* **已排除的假设**（都实测过，别再试）：

| 假设 | 实验 | 结果 |
|---|---|---|
| 目标文件损坏/被截断 | 全文件扫零页、看结构头 | ❌ 结构完整 |
| 与 `-ga`/`-ng`/`-k`/`-r`/`-Mm`/`-w*` 选项有关 | 逐项试 | ❌ 都报同一个错 |
| 与 CPU 环境 `-T900` 有关 | `-T900` / 不带 / `-T900H` | ❌ 无关（`-T900H` 甚至不认） |
| 库封装形式能绕过 | TULIB 打包成 `.lib` 再链 | ❌ 一样报错（库成员是原样存储的） |
| 目标文件被污染（调试信息） | 对比 316 个好文件 | ❌ 好/坏文件结构头完全一致 |
| 编译器版本混杂 | 读每个文件里的 `_C900_VERSION` | ❌ 全部是 `470`（同一版） |
| 汇编器版本混杂 | 读每个文件里的版本串 | ❌ 全部是 ASM900 `2.2i` |
| 尺寸/区域阈值 | 统计 8 个区的长度 | ❌ 与失败无关 |
| 新增记录类型 | 差分“只出现在失败文件里的字节串” | ❌ 没有这样的标记 |

**结论**：出厂 `.rel` 是 **ASM900 2.2i** 产出、由 **TULINK 2.0l** 链接；
ngpc 里的 **TULINK 只有 2.0f**，两者目标文件格式存在**内容相关**的不兼容
（所有失败点都落在同一个“代码+调试”数据区，TULIB 1.2g 却能读）。

## 5. 现在能做什么 / 不能做什么

能做：

* 用 `tools\v5100\cc900.ps1` 编译任意 `.c`（含 SDK 自带源码）→ `.rel`；
* 用 TULINK + SDK 的 `v6100.lcf` / `C900ml.lib` 链接自己的小程序；
* 用 TUCONV 转 `.s24`、用 `Convert_S24.exe` 转 `.bin`。

不能做（暂时）：

* 用 `relfile\*.rel` 重新链接出 `output\v6100.abs`（→ 也就无法重新生成 `v6100.s24/.bin`）；
* 链接应用工程（缺 SDK 未附带的 `c900pic.lib`）。

出厂镜像本身是完整的（`IDE\output\v6100.s24 / v6100.bin / system.* / load_img.*`），
所以“烧录/对比”不受影响，只是**不能重新构建**。
